Search for Webiny SaaS:
OpenSearch vs turbopuffer

Which search engine should back Webiny Cloud when thousands of tenants sign up and each one builds its own content models, pages and files?

October 2026 Scope: hosted Webiny, not self-hosted deployments Status: spike, turbopuffer latency not yet measured

Recommendation

Turbopuffer for Webiny SaaS

One namespace per tenant and model. Isolation per tenant, close to zero cost for idle tenants, and no search cluster for us to run.

  • Keep ddb+os for self-hosted deployments.
  • Add explicit per-field index flags (filterable, sortable, searchable) first. They are needed with either engine.
  • Benchmark turbopuffer before committing. Latency is the one open question.

Why OpenSearch struggles here

Webiny stores CMS entries in OpenSearch either with an index per tenant per model, or with one shared index per model. Neither works at this scale when every tenant defines its own models.

150,000indexes for 10k tenants × 15 models, one index each
1,000default shards per data node in OpenSearch
1,000default fields per index mapping

Index per tenant per model

The index count grows with tenants × models. Every index costs shards and cluster state, even if the tenant never searches.

Shared index per model

Fields built in the admin UI get a random storage ID per tenant. All of them land in one mapping, which grows with every tenant until it hits the field limit. Avoiding this needs a slot-mapping layer we would have to build.

Every filter the CMS list API sends to OpenSearch today, and its turbopuffer equivalent. Files, pages, ACO folders and Website Builder data are CMS models too, so this covers them.

Decide: startsWith

Today "car" matches "red car" because OpenSearch matches a phrase prefix at any word. With turbopuffer's Glob it only matches at the start of the text. That is closer to what the name says, but it changes results. ContainsAllTokens with last_as_prefix keeps the old behaviour.

Decide: the search box

Today it is a substring match across fields, with no relevance ranking. Keeping that means one glob per field, which gets slower on large namespaces. BM25 is faster and ranks by relevance, but returns different results.

Next steps

  1. Benchmark turbopuffer. Single-entry writes, warm and cold namespace queries, list + count in one request. Needs an API key.
  2. Per-field index flags. Filterable, sortable and searchable flags in the model builder and admin UI, with a cap per model. Validate where and sort against them.
  3. Engine-neutral query layer. Replace the four extension points that expose raw OpenSearch queries (CmsEntryOpenSearchBodyModifier, SortModifier, QueryModifier, FullTextSearch).
  4. Decide the two behaviour changes. startsWith and the search box.
  5. Build ddb+tpuf. CMS entry storage behind the existing storage operations, with sync modelled on api-sync-ddb-to-opensearch.
