# @webiny/plugins

> Level 0 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/plugins` is the foundational plugin-registry package used across the whole monorepo: a small, dependency-free (aside from `uniqid`) class-based registry (`PluginsContainer`) that stores plugin objects keyed by name, indexes them by `type` with a cache, and an abstract `Plugin` base class that subclasses use to get an auto-derived `type` getter. It also ships an `AsyncPluginsContainer` that can resolve lazily-loaded plugin factories, and exports a single global `plugins` singleton instance that the front-end packages (`app`, `app-admin`, `app-headless-cms`) use as a shared, process-wide registry. The package is small, well tested for its core path, and overall healthy; the one real correctness bug is a silent-failure edge case in argument normalization, and `AsyncPluginsContainer`/several `PluginsContainer` methods are unused anywhere in the monorepo. Other packages needing "register things by type/name with caching" should reuse `PluginsContainer` rather than reimplementing it.

## Public API
- `PluginsContainer` (packages/plugins/src/PluginsContainer.ts:56) — the core registry (`register`, `unregister`, `byName`, `byType`, `oneByType`, `atLeastOneByType`, `merge`, `mergeByType`, `all`). Instantiated directly across `api-headless-cms`, `api-sync-system`, `api-graphql`, `api-headless-cms-storage`, and re-exposed as a DI abstraction token in `packages/api-headless-cms/src/legacy/abstractions.ts`. Dozens of call sites across the API packages consume `byType`/`byName`/`register`.
- `plugins` (packages/plugins/src/index.ts:5) — a module-level singleton `PluginsContainer` instance. Imported directly (not re-instantiated) by `packages/app/src/plugins/index.tsx`, `packages/app/src/contexts/Ui/index.tsx`, `packages/app/src/components/Image.tsx`, `packages/app/src/hooks/useRegisterLegacyPlugin.tsx`, `packages/app-headless-cms/src/HeadlessCMS.tsx` and several admin components, and `packages/app-admin/src/base/Admin.tsx` — this is the de facto global plugin registry for the client apps.
- `Plugin` (packages/plugins/src/Plugin.ts:1) — abstract base class exposing a `type` getter derived from a static `type` field. Extended by ~20 concrete plugin classes across `api-sync-system`, `api-headless-cms-storage`, `api-headless-cms`, `api-file-manager`, `api-aco`, `handler`, and `app`.
- `AsyncPluginsContainer` (packages/plugins/src/AsyncPluginsContainer.ts:8) — resolves nested/lazy plugin factories into a `PluginsContainer`. No consumers found anywhere in the monorepo outside its own test file (see Dead code).
- Types `Plugin`, `PluginCollection`, `PluginFactory` (packages/plugins/src/types.ts) — consumed via the deep import `@webiny/plugins/types.js` by numerous packages (e.g. `packages/app/src/plugins/index.tsx:5`).

## Convention issues
- `types.ts` (packages/plugins/src/types.ts:1) re-exports the runtime `PluginsContainer` class (`export { PluginsContainer } from "./PluginsContainer.js";`) alongside pure type declarations. `AsyncPluginsContainer.ts:1-2` then imports both the type and the class from `~/types.js` rather than importing the class directly from `./PluginsContainer.js`. This blurs the type-only purpose of `types.ts` and adds an indirection with no apparent benefit (no circular-import necessity was found — `PluginsContainer.ts` does not import from `AsyncPluginsContainer.ts`).
- This package predates the repo's newer DI (`createAbstraction`/`createImplementation`) conventions and is a plain class-based module; that is expected for a Level 0 foundational package and is not flagged as an issue, just noted for context when auditing higher-level packages that do use DI.

## Test gaps
- `merge`, `mergeByType`, `atLeastOneByType`, and `oneByType` have no test coverage at all (see Dead code — three of the four are also unused, so this is low priority, but `merge` is used in production code in `api-sync-system` with no direct unit test).
- The `skipExisting` option (`assign()` in PluginsContainer.ts:49) is never exercised by a test — no test registers the same plugin name twice with `{ skipExisting: true }` to confirm the second registration is dropped and `init()` is not called again.
- The silent-failure bug described above (Bug #1) is untested; a test asserting that `register()` throws for a plugin object missing `type` — including the single-argument, no-`name` case — would have caught it.
- `AsyncPluginsContainer` error paths are untested: e.g. what happens if a `PluginFactory` rejects, or if the input passed to `traverseAndLoadPlugins` is a non-array plugin missing `type` (no validation happens before `new PluginsContainer(plugins)` is constructed, so the error is deferred to whatever calls `byType`/`register` afterward, or to `PluginsContainer`'s own constructor path — worth an explicit test either way).

## Recommendations
1. Fix the silent-failure bug in `isOptionsObject`/`normalizeArgs` (PluginsContainer.ts:6-16): a plugin missing `type` should always be surfaced as the existing "Missing type definition" error rather than silently being reinterpreted as an options object. The safest fix is to only treat the trailing argument as options when there are at least two arguments, or to require options objects to be explicitly tagged (e.g. a marker property) instead of inferring by absence of `type`/`name`.
2. Decide the fate of `AsyncPluginsContainer`, `mergeByType`, `atLeastOneByType`, and `oneByType`: either wire them into a real call site (if they were added for upcoming work), add tests, and document intended usage, or remove them to reduce surface area of a foundational, widely-depended-on package.
3. Add tests for the `skipExisting` registration option and for the `register()` validation error paths (missing `type`, non-object plugin, and the single-malformed-plugin edge case from Bug #1) to lock in the fix and prevent regressions in this heavily-depended-on package.
