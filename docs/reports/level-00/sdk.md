# @webiny/sdk

> Level 0 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/sdk` is a framework-agnostic, isomorphic (browser + Node) HTTP/GraphQL client for the Webiny Cloud API, organized as one thin `*Sdk` facade class per domain (`CmsSdk`, `FileManagerSdk`, `TenantManagerSdk`, `LanguagesSdk`, `TasksSdk`, `WebhooksSdk`) wired together by the top-level `Webiny` class. Each API operation is a standalone function under `src/methods/**` that calls the shared `executeGraphQL` helper and returns a `Result<TValue, TError>` (an `Either`-style type, `src/Result.ts`) instead of throwing; input validation is centralized through `createMethod`/`parseParams` (zod-schema based) and error typing through `BaseError`/`HttpError`/`ApiError`/`NetworkError`/`ValidationError` (`src/errors.ts`). Overall health is good — small, consistent, well-commented, no obvious runtime crashes in the common paths — but the package has **zero tests** and a couple of real gaps in its file-upload error-typing and its batch-upload fail-fast semantics. Other packages should reuse `Result`, `BaseError`, `createMethod`/`parseParams`, and `transformFieldErrors` rather than reinventing them.

## Public API
- `Webiny` (aka `Sdk`) — root facade composing the six domain SDKs; consumed by ~11 packages across the repo (e.g. `app-admin`, `app-file-manager`, `sdk-frontend`, `sdk-nextjs`, `cms-sdk`, `background-tasks`, `webhooks`, `remote-components`, `website-builder-sdk`, `api-headless-cms`, `app-sdk-playground`).
- `Result<TValue, TError>` (`src/Result.ts`) — the `ok`/`fail`/`map`/`flatMap`/`match` container used by literally every SDK method; re-exported from `index.ts` for consumers to pattern-match on.
- `HttpError`, `ApiError`, `NetworkError`, `ValidationError` (`src/errors.ts`, extending `BaseError`) — typed error hierarchy returned inside failed `Result`s.
- `createMethod`/`parseParams` (`src/utils/createMethod.ts`, `src/utils/validateParams.ts`) — zod-schema-driven wrapper used by ~30 of the ~40 method files to add pre-flight validation.
- `transformFieldErrors` (`src/utils/transformFieldErrors.ts`) — regex-based GraphQL error-message humanizer, used by all CMS entry methods (9 call sites) to strip internal type names from field-selection errors.
- Domain SDK classes (`CmsSdk`, `FileManagerSdk`, `TenantManagerSdk`, `LanguagesSdk`, `TasksSdk`, `WebhooksSdk`) and their per-method param/result types, all re-exported from `src/index.ts`.
- `@webiny/sdk/webhooks` (`src/webhooks.ts` subpath export) — Node-only `createVerifyWebhookPayload` for verifying inbound webhook signatures via `standardwebhooks`; guarded to throw if imported in a browser bundle.

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|----------|----------|---------|-------------------|------------|
| 1 | medium | `packages/sdk/src/methods/fileManager/createFiles.ts:87-105` | With the default `strategy: "fail-fast"`, when one item in the batch fails, the code does `throw result.error` / `throw error` inside the `p-map` mapper. Per `p-map`'s own implementation (`stopOnError` defaults to `true`), this rejects the outer promise on the *first* failure, but concurrently-running mapper invocations that already started (up to `concurrency`, default 5) are **not cancelled** — they keep running to completion in the background. | Uploading a batch of files with the default settings: if item #2 fails validation quickly while items #1, #3, #4 are still mid-upload, `createFiles` returns `Result.fail(...)` immediately, but #1/#3/#4 continue uploading to S3 and still call `createFileRecord` (a GraphQL mutation) afterwards, silently creating file records the caller's error-handling code never learns about. This can leave orphaned/duplicate file records that only show up later via `listFiles`. | high (confirmed via `node_modules/p-map/index.js` semantics + the fail-fast code path) |
| 2 | medium | `packages/sdk/src/methods/fileManager/createFile.ts:76,96,188` | The function's declared return type is `Result<FmFile, HttpError \| ApiError \| NetworkError>`, but on the "missing name/type" precondition (line 76) and inside the upload catch blocks (lines 96, 188) it does `Result.fail(new Error(...) as any)` / `Result.fail(error as any)`, wrapping a plain `Error` (or whatever `uploadToS3`/`uploadLargeFile` throw, which are also plain `Error`s, e.g. "Upload failed with status 500", "Upload aborted") using an `as any` cast. | Any caller that exhaustively narrows the error union (`instanceof ApiError` / `instanceof NetworkError` / `instanceof HttpError`) per the declared type — which TypeScript tells them is safe — will hit a plain `Error` object that matches none of the three branches, so `error.data`/`error.code` access silently returns `undefined` or the error falls through to an "unreachable" branch. No in-repo caller currently does this narrowing (checked `app-file-manager`, `sdk-frontend`, `app-sdk-playground`), so today's impact is limited to the type contract itself, but any external/future consumer relying on the public `.d.ts` types is misled. | high (read directly; `as any` casts are the tell) |

## Duplication
jscpd found 15 clones totaling 180/5219 lines (3.45%) — the entire monorepo standard for this rule is that every clone group here is the same *shape* of boilerplate, not copy-pasted business logic:
- **GraphQL call/error-unwrap boilerplate** (the bulk of the clones): `executeGraphQL(...)` → `if (result.isFail()) return Result.fail(result.error)` → check `responseData.<domain>.<op>.error` → `return Result.ok(...)`. Repeats near-verbatim across `webhooks/{getWebhook,deleteWebhook,getWebhookDelivery,resendWebhookDelivery}.ts`, `tenantManager/{enableTenant,disableTenant,installTenant}.ts`, `tasks/{listTasks,listDefinitions}.ts`, `cms/{getEntry,listEntries,publishEntryRevision,unpublishEntryRevision}.ts`, and `fileManager/{getFile,listFiles}.ts`. This is a legitimate candidate for a small shared helper (e.g. `unwrapGraphQLResult(result, path)`) but is currently harmless, consistent duplication rather than drift.
- **Shared import header** across `cms/{publishEntryRevision,unpublishEntryRevision,listEntries,getEntry}.ts` (jscpd flagged the identical 7-line import block) — cosmetic, not worth deduplicating.
- **Type-shape duplication**: `fileManagerTypes`-style optional metadata fields duplicated between `createFile.ts:16-25` and `updateFile.ts:10-19` (`createdOn`/`modifiedOn`/`savedOn`/`createdBy`/... /`keyPrefix`), and a large 43-line field block duplicated between `cms/cmsTypes.ts:64-106` and `cms/createEntry.ts:16-58` (entry meta fields). These two are real type-duplication risks — a change to one (e.g. adding a new meta field) requires manually updating the other, and nothing enforces they stay in sync.
- **Upload internals**: the small `Promise`-wrapped-`XMLHttpRequest` progress/abort-handling snippet (`uploadToS3.ts:58-72`) is structurally duplicated inside `uploadLargeFile.ts:171-185`'s `uploadPartWithXHR`; both hand-roll the same XHR boilerplate for whole-file vs. per-part uploads.

No duplication against other packages was checked cross-repo (out of scope for a level-0 audit — this package has no internal `@webiny/*` deps to compare against).

## Dead code
- `transformFieldError` (singular, `src/utils/transformFieldErrors.ts:48-49`) — a thin alias of `transformFieldErrors` documented as "Single-message variant used by FileManager methods," but codegraph shows **zero callers** anywhere in the repo; all 9 real call sites use the plural `transformFieldErrors` directly. Safe to delete.
- `createVerifyWebhookPayload` / the entire `src/webhooks.ts` subpath entry (`@webiny/sdk/webhooks`) — a repo-wide `grep` for `createVerifyWebhookPayload` finds only its own definition and re-export; the natural consumer, `packages/webhooks`, does not import it despite depending on `@webiny/sdk`. Either it's meant purely for external plugin authors (in which case that intent is undocumented) or it's unused scaffolding.

## Convention issues
- `AGENTS.md`'s DI-naming/one-abstraction-per-file rules don't really apply here — this package isn't a DI container, it's a functional SDK, and its "one exported method + a couple of private helpers per file" pattern (e.g. `createFile.ts` holding `uploadSmallFile`/`uploadLargeFileWrapper`/`createFileRecord` as private, non-exported helpers) is consistent and reasonable, not a violation.
- `index.ts` is a large, manually-curated barrel (149 lines) that re-exports types one-by-one per method file rather than `export *`-ing method modules; this is intentional (avoids leaking private helpers) and matches the "minimal barrel exports" convention rather than violating it.
- No convention violations worth flagging beyond the two `as any` casts already covered under Bugs.

## Test gaps
The package has **no `__tests__` directory and no `*.test.ts` files at all** (confirmed via `find`), despite `vitest.config.ts` being present and ~5.2k lines of non-trivial logic:
- `Result`'s `map`/`flatMap`/`mapError`/`match` and the "throws when accessing `.value`/`.error` on the wrong branch" guards are untested.
- `createMethod`/`parseParams`'s zod-validation-to-`ValidationError` conversion, and `transformFieldErrors`'s three regex transforms (field-not-found, needs-subfields, unknown-where-filter), are untested — these are exactly the kind of string-matching logic that regresses silently on GraphQL server message-format changes.
- The file-upload path (`createFile`, `createFiles`, `uploadToS3`, `uploadLargeFile`) — arguably the riskiest code in the package (browser/Node branching, XHR vs. fetch, multi-part chunking, retry via `p-retry`, abort-signal handling, the fail-fast concurrency bug above) — has no unit coverage; it's only exercised indirectly by server-side `api-file-manager` integration tests that hit the real methods through HTTP, not the SDK's client-side upload-strategy branching.

## Recommendations
1. Fix the `createFiles` fail-fast/`p-map` interaction (Bug #1) — either cancel in-flight work via `AbortController` when a fail-fast error is thrown, or switch to `stopOnError: false` and surface partial completion explicitly in `CreateFilesResult`, so callers can't be misled about what actually got persisted.
2. Add a test suite, starting with `Result`, `createMethod`/`parseParams`, and `transformFieldErrors` (pure, fast, high-value units), then targeted tests for the upload-strategy branching in `createFile`/`createFiles` (mocking `fetch`/XHR) given it's the most complex and currently the least verified code path.
3. Tighten the upload error typing: replace the `Result.fail(... as any)` casts in `createFile.ts` (lines 76, 96, 188) with a proper typed error (e.g. wrap in `NetworkError`/a new `UploadError`) so the declared `Result<FmFile, HttpError | ApiError | NetworkError>` contract is actually sound, and remove the dead `transformFieldError` alias.
