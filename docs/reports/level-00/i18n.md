# @webiny/i18n

> Level 0 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
A small, dependency-free internationalization library providing a translation engine (`I18N` class) with pluggable modifiers (count, plural, gender, if, date, time, dateTime, number, price) and processors, plus a source-scanning `Extractor` used to pull translatable strings out of `.js`/`.ts` files by hashing them into namespaced keys. It exports a shared singleton instance (`i18n`) that downstream packages register their own processors/modifiers onto (e.g. `packages/app` adds the default processor plus `@webiny/i18n-react`'s React processor). Overall health is reasonable — the code is small and mostly well tested — but locale-aware date/time/number/price formatting is silently broken (see Bugs).

## Public API
- `I18N` class (default export `I18n`) — `translate`, `namespace`/`ns`, `date`/`time`/`dateTime`/`price`/`number`, `registerModifier(s)`/`registerProcessor(s)`, `setLocale`/`getLocale`, `setTranslations`/`mergeTranslations`. Consumed by `packages/app/src/i18n/i18n.ts` (the only in-repo importer of `@webiny/i18n`), which re-exports the pre-configured singleton for the rest of the admin app; `@webiny/i18n-react` supplies the React-aware processor registered on top of it.
- `defaultModifiers`, `defaultProcessor` — used by `packages/app/src/i18n/i18n.ts` to populate the shared singleton (the package itself registers nothing on `i18n` by default, by design — instantiation and registration are separate steps).
- `Extractor` class (`src/extractor/index.ts`) and `extract()` function (`src/extractor/extract.ts`) — used by the package's own CLI bin (`bin/run.js` → `webiny-i18n` command) to statically extract translation strings from source globs. No other in-repo consumers found.

## Bugs

| 1 | medium | `packages/i18n/src/I18n.ts:391,398,405,415-416,426-427` | `getDateFormat`/`getTimeFormat`/`getDateTimeFormat`/`getPriceFormat`/`getNumberFormat` all call `lodashGet(this.locale, "formats.date", ...)` (and similar), but `this.locale` is typed and set as a plain `string \| null` (`setLocale(locale: string)`, `I18N.locale: string | null`). `lodash.get` on a string can never resolve a `"formats.date"` path, so the lookup always misses and every call silently falls back to `this.defaultFormats`. | Any consumer that calls `i18n.setLocale("de-DE")` expecting subsequent `i18n.date()`, `i18n.time()`, `i18n.price()`, or `i18n.number()` calls to use a locale-specific format never gets locale-specific formatting — output is always the hardcoded default (`DD/MM/YYYY`, comma/period separators, etc.), regardless of which locale is active. | high |

## Duplication
- `packages/i18n/src/I18n.ts:133-153` (`date`), `160-180` (`time`), `183-202` (`dateTime`) are near-identical (parse-with-fecha-or-construct-Date, then `fecha.format`) — flagged by jscpd as three-way clones. Could be collapsed into one private helper parameterized by the format getter.
- `packages/i18n/src/modifiers/countModifier.ts:5-11` and `packages/i18n/src/modifiers/pluralModifier.ts:5-11` duplicate the same "match value against `default`/single-number/range parameters" loop (jscpd-flagged, 6 duplicated lines / 89 tokens). Only the matched return value differs (`value + " " + label` vs `label`).
- `dateModifier.ts`, `dateTimeModifier.ts`, `numberModifier.ts`, `priceModifier.ts`, `timeModifier.ts` are all trivial one-line delegations to `i18n.<method>(value)` with an identical shape (below jscpd's size threshold, so not reported by the tool, but structurally repetitive — could be generated from a table of method names).

## Dead code
- `Extractor.listOnly`/`setListOnly` (see Bug #2) — no reader anywhere in the package or its consumer (`bin/run.js` only calls `setGlob().execute()`).
- `Extractor.setContent`/`content` field is public API but has no in-repo caller (`bin/run.js` uses only `setGlob`); kept for library completeness, not exercised.

## Convention issues
No significant violations — this is a small, pre-DI-era utility library with no `createImplementation`/token wiring expected, and `index.ts` only exports what `packages/app` and the CLI actually consume (`I18n`, `defaultModifiers`, `defaultProcessor`), consistent with the "minimal barrel exports" convention.

## Test gaps
- No test exercises locale-specific formats (`getSetLocale.test.js` only round-trips `setLocale`/`getLocale`; `date.test.js`/`time.test.js`/`price.test.js`/`number.test.js` never call `setLocale` before formatting), which is why Bug #1 has shipped unnoticed.
- The `Extractor` class (`setGlob`/`setContent`/`execute`/`setListOnly`) is untested — only the underlying `extract()` function is covered by `extract.test.js`.

## Recommendations
1. Fix or remove the locale-aware format lookup in `getDateFormat`/`getTimeFormat`/`getDateTimeFormat`/`getPriceFormat`/`getNumberFormat` (`I18n.ts:390-428`) — either store locale-specific formats in a real lookup structure keyed by locale, or drop the dead `lodashGet(this.locale, ...)` branch and document that only `defaultFormats` are supported today.
2. Add a test that calls `setLocale` and verifies (or documents the current lack of) locale-specific format overrides, so the behavior in #1 is intentional and covered going forward.
3. Deduplicate the `date`/`time`/`dateTime` methods in `I18n.ts` and the `countModifier`/`pluralModifier` matching loop into shared helpers to remove the jscpd-flagged clones.
