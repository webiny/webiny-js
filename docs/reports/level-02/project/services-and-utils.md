# @webiny/project — Services and utils

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers `packages/project/src/{services,utils,components,exports}`: the ~35 dependency-injected `Default*Service` implementations that do the actual work behind the `ProjectSdk` facade (project/app/config discovery, Pulumi CLI orchestration, WCP licensing and PAT management, local storage/logging/UI, lambda-function and package listing), plus the package's small collection of pure utility helpers (env-var allowlisting, region/variant validation, tracing, extension source resolution, env-configuration builders) and its handful of React exports (`FeatureFlag.CanUse*` gates, the `infra`/`infra/*` hook re-export barrels). The code is generally careful and well-commented (particularly the Pulumi/WCP pieces, which document *why* certain duplication or DI-avoidance choices were made), but this slice contains three confirmed, concretely reachable bugs of real consequence: a production-safety check that can be silently bypassed while state is still written locally, a hook type that gets registered twice due to a copy-paste duplicate, and a lexicographic (non-semver) version comparison in the extension installer that the code's own example comment proves is already broken at today's version numbers. Test coverage for this slice is almost nonexistent — 5 test files exist in `packages/project/__tests__`, covering only `isTraceRequested`, `formatTraceReport`, `getRenderCacheKey`, `hasDefaultExport`, and `GetProjectEnvironment`; none of the ~30 other services, and none of the validation/env utilities, have any test at all.

## Public API
- **Services** (`packages/project/src/services/*`) — ~30 `Default*Service` classes wired via `@webiny/di`'s `createImplementation` behind abstraction tokens (`GetProjectService`, `GetProjectConfigService`, `WcpService`, `InitProjectSdkService`, `InstallExtensionService`, the `Pulumi*Service` family, `LoggerService`, `UiService`, `LocalStorageService`, `ListAppLambdaFunctionsService`, etc.). These are the engine behind the `ProjectSdk` class (`packages/project/src/ProjectSdk.ts`) and are consumed, via constructor injection, throughout `@webiny/project` itself and by `@webiny/project-aws`, `@webiny/project-standalone`, `@webiny/cli-core`, and `@webiny/cli-aws` (e.g. `GetPulumiService` in `project-aws`, `ValidateProductionPulumiState` in `project-aws` depends on `IsRemotePulumiBackendService`).
- **Utils** (`packages/project/src/utils/*`) — `getStackName`/`splitStackName`, `isValidRegionName`/`isValidVariantName`, `measureDuration`, `ExtensionSrcResolver` (10 call sites: `registerHooks`, `registerDecorators`, `registerImplementations`, `registerPulumiExtensions`, `zodSrcPath`, plus `project-aws`'s `ApiLambdaFunction.tsx`/`ApiRoute.tsx`), `pickApiRuntimeEnvVariables`/`pickServerRuntimeEnvVariables` (used to build the exact env allowlist for Lambda and the standalone server process), the `env/with*` configuration builders (`withRegion`, `withEnv`, `withPulumiConfigPassphrase`, …) used by every Pulumi service to build `execa` env, and the `trace/*` CLI-timing helpers used from `bin.ts` and `GetProjectConfigService`.
- **Components** (`packages/project/src/components/FeatureFlag.tsx`) — `FeatureFlag.CanUse*` React gates (`CanUseMultiTenancy`, `CanUseTeams`, `CanUseWorkflows`, etc.), used by extension authors inside `webiny.config.tsx` to conditionally render config JSX based on the license-decorated feature flags.
- **Exports** (`packages/project/src/exports/infra*.ts`) — pure re-export barrels giving `Admin/Api/Core` hook abstractions public, renamed names (`AdminAfterBuildHook`, `ApiBeforeDeployHook`, …) plus `EnvVar`; this is the surface project extensions (in `project-aws`, `project-standalone`, and end-user `webiny.config.tsx` files) import to register custom build/deploy/watch hooks.

## Duplication
- `packages/project/src/utils/measureDuration.ts:1-10` is byte-for-byte identical to `packages/project/src/features/Watch/watchers/utils/measureDuration.ts:1-10` (flagged by jscpd, 10 lines). The `utils/` copy is exported from the package's public `utils/index.ts` barrel; the `features/Watch` copy is a private, unexported duplicate that could simply import the shared one.
- `PulumiGetStackOutputService.execute` (`packages/project/src/services/PulumiGetStackOutputService/PulumiGetStackOutputService.ts:37-66`) and `PulumiSelectStackService.getAppStackOutput` (`packages/project/src/services/PulumiSelectStackService/PulumiSelectStackService.ts:90-120`) duplicate the same "run `pulumi stack output --json`, parse, log on failure" logic (jscpd, 21 lines). This one is explicitly intentional and documented in a comment in `PulumiSelectStackService.ts:91-93` explaining that reusing `PulumiGetStackOutputService` would create a circular dependency — worth keeping in mind if the two ever drift, but not something to "fix" without addressing the underlying circular-dependency constraint.
- `GetProjectConfigService.hydrateConfig`'s inline `importFromPath` helper (`packages/project/src/services/GetProjectConfigService/GetProjectConfigService.ts:102-113`) re-implements a subset of `ExtensionSrcResolver.resolvePath`'s logic (the `/extensions/`-prefix vs. absolute-path branching) but omits the tsconfig path-alias resolution that `ExtensionSrcResolver` added. Below jscpd's detection threshold, but a real "two slightly different implementations of the same idea" risk: an `extensionDefinitions` extension's `src` that relies on a tsconfig path alias would resolve fine through `ExtensionSrcResolver` (used everywhere else) but not through this one, purely because they happen to duplicate rather than share the resolution logic.
- `isValidRegionName.ts:12` and `withRegion.ts:14` both independently implement `regions.some(item => item.value === region)`; small (one line) and below jscpd's threshold, but a candidate for extracting a single `isKnownRegion(region)` helper in `utils/regions.ts`.

## Dead code
- `packages/project/src/services/WcpService/LogoutUser.ts` — the `LogoutUser` class is not re-exported from `WcpService/index.ts` (which only exports `WcpService.js`), and codegraph shows no callers anywhere in the repo. `DefaultWcpService.unsetPatFromLocalStorage()` already does the same thing directly (via its own `UnsetPatFromLocalStorage` instantiation), so this file is fully redundant dead code.
- `packages/project/src/services/InstallExtensionService/downloadFolderFromS3.ts:11` — `NoObjectsFoundError` is exported but codegraph shows its only reference is the `throw` inside the same file; no code elsewhere catches or imports it by name (confidence: medium, single codegraph query).

## Convention issues
- `DefaultWcpService` (`packages/project/src/services/WcpService/WcpService.ts`) breaks from the DI pattern used by every other service in this slice: instead of registering `GetUser`, `GenerateUserPat`, `GetUserPat`, `CreateUserPat`, `StorePatToLocalStorage`, `UnsetPatFromLocalStorage`, `GetProjectEnvironment`, and `GetProjectLicense` as proper DI abstractions/implementations and injecting them through the constructor, it manually `new`s each one inside the relevant method (e.g. `WcpService.ts:28-29`, `:53-57`). This is the one place in the slice where the "reach abstractions through the namespace" / constructor-injection convention that's followed everywhere else (every `Default*Service` in `packages/project/src/services/*`) is not applied — none of these seven collaborators can be swapped or mocked the way every other dependency in the package can.
- The same anti-pattern repeats in the (dead) `LogoutUser.ts`, which `new`s `UnsetPatFromLocalStorage` rather than depending on the `WcpService` abstraction.

## Test gaps
- Of the ~30 `Default*Service` implementations in this slice, only `GetProjectEnvironment` (part of `WcpService`) has a dedicated test. Nothing exercises `GetProjectConfigService`'s render/hydrate/cache-key logic, `InstallExtensionService`'s version-folder selection (where Bug #3 lives), `InitProjectSdkService`'s hook/decorator/implementation registration (where Bug #2 lives), any of the seven `Pulumi*Service` classes, or `WcpService`'s license/PAT flows.
- `isValidRegionName` and `isValidVariantName` (both small, pure, and easy to unit test) have no tests — Bug #5 would have been caught immediately by a test asserting `isValidVariantName(undefined).isOk()` and inspecting the returned value.
- `ExtensionSrcResolver` (path-alias resolution, `/extensions/` resolution, static-cache behavior) has no tests, despite being on the hot path for every hook/decorator/implementation/Pulumi-extension the project config declares.
- `pickApiRuntimeEnvVariables`/`pickServerRuntimeEnvVariables` (`utils/apiRuntimeEnv.ts`) — the allowlist that decides which env vars a Lambda or the standalone server actually receives, explicitly including a comment about `WCP_PROJECT_LICENSE` being deliberately excluded — has no test guarding against a future edit accidentally widening or narrowing that allowlist.

## Recommendations
1. Fix the `IsRemotePulumiBackendService` / `PulumiLoginService` env-var mismatch (Bug #1) first — it's a silent production-safety bypass. Either make `PulumiLoginService` recognize all four variables, or make `IsRemotePulumiBackendService` only recognize the two `PulumiLoginService` actually understands, and add a test asserting the two services agree for every variable combination.
2. Remove the duplicate `AdminAfterBuildExt` entry in `registerHooks.ts` (Bug #2) and add a test that asserts each hook-extension type in the array appears exactly once (a simple `new Set(...).size === array.length` check on the extension-type list would have caught this).
3. Replace the lexicographic version comparison/sort in `InstallExtensionService`'s `getVersionFromVersionFolders` (Bug #3) with a proper semver comparison (e.g. `semver.compare`/`semver.rcompare`), and add a regression test using the exact `5.9.x`/`5.10.x`/`5.40.x` folder set the code's own comment describes.
