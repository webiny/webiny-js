# @webiny/project — Features, extensions and abstractions

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice is the DI backbone of `@webiny/project`: `abstractions/` declares ~35 feature tokens (`GetApp`, `BuildApp`, `DeployApp`, `Watch`, `GetProjectConfig`, `GetFeatureFlags`, ...), ~20 build/deploy/watch lifecycle "hook" tokens, and the plain model interfaces (`IProjectModel`, `IAppModel`, `IWcpUserModel`, ...); `features/` holds their default `createImplementation` implementations plus the "composite" hook aggregators; `decorators/` layers cross-cutting behaviour (hook running, watched-Lambda replacement, license-aware feature flags, stack-output cache invalidation) on top via `createDecorator`; `defineExtension/` is the small framework (`defineExtension`, `zodSrcPath`) that turns a spec into both a React `<Property>`-registering component and a validated `ExtensionDefinitionModel`, and is reused far outside this package (~70 callers of `defineExtension`, ~31 of `zodSrcPath` across `cli-core`, `project-aws`, `auth0`, `cognito`, `app-mailer`, etc.); `extensions/` is where the concrete `Project/*`, `Admin/*`, `Api/*` extension points and their default hook wiring live; `models/` holds the plain DTO/model class pairs. The code is consistently idiomatic (one class per file, `Namespace.Interface`, `createImplementation`/`createDecorator`/`createComposite` used correctly throughout) and mostly small, delegate-only classes, so the main risks are a real child-process error-handling gap in the build pipeline, a sizeable amount of copy-paste duplication between the Build/Watch and Admin/Api code paths, and essentially zero test coverage.

## Public API
- `defineExtension` / `ExtensionComponent` (`defineExtension/defineExtension.ts:13`) — the extension-definition builder used everywhere in the framework; codegraph shows ~70 callers across the monorepo (`packages/auth0/src/Auth0.tsx`, `packages/cognito/src/Cognito.tsx`, `packages/cli-core/src/extensions/CliCommand.ts`, `packages/project-aws/*`, etc.), not just inside `project`.
- `zodSrcPath` (`defineExtension/zodTypes/zodSrcPath.ts:22`) — zod schema factory that validates an extension's `src` path exists, is a file, and (optionally) exports a class implementing the expected abstraction; ~31 callers (`cli-core/src/extensions/CliCommand.ts`, `project-aws/src/extensions/ApiLambdaFunction.tsx`, `ApiRoute.tsx`, etc.).
- `createAbstraction` (`abstractions/createAbstraction.ts`) — one-line wrapper around `@webiny/di`'s `Abstraction`; used to declare every token under `abstractions/features/*`.
- The feature/hook abstractions and their default implementations/decorators (`GetApp`, `BuildApp`, `DeployApp`, `DestroyApp`, `Watch`, `RunPulumiCommand`, `GetFeatureFlags`, the `*BeforeBuild/AfterBuild/BeforeDeploy/AfterDeploy/BeforeWatch` hook family, etc.) — internal DI tokens, but deep-importable (package `exports` map is `"./*": "./*"`); consumed by `project-aws`/`cli-aws` to register their own decorators around `DeployApp`/`GetPulumiService` (per the `pulumi-sdk` and `wcp` dependency summaries).
- `models/*` (`ProjectModel`, `AppModel`, `AppPackageModel`, `PathModel`, `UrlModel`, `ProjectConfigModel`, `WcpEnvironmentModel`, `WcpUserModel`, `WcpUserPatModel`) — re-exported publicly via `export type * from "./abstractions/models/index.js"` in `src/index.ts`, so `IProjectModel` etc. are part of the package's external type surface.
- `extensions/*` — ~40 `defineExtension` instances that make up the declarative surface end users/other packages register against (`Project`, `AdminExtension`, `ApiExtension`, `FeatureFlags`, `Telemetry`, `ProjectId`, `EnvVar`, `DatabaseSetup`, the `pulumi/*` stack-output extensions, `infra/{Ci,Encryption,Env,Hashing}`).

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|----------|----------|---------|-------------------|------------|
| 1 | high | `packages/project/src/features/BuildApp/PackagesBuilder/RunnableBuildProcess.ts:29-51` | `run()` forks a worker and only listens for `"message"`; there is no `"error"` or `"exit"` listener on the returned `ChildProcess`. Node throws an uncaught exception when an `"error"` event has no listener, and the returned promise never settles if the child dies (OOM-killed, `SIGKILL`, crash before it can `process.send`) without ever posting an IPC message. | If `fork()` fails to spawn the worker (missing/unbuilt `worker.js`, `EMFILE`, permission error) the unhandled `"error"` event crashes the whole `webiny build` process instead of failing just that package's build; if the child is killed externally, `RunnableBuildProcesses.run()` (`RunnableBuildProcesses.ts:27`) awaits the never-resolving promise and the build hangs forever. Contrast with the sibling `features/Watch/watchers/RunnableWatchProcess.ts:44-56`, which listens on `"exit"` and resolves/rejects from the exit code — the Build path is the one missing this handling. | high |

## Duplication
- `extensions/Project/SetAdminAppEnvVarsBeforeBuild.ts:11-68` and `extensions/Project/SetAdminAppEnvVarsBeforeWatch.ts:11-68` are byte-for-byte identical (60 duplicated lines per jscpd) apart from the hook abstraction they implement (`AdminBeforeBuild` vs `AdminBeforeWatch`). Should be a single function taking the env vars to set, invoked from two thin hook classes.
- The extension-build loop (`for (const extensionType in projectConfig.config) { ... await extensionInstance.build(); }`) is duplicated verbatim between `features/BuildApp/BuildApp.ts:31-44` and `features/Watch/Watch.ts:89-102`.
- `features/BuildApp/PackagesBuilder/{worker.ts,RunnableBuildProcess.ts}` and `features/Watch/watchers/{worker.ts,RunnableWatchProcess.ts}` are structurally near-identical (fork + IPC/exit handling) but have drifted (see Bug #1) — a good candidate to unify into one shared runner instead of two copies that can silently diverge.
- `extensions/{AdminBuildParam.ts,ApiBuildParam.ts,AdminExtension.ts,ApiExtension.ts}` share several 10-20 line blocks (per jscpd: `AdminBuildParam.ts:164-200` ~ `ApiBuildParam.ts:11-51`; `AdminExtension.ts:12-21` ~ `ApiExtension.ts:12-21`; `AdminBuildParam.ts:117-126` ~ `AdminExtension.ts:83-93`) — the "generate a build-param feature file / register it" logic is copy-pasted between the Admin and Api variants rather than parameterized by app name/folder.
- `features/DeployApp/DeployApp.ts`, `DestroyApp/DestroyApp.ts`, `RefreshApp/RefreshApp.ts`, `RunPulumiCommand/RunPulumiCommand.ts`, `GetAppOutput/GetAppOutput.ts` share several near-identical 9-15 line blocks (get app → get pulumi service → run command), consistent with them all being thin wrappers over the same Pulumi-invocation pattern.
- `decorators/DeployAppClearWatchedLambdaFunctions.ts:14-28` and `decorators/DeployAppWithWatchedLambdaReplacement.ts:14-28` duplicate the "get core app → get its stack output → derive `deploymentId`" preamble; both could share a small helper.
- Two low-value/likely-noise clones: `extensions/hooks/index.ts` vs `abstractions/features/hooks/index.ts` (both are 20-line alphabetical barrel-export lists — same shape because they mirror the same hook set, not real duplicated logic), and `defineExtension/models/ExtensionDefinitionModel.ts:9-18` vs `:24-34` (interface fields vs. the class fields that mirror them — an unavoidable consequence of the interface+class pattern).
- `utils/measureDuration.ts` (outside this slice) duplicates `features/Watch/watchers/utils/measureDuration.ts` (10 lines) — the in-slice copy should just import the package-level one.

## Dead code
None found with high confidence. The two exports checked as plausible dead code (`zodSrcPath`, `defineExtension`) both turned out to be heavily used outside the package (31 and 70 callers respectively via codegraph). Given the budget for this slice, a full sweep of all ~150 exports was not performed; nothing else stood out as an obvious orphan during reading.

## Convention issues
- Six composite hook-implementation files are misnamed after the sibling hook they were copy-pasted from, violating "one class per file, file named after the thing it contains": `features/hooks/AdminAfterBuild/AdminBeforeBuild.ts` (contains `CompositeAdminAfterBuild`), `features/hooks/AdminAfterDeploy/AdminBeforeBuild.ts`, `features/hooks/ApiAfterBuild/ApiBeforeBuild.ts`, `features/hooks/ApiAfterDeploy/ApiBeforeBuild.ts`, `features/hooks/CoreAfterBuild/CoreBeforeBuild.ts`, `features/hooks/CoreAfterDeploy/CoreBeforeBuild.ts`. All six are functionally correct (the composite class and the abstraction it implements are consistent) — this is a pure naming/copy-paste artifact, but it actively misleads anyone navigating by filename. The sibling `*BeforeBuild/*BeforeBuild.ts` files (e.g. `AdminBeforeBuild/AdminBeforeBuild.ts`) are named correctly.
- In those same composite classes, the constructor parameter is capitalized like the type it's typed as instead of a camelCase identifier, e.g. `constructor(private AdminAfterBuild: AdminAfterBuild.Interface[])` (`features/hooks/AdminAfterBuild/AdminBeforeBuild.ts:5`) — inconsistent with sibling composites that use a lowercase local name (`apiAfterBuild`, `coreAfterBuild`).
- `abstractions/models/*` (`IProjectModel`, `IAppModel`, ...) are plain data interfaces, not `createAbstraction` tokens, so the "reach through the namespace" rule doesn't strictly apply to them (per AGENTS.md's own carve-out for "a plain data type with no abstraction behind it") — flagged here only to note it was checked, not as a violation.

## Test gaps
There is effectively no test coverage for this slice: `packages/project/__tests__/` contains only 5 files, and only `hasDefaultExport.test.ts` touches anything under `features/extensions/abstractions/decorators/defineExtension/models` (it covers `extensions/hasDefaultExport.ts`). None of the following have any test: the entire hook-decoration chain (`BuildAppWithHooks`, `DeployAppWithHooks`, `WatchWithHooks`), the watched-Lambda-replacement decorators, `GetFeatureFlagsWithLicense`'s license-gating logic (`LICENSE_CHECKS` table), `defineExtension`/`zodSrcPath`'s validation behaviour (including the abstraction-conformance check), or the `PackagesBuilder`/`RunnableBuildProcess(es)` fork-and-collect pipeline — the last of which is exactly where Bug #1 lives.

## Recommendations
1. Fix `RunnableBuildProcess.run()` (`features/BuildApp/PackagesBuilder/RunnableBuildProcess.ts`) to handle child-process `"error"` and `"exit"` the way `RunnableWatchProcess` already does, so a spawn failure or a killed worker fails the build instead of crashing the CLI or hanging forever.
2. Rename the six misnamed composite-hook files (`*AfterBuild/*BeforeBuild.ts`, `*AfterDeploy/*BeforeBuild.ts`) to match their contents, and de-duplicate `SetAdminAppEnvVarsBeforeBuild`/`SetAdminAppEnvVarsBeforeWatch` and the Admin/Api build-param generation logic into shared helpers.
3. Add unit tests for the hook-decoration chain and the `PackagesBuilder`/`RunnableBuildProcess(es)` pipeline before touching either — right now a regression in build/deploy/watch hook ordering or in the fork-based build runner would ship silently.
