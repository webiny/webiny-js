# @webiny/aws-sdk

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/aws-sdk` is a thin re-export wrapper around ~18 `@aws-sdk/client-*` packages, giving the rest of the monorepo a single place to pin AWS SDK versions and, for the hottest clients (S3, Lambda, Scheduler, Cognito, DynamoDB `DynamoDBDocument`, Step Functions), a small "create-or-return-cached-client-by-config" helper built on `@webiny/utils`'s `createCacheKey`. Most of the package is pure re-exports with no logic to break, but two of the caching helpers have real, independently-confirmed bugs: the Step Functions client factory never actually populates its cache, and the DynamoDB document client's "decorate once" safeguard is unenforced. The package has zero automated tests.

## Public API
- `getDocumentClient`/`createDocumentClient`/`decorateDocumentClient` (`packages/aws-sdk/src/client-dynamodb/getDocumentClient.ts:32,58`) — the most heavily used export in the package; codegraph shows ~24 callers across `api-event-handler-aws`, `api-sync-system`, `api-headless-cms-ddb*`, `db-dynamodb`, and 10+ test files, i.e. it's on the hot path of essentially every DynamoDB-backed request.
- `createS3Client`/`createS3` (`packages/aws-sdk/src/client-s3/index.ts:66,94`) — used by file-manager and asset-delivery packages.
- `createStepFunctionClient`/`triggerStepFunctionFactory`/`listExecutionsFactory`/`describeExecutionFactory` (`packages/aws-sdk/src/client-sfn/index.ts:48,71,86,97`) — consumed by `packages/background-tasks-aws/src/service/StepFunctionService.ts`, the production path for triggering/monitoring background tasks via AWS Step Functions.
- `createLambdaClient`, `createCognitoIdentityProviderClient`, `createSchedulerClient`, `createEventBridgeClient` — same "config-keyed client cache" pattern, each consumed by their respective domain packages (Lambda invocation, Cognito user admin, EventBridge Scheduler, EventBridge events).
- The remaining subpaths (`client-iam`, `client-iot`, `client-sts`, `client-sqs`, `client-cloudfront`, `client-apigatewaymanagementapi`, `client-cloudwatch`, `lib-storage`, `credential-providers`, `types`) are pure re-exports of the underlying `@aws-sdk/*` symbols with no added logic.

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|---|---|---|---|---|
| 1 | medium | `packages/aws-sdk/src/client-sfn/index.ts:48-69` (`createStepFunctionClient`) | The cache-miss branch creates `new SFNClient({...config})` and returns it directly — it never does `stepFunctionClientsCache.set(key, client)`. Every other client factory in this same package (`createS3Client`, `createLambdaClient`, `createCognitoIdentityProviderClient`, `createSchedulerClient`) stores the newly created client before returning it; this one is the odd one out. | `stepFunctionClientsCache` never gets populated, so `stepFunctionClientsCache.has(key)` is always `false` and a brand-new `SFNClient` (with its own HTTP agent, connection pool, and credential-provider resolution) is constructed on every single call to `createStepFunctionClient`/`triggerStepFunctionFactory`/`listExecutionsFactory`/`describeExecutionFactory`. Codegraph confirms `background-tasks-aws/src/service/StepFunctionService.ts` calls these on the production task-triggering path, so every background task trigger/list/describe pays the cost of a fresh client instead of reusing one, unlike the sibling AWS clients in this same package. | high |
| 2 | low | `packages/aws-sdk/src/client-dynamodb/getDocumentClient.ts:48-56` (`applyDecoration`) | The comment above `applyDecoration` says "Client will not be decorated more than once," and the function sets `client.__decoratedByWebiny = true`, but nothing ever reads that flag — `decorateDocumentClientCallable(client)` runs unconditionally whenever a callback is registered, both on every cache-hit call to `getDocumentClient()` and on every call to `decorateDocumentClient()` (which loops all cached clients and re-invokes the callback). The promised "only once" guard does not exist in this file. | The one current consumer of `decorateDocumentClient` (`packages/api-sync-system/src/sync/attachToDynamoDbDocument.ts`) has its own partial guard (`client.__webinyHandler?.id === handler.id`), but that only protects against the *same* handler instance being re-applied — if `attachToDynamoDbDocument` is ever called again with a *different* handler object against the same cached client (e.g. once per request while the underlying DynamoDB client is reused across a warm Lambda container), the client's `send`/`put`/`delete`/`update`/`batchWrite` methods get wrapped again on top of the previous wrapper, stacking layers indefinitely instead of being decorated once as the comment promises. No production caller of `attachToDynamoDbDocument` was found (only a test), so this is currently latent, but the bug is in `@webiny/aws-sdk`'s own code and would affect any future consumer of the public `decorateDocumentClient` API. | medium |

## Duplication
The "create-or-return-cached-client-by-config-key" pattern is copy-pasted across six files (`client-s3/index.ts` ×2, `client-lambda/index.ts`, `client-cognito-identity-provider/index.ts`, `client-scheduler/index.ts`, `client-sfn/index.ts`) with small, unexplained differences between them: some accept a `cache?: boolean` opt-out (`S3`, `Scheduler`), some don't (`Lambda`, `Cognito`); one variant has the caching bug described above. `createEventBridgeClient` (`client-eventbridge/index.ts:13`) doesn't cache at all, unlike its siblings — inconsistent, though not necessarily wrong. A single shared `createCachedAwsClient(ClientClass, defaultConfig)` helper (already half-implied by the repeated shape) would remove both the duplication and the class of bug found in `createStepFunctionClient`.

## Dead code
Not checked exhaustively (18 client subpaths, mostly pure re-exports) per the audit's cost rules; no unused exports were found among the subpaths that were read in depth (`client-dynamodb`, `client-s3`, `client-sfn`, `client-lambda`, `client-cognito-identity-provider`, `client-scheduler`, `client-eventbridge`) — all of their non-trivial (non-re-export) helpers have confirmed consumers via codegraph.

## Convention issues
None found. Each client subpath is one cohesive module for one AWS service, consistent with the package's role as a version-pinning re-export layer.

## Test gaps
The package has no test files at all (`find` for `*.test.ts` and `__tests__` returns nothing). Neither of the two confirmed bugs above (the SFN cache miss, the DynamoDB decoration-guard gap) would be caught by any existing test in the package or, per codegraph, in its direct consumers.

## Recommendations
1. Fix `createStepFunctionClient` to actually store the newly created client in `stepFunctionClientsCache` before returning it (one-line fix, matches the pattern already used by every sibling factory in this package).
2. Either implement the `__decoratedByWebiny` check that `applyDecoration`'s comment claims exists (skip re-invoking `decorateDocumentClientCallable` on an already-decorated client), or update the comment to reflect that re-decoration is the caller's responsibility — as written, the code and the comment disagree.
3. Add basic unit tests for the client-caching helpers (at minimum: two calls with the same config return the same client instance; two calls with different configs don't) — this is exactly the kind of small, cheap test that would have caught the Step Functions bug immediately.
