# @webiny/website-builder-vue

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/website-builder-vue` is the Vue 3 binding for Webiny's website-builder SDK — the direct sibling of `@webiny/website-builder-react`, built against the same `@webiny/website-builder-sdk` (`documentStoreManager`, `contentSdk`, `BindingsProcessor`, `environment`) but implemented with `defineComponent`/`h()` render functions and a `useObservable` MobX-to-Vue bridge in place of `mobx-react-lite`'s `observer`. Structurally it mirrors the React package file-for-file (`DocumentRenderer`, `ElementRenderer`, `EditingElementRenderer`, `ElementSlot`/`LiveElementSlot`/`PreviewElementSlot`, the same Box/Grid/GridColumn/Image/Lexical/Fragment/Root editor components) and its own public barrel is noticeably more complete than React's sibling. However, comparing the two bindings directly surfaces two concrete correctness/consistency risks unique to this package: it keys the shared `documentStoreManager` by `document.id` where the SDK's own `LiveSdk`/`EditingSdk` and the React binding both key it by `document.properties.id` (a different identifier, per the codebase's own documentation of the distinction), and every built-in editor-component manifest is missing the `aiContext` metadata its React counterpart supplies, silently degrading the AI content-generation feature for Vue-based sites. It is also the only one of the two packages with zero tests. Consumers should keep building on the SDK's `documentStoreManager`/`BindingsProcessor`/`contentSdk` as this package does; the risk here is in this package's own wiring, not reimplementation of SDK internals.

## Public API
- `DocumentRenderer`, `DocumentFragment`, `ElementSlot`, `DocumentStoreProvider`/`useDocumentStore`, `FragmentsProvider`/`useDocumentFragments`, `ElementSlotDepthProvider`/`useElementSlotDepth`, `ElementIndexProvider`/`useElementIndex`, `EditingElementRenderer` (`components/index.ts`) — all explicitly re-exported, unlike the React package which only exports the first four of these equivalents.
- `useBindingsForElement`, `useDocumentState`, `useSelectFromState`, `useObservable`, `useViewport` (`composables/*`, re-exported via `src/index.ts`) — the MobX/Vue reactivity bridge. Consumed internally by `LiveElementRenderer.ts`/`EditingElementRenderer.ts`, and exposed for consumers building custom components.
- `createComponent`, `editorComponents` (also individually: `Box`, `Fragment`, `Grid`, `GridColumn`, `Image`, `Lexical`, `Root`) — the built-in manifests, exported both as a group and individually (`editorComponents/index.ts`).
- Consumers: per CodeGraph/grep, the sole in-repo consumer is `@webiny/website-builder-nuxt`, which re-exports this package's full surface (`export * from "@webiny/website-builder-vue"`) the same way `website-builder-nextjs` wraps the React package.
- Large SDK re-export list in `index.ts` (input builders, `contentSdk`, `environment`, `StyleSettings`) — note this list is shorter than the React package's: it does not re-export the asset helpers (`normalizeToAsset`, `getAssetUrl`, `getImageSrcSet`, `Asset`/`AssetImage` types, etc.) or the A/B-experiment helpers (`getPageWithExperiment`, `resolveVisitorContext`, etc.) that `website-builder-react/src/index.ts` does, even though this package's own `Image.ts` editor component needs `CssProperties` (imported directly from the SDK, bypassing the barrel) and has no asset-cropping utility at all (see Duplication).

## Duplication
- Per jscpd (`jscpd-website-builder-vue/jscpd-report.json`): `components/ElementSlot.ts:14-23` and `components/PreviewElementSlot.ts:17-26` are a 10-line clone — both `defineComponent` calls declare an identical `props: { parentId, slot, elements }` schema instead of one importing/reusing the other's. The same duplication pattern (a `PreviewElementSlot`/`ElementSlot` prop-shape clone) exists independently in `website-builder-react` too (see that package's report), so it isn't Vue-specific, but neither package factored it out.
- `composables/useDocumentState.ts` and `composables/useBindingsForElement.ts` both hand-roll `useObservable(...) + computed(...)` inline instead of calling this package's own `composables/useSelectFromState.ts`, which exists specifically to combine those two steps (`useObservable(getState)` then `computed(() => selector(stateRef.value))`) and is exported from the package's barrel. CodeGraph confirms `useSelectFromState` has no callers anywhere in the repo — it was built as the shared primitive (mirroring React's `useSelectFromState`, which React's own `useDocumentState`/`useBindingsForElement` *do* call) but was never adopted, so the same two-line pattern now exists three times in this package (once as the unused general utility, twice as ad hoc copies).
- This package has no equivalent of `website-builder-react`'s `src/image/*` (`Image`, `BackgroundImage`, `getImageProps` — CSS-based aspect-ratio/focal-point cropping for consumer-authored components). Given that submodule is dead code in the React package (see that report), this gap is low priority in practice, but it does mean a Vue-app author has no framework-native equivalent to reach for if that submodule is ever revived/exported.

## Dead code
- `composables/useSelectFromState.ts` (`useSelectFromState`) — exported from the package's public barrel but, per CodeGraph, has zero callers inside this package (its own two natural call sites reimplement its body instead, see Duplication) and no callers in any other package either: "codegraph: no consumers."

## Convention issues
- None of significant weight beyond the manifest/`aiContext` drift already covered under Bugs — the package otherwise follows the repo's Vue conventions consistently (composables prefixed `use*`, `defineComponent` + typed `props`, forward-declared circular-dependency breaks between `ElementRenderer`/`LiveElementSlot` and `LiveElementSlot`/`PreviewElementSlot` are consistent and commented in both directions).

## Test gaps
- There are no `*.test.*` files, no `__tests__` directory, and no test script wired for this package at all — in contrast to `website-builder-react`, which has two (`createComponent.test.ts`, `getImageProps.test.ts`). Nothing here is under test: the `Grid.manifest.ts` `onChange` row/column arithmetic (identical logic to React's, equally untested there), the `useObservable` MobX→Vue bridge (the single most load-bearing piece of custom logic in this package — a `shallowRef`/`autorun`/`triggerRef` bridge with no verification that it actually re-renders on nested MobX mutations), and the store-keying behavior flagged in Bug #2 are all unverified.

## Recommendations
1. Fix the `documentStoreManager` keying mismatch (Bug #2): key by `document.properties.id` in `ConnectToEditor.ts` and `DocumentRenderer.ts`, matching the SDK's own `LiveSdk` convention and the React binding, so a single logical document can't end up with two independent `DocumentStore` instances depending on which binding rendered it first.
2. Add the missing `aiContext` (and `Fragment`'s `useInAiContentGeneration: false`) to every built-in manifest, copying the strings already written for the React package's equivalents, so the AI content-generation feature behaves the same for Vue-based sites.
3. Either delete `useSelectFromState` or adopt it in `useDocumentState`/`useBindingsForElement` (as the React package already does with its own version) — right now the package maintains an unused "canonical" composable alongside two ad hoc duplicates of exactly what it does.
