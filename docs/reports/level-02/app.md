# @webiny/app

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/app` is the base framework package that every Webiny front-end app (admin, headless CMS, page/website builder) is built on: it defines the `App`/`AppContainer`/`Plugin`/`Plugins`/`Provider` composition primitives (built on top of `@webiny/react-composition`), a small DI-feature layer (`createFeature`/`useFeature`/`DiContainerProvider`, wrapping `@webiny/di`), a MobX-backed router (`RouterPresenter`/`RouterRepository`/`Router`/`RouteUrl`/`HistoryRouterGateway`, exposed via `useRouter`/`useRoute`/`RouteLink`), a GraphQL client with pluggable decorators (batching, retry, error publishing), a local-storage feature, an env-config feature, an event publisher, and an SSE-based `ApiStreamClient`. It configures the shared `@webiny/i18n` singleton with `@webiny/i18n-react`'s processor and re-exports the global `@webiny/plugins` registry rather than reimplementing either. Overall health is good — the newer "feature" modules (`graphqlClient`, `router`, `apiStreamClient`, `envConfig`) are well structured and mostly tested — but there are a few real defects: a `baseUrl`-handling inconsistency in the router that breaks link generation and navigation the moment a non-empty `baseUrl` is used, an unbounded MobX `autorun` leak in the widely-used `useRoute` hook, and fragile string-based error classification in the GraphQL retry/error-publishing decorators that can throw on non-conforming API error bodies.

## Public API
- `useFeature`/`createFeature`/`useContainer`/`DiContainerProvider` (`shared/di/*`) — the DI-feature pattern used to register and resolve app-level services; `useFeature` alone has ~310 call sites across `app-admin`, `app-headless-cms`, `app-website-builder`, extensions, etc. (per codegraph).
- `useRouter`/`useRoute`/`Route`/`RouteLink`/`SimpleLink` (`features/router/*`, `presentation/router/*`) — the router surface; `useRouter` has ~135 callers and `useRoute` ~49 callers monorepo-wide (codegraph).
- `App`/`AppContainer`/`Plugin`/`Plugins`/`Provider`/`createProvider`/`createProviderPlugin` (`App.tsx`, `AppContainer.tsx`, `core/*`) — the composition root used by `app-admin`'s `Admin` component and similar bootstraps in other apps.
- `useEnvConfig`/`EnvConfig` (`features/envConfig/*`) — thin typed wrapper over injected env config, consumed by `packages/app/src/exports/admin/env-config.ts` and `packages/webiny/src/admin/env-config.ts`.
- `useLocalStorage`/`useLocalStorageValue`/`useLocalStorageValues` (`presentation/localStorage/*`, `features/localStorage/*`) — MobX-observable local storage repository; used across `app-admin`, `app-headless-cms`, `app-file-manager` UI components.
- `GraphQLClientFeature` (`features/graphqlClient/feature.ts`) — assembles `FetchGraphQLClient` behind optional `BatchingGraphQLClient`/`RetryGraphQLClient` decorators plus mandatory `NetworkErrorPublishing`/`AuthenticationErrorPublishing` decorators; consumed by `app-admin`'s GraphQL client wiring.
- `ApiStreamClient` / `readServerSentEvents` (`features/apiStreamClient/*`) — SSE-based streaming HTTP client for routes that live beside `/graphql`; well documented and tested.
- `plugins`, `renderPlugin`/`renderPlugins`, `legacyPluginToReactComponent` (`plugins/index.tsx`, `utils/legacyPluginToReactComponent.ts`) — legacy plugin-registry helpers layered on `@webiny/plugins`' global `plugins` singleton; `renderPlugins` is still consumed (e.g. `app-headless-cms`'s `ContentModelEditor/Header.tsx`).

No test in `GraphQLClient.test.ts` mocks a non-200 response (every mock uses `status: 200`), so this path is unexercised. | medium |

## Duplication
Within the package (per jscpd):
- `RouterPresenter.ts:34-42` and `:45-53` — `setRouteParams`/`replaceRouteParams` share an identical 9-line "read current + matched route" block.
- `HistoryRouterGateway.ts:39-47` and `:50-58` — `goToRoute`/`replaceRoute` share an identical 9-line "find route or warn, then push/replace" block.
- `AuthenticationErrorPublishing.ts:6-18` and `NetworkErrorPublishing.ts:6-18` — the decorator constructor + try/catch scaffold (13 lines) is duplicated verbatim between the two error-publishing decorators.
- `BatchingGraphQLClient.ts:152-161` and `FetchGraphQLClient.ts:34-42` — the same "fetch with try/catch + JSON-parse" block is duplicated between the batching and non-batching clients.
- `GraphQLClient.test.ts` has several near-duplicate test blocks (e.g. lines 33-50 vs 121-138, 195-213 vs 250-291/325-343), suggesting copy-pasted setup that could be extracted into shared test helpers.

Cross-package: no reimplementation of lower-level dependency utilities was found — the package correctly reuses `makeDecoratable`/`compose`/`CompositionProvider` from `react-composition`, `createConfigurableComponent` from `react-properties`, the global `plugins` singleton from `plugins`, and `createAbstraction`/`createImplementation`/`createDecorator`/`BaseError` from `feature`, rather than rebuilding any of them.

## Dead code
- `RouteParamsSync` and its associated types (`packages/app/src/presentation/router/components/RouteParamsSync.tsx`, re-exported via `presentation/router/index.ts`) — codegraph shows its only caller is its own barrel re-export; it is not re-exported by the package's public entrypoints (`index.ts`, `exports/admin/router.ts`) and no other package imports it. Meanwhile `app-file-manager` and `app-headless-cms` each ship their own separately implemented `RouteParamsSync` components solving the same URL-param ⇄ state sync problem, suggesting this generic version was never adopted (codegraph: no consumers).

## Convention issues
DI naming (`createImplementation`/`createDecorator`/`createAbstraction`, one abstraction/implementation per file) is followed consistently throughout `features/*`. The one notable deviation is `packages/app/src/plugins/index.tsx`, which mixes several unrelated concerns in a single file (the legacy `renderPlugin`/`renderPlugins` render helpers, `PluginComponent`/`PluginsComponent`, and the re-export of the image plugin) — this predates the DI-feature convention used elsewhere in the package and isn't worth restructuring on its own, but it's the one place that clearly violates "one abstraction per file".

## Test gaps
- `features/localStorage`, `features/envConfig`, and `features/eventPublisher` have no `__tests__` at all, despite being core DI-registered features that other tested code (the GraphQL client's error-publishing decorators, `apiStreamClient`) depends on.
- `RetryGraphQLClient`'s non-200/API-error branch and the classification bug above (finding #3) are untested — every response mocked in `GraphQLClient.test.ts` uses `status: 200`.
- `Router`/`RouteUrl`'s `baseUrl`-prefixed matching and generation — the exact feature involved in finding #1 — has no direct unit test for `RouterRepository.getLink()`; only `HistoryRouterGateway.test.ts` exercises `baseUrl` for push/replace.
- `useRoute`'s subscription lifecycle (mount/unmount of the `autorun`) is untested — a test asserting the reaction is disposed on unmount would have caught finding #2.

## Recommendations
1. Fix the `baseUrl` handling in the router: thread `baseUrl` through `RouterRepositoryImpl.getLink()` (or centralize URL building so `getLink`, `pushState`, and `goToRoute` all go through one baseUrl-aware path), and add a test that exercises `getLink()`/`SimpleLink` navigation under a non-empty `baseUrl`.
2. Fix the leak in `useRoute` by returning the `autorun` disposer from the effect (`return autorun(...)`), matching the pattern already used correctly in `RouteParamsSync`.
3. Make `FetchGraphQLClient`'s non-200 error path throw a real `Error`/`BaseError` with a guaranteed string `message`, and add tests for `RetryGraphQLClient`, `NetworkErrorPublishing`, and `AuthenticationErrorPublishing` against non-200 responses so the string-based error classification is protected against malformed or unexpected backend error bodies.
