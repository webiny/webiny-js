# @webiny/website-builder-react

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/website-builder-react` is the React binding for Webiny's website-builder SDK: it renders a `Document` fetched from `@webiny/website-builder-sdk` into a React tree (`DocumentRenderer` → `ElementRenderer` → `EditingElementRenderer`/`LiveElementRenderer` → `ElementSlot`), provides the built-in "Webiny/*" editor components (Box, Grid, GridColumn, Image, Lexical, Fragment, Root), and re-exports the SDK's input/theme/asset helpers for consumers. It builds correctly on the SDK's `DocumentStore`, `BindingsProcessor`, and asset helpers rather than reimplementing them. Overall health is fair: the rendering pipeline itself is small and coherent and is consumed by real downstream packages (`website-builder-nextjs`, `remote-components`), but the package carries a whole unreachable submodule (`src/image/*` is never exported from the package's public entry point, despite having its own tests), a duplicate component definition inside `Grid.tsx`, and — compared directly against its sibling `@webiny/website-builder-vue` — a noticeably narrower public API (several hooks the Vue package exports are not exported here) and a store-keying convention that, unlike Vue's, correctly matches the SDK's own convention (`properties.id`). Other packages should keep using `BindingsProcessor`/`documentStoreManager`/`contentSdk` from the SDK directly rather than re-deriving bindings logic, which this package itself does correctly.

## Public API
- `DocumentRenderer`, `DocumentFragment`, `ElementSlot`, `DocumentStoreProvider`/`useDocumentStore` (`components/index.ts`) — the only symbols re-exported from this package's own code. Consumed by `website-builder-nextjs` (`DocumentRenderer.tsx` wraps `BaseDocumentRenderer`) and by `remote-components`' `ComponentSandbox` (renders `DocumentRenderer` directly, per CodeGraph).
- `createComponent` (`createComponent.ts`, a straight re-export of the SDK's `createComponent`) — used by every `editorComponents/*.manifest.ts` file in this package and by consumers building custom components (`website-builder-nextjs/src/editorComponents/Image.manifest.ts`).
- `editorComponents` (`editorComponents/index.ts`, not exported from the top-level barrel but consumed internally by `DocumentRenderer.tsx`) — the built-in Box/Grid/GridColumn/Image/Lexical/Fragment/Root manifests, always registered alongside a consumer's own components.
- `Image`, `BackgroundImage`, `getImageProps` (`src/image/*`) — a small CSS-based asset-rendering utility library with its own test file. Not part of the public API at all (see Dead code) and not currently reachable by any consumer.
- Large SDK re-export list in `index.ts` (input builders, `contentSdk`, `environment`, asset helpers, experiment helpers) — passthrough only, no reimplementation.

## Duplication
- Per jscpd (`jscpd-website-builder-react/jscpd-report.json`): the only detected clone is internal to `createComponent.test.ts:54-69` / `:134-148` (two near-identical test blocks for "inputs as array" vs. "inputs as object" — acceptable test duplication, not source duplication).
- Not caught by jscpd (below its default token threshold) but confirmed by reading the code: `Grid.tsx`'s local `GridColumnComponent` duplicates `GridColumn.tsx`'s exported one (Bug #3), and `PreviewElementSlot.tsx`'s local `ElementSlotProps` duplicates `ElementSlot.tsx`'s exported one (Bug #4).
- Cross-package: `@webiny/website-builder-vue`'s `Image.ts`/`ImagePlaceholder` and this package's `editorComponents/Image.tsx`/`ImagePlaceholder` implement the same SVG-placeholder markup, resize-width computation, and fade-in-on-load logic independently per framework — expected given the frameworks differ, but the resize-width/srcSet math (`SUPPORTED_IMAGE_RESIZE_WIDTHS` / `SUPPORTED_WIDTHS`, the identical `[100, 300, 500, 750, 1000, 1500, 2500]` array) could be centralized in the SDK instead of being copy-pasted per binding; it isn't part of `getImageSrcSet` in the SDK despite that function existing for exactly this purpose.

## Dead code
- `src/image/*` (`Image.tsx`, `BackgroundImage.tsx`, `getImageProps.ts`, plus `getImageProps.test.ts`) — exported via `src/image/index.ts`, but `src/index.ts` never re-exports `./image/index.js`, and `package.json`'s `exports` map is `{"." : "./index.js"}` only (no `./image` subpath). CodeGraph/grep confirm the only consumer of this package (`website-builder-nextjs`) imports exclusively from the main entry point and, for its own `Image` component, uses the SDK's lower-level `getAssetUrl`/`getImageDimensions`/`getImageSrcSet`/`normalizeToAsset` directly rather than this package's `Image`/`getImageProps`. The entire submodule (~230 lines plus its test file) is unreachable from outside the package: "codegraph: no consumers" reachable through the public surface.
- `editorComponents` (`editorComponents/index.ts`) is not re-exported from the top-level barrel either; it's only usable internally by `DocumentRenderer.tsx`. A consumer wanting to list/inspect the built-in components (as `@webiny/website-builder-vue`'s barrel allows via `export { Box, Fragment, Grid, GridColumn, Image, Lexical, Root } from "./editorComponents/index.js"`) cannot do so through this package's public API.

## Convention issues
- `components/index.ts` only re-exports 4 of the package's ~15 public-shaped symbols (`DocumentRenderer`, `DocumentFragment`, `ElementSlot`, `DocumentStoreProvider`). `useDocumentFragments` (defined and used internally in `FragmentsProvider.tsx`/`Fragment.tsx`), `useElementSlotDepth`, `useElementIndex`, `EditingElementRenderer`, `useBindingsForElement`, `useDocumentState`, `useSelectFromState`, and `useViewport` all exist but are not exported anywhere from `src/index.ts` or `components/index.ts`. This is a real asymmetry against `@webiny/website-builder-vue`, whose barrel exports the equivalent of every one of these. A consumer of this package who wants to build a custom component that reads document fragments, slot depth, or viewport/breakpoint info — all things the built-in `Fragment`/`Grid`/`Image` components use internally — has no supported way to do so, unlike a Vue-binding consumer.
- `src/image/getImageProps.ts` documents itself as "the escape hatch for custom rendering" for consumers who don't want the full `Image` component, but per the barrel-export gap above this escape hatch isn't actually reachable either.

## Test gaps
- `createComponent.test.ts` only exercises TS-type inference of `createComponent`/`ExtractInputNames` (its own comment says as much); it doesn't test any runtime rendering behavior.
- `getImageProps.test.ts` covers the (currently unreachable, see Dead code) `getImageProps` utility well, but nothing tests the actual rendering pipeline: `DocumentRenderer`, `ElementRenderer`, `LiveElementRenderer`, `EditingElementRenderer`, `ElementSlot`/`LiveElementSlot`/`PreviewElementSlot`, or any of the built-in editor components (Box/Grid/GridColumn/Fragment/Lexical/Image) have zero tests. In particular, `Grid.manifest.ts`'s `onChange` handlers (auto-creating/removing `GridColumn` children when `gridLayout`/`rowCount` change) contain non-trivial arithmetic (`remainder`, `fullColumnCount`, row chunking) that is completely untested.

## Recommendations
1. Either delete `src/image/*` (dead, unreachable code duplicating logic the SDK already exposes at a lower level) or wire it into the public API (`export * from "./image/index.js"` in `src/index.ts` plus an `./image` subpath in `package.json`'s `exports`) if it's meant to be used — right now it's neither.
2. Align the public barrel with `@webiny/website-builder-vue`'s: export `useDocumentFragments`, `useElementSlotDepth`/`ElementSlotDepthProvider`, `useElementIndex`/`ElementIndexProvider`, `EditingElementRenderer`, and the state hooks (`useBindingsForElement`, `useDocumentState`, `useSelectFromState`, `useViewport`), so consumers of the React binding have the same extension points available to Vue-binding consumers.
3. Fix the two duplicate declarations (`Grid.tsx`'s private `GridColumnComponent`, `PreviewElementSlot.tsx`'s local `ElementSlotProps`) by importing the canonical versions, closing off the silent-drift risk both currently carry.
