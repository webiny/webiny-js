# @webiny/lexical-editor

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`lexical-editor` is Webiny's full rich-text editor UI built on `@lexical/react`: it assembles `RichTextEditor`/`LexicalHtmlRenderer` (composer + plugin wiring), a `StaticToolbar` with a set of composable `ToolbarActions` (bold, lists, links, images, font color/size, typography), a `LexicalEditorConfig` extension API (register custom nodes/plugins/toolbar elements via `@webiny/react-properties`), and supporting hooks/utilities largely forked from Meta's Lexical playground examples (drag/drop images, floating link editor, URL sanitization). It correctly reuses `@webiny/lexical-nodes` (`allNodes`, node predicates, `formatToHeading`/`formatToParagraph`), `@webiny/lexical-theme` (always sets `$cacheKey` when building the Lexical `theme` config, avoiding the stale-cache bug flagged in `lexical-theme`'s own audit), `@webiny/react-composition` (`makeDecoratable`/`Compose`) and `@webiny/react-properties` (`createConfigurableComponent`/`Property`) rather than reimplementing any of them. Overall health is good and it is heavily consumed (by `app-admin`, `app-headless-cms`, `app-website-builder`), but the package has **zero automated tests** for ~90 source files, and its `Plugin`/`ToolbarElement`/`Node` config components are copy-pasted three times with no functional difference beyond a string prefix.

## Public API
- `RichTextEditor` (`src/components/Editor/RichTextEditor.tsx:189`) — the main editor component; consumers: `app-admin`'s `lexicalValueFromHtml.ts`/`lexicalValueWithHtml.ts`, and re-exported through `app-headless-cms`/`app-website-builder` Lexical wrappers.
- `LexicalEditorConfig` / `useLexicalEditorConfig` (`src/components/LexicalEditorConfig/LexicalEditorConfig.tsx:16,30`) — the extension-point API (`.ToolbarElement`, `.Plugin`, `.Node` sub-components) used by `app-admin`'s `LexicalPreset`, `DefaultLexicalEditorConfig`, `LexicalEditorCmsPlugin`, and `app-website-builder`'s `DefaultLexicalConfig` (~4-5 packages configure the editor this way); `useLexicalEditorConfig` alone has ~11 call sites across the monorepo.
- `StaticToolbar` and the `*Action` components (`BoldAction`, `FontColorAction`, `FontSizeAction`, `TypographyAction`, `ImageAction`, etc., under `src/components/ToolbarActions/`) — consumed the same way, e.g. `app-website-builder/src/inputRenderers/LexicalInput/DefaultLexicalConfig.tsx` wires in `FontSizeAction`.
- Plugins (`LinkPlugin`, `FloatingLinkEditorPlugin`, `ImagesPlugin`, `FontColorPlugin`, `TypographyPlugin`, `QuotePlugin`/`ListPlugin`, `StateHandlingPlugin`, `CodeHighlightPlugin`, `BlurEventPlugin`) exported from `src/index.ts` — registered by the same config consumers to build the concrete Lexical node/plugin set per app.
- `isValidLexicalData`, `sanitizeUrl` (internal, not exported from `src/index.ts`), and command creators (`INSERT_IMAGE_COMMAND`, `ADD_TYPOGRAPHY_COMMAND`, list/quote commands) under `src/commands/`.

## Duplication
- `src/components/LexicalEditorConfig/components/Plugin.tsx`, `ToolbarElement.tsx`, and `Node.tsx` are the same ~25-line `Property`-wrapping component three times over (jscpd flagged the Plugin/ToolbarElement pair as a clone; `Node.tsx` — not shown in the jscpd report, likely just under the size threshold — is structurally identical too), differing only in the id/name string prefix (`plugin:`/`element:`/`node:`) and the collection name (`plugins`/`toolbarElements`/`nodes`). This is a strong candidate for a single generic `createOrderedPropertyList(prefix, collectionName)` helper.
- `src/components/ToolbarActions/TypographyAction.tsx:98-134` — the two `useEffect` branches (paragraph/heading/quote vs. list) duplicate the identical "read `styleId`, look up `theme.getTypographyById`, `setTypography(...)`" block almost verbatim (jscpd self-match at lines 103 vs 120).
- `src/components/Toolbar/StaticToolbar.css` — the `.static-toolbar .chevron-down` and `.static-toolbar .chevron-down.inside` rule blocks are defined twice, verbatim, once around line ~103 and again at ~215-222 (confirmed by direct read).
- `src/components/LexicalHtmlRenderer.tsx:23-40` and `src/components/Editor/RichTextEditor.tsx:95-112` build near-identical `initialConfig` objects (same `nodes: [...allNodes, ...]`, same `theme: {...tokens, $colors, $typography, $cacheKey: JSON.stringify(...)}` block) — worth extracting into a shared `buildLexicalTheme(theme)`/`buildInitialNodes(nodes)` helper so the two call sites can't drift (e.g. one forgetting `$cacheKey`, which would reintroduce the `lexical-theme` caching bug from a different code path).

## Dead code
None found with high confidence. The main components/hooks/plugins all show external consumers via codegraph (`RichTextEditor`, `useLexicalEditorConfig`, `FontSizeAction`, etc., each with multiple callers in `app-admin`/`app-website-builder`/`app-headless-cms`). Not every export (e.g. `Divider`, `DropDown`/`DropDownItem`, `LinkAction`, `UnderlineAction`) was individually checked given the cost budget, but the barrel (`src/index.ts`) mirrors the toolbar-action set actually rendered by `StaticToolbar`, so wholesale dead exports are unlikely.

## Convention issues
- `src/plugins/ListPLugin/ListPlugin.ts` — the directory is misspelled `ListPLugin` (capital "L" mid-word) vs. every sibling plugin directory (`FontColorPlugin`, `TypographyPlugin`, `QuoteNodePlugin`, etc.). Cosmetic but inconsistent with the rest of the package's naming.
- `src/context/TextAlignmentActionContextProps.tsx` is named `...ContextProps` but exports a context object plus its provider, not just a props type — inconsistent with the sibling `FontColorActionContext.tsx`/`TypographyActionContext.tsx` naming (no `Props` suffix). Not verified further given budget.
- The barrel `src/index.ts` re-exports low-level UI primitives (`Divider`, `DropDown`, `DropDownItem`) alongside the app-facing `RichTextEditor`/`*Action` components; per the repo's "minimal barrel exports" convention this is arguably borderline (these are generic building blocks rather than the package's main feature surface), but they do appear to be intended for consumers building custom toolbar actions, so this is a low-confidence nit rather than a clear violation.

## Test gaps
- The package has **no `__tests__` directory and no test files at all** (confirmed via directory listing), despite implementing non-trivial, stateful logic: the debounced two-way state sync in `StateHandlingPlugin` (`src/plugins/StateHandlingPlugin.tsx:17-89`, including its 500ms anti-echo-loop heuristic), the floating link editor's selection-suppression state machine (`src/plugins/FloatingLinkEditorPlugin/useFloatingLinkEditor.ts:60-109`), image drag/drop (`src/plugins/ImagesPlugin/ImagesPlugin.tsx`), and `sanitizeUrl`'s URL-scheme allowlist (`src/utils/sanitizeUrl.ts`) — a security-relevant function with zero direct unit tests in this package (only exercised indirectly through consuming apps, if at all).
- `TypographyAction`'s typography-restoration `useEffect` (paragraph/heading/quote vs. list branches) and the `LexicalEditorConfig` ordering/merge behavior (`before`/`after` placement across `Plugin`/`ToolbarElement`/`Node`) are untested at this layer.

## Recommendations
1. Add unit/integration tests for `StateHandlingPlugin`'s two-way sync (the 500ms anti-echo guard) and `sanitizeUrl`, since both are correctness/security-sensitive and currently have zero coverage in a package with no tests at all.
2. Collapse `Plugin.tsx`/`ToolbarElement.tsx`/`Node.tsx` into one generic, parameterized component to remove the triplicated `Property`-wrapping logic and prevent the three from drifting further.
3. Extract the duplicated `initialConfig`/theme-building block shared by `RichTextEditor.tsx` and `LexicalHtmlRenderer.tsx` into a single helper, so the `$cacheKey` requirement (needed to avoid `lexical-theme`'s stale-cache bug) can't be accidentally dropped from one of the two call sites in a future edit.
