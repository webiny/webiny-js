# @webiny/api-opensearch

> Level 2 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-opensearch` is the shared, storage-agnostic layer for talking to OpenSearch/Elasticsearch: a cached client factory (`createOpenSearchClient`), a DI-registered set of query-builder operators (`eq`, `not`, `in`, `between`, `contains`, `startsWith`, …) plus the `where`/`sort`/`limit`/`cursor` helpers that turn a GraphQL-style filter into an OpenSearch bool query, cursor encoding/decoding, cluster-health polling (`waitUntilHealthy`), and the base index mapping/settings shared by every OpenSearch-backed storage package. It correctly builds on `@webiny/error`/`@webiny/feature`/`@webiny/handler` rather than reinventing them, and it is a genuinely load-bearing level-1 dependency: `createSort`, `createLimit`, `OpenSearchQueryBuilderOperatorRegistry`, and `getBaseConfiguration` are consumed directly by `api-headless-cms-utils-os`, `api-headless-cms-ddb-es`, `api-headless-cms-pg-os`, and `api-opensearch-aws`. Overall health is good — small, focused files, clean DI wiring, decent operator-level test coverage — but there is one real, currently-inert bug in the shared index mapping's dynamic templates, a scattering of `console.*` calls in backend code, and one fully dead exported function.

## Public API
- `createOpenSearchClient` (`src/client.ts:22`) — process-wide cached client factory keyed by a hash of the connection options; used internally by `OpenSearchClientFactory` and `registerOpenSearchCore`, and directly by `api-opensearch-aws`'s `createAwsOpenSearchClient` (~1 external consumer, plus 2 internal).
- `registerOpenSearchCore` (`src/registerOpenSearchCore.ts:10`) — the extension-registration entrypoint (built on `@webiny/handler`'s `createRegisterExtensionPlugin`) that wires the client and all of this package's features into the request container; called from project-level API composition and from `testing/registerOpenSearchCoreForTests.ts`.
- `applyWhere`/`parseWhereKey` (`src/where.ts`), `createSort` (`src/sort.ts:20`), `createLimit` (`src/limit.ts:11`), `encodeCursor`/`decodeCursor` (`src/cursors.ts`) — the filter/sort/pagination building blocks. `createSort` and `createLimit` are consumed by `api-headless-cms-utils-os` (`CmsEntryOpenSearchBodyBuilder/sort.ts`) and `api-headless-cms-ddb-es`/`api-headless-cms-pg-os` list operations; `parseWhereKey` is exercised by this package's own `where.test.ts`; `applyWhere` has zero consumers anywhere (see Dead code).
- `OpenSearchQueryBuilderOperatorRegistry`/`OpenSearchField`/`OpenSearchFieldFactory`/`OpenSearchIndex`/`OpenSearchIndexRegistry` (DI abstractions under `src/features/*`) — the pluggable operator/field/index registries. `OpenSearchQueryBuilderOperatorRegistry` is consumed by `api-headless-cms-utils-os`'s `CmsEntryOpenSearchOperatorList` and by `packages/webiny/src/api/opensearch.ts`.
- `getBaseConfiguration`/`getCommonMappings` (`src/indexConfiguration/*`) — the shared index body (dynamic templates + settings). Used as-is (no modifier) by `api-headless-cms-utils-os`'s `BaseOpenSearchIndex` and `DefaultCmsModelOpenSearchIndex` to create the real CMS-entry OpenSearch index.
- `OpenSearchCatHealth`/`OpenSearchCatNodes`/`createWaitUntilHealthy` (`src/operations/*`, `src/utils/waitUntilHealthy/*`) — cluster health/readiness polling, used by deployment/bootstrap code that waits for a freshly-created cluster to become healthy.

## Duplication
- `In.ts`/`NotIn.ts` (`src/features/OpenSearchQueryBuilderOperator/operators/In.ts:5-16` / `NotIn.ts:5-16`) and `Between.ts`/`NotBetween.ts` (`Between.ts:5-15` / `NotBetween.ts:5-15`) are near-identical per the jscpd report (12 and 11 duplicated lines respectively) — each pair differs only in the operator name and which query clause (`filter` vs `must_not`) it pushes to. This is inherent to the one-operator-per-file convention and is low-risk, but a shared `applyInClause`/`applyRangeClause` helper would remove the duplication if it grows further (there are 15 operator files total, several sharing similar shape).
- `Contains.ts`/`NotContains.ts` are likewise structurally identical except for the target clause and operator name (not flagged by jscpd because the block is just under its duplicate-detection threshold, but visibly the same pattern).
- No duplication with lower-level dependencies (`error`, `feature`, `handler`) was found; the package correctly reuses `WebinyError`/`WError`, `createFeature`/`createAbstraction`, and `createRegisterExtensionPlugin` rather than reimplementing them.

## Dead code
- `applyWhere` (`src/where.ts:45`) is exported from the package root (`export * from "./where.js"` in `src/index.ts:4`) but has zero consumers anywhere in the monorepo — not even in this package's own `__tests__/where.test.ts`, which only tests `parseWhereKey`. Confirmed via repo-wide grep (no other file references `applyWhere`). Downstream consumers that build OpenSearch bool queries from a `where` object (e.g. `api-headless-cms-utils-os`) do so with their own field/operator wiring rather than this helper.

## Convention issues
- Repeated `console.*` usage in backend code (see Bugs #2) — the most visible convention violation in the package.
- Everything else follows the repo's DI conventions cleanly: one abstraction/implementation/feature per file, implementation classes declared separately and passed by reference to `createImplementation`, namespaces used to reach `.Interface` rather than re-exporting raw `I*` types.
- One minor inconsistency: `StartsWith`/`NotStartsWith` operators register themselves under the camelCase names `"startsWith"`/`"not_startsWith"` (`operators/StartsWith.ts:5`, `NotStartsWith.ts:5`) while every other operator uses lower_snake_case (`eq`, `not_in`, `not_between`, `gt`, …). Not a bug (the suffix parsing in `where.ts` is case-insensitive to the operator string itself, it just splits on `_`), but it is an inconsistent naming convention within the same registry.

## Test gaps
- No test indexes an actual document and inspects the resolved field mapping to verify the `ids`/`dates` dynamic templates match real field names (see Bug #1) — `__tests__/index.test.ts` only round-trips the submitted config through `create`/`getMapping`.
- `AndIn` (`src/features/OpenSearchQueryBuilderOperator/operators/AndIn.ts`) has no dedicated test under `__tests__/plugins/operators/`, unlike all 14 of its sibling operators.
- `createSort` (`src/sort.ts`) has no direct unit test in this package (only exercised indirectly through `api-headless-cms-utils-os`'s own sort tests); the `createSort`/`SortType` merged-object output relies on legacy Elasticsearch/OpenSearch multi-field-object sort syntax rather than the documented array form, and nothing in this package pins that behavior down.

## Recommendations
1. Fix the `ids`/`dates` dynamic-template `match` patterns in `src/indexConfiguration/common.ts:7,16` to either use simple glob syntax (e.g. separate templates per field, or `match: "id"` / a shared prefix) or explicitly set `match_pattern: "regex"`, and add a test that indexes a document and asserts the resolved field type.
2. Replace the `console.*` calls in `client.ts`, `cursors.ts`, `createIndex.ts`, `OpenSearchCatHealth.ts`, and `OpenSearchCatNodes.ts` with the DI `Logger`, per `ai-context/code-style/no-console-in-backend.md`.
3. Remove the dead `applyWhere` export (or wire it up somewhere) and add a unit test for `AndIn`.
