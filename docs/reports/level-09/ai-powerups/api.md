# @webiny/ai-powerups — API

> Level 9 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice (`packages/ai-powerups/src/api`, ~6.3k lines) is the backend half of Webiny's AI Power-Ups: a settings/connections/provider layer for configuring one or more LLM connections and per-capability model roles, a "Capabilities" registry that lets each AI feature declare a default model role and system-prompt additions, and a set of independent AI capabilities built on `@webiny/api-core`'s `Ai`/`AiSdkTools` abstractions — an admin chat assistant with human-approval-gated tool use (`AdminAssistant`), CMS entry content generation (`CmsGenerateEntryContent`), website-builder page content generation (`WbGeneratePageContent`), page translation on create (`WbTranslatePage`), image alt-text/tag enrichment on upload (`AiImageEnrichment`), markdown frontmatter extraction on upload (`ExtractFrontmatter`), and entry-revision comparison (`CmsCompareEntryRevisions`, previously audited — see below). The `AdminAssistant` capability is well designed from a safety standpoint: every mutating tool call is paused for human approval unless the tool explicitly declares itself read-only, defaulting to "unsafe" for unannotated tools. One finding in this slice is security-sensitive and is tracked only in private notes (see Bugs). Other packages should reuse this slice's `GetSettingsUseCase`/`ResolveAiCapabilityUseCase`/`withAdditionalInstructions`/`AI_MODEL_ROLE_IDS` (already consumed by `@webiny/remote-components`) rather than re-deriving AI-connection/capability resolution, and its `Encryption`/`Masker`-based pattern in `ConnectionsHandler` for storing any other provider credential.

## Public API
- `GetSettingsUseCase` (`features/GetSettings/abstractions.ts`) — reads the full AI Power-Ups settings blob (connections, model roles, personas, projects). Consumed inside the package by every capability's `ResolveAiCapabilityUseCase`, and externally by `@webiny/remote-components`'s `RefineRemoteComponentUseCase`/`GenerateRemoteComponentUseCase` (~2 external call sites) and re-exported from `@webiny/webiny/api/ai-powerups.ts`.
- `UpdateSettingsUseCase`/`UpdateSettingsRepository` (`features/UpdateSettings/*`) — validates (per-group Zod schema) and persists settings via `KeyValueStore`; wired to the sole `updateSettings` GraphQL mutation.
- `ResolveAiCapabilityUseCase`, `withAdditionalInstructions`, `AiCapability` (`features/Capabilities/*`) — resolves which model/connection a given capability (e.g. `ADMIN_ASSISTANT_CAPABILITY`, `CMS_GENERATE_ENTRY_CAPABILITY`) should use and appends any admin-configured extra instructions to the system prompt; re-exported via `@webiny/webiny/api/ai-powerups.ts` and used by every capability in this slice.
- `AI_MODEL_ROLE_IDS`/`AiModelRoleId` (`features/ModelRoles/*`) — the fixed set of model roles (e.g. "standard") settings map to; re-exported the same way.
- `AdminAssistantUseCase.stream` (`features/AdminAssistant/AdminAssistantUseCase.ts`) — the chat-with-tools loop; consumed by `AdminAssistantStreamRoute.ts` (`POST` SSE route), the only entry point.
- `CmsGenerateEntryContentUseCase`/`WbGeneratePageContentUseCase` — invoked only from their respective `TaskHandler`s (`CmsGenerateEntryContentTask.ts`, `WbGeneratePageContentTask.ts`), themselves triggered from `BaseGraphQLSchema.ts`'s `generateEntryContent`/`generatePageContent` mutations via `TaskService.trigger`. `CmsGenerateEntryContentUseCase` abstraction is also re-exported from `@webiny/webiny/api/ai-powerups.ts`.
- `ApplyImageEnrichmentUseCase`/`PrepareImageEnrichmentUseCase` (`features/AiImageEnrichment/*`) — auto-triggered on every image upload (`AiImageEnrichmentAfterCreateHandler`) and reusable synchronously via `AiImageEnrichmentStreamRoute` (`POST /stream/fm/files/:fileId/enrich`, SSE, propose-only — nothing is persisted from that route).
- `WbTranslatePageDecorator` — a `TranslatePageUseCase` decorator (from `@webiny/api-website-builder`) that machine-translates a freshly created page's bindings/properties into the target language and writes the result back via `UpdatePageRepository`.

## Duplication
Package-wide jscpd summary for `@webiny/ai-powerups`: 32 clones / 495 duplicated lines, spanning both `src/api` (this slice) and `src/admin` (audited separately). Within this slice specifically:
- `features/ReaderPersonas/ReaderPersonasHandler.ts` and `features/WriterPersonas/WriterPersonasHandler.ts` are near-identical (two clone blocks, 14 lines each) — both are thin `AiPowerUpsSettingsGroupHandler` implementations that differ only in the persona type; a shared generic handler factory would remove the duplication.
- `features/Providers/ProvidersHandler.ts`, `features/Connections/ConnectionsHandler.ts` and `features/WriterPersonas/WriterPersonasHandler.ts` share smaller overlapping blocks (8-9 lines) of the same settings-handler boilerplate.
- `features/CmsGenerateEntryContent/CmsGenerateEntryContentUseCase.ts` and `features/WbGeneratePageContent/WbGeneratePageContentUseCase.ts` share four large clone blocks (21, 7, 30, and 15 lines) — the capability-resolution → prompt-context-building → `ai.generateText` → JSON-response-parsing pipeline is copy-pasted between the CMS-entry and page-content generation flows rather than factored into one shared "run a generation capability" helper.
- `features/CmsGenerateEntryContent/CmsGenerateEntryContentTask.ts` and `features/WbGeneratePageContent/WbGeneratePageContentTask.ts` share a 22-line clone — the same "run the use case, catch, send success/error to the identity over websockets" task-handler boilerplate.
- `features/WbGeneratePageContent/WbGeneratePageContentTask.ts` and `features/WbGeneratePageContent/abstractions.ts` share a 12-line clone (likely a type shape duplicated between the task input and the use-case params rather than imported once).
- `graphql/BaseGraphQLSchema.ts` has one internal self-duplication (lines 146-164 vs 182-200) — the `generatePageContent`/`generateEntryContent` resolver bodies (build task input, trigger, handle failure) are structurally identical and could share a small helper.

None found with confidence — every exported use case/handler in this slice is wired into either `BaseGraphQLSchema.ts`, a `feature.ts` DI registration, a `TaskDefinition`, an `HttpRouteDefinition`, or a file-manager event handler, and the package's own `feature.ts`/`index.ts` files register all of them. ## Convention issues
- `WbTranslatePage/WbTranslatePageDecorator.ts` writes its result via `UpdatePageRepository` directly instead of going through the page feature's `UpdatePageUseCase`, which is the one place the rest of the `pages` slice (per the level-8 `api-website-builder` audit) does its "own"/rwd permission re-check. In this specific call site it is not a live authorization gap (the write targets the very page that `TranslatePageUseCase`'s decoratee just successfully created/returned under the caller's own identity), but it is an inconsistency with the repo's one-use-case-per-mutation convention and would become a real gap if this decorator's write target were ever changed to something the caller hasn't already been authorized against.
- `features/CmsGenerateEntryContent` and `features/WbGeneratePageContent` duplicate an entire generation pipeline (see Duplication) instead of sharing one generic "capability-driven generation" abstraction, which is the kind of one-per-feature proliferation AGENTS.md's DI conventions are meant to keep in check as more content-generation capabilities are added.

## Test gaps
Only five test files exist under this slice's part of `__tests__/` (`upgradeFromLegacyProviders`, `AiImageEnrichmentStreamRoute`, `AdminAssistantUseCase`, `ComponentFilter`, `ConnectionsHandler`). Notably untested: `CmsGenerateEntryContentUseCase`/`WbGeneratePageContentUseCase`, `GetSettingsUseCase`/`UpdateSettingsUseCase`/`UpdateSettingsRepository`, `WbTranslatePageDecorator`, `ExtractFrontmatterBeforeCreateHandler`, `ApplyImageEnrichmentUseCase`/`PrepareImageEnrichmentUseCase`, `ModelRoles`/`Providers`/`ReaderPersonas`/`WriterPersonas` handlers, and every resolver in `BaseGraphQLSchema.ts`.

## Recommendations
1. See private security notes for the highest-priority action in this slice.
2. Add tests covering `GetSettingsUseCase`/`UpdateSettingsUseCase`, `CmsGenerateEntryContentUseCase`, and `WbGeneratePageContentUseCase`, so that any future capability added to this slice has regression coverage from the start.
3. Factor `CmsGenerateEntryContentUseCase`/`WbGeneratePageContentUseCase` (and their matching `*Task.ts` handlers) into one shared "capability-driven generation" pipeline to remove the largest duplication blocks and ensure a fix or safety check added to one cannot be forgotten in the other.
