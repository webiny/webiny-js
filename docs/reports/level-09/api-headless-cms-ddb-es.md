# @webiny/api-headless-cms-ddb-es

> Level 9 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-headless-cms-ddb-es` is one of two "CMS entries in DynamoDB, searchable via OpenSearch" storage-operations backends (the other being `api-headless-cms-pg-os`). It implements every `CmsEntry`/`CmsModel`/`CmsModelGroup` storage operation against a primary DynamoDB entries table plus a second DynamoDB table (`ENTRIES_ES`, via `@webiny/api-opensearch-aws`'s DynamoDB-Streams-to-OpenSearch bridge) that a downstream stream consumer relays into OpenSearch, and it correctly delegates `where`/`sort` query-DSL construction, tenant/index-name computation, and the dynamic-template mapping entirely to the already-audited `@webiny/api-opensearch` and `@webiny/api-headless-cms-utils-os` packages rather than reimplementing them (so it also transitively inherits the level-2 dynamic-template glob/regex bug and the level-7 zero-test-coverage gap in that layer). The package's own weak spot is that every mutating operation (create/update/delete/publish/unpublish/move/restore) performs two independent, non-atomic writes — one to the primary entries table, one to the ES-bridge table — with no compensation if the second write fails after the first succeeds, and it hardcodes an effectively-unbounded (1,000,000-bucket) terms aggregation for "get unique field values" that is duplicated verbatim in `api-headless-cms-pg-os`.

## Public API
- `HeadlessCmsDdbEsFeature` (`src/feature.ts:23`) — the top-level DI feature; wires DynamoDB table/entity instances, `DdbEsGroupStorageOpsFeature`/`DdbEsModelStorageOpsFeature`/`DdbEsEntryStorageOpsFeature`, and registers `CreateElasticsearchIndexTask` (a `TenantIndexFactory` implementation used by `api-search-index-tasks`'s `CreateIndexesTask`). Consumed from `src/index.ts`; like its `api-headless-cms-pg-os` counterpart, its only in-repo callers are its own barrel and test setup — real consumption happens from generated project scaffolds outside this monorepo's static graph.
- The individual `DdbEs*` storage-operation classes (`DdbEsCreateEntry`, `DdbEsListEntries`, `DdbEsGetRevisions`, etc., `src/operations/entry/*.ts`) — each implements one `@webiny/api-headless-cms` `*StorageOperation.Interface` abstraction and is wired into that package's `HeadlessCmsFeature` facade when this backend is selected (per the level-6 `api-headless-cms` "crud-and-utils" report's description of `crud/*.crud.ts` resolving `features/**/UseCase`s that ultimately call these storage operations).

## Duplication
jscpd reports 11.74% duplication within the package (30 clone pairs, 535 duplicated lines), concentrated in the entry-operation family: `DdbEsPublishEntry.ts`/`DdbEsUnpublishEntry.ts`/`DdbEsMoveToBin.ts`/`DdbEsRestoreFromBin.ts` all repeat large blocks of `DdbEsUpdateEntry.ts`'s key-building/entity-writer-construction logic (e.g. `DdbEsPublishEntry.ts:8-25,33-63` vs `DdbEsUpdateEntry.ts:7-25,34-63`), and the three `dataLoader/get*ByEntryId.ts` files (`getPublishedRevisionByEntryId.ts`, `getRevisionById.ts`, `getLatestRevisionByEntryId.ts`) are near-identical DataLoader-construction wrappers around a differently-parameterized DynamoDB query. `DdbEsCreateGroup.ts`/`DdbEsUpdateGroup.ts` share the same clone pattern. None of this is a correctness bug — the operations are genuinely almost-identical state transitions — but it means any future fix to the two-phase-write pattern (Bug #1) needs to be applied consistently across 6+ files rather than one shared helper.

Cross-package: `DdbEsGetUniqueFieldValues.ts` (`src/operations/entry/DdbEsGetUniqueFieldValues.ts:31-104`) is a near-verbatim copy of `api-headless-cms-pg-os`'s `search/getUniqueFieldValues.ts`, including the hardcoded `size: 1000000` (Bug #2) — a candidate for extraction into the shared `api-headless-cms-utils-os` package both backends already depend on.

## Dead code
None found with high confidence in the scope reviewed; the package's storage-operation classes are all wired through `feature.ts`/the per-entity `feature.ts` files into `HeadlessCmsDdbEsFeature`, and `HeadlessCmsDdbEsFeature` itself, while only reachable from this package's own `index.ts` within the monorepo's static graph, is the documented entry point selected by generated project templates (same pattern as `api-headless-cms-pg-os`'s `HeadlessCmsPgOsFeature`, confirmed via codegraph).

## Convention issues
None found beyond the duplication noted above — DI naming (`DdbEs*` implementation classes matching their abstraction names) and one-class-per-file conventions are followed consistently.

## Test gaps
- `getAllEntryRevisions` (`src/operations/entry/dataLoader/getAllEntryRevisions.ts:7-38`) queries DynamoDB with no reverse option (ascending/oldest-first sort-key order); this is the DDB-side half of the level-8 revision-ordering drift already reported against `api-headless-cms-sql`'s `.orderBy("version", "desc")`. There is no test in this package that asserts revision ordering, so a future change here (or in the SQL backend) that "fixes" one side without checking the other would go unnoticed by either package's test suite.
- No test exercises the two-phase-write failure path in Bug #1 (i.e., primary-table write succeeds, ES-bridge-table write throws) — the 31 test files in `__tests__/` focus on happy-path CRUD behavior.

## Recommendations
1. Address the non-atomic primary/ES-bridge write pattern (Bug #1): at minimum, log/track entries whose ES-bridge write failed after a successful primary write (an outbox-style reconciliation record, similar to what `api-headless-cms-pg-os`'s `SyncWriter` already does for Postgres) so they can be automatically or manually resynced, instead of relying on the caller's error alone.
2. Replace the hardcoded `size: 1000000` terms-aggregation cap (Bug #2) with a bounded value derived from configuration or an explicit, documented maximum, and share the fix with `api-headless-cms-pg-os` since the code is duplicated.
3. Add a test asserting the entry-revisions read order (ascending) so it can be compared against `api-headless-cms-sql`'s descending order and the drift is caught if either side changes independently.
