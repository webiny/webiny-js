# @webiny/api-headless-cms-pg-os

> Level 9 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-headless-cms-pg-os` is the "CMS entries in Postgres, searchable via OpenSearch" storage-operations backend: it decorates `api-headless-cms-sql`'s entry storage operations (create/update/delete/publish/etc.) so that, after every primary Postgres write succeeds, it writes a corresponding row into a Postgres "sync" outbox table (`features/SyncWriter`), and a separate `SyncEventHandler`/`SynchronizationBuilder` (built on the already-audited `api-sync-to-opensearch` package, with retry/backoff) drains that table into OpenSearch. Reads (list/get/get-unique-field-values) go through OpenSearch via a thin `search/*.ts` layer that reuses `api-headless-cms-utils-os`'s shared body-builder and index-provider, same as `api-headless-cms-ddb-es`. Architecturally this is meaningfully more resilient to transient OpenSearch failures than `api-headless-cms-ddb-es` — the outbox write is a same-database, low-risk operation and OpenSearch delivery is retried asynchronously with an explicit `resyncLatestAndPublishedFromPg` reconciliation path — but the package's own OpenSearch-facing read path never calls the `convertValueKeyToStorage`/`convertValueKeyFromStorage` field converters that `api-headless-cms-ddb-es` applies on every read and write, meaning entries with `object`/`dynamicZone` fields going through OpenSearch here may carry mismatched value shapes; the package also duplicates `api-headless-cms-ddb-es`'s hardcoded, effectively-unbounded terms-aggregation size.

## Public API
- `HeadlessCmsPgOsFeature` (`src/features/HeadlessCmsPgOsFeature.ts:22`) — the top-level DI feature; wires `SyncTableManager`, `SyncWriter`'s decorators onto the SQL entry storage operations, `syncEventHandler`, and `EntrySearchOperations` (list/get/get-unique-field-values against OpenSearch). Codegraph shows 2 callers, both within this package (`src/index.ts` and a test setup file) — like `api-headless-cms-ddb-es`, real consumption is from generated project scaffolds outside the monorepo's static graph.
- `PgOsCreateEntry`/`PgOsUpdateEntry`/`PgOsDeleteEntry`/etc. (`src/operations/entry/PgOs*.ts`) — `createDecorator`-based wrappers around `api-headless-cms-sql`'s equivalent storage operations; each calls the inner SQL operation, then `SyncHelpers.writeSyncForEntry`/`resyncLatestAndPublishedFromPg` to keep the OpenSearch-bound outbox table current.
- `EntrySearchOperations` (`src/operations/entry/EntrySearchOperations.ts`, `abstractions/EntrySearchOperations.ts`) — provides `list`/`get`/`getUniqueFieldValues` against OpenSearch; this package does not implement its own `GetRevisions`/`GetEntry`-by-id (non-search) operations, which come entirely from `api-headless-cms-sql`.

## Duplication
jscpd reports only 1.62% duplication within the package (3 clone pairs, 27 lines) — `PgOsCreateEntry.ts`/`PgOsCreateEntryRevisionFrom.ts` share their decorator boilerplate with `PgOsUpdateEntry.ts`, and `WriteLatest.ts`/`WritePublished.ts` share a small block — all expected given the consistent decorator pattern. The package is much thinner than `api-headless-cms-ddb-es` (1,677 vs 4,559 lines) because it delegates the bulk of entry storage logic to `api-headless-cms-sql` and only adds the sync/search layer.

Cross-package: `search/getUniqueFieldValues.ts` and `search/list.ts` are near-verbatim copies of `api-headless-cms-ddb-es`'s `DdbEsGetUniqueFieldValues.ts`/`DdbEsListEntries.ts` (see Bug #2); both would benefit from being extracted into the shared `api-headless-cms-utils-os` package.

## Dead code
None found with meaningful confidence; every exported feature/decorator is wired through `HeadlessCmsPgOsFeature.ts` and codegraph confirms it is the package's real entry point (consumption happens outside the monorepo's static graph, in generated project scaffolds, same as `api-headless-cms-ddb-es`).

## Convention issues
None found — the decorator classes consistently follow one-abstraction-per-file and the `PgOs*`/DI naming conventions.

## Test gaps
- `__tests__/` contains only 3 test files for a 1,677-line package covering sync/decoration logic across create/update/delete/publish/unpublish/move/restore/revision-from — the `SyncWriter`/`SyncHelpers`/`BuildSyncRecord` outbox-record construction (including the field-conversion gap in Bug #1) has no direct unit test exercising an `object`/`dynamicZone` field round-trip.
- No test covers the interrupted-write scenario in Bug #3 (primary write succeeds, outbox write fails/never happens) or exercises `resyncLatestAndPublishedFromPg` as a recovery mechanism.
- This package does not implement its own `GetRevisions`; revision-ordering behavior for this backend is entirely determined by `api-headless-cms-sql`'s already-flagged (level-8) `.orderBy("version", "desc")`, which drifts from `api-headless-cms-ddb-es`'s ascending DynamoDB order — worth a cross-backend regression test once fixed, since neither package currently asserts revision order against the other.

## Recommendations
1. Apply the model's `convertValueKeyToStorage`/`convertValueKeyFromStorage` converters on both the OpenSearch write path (`BuildSyncRecord.ts`) and read path (`search/list.ts`), matching `api-headless-cms-ddb-es`'s `convertEntryKeysToStorage`/`convertEntryKeysFromStorage` usage, to close the `object`/`dynamicZone` field-shape drift in Bug #1.
2. Fix the hardcoded `size: 1000000` terms-aggregation cap in `search/getUniqueFieldValues.ts`, ideally via a shared fix with `api-headless-cms-ddb-es` given the code is duplicated (Bug #2).
3. Verify (and if needed, wrap) `PgOsCreateEntry`/`PgOsUpdateEntry`/etc.'s primary-write + outbox-write pair in a single Postgres transaction to remove the narrow interrupted-write gap in Bug #3, and add a test that exercises `resyncLatestAndPublishedFromPg` as the documented recovery path.
