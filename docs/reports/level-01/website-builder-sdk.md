# @webiny/website-builder-sdk

> Level 1 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/website-builder-sdk` is the framework-agnostic core of Webiny's visual page builder: it owns the document/element data model (MobX-observable `DocumentStore`), the flat-binding ↔ deep-value conversion pipeline for inputs and styles (`InputBindingsProcessor`/`InputsBindingsProcessor`, `StylesBindingsProcessor`, `BindingsProcessor`, `InheritanceProcessor`, `BindingsResolver`), the editor/preview/live "SDK" facades (`LiveSdk`, `PreviewSdk`, `EditingSdk`, `NullSdk`, `ContentSdk`) that talk to the parent editor iframe over `postMessage` via `Messenger`, and a constraint/placement engine (`ConstraintEvaluator`) plus element creation/mutation (`ElementFactory`, `documentOperations/*`). It builds on `@webiny/sdk`'s `Result`/error types only indirectly (data providers wrap `ApiClient`, not `@webiny/sdk` directly), so there is little risk of the reimplementation patterns that `@webiny/sdk`'s summary warns about. Overall the code is dense but coherent, with decent unit coverage of the trickiest algorithms (bindings resolution, inheritance, constraints); the main risks are (a) a real, reachable null-dereference in `DocumentStore.applyPatch`, (b) a security finding tracked privately (SEC-2), and (c) several sizeable pieces of copy-pasted override/inheritance logic across the bindings processors. Other packages/consumers (`website-builder-react`, `website-builder-vue`, `app-website-builder`) should reuse `BindingsResolver`/`ComponentResolver`/`DocumentStore` rather than re-deriving flat/deep binding conversion or inheritance logic.

## Public API
- `ContentSdk` / `contentSdk` singleton (`ContentSdk.ts`) — top-level facade (`init`, `getPage`, `listPages`, `getPageWithExperiment`, `resolveElement`, `registerComponent`, redirects). Consumed by `app-website-builder`, `website-builder-react`, `website-builder-vue` (Next.js/Nuxt/etc. integration layers reference it via `@webiny/website-builder-sdk`).
- `EditingSdk` / `LiveSdk` / `PreviewSdk` / `NullSdk` — `IContentSdk` implementations selected by `ContentSdk.init` depending on environment (editing iframe vs. live vs. preview-with-experiments).
- `DocumentStore` / `documentStoreManager` (`DocumentStore.ts`, `DocumentStoreManager.ts`) — the MobX-observable per-document state store; ~15 direct callers across `website-builder-react`/`website-builder-sdk` per CodeGraph, notably `EditingElementRenderer.presenter.ts` and `EditingSdk`.
- `BindingsResolver` / `ComponentResolver` (`BindingsResolver.ts`, `ComponentResolver.ts`) — resolves per-element input/style values (including `$repeat` list bindings and `$state`/expression bindings) for rendering; consumed directly by `website-builder-react`'s and `website-builder-vue`'s `LiveElementRenderer`, and by `app-website-builder`'s editor-side `$getElementInputValues`.
- `ElementFactory` / `documentOperations/*` (`ElementFactory.ts`, `documentOperations/index.ts`) — builds the `IDocumentOperation` sequences (`AddElement`, `AddToParent`, `SetGlobalInputBinding`, `SetInputBindingOverride`, etc.) used to mutate a `Document` when a component is placed.
- `evaluateConstraints` / `evaluateDeleteConstraint` (`ConstraintEvaluator.ts`) — component placement/deletion rules engine driven by component-manifest `constraints`/`descendantConstraints`/`canDelete`.
- `Messenger` / `MessageOrigin` (`messenger/`) — typed, origin-checked `postMessage` pub/sub used by every `*Sdk` class talking to the parent editor frame.

## Duplication
- `src/InputBindingsProcessor.ts:268-297` vs `:325-354` (jscpd, 30 lines) — the "responsive override vs. base-binding" branch is duplicated almost verbatim between the `CreateElement` binding path and the plain-value binding path inside `createUpdate`'s `compareAndCollect`. A shared `applyResponsiveOrBase(binding, flatKey, breakpoint, rebuilt, valueResolver)` helper would remove ~30 duplicated lines and reduce the risk of the two paths drifting.
- `src/InheritanceProcessor.ts:110-121` vs `:143-154` (jscpd, 12 lines) — the "find nearest ancestor breakpoint override" loop is copy-pasted between the inputs and styles sections of `getInheritanceMap`. Same fix as above: extract a small `resolveInheritance(overrideIndicesMap, key, currentBpIndex, breakpoints)` helper.
- `src/BindingsProcessor.ts:29-38` vs `src/InheritanceProcessor.ts:43-52` (jscpd, 10 lines) — both classes independently implement "iterate breakpoints 0..upTo, merge each breakpoint's `overrides[bp]`" — a candidate for a small shared "collect active breakpoint overrides" utility so `BindingsProcessor` (used for rendering-time flattening) and `InheritanceProcessor` (used for editor inheritance display) can't silently diverge on override semantics.
- `src/BindingsResolver.ts:154-166` (`getUniqueIndexesFromPath`) vs the equivalent inline block in `src/InputBindingsProcessor.ts:93-102` (jscpd flags `BindingsResolver.ts:157-165` ↔ `InputBindingsProcessor.ts:94-102`) — the same "regex-extract numeric indexes from flat binding keys, dedupe, sort" logic is implemented twice with no shared helper.
- `src/documentOperations/SetInputBindingOverride.ts:13-26` vs `src/documentOperations/SetStyleBindingOverride.ts:13-26` (jscpd, 14 lines) and `src/InputsUpdater.ts:39-47` vs `src/StylesUpdater.ts:32-40` (jscpd, 9 lines) — the "inputs" and "styles" document-operation/updater pairs are structurally identical apart from the field name; a shared generic `SetBindingOverride<TBinding>`/`BindingsUpdater<TBindings>` base could collapse these pairs.
- `src/ConstraintEvaluator.ts:267-273`/`:273-279` vs `:400-406`/`:406-412` (jscpd, 7 lines each) — the `isChildOf`/`isDescendantOf`/`getAncestor` closures in the `ConstraintContext` built by `evaluateConstraints` are duplicated in `evaluateDeleteConstraint`. Low risk but a natural `buildBaseContext(ancestors, components, document)` extraction candidate.
- `src/types.ts:197-205` vs `:218-226` — `ComponentChangeContext` and `DescendantChangeContext` share an almost identical tail (`getElement`, `executeCommand`, `breakpoint`, `log`, `stop`, `continue`); minor, could share a base type.
- Test-file duplication (`ElementFactory.test.ts:109-140`/`:212-243`, `BindingsResolver.test.ts` several 14-line blocks, `InputsBindingsProcessor.test.ts:155-189`) is copy-pasted test setup/assertions rather than parameterized cases — low priority, doesn't affect production code.

## Dead code
- `src/HotkeyManager.ts` (`HotkeyManager` class, line 46) — not exported from `src/index.ts`'s barrel and has zero references anywhere else in the monorepo (`grep -rn "HotkeyManager"` across `packages/` only matches its own definition). Appears to be an abandoned/unfinished feature.
- `src/ResizeObserver.ts` — exported via the barrel (`index.ts:21`) but no in-repo consumer was found (`app-website-builder`'s `useReservedUISpace.ts` uses the native global `ResizeObserver`, not this module). Since the package is published, this could still be used by external/downstream consumers, so confidence here is lower than for `HotkeyManager`.

## Convention issues
- **Barrel exports far exceed "export what external consumers need."** `src/index.ts` is 36 `export *`/`export type *` lines re-exporting nearly every internal class (`BindingsProcessor`, `InheritanceProcessor`, `InputBindingsProcessor`, `StylesBindingsProcessor`, `ConstraintEvaluator`, `ElementFactory`, `jsonPatch`, `findMatchingAstNode`, `generateElementId`, etc.), including pure implementation-detail helpers that only other files inside this same package should need. This directly conflicts with the "minimal barrel exports" convention and makes it hard to tell which of these are actually meant to be a stable public surface for `website-builder-react`/`website-builder-vue`/`app-website-builder` vs. internal wiring.
- **DI naming mismatch.** `src/InputBindingsProcessor.ts` (filename, singular "Input") exports `class InputsBindingsProcessor` (plural "Inputs") — the file name does not match the exported class name, and the companion test file is named `InputsBindingsProcessor.test.ts` (matching the class, not the source file). This is exactly the kind of impl-file/class-name mismatch the project's DI naming convention calls out.

## Test gaps
- `DocumentStore.ts` and `DocumentStoreManager.ts` — the core observable document state container has no test file at all; the `applyPatch` null-dereference (Bug #1) would have been caught by a single test that calls `applyPatch` before `setDocument`.
- `Messenger.ts` / `MessageOrigin.ts` — the `postMessage`-based pub/sub used by every `*Sdk` facade (origin/pattern matching, prefix stripping, ignored-type filtering) has no tests.
- `StylesBindingsProcessor.ts` and `BindingsProcessor.ts` — unlike their `Inputs`/`Inheritance` counterparts, neither has a dedicated test file, despite implementing the same breakpoint-override merge logic flagged above as duplicated (and therefore more likely to drift undetected).
- `documentOperations/*` (`AddElement`, `AddToParent`, `RemoveElement`, `SetGlobalInputBinding`, `SetGlobalStyleBinding`, `SetInputBindingOverride`, `SetStyleBindingOverride`) — none of these `IDocumentOperation` implementations, which are the actual mutators applied to `Document`, have tests.
- `ComponentResolver.ts` — the class that wires `BindingsResolver` + `ComponentRegistry` together for live rendering (confirmed via CodeGraph to be the entry point `LiveElementRenderer` in both React and Vue packages use) has no test file.

## Recommendations
1. Add a guard to `DocumentStore.applyPatch` (`src/DocumentStore.ts:58-62`) matching its sibling methods (`if (!this.document) return`, or queue the patch until `waitForDocument()` resolves), and add a regression test that calls `applyPatch` before `setDocument`.
2. Review security finding SEC-2 (See private security notes (`docs/.reports/security.md`, not committed).)
3. Extract the duplicated override/inheritance-merge helpers (`InputBindingsProcessor` responsive-override branch, `InheritanceProcessor`'s inputs/styles ancestor lookup, and the `BindingsProcessor`/`InheritanceProcessor` breakpoint-merge loop) into shared utilities, and trim `src/index.ts`'s barrel to the classes/functions that `website-builder-react`/`website-builder-vue`/`app-website-builder` actually import, per the project's minimal-barrel-export convention.
