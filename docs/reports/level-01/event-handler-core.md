# @webiny/event-handler-core

> Level 1 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/event-handler-core` is the cloud-agnostic, DI-native handler chain that replaced the old Fastify-based `@webiny/handler` HTTP stack: `HandlerApp` builds a per-process root container and per-request child container via decoratable `RootContainerFactory`/`ChildContainerFactory` abstractions, matches an incoming event against registered `EventType`s, and dispatches it through an `EventHandler` middleware chain (`executeChain`). Its `http` feature layers a route abstraction on top (`HttpRouter`/`HttpRouteDefinition`/`HttpRouteHandler`, matched by method+path with `:param`/`/*` support), an Express-style `HttpResponseBuilder` (status/headers/cookies/json/sse), and two production decorators (CORS `SecureHeadersDecorator`, gzip/brotli `CompressionDecorator`). A `testing` feature (imported by ~30 API packages via the `@webiny/event-handler-core/features/testing` subpath) lets tests feed `IHttpRequest` straight into the chain without an AWS/Node transport. The package is well-designed, well-documented, well-tested (13 test files covering router matching, compression, streaming, decoration, and the handler lifecycle), and other packages needing "match a route and run its handler through DI" or "an SSE/streaming HTTP response" should use `HttpRouter`/`HttpResponseBuilder`/`HttpStreamBody` rather than reimplementing them. The one real gap found is architectural, not a bug: `SecureHeadersDecorator` unconditionally overwrites any `Vary` header a route already set.

## Public API
- `HandlerApp.init`/`.handle`/`.getRootContainer` (`packages/event-handler-core/src/features/events/HandlerApp.ts:20`) — the platform-invocable handler entry point. Used to build every concrete Lambda/server handler across the API packages (e.g. `api-sync-system`'s `SyncWorkerLambdaHandler`/`SyncResolverLambdaHandler`, and transitively every package that composes via `api-event-handler-core`/`api-event-handler-aws`/`api-event-handler-server*`).
- `HttpRouter`/`HttpRouteDefinition`/`HttpRouteHandler`/`createHttpRouteDefinition` (`packages/event-handler-core/src/features/http/abstractions.ts`, `createHttpRouteDefinition.ts:20`) — the route-matching/registration abstractions. Consumed directly by ~10+ packages (`api-file-manager-standalone`'s upload routes, `api-file-manager`'s `AssetDeliveryRoute`, `background-tasks-standalone`'s `BackgroundTaskRoute`, etc.).
- `HttpResponseBuilder`/`IHttpResponseBuilder` (`packages/event-handler-core/src/features/http/HttpResponseBuilder.ts:50`) — the Express-style response builder (`.status().json()`, `.cookie()`, `.sse()`); the object every route handler is given as its second argument.
- `HttpStreamBody`/`toSseFrame` (`HttpStreamBody.ts:19`, `toSseFrame.ts:10`) — streaming/SSE primitives; `toSseFrame` is the server-side counterpart to `readServerSentEvents` in `@webiny/app`.
- `createTestHttpHandler`/`registerHttpRouteInstance`/`TestHttpEventHandler` (`features/testing/`, reached via the `@webiny/event-handler-core/features/testing` subpath, not the root export) — used by ~30 API packages' test helpers (`useGraphQLHandler.ts`, `useHandler.ts` etc.) to build an in-process test handler.
- `EventType`/`EventHandler`/`RequestContainer`/`Transport` (`features/events/`) — the lower-level dispatch abstractions; consumed directly by `api-sync-system` (`SyncWorkerEventType`, `SyncWorkerEventHandler`) for its own transport.

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|---|---|---|---|---|
| 1 | low | `packages/event-handler-core/src/features/http/decorators/SecureHeadersDecorator.ts:31-39` | `SecureHeadersDecorator.route()` unconditionally sets `vary: "origin"` on every non-OPTIONS response, discarding whatever `Vary` value the wrapped router/route already produced (`...response.headers` is spread first, then `vary` is overwritten, not merged). | A route that sets its own `Vary` header (e.g. `Vary: Accept` for content-negotiated responses) has that value silently replaced with `origin` by this decorator. `CompressionDecorator`, which wraps `SecureHeadersDecorator` and does correctly *merge* into whatever `vary` it receives (`mergeVary`), only ever sees `"origin"` by the time it runs, so the route's original `Vary` value never reaches the client — a shared/CDN cache could then serve a response negotiated for one `Accept` value to a client that sent a different one. No route in the current codebase was found setting `Vary` itself, so this is latent rather than currently triggered. | medium |

## Duplication
No jscpd clones reported for this package (`jscpd-event-handler-core/jscpd-report.json`: 0 total duplicates across all 27 source files) — no internal duplication.

Cross-package: see the `@webiny/handler` audit (`docs/reports/level-01/handler.md`) — its `ResponseHeaders` and this package's `HttpResponseBuilder` both accumulate HTTP response headers, as two abstractions from different architectural eras. That duplication is on the `@webiny/handler` side (the older one); `HttpResponseBuilder` here is the current, actively-extended implementation and is not itself duplicating anything within this package.

## Dead code
- `packages/event-handler-core/src/exports/api.ts` re-exports `HttpRouteDefinition`, `HttpRouteHandler`, and the `IHttpRequest`/`IHttpResponse`/`IHttpResponseBuilder`/`IMatchedRouteDefinition` types, but every real consumer imports the same symbols from the package root (`@webiny/event-handler-core`, which already re-exports all of `features/http/index.js`) instead — a grep for `@webiny/event-handler-core/exports/api` across the monorepo returns zero hits. The file is redundant with the root barrel and unused via its own subpath.

## Convention issues
None found that are meaningful: every DI implementation class (`RootContainerFactoryImpl`, `ChildContainerFactoryImpl`, `HttpRouterImplClass`, `CompressionDecoratorImpl`, `SecureHeadersDecoratorImpl`, `HttpRouterHandlerImpl`, `TestHttpEventTypeImplementation`) is declared as a named class and passed by reference to `createImplementation`/`createDecorator` (no inline classes, matching `no-inline-class-in-create-implementation.md`); `HttpRouterImplClass` is the documented exception to "no container as service locator" (it takes the container to build only the matched route, per `no-container-as-service-locator.md`); and the `HttpRouteDefinition`+`HttpRouteHandler` pairing in `createHttpRouteDefinition.ts`/`registerHttpRouteInstance.ts` matches the documented definition+handler exception to one-class-per-file.

## Test gaps
- `HandlerApp.handle`'s "no event type matched" error branch (`HandlerApp.ts:66-93`, the shape-summary/registered-types debug message) does not appear to be directly exercised by `__tests__/HandlerApp.test.ts` (based on the file's presence covering the happy dispatch path); a test asserting the thrown error's message shape when no `EventType` claims an event would guard this diagnostic path from regressing silently.
- `SecureHeadersDecorator`'s interaction with a route-supplied `Vary` header (see Bug #1) is untested — `__tests__/SecureHeadersDecorator.test.ts` would be the natural place to assert that an existing `Vary` value from the decoratee is preserved/merged rather than clobbered.

## Recommendations
1. Fix `SecureHeadersDecorator` to merge into any existing `Vary` header from the decoratee (the same way `CompressionDecorator.mergeVary` already does) instead of overwriting it with the literal string `"origin"`.
2. Delete `packages/event-handler-core/src/exports/api.ts` — it duplicates the root barrel's exports and has no consumers via its own subpath.
3. Add a test for `HandlerApp`'s "no event type matched" error path, since its debug-message construction (event shape + registered-type names) is exactly the kind of code that only runs when something has already gone wrong in production.
