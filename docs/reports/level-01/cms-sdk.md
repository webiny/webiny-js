# @webiny/cms-sdk

> Level 1 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/cms-sdk` is the browser-side runtime for Webiny's headless-CMS content preview/editing experience: a `contentSdk` facade (`ContentSdk`) that switches between a network-backed `LiveSdk` and an in-iframe, `postMessage`-driven `EditingSdk` depending on whether the page is running inside the visual editor, plus supporting mobx stores (`EntryStore`/`EntryStoreManager`, `RefCache`), a reference-field resolver (`refUtils`/`resolveRefs`), a JSON-patch wrapper, a small `postMessage` messenger, and a component registry used to map CMS template ids to registered React components. It correctly builds on `@webiny/sdk`'s `Result`/error types rather than reinventing them, and the core happy-path logic (fetching entries/models, applying patches, resolving refs) is reachable and used by real consumers (`cms-nextjs`, `sdk-frontend`, `app-headless-cms`, `remote-components`). Overall health is fair: there are zero automated tests for a package whose hardest logic is stateful (mobx stores, patch application, ref resolution), the same ref-resolution algorithm is implemented three times with subtly different lifetimes, and one implementation has a real correctness/perf bug where already-resolved reference fields get treated as unresolved on every subsequent edit. Other packages should reuse `collectRefs`/`setAtPath` (`refUtils.ts`) as the single ref-pointer scanner rather than re-deriving similar logic.

## Public API
- `contentSdk` (singleton `ContentSdk`, `ContentSdk.ts`) — `init`, `getModel`, `getEntry`, `listEntries`, `registerComponent`, `isEditing/isServer/isClient`. Consumed directly by `cms-nextjs` (`EntryRenderer.tsx`, `ConnectToEntryEditor.tsx`) and wired up by `sdk-frontend`'s `FrontendSdk.init()`.
- `componentRegistry` / `ComponentRegistry`, `createComponent`, `ComponentResolver` (`component/*`) — used by `cms-nextjs` (`EntryRenderer.tsx`, `DynamicZoneField.tsx`) and, via `sdk-frontend`'s `ComponentsSdk`, by the `remote-components` runtime bundle template (`browserBundler.ts:335`, `bundleComponent.ts`) to wrap dynamically-loaded third-party components.
- `EntryStore` / `entryStoreManager`, `RefCache`/`refCache`, `jsonPatch`, `resolveRefs`, `EditorBridge`, `environment` — re-exported for downstream packages; `EntryStore`+`entryStoreManager` and `refCache` are used by `cms-nextjs` (`EntryStoreProvider.tsx`, `RefField.tsx`) and `EditingSdk.ts` internally. `resolveRefs` and `EditorBridge` are exported but have no real callers anywhere in the repo (see Dead code).
- `IContentSdk`, `CmsSdkConfig`, `CmsEntry`, `CmsModelDefinition`, etc. (`types.ts`) — type-only exports consumed across `cms-nextjs` and `sdk-frontend`.

## Duplication
- Per jscpd (`jscpd-cms-sdk/jscpd-report.json`): `LiveSdk.ts:94-130` and `EntryStore.ts:101-121` are near-clones of `resolveRefs.ts:13-50`. In effect the same "collect ref pointers → dedupe → fetch → `setAtPath`" algorithm is implemented three separate times (`LiveSdk.resolveEntryRefs`, `EntryStore.resolveRefsLazy`, the standalone `resolveRefs` function) with slightly different surrounding concerns (mobx `observable`/`toJS` vs. `JSON.parse(JSON.stringify(...))`). The standalone `resolveRefs` (the one place this could have been centralized) is unused (see Dead code), so the duplication buys nothing.
- `messages.ts` defines `PREVIEW_READY`, `PREVIEW_COMPONENT_REGISTER`, `DOCUMENT_SET`, `DOCUMENT_PATCH` string constants, but every actual send/subscribe call (`EditingSdk.ts:34-46`, `EditorBridge.ts:18-31`, and the external consumer `app-headless-cms/src/presentation/contentEntries/preview/PreviewPane.tsx:70-122`) hardcodes the string literals (`"document.set"`, `"preview.ready"`, etc.) instead of importing the constants — the same magic strings are duplicated at every call site the constants were meant to centralize.

## Dead code
- `resolveRefs` (`packages/cms-sdk/src/resolveRefs.ts`) — exported from `index.ts` and re-exported by `sdk-frontend/src/index.ts`, but codegraph shows its only "callers" are those two barrel re-exports; nothing in the repo actually invokes it as a function.
- `EditorBridge` (`packages/cms-sdk/src/EditorBridge.ts`) — exported from `index.ts`, zero consumers anywhere; the one place that does the equivalent wiring (`app-headless-cms/.../PreviewPane.tsx:80-105`) constructs `Messenger`/`MessageOrigin` directly instead of using this class.
- `messages.ts` — all four exported constants are unused (see Duplication above); the file itself is never imported by anything, including `index.ts`.
- `EntryStoreManager.removeStore` / `.hasStore` (`EntryStoreManager.ts:14-20`) — never called anywhere in the repo. Because nothing ever removes a store, `entryStoreManager`'s internal `Map` (keyed by the `wb.id` query-string entry id) grows for every distinct entry id ever opened in the visual editor for the lifetime of the page/tab.
- `RefCache.has` / `.invalidate` / `.clear` (`RefCache.ts:25-27, 60-70`) — never called; only `get`, `set`, `setResolver`, and `resolve` have real callers (`cms-nextjs/src/RefField.tsx`, `EntryStore.ts`).

## Convention issues
- `ContentSdk.ts` defines two classes (`InternalContentSdk` at line 18 and `ContentSdk` at line 47) in one file. This doesn't fit the "definition + handler" exception in `ai-context/code-style/one-class-per-file.md` (neither class names/registers the other as a DI pair); it should be split, or `InternalContentSdk` should be inlined/removed since it's a thin pass-through with no behavior of its own beyond selecting `editingSdk ?? liveSdk`.
- `types.ts:74-79` — `CmsModelDefinition.fields` is typed as `Array<{ fieldId: string; type: string; list?: boolean; settings?: Record<string, unknown> }>`, an inline anonymous object type rather than a named interface (e.g. `CmsModelFieldDefinition`).

## Test gaps
There are no `__tests__` directories or `*.test.*` files anywhere in this package (confirmed via `find`), despite `vitest.config.ts` being set up for it. Nothing is under test, in particular:
- `EntryStore.setEntry` / `.applyPatch` / `.resolveRefsLazy` — the mobx observable bookkeeping, the patch-based key touching in `applyPatch` (`EntryStore.ts:53-77`), and the ref re-resolution bug (Bug #1) would all have been caught by a basic patch-then-resolve test.
- `LiveSdk.getEntry`/`getModel`/`resolveEntryRefs` — including the model-cache ordering dependency (Bug #4).
- `Messenger`/`MessageOrigin` origin filtering and the `EditingSdk` message handlers.
- `ComponentResolver.resolve` and `ComponentRegistry.register`'s dedupe-by-name behavior.

## Recommendations
1. Fix the ref re-resolution bug: make `isRefObject`/`collectRefs` distinguish an unresolved ref pointer (`{id, modelId}` only) from an already-resolved entry (which additionally carries `values`/`entryId`), or track resolved ref ids explicitly, and consolidate the three duplicated ref-resolution implementations (`LiveSdk.resolveEntryRefs`, `EntryStore.resolveRefsLazy`, `resolveRefs.ts`) into one shared function.
2. Add unit tests for `EntryStore` (set/patch/resolveRefsLazy) and `LiveSdk` (getModel/getEntry/ref resolution ordering) — this is the package's most stateful, highest-risk code and currently has zero coverage.
3. Remove or wire up the dead code identified above (`EditorBridge`, `resolveRefs` export, `messages.ts` constants, `EntryStoreManager.removeStore`/`hasStore`, `RefCache.has`/`invalidate`/`clear`), and actually call `entryStoreManager.removeStore` on cleanup to bound the store map's growth in long-lived editing sessions.
