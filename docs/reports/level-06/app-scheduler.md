# @webiny/app-scheduler

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/app-scheduler` is the admin-UI package that lets content in other admin apps (headless CMS, website builder pages/redirects) be scheduled for future publish/unpublish: it provides a DI "feature" module wiring GraphQL gateways (`schedulePublishAction`, `scheduleUnpublishAction`, `cancelScheduledAction`, `getScheduledAction`, `listScheduledActions`) around a MobX `ScheduleDialogPresenter`/`SchedulerListPresenter`, plus the "Schedule On" dialog, a `Scheduler` list view registered into `app-aco`'s browser config, and reusable exports (`useScheduleDialog`, `Scheduler`, `SchedulerDialogFormComponentDateTimeInput`, `CellScheduledOn`) consumed by `app-headless-cms-scheduler` and `app-website-builder-scheduler`. Code quality and DI/MVP conventions are consistently good and the package correctly reuses `@webiny/app-admin`'s `ListPresenter`/`DateFormatter`/`useDialogs`/`useConfirmationDialog` rather than reimplementing them. However, the package has a critical, confirmed timezone bug in its date/time picker path (inherited from a shared `@webiny/admin-ui` primitive but exercised on every "Schedule On" submission) that silently schedules publish/unpublish actions at the wrong wall-clock instant for any user not in UTC, and the package has zero automated tests.

## Public API
- `useScheduleDialog` (`presentation/scheduleDialog/useScheduleDialog.tsx`) — opens the schedule/reschedule/cancel dialog; consumed by `app-headless-cms-scheduler` (`Editor/MenuItem.tsx`, `Browser/MenuItem.tsx`) and `app-website-builder-scheduler` (`redirects/MenuItem.tsx`, `pages/MenuItem.tsx`, `editor/PageEditorScheduleMenuItem.tsx`) — 5 external call sites.
- `Scheduler` / `SchedulerModule` (`presentation/schedulerList/Scheduler.tsx`, `index.tsx`) — the standalone "Scheduled actions" list view/module, registered by the same downstream `-scheduler` packages.
- `SchedulerDialogFormComponentDateTimeInput`, `CellScheduledOn` — reusable form field / table cell, re-exported for downstream customization via `@webiny/react-composition`'s `makeDecoratable`.
- `SchedulerConfigs` — registers the scheduler's `AcoConfig`/table-column wiring into the ACO browser list.

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|---|---|---|---|---|
| 1 | critical | `packages/admin-ui/src/DatePicker/primitives/DateTimePicker.tsx:79` (reached via `packages/app-scheduler/src/presentation/scheduleDialog/components/SchedulerDialogFormComponentDateTimeInput.tsx:15`, `type={"dateTimeLocal"}`) | When the "Schedule On" `DatePicker` is used in `dateTimeLocal` mode, `emitChange` builds the value with `format(date, "yyyy-MM-dd'T'HH:mm:ss") + ".000Z"`. `format()` (date-fns) renders the Date's *local* wall-clock components, but the code then appends `.000Z`, mislabeling that local time as UTC. | A user who is not in UTC picks, e.g., 15:00 local time to schedule a publish. The emitted string is `"...T15:00:00.000Z"`. `useScheduleDialog.tsx:137` (`scheduleOn = new Date(data.scheduleOn)`) parses this as 15:00 **UTC**, and that `Date` is sent verbatim as the `scheduleFor` GraphQL variable (`SchedulePublishActionGateway.ts:62`/`ScheduleUnpublishActionGateway.ts`). The actual publish/unpublish fires at 15:00 UTC instead of the intended 15:00 local — off by the user's full UTC offset (e.g. 4-5h early for US Eastern, 9h late for JST), and the offset silently changes across a DST boundary. The same mislabeled string is also fed back through `formatDateForDisplay`'s `"dateTimeLocal"` branch (`DatePicker/utils/dateHelpers.ts:27`, `new Date(value as string)` then local `format`), so redisplaying a previously-picked time shows a *different* clock time than what was picked, which is an independent, visible symptom of the same defect. This code path is shared (also used by `app-admin`'s `DateTimeRenderer`/`DateTimeInputsRenderer` and `app-audit-logs`'s `FilterByCreatedOn`), but for `app-scheduler` it means every non-UTC user's scheduled publish/unpublish is wrong. | high |
| 2 | medium | `packages/app-scheduler/src/presentation/scheduleDialog/createMinDateValidator.ts:10-15` | The "must be at least 2 minutes in the future" validator runs `new Date(input)` on the same mislabeled `.000Z`-suffixed string described in #1, so its future/past comparison is computed against the wrong instant (shifted by the user's UTC offset), not corrected by the offset used to build `input`. | For a user west of UTC (e.g. US Pacific, UTC-8), a genuinely-future local time close to "now" can be evaluated as already in the past (or vice-versa for users east of UTC), because the mis-tagged string's apparent UTC instant differs from the true intended instant by the local offset. The validator's pass/fail does not reliably reflect whether the chosen local time is actually ≥2 minutes in the future. | medium |
| 3 | low | `packages/app-scheduler/src/presentation/scheduleDialog/useScheduleDialog.tsx:135-142` | `scheduleOn = new Date(data.scheduleOn)` is wrapped in a `try/catch` that reports "Invalid date" on exception, but the `Date` constructor never throws for a bad string — it silently produces an `Invalid Date`, which then flows through unchecked (no `isNaN(scheduleOn.getTime())` check) into the schedule GraphQL call. | An unparsable `scheduleOn` value (e.g. from a decorator that changes the bind value shape) would not be caught here and could reach the gateway as `Invalid Date`, only failing (if at all) server-side rather than with the intended client-side toast. | low |

## Duplication
`jscpd-app-scheduler/jscpd-report.json` reports zero clone pairs in the package (empty `duplicates` array). The four use-case/gateway triads (`schedulePublishAction`, `scheduleUnpublishAction`, `cancelScheduledAction`, `getScheduledAction`) share an obviously similar shape (constructor-injected `MainGraphQLClient`, a `SchedulePublishActionGateway`-style mutation, zod-validated response, thrown "Network error"/"Could not ..." errors), but each is short enough and varies enough in its GraphQL document that it stays under jscpd's clone threshold; this is expected DI boilerplate for the package's "one abstraction/implementation/feature per file" convention rather than reportable duplication.

## Dead code
None found. Every exported component/config checked (`Title`, `BottomInfoBar`/`ListStatus`, `graphqlFields` constants, `SchedulerConfigs`, `CellActions`, barrels in `index.tsx`) has at least one internal consumer, and the package's five external call sites (in `app-headless-cms-scheduler` and `app-website-builder-scheduler`) exercise `useScheduleDialog`/`Scheduler`.

## Convention issues
None significant. The package consistently follows the abstraction/implementation/feature-per-file DI pattern (e.g. `schedulePublishAction/{abstractions,SchedulePublishActionGateway,feature}.ts`), export names match their abstractions, and the top-level barrel (`index.tsx`) exports only what downstream `-scheduler` packages actually consume rather than the internal DI wiring.

## Test gaps
The package has no test files at all (`find packages/app-scheduler -iname "*.test.*"` and `__tests__` both empty) — every MobX presenter (`ScheduleDialogPresenter`, `SchedulerListPresenter`), every gateway, and `createMinDateValidator` are untested. In particular, there is no unit test that would have caught the timezone bugs above: a test constructing a `Date` in a non-UTC test timezone (e.g. via `TZ=America/New_York`) and asserting the round-tripped/submitted `scheduleFor` value equals the originally-selected wall-clock time would fail today.

## Recommendations
1. Fix the `dateTimeLocal` timezone mislabeling in `admin-ui/src/DatePicker/primitives/DateTimePicker.tsx:79` (and its display counterpart in `DatePicker/utils/dateHelpers.ts:27`) so the emitted string's UTC instant matches the picked local wall-clock time — since this is shared with `app-admin` and `app-audit-logs`, fixing it once benefits all consumers; then add a regression test in `app-scheduler` that schedules from a non-UTC `TZ` and asserts the exact instant sent to `SchedulePublishActionGateway`/`ScheduleUnpublishActionGateway`.
2. Add unit tests for `createMinDateValidator` and `ScheduleDialogPresenter.schedule/cancel/load`, covering non-UTC timezones and DST-boundary dates, since this package currently has zero test coverage protecting its core scheduling correctness.
3. Replace the dead `try/catch` around `new Date(data.scheduleOn)` in `useScheduleDialog.tsx` with an explicit `isNaN(scheduleOn.getTime())` check so genuinely invalid dates are caught client-side instead of silently reaching the gateway.
