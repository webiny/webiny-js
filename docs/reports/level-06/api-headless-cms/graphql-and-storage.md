# @webiny/api-headless-cms — GraphQL, storage and shared features

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice is the part of `@webiny/api-headless-cms` that turns content models into an executable GraphQL sub-schema (`src/graphql`) and that maps GraphQL-level `where`/`sort` filters, field storage transforms, field validators, AI tools, webhooks and the tenant installer onto the rest of the package (`src/features/{graphql,storage,shared,validation,ai,webhooks,whereMapper,sortMapper,installer}`). Read/Preview/Manage separation is correctly implemented at the resolver level — Read always goes through `ListPublishedEntriesUseCase` and Preview/Manage always go through `ListLatestEntriesUseCase`, so the Read API cannot return drafts. One security finding was found in this slice — see Bugs and private notes. `CmsWhereMapper`/`CmsSortMapper` (used by ~24/~18 files respectively, including the new `queryEntries` AI tool) are small, well-reasoned field-vs-meta routers with no injection risk of their own — they only reshape a plain object, the actual storage-operations packages build the physical query. Health is otherwise good: the field-to-GraphQL adapters (`features/graphql/fields/base/*ToGraphQL.ts`) are consistently structured (one `ReadApi`/`ManageApi` pair per field type) even though that structure produces a lot of near-identical jscpd-flagged boilerplate.

## Public API
- `checkEndpointAccess` (`src/graphql/checkEndpointAccess.ts`) — see Bugs (security finding — private notes).
- `CmsSchemaExecutor` (`src/graphql/CmsSchemaExecutor.ts:13`) — builds + executes the CMS GraphQL sub-schema for a given endpoint type and request body; ~11 files, the single production caller being `createCmsRoute.ts`'s `CmsGraphQLRoute.handle`, plus the `graphql/schema/cms/*Resolver.ts` proxy resolvers (create/update/delete/publish/unpublish/list/get entry) that re-invoke it to run the "cms." namespace queries.
- `getSchema`/`generateSchema`/`buildSchemaPlugins` (`src/graphql/getSchema.ts`, `generateSchema.ts`, `buildSchemaPlugins.ts`) — schema composition pipeline, cached per `tenant#endpoint` key (`getSchema/generateCacheId.ts`) and invalidated on model `savedOn` change (`getSchema/generateCacheKey.ts`); called only from `CmsSchemaExecutor`.
- `CmsWhereMapper` / `CmsSortMapper` (`src/features/whereMapper/WhereMapper.ts`, `src/features/sortMapper/SortMapper.ts`) — map a flat `where`/`sort` object's keys onto `values.<fieldId>` vs. top-level entry-meta keys. ~24 and ~18 consumer files across the package, including the new `queryEntries` AI tool.
- `StorageTransform` / `StorageTransformRegistry` (`src/features/storage/abstractions/*`) — per-field-type to/from-storage transform abstraction; every `features/storage/fields/*StorageTransform.ts` implementation registers against it.
- `CmsModelFieldValidatorRegistry` / `CmsModelFieldValidator` implementations (`src/features/validation/*`) — the 12 built-in validators (`required`, `minLength`/`maxLength`, `gte`/`lte`, `dateGte`/`dateLte`, `timeGte`/`timeLte`, `in`, `pattern`, `unique`), registered by `ValidationFeature`.
- `QueryEntriesTool`, `ListContentModelsTool`, `DescribeContentModelTool` (`src/features/ai/*.ts`) — read-only `AiSdkToolDefinition` implementations registered by `CmsAiToolsFeature`; each has 3 references (definition, registration in `feature.ts`, and `index.ts` re-export) — no separate external consumer, they're picked up structurally by whatever assembles the AI tool set from the `AiSdkToolDefinition` abstraction.
- `CmsWebhookFactory` (`src/features/webhooks/CmsWebhookFactory.ts`) — generates the `cms.entry.<modelId>.<action>` webhook event catalogue from all non-hidden models; consumed by `@webiny/api-core`'s `WebhookFactory` abstraction.
- `CmsInstaller` (`src/features/installer/CmsInstaller.ts`) — creates/deletes the default "Ungrouped" content model group via the tenant install/uninstall lifecycle.

## Duplication
Within this slice, jscpd reports two clusters, both structural rather than accidental:
- **Read/Preview/Manage resolver boilerplate**: `graphql/schema/resolvers/{read,preview}/resolveGet.ts` and `resolveList.ts` are ~90% identical pairs (only the use case — `ListPublishedEntriesUseCase` vs `ListLatestEntriesUseCase` — and the not-found handling differ), and `graphql/schema/resolvers/manage/{resolvePublish,resolveRepublish,resolveUnpublish,resolveListDeleted,resolveList}.ts` share the same try/catch-and-wrap-in-Response shape. This is an intentional per-endpoint-type resolver split (see Summary) rather than copy-paste drift, but the boilerplate (the try/catch + `ErrorResponse`/`ListErrorResponse` wrapping) could be a single higher-order helper.
- **Field-to-GraphQL adapters** (`features/graphql/fields/base/*ToGraphQL.ts`): `TextToGraphQL`/`LongTextToGraphQL`/`NumberToGraphQL`/`BooleanToGraphQL`/`RichTextToGraphQL`/`SearchableJsonToGraphQL`/`JsonToGraphQL`/`FileToGraphQL`/`AssetToGraphQL`/`DateTimeToGraphQL` each repeat the same `ReadApi`/`ManageApi` `createTypeField`/`createListFilters` scaffolding jscpd flags 8-19 line clones between essentially every pair of these files. `ObjectToGraphQL.ts` and `DynamicZoneToGraphQL.ts` additionally duplicate large blocks (18-20 lines) *within themselves* between their own `ReadApi`/`ManageApi` classes (e.g. `ObjectToGraphQL.ts:108-127` vs `:172-194`). None of these are bugs — each pair differs correctly in `type: "read"` vs `"manage"` — but a shared `createFieldTypeAdapter(type)` helper would remove most of it.
- `features/storage/fields/DynamicZoneStorageTransform.ts:13-51` (`processToStorage`) vs `:54-92` (`processFromStorage`) are near-identical `pReduce` loops; verified the one behavioral difference (an explicit no-op `values[field.fieldId] = value` on the falsy-value branch in `processToStorage` only) has no functional effect, so this is pure duplication, not a bug.
- One cross-folder clone touches this slice: `graphql/generateSchema.ts:29-40` duplicates `domain/contentModel/validation/modelFields.ts:228-239` (outside this slice, not further assessed).

## Dead code
- `formatErrorPayload` (`src/graphql/formatErrorPayload.ts:3`) — zero consumers anywhere in `src/` (grep: only its own definition). It formats a non-`WebinyError` into a payload that includes the raw `error.stack`; since nothing calls it today there's no active stack-trace-exposure risk, but it's worth removing or wiring in deliberately rather than leaving an unused stack-trace formatter around.

## Convention issues
No significant AGENTS.md convention violations found in this slice (DI naming, one-implementation-per-file, and barrel exports in `features/graphql`, `features/storage`, `features/whereMapper`, `features/sortMapper`, `features/validation`, `features/ai`, `features/webhooks`, `features/installer` all follow the abstraction/implementation split used elsewhere in the package). The `ReadApi`/`ManageApi` pair per field-type file (e.g. `TextToGraphQL.ts` contains both classes) is arguably two "implementations" in one file, but this mirrors the field-type's existing intentional per-endpoint split rather than an accidental combination, so it is not flagged as a violation.

## Test gaps

- No test feeds a malformed `dateGte`/`dateLte` validator configuration value through `DateGteValidator`/`DateLteValidator` to confirm the swallow-to-`false` behavior in Bug #2 (matches the level-0 finding's own test-gap note).

## Recommendations
1. Address the security finding in `src/graphql/checkEndpointAccess.ts` — see private notes.
2. Fix `dateGte`/`dateLte` validator config handling so a malformed comparison date surfaces a clear "validator misconfigured" error instead of a silent, unexplained always-fails result (fix belongs primarily in `@webiny/validation`, per the level-0 report, but `DateGteValidator`/`DateLteValidator`'s `.catch(() => false)` should stop masking it either way).
3. Remove the unused `formatErrorPayload` helper, or wire it into the actual GraphQL error-formatting path if it was meant to be used — an unused stack-trace formatter sitting in the codebase is a latent info-disclosure risk if someone wires it up later without noticing the raw `stack` field.
