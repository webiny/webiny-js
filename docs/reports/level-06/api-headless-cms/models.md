# @webiny/api-headless-cms — Models and model builder

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers the CRUD feature-slices for content models (`features/contentModel`) and model groups (`features/contentModelGroup`), plus the code-first `modelBuilder` DSL (`features/modelBuilder`) used to define models/fields programmatically instead of through the database. All three follow the repo's use-case/repository/DI-abstraction pattern consistently (Create/Update/Delete/Get/List, each with its own `abstractions.ts`/`feature.ts`), with access control, Zod input validation, and event publishing applied uniformly for DB-backed models and groups. Two real gaps stand out: (1) content models built via `modelBuilder` (`PrivateModelBuilder`/`PublicModelBuilder`) skip the field-uniqueness validation (`validateModelFields`) that DB-created models go through, so a code-defined model can silently define two fields with the same `storageId`; and (2) the "ModelCache"/"GroupCache" the CRUD repositories rely on is a plain in-memory `Map` that is recreated on every request (feature `register()` runs per-request, confirmed via `HeadlessCmsFeature.ts`/`registerApiRequestStack.ts`), so despite the tenant-scoped cache-key machinery it never actually caches anything across requests — it's effectively just per-request memoization, and the doc comments describing "multi-level caching...per tenant" are misleading. Health is otherwise good: permission checks are applied both up-front and per-entity in every use case, and DB-model validation (id/fieldId/storageId uniqueness, API-name uniqueness) is thorough.

## Public API
- `ContentModelFeature` / `ContentModelGroupFeature` (`features/contentModel/ContentModelFeature.ts:18`, `features/contentModelGroup/ContentModelGroupFeature.ts:11`) — registered from `HeadlessCmsFeature.ts:127,129`; wire up all Create/Update/Delete/Get/List use cases and repositories for models and groups.
- `CreateModelUseCase`/`UpdateModelUseCase`/`DeleteModelUseCase`/`GetModelUseCase`/`ListModelsUseCase`/`CreateModelFromUseCase` (`features/contentModel/*/`.`*UseCase.ts`) — consumed by `crud/contentModel.crud.ts` (the GraphQL-facing CRUD API, ~7 call sites via codegraph) and by `export/crud/imports/importModels.ts`.
- `ModelsFetcher` (`features/contentModel/shared/ModelsFetcher.ts:24`) — the shared "get all models" abstraction (merges plugin + DB models, applies field decompression); consumed by every model repository in this slice and by `RefModelsGenerator`.
- `PluginModelsProvider`/`ModelsProvider` (`features/contentModel/shared/PluginModelsProvider.ts`, `features/modelBuilder/models/ModelsProvider.ts`) — bridge between legacy `CmsModelPlugin` instances and the new `modelBuilder` DSL; both apply `AccessControl.canAccessModel`.
- `PrivateModelBuilder`/`PublicModelBuilder`/`BaseModelBuilder` and the field builders under `features/modelBuilder/fields/*` (e.g. `DataFieldBuilder`, `TextFieldType`, `ObjectFieldType`) — the code-first model/field DSL; used by `~/exports/api/cms/model.ts` and generated project code (`packages/webiny/src/api/cms/model.ts`), i.e. every "code-defined model" in a Webiny project.
- `ComponentMapGenerator`/`ModelToAstConverter`/`RefModelsGenerator`/`ValuesSelectionGenerator` (`features/contentModel/*Generator*`) — small AST-based helpers consumed by GraphQL schema/resolver code (`graphql/schema/cms/getModelResolver.ts`, `graphql/schema/contentModels.ts`).

## Duplication
Per the jscpd report (`jscpd-api-headless-cms/jscpd-report.json`), clones within this slice:
- `CreateModelRepository.ts` and `CreateModelFromRepository.ts` share four separate near-identical blocks (lines 5-19/8-22, 23-42/26-45, 64-75/67-78, 76-103/79-100, 161-178/162-179 respectively) — the plugin-conflict check, the modelId/API-name uniqueness loop, and the persist+clear-cache tail are duplicated almost verbatim between "create" and "create from" instead of being extracted into a shared helper.
- `CreateModelUseCase.ts:7-14` / `CreateModelFromUseCase.ts:7-14` and `CreateModelFromUseCase.ts:47-60` / `UpdateModelUseCase.ts:47-60` — the imports block and the "access-control + merge model" block are duplicated across the three model use cases.
- `DeleteModelRepository.ts:30-37` / `UpdateModelRepository.ts:66-73` — the "check if this is a plugin model, fail if so" block is duplicated (same pattern also appears a third time in `CreateModelRepository`'s plugin-conflict check, though jscpd only paired two of the three).
- Group side: `GetGroupRepository.ts:26-37,50-88` / `ListGroupsRepository.ts:25-36,43-81` (near-identical fetch/filter logic), `CreateGroupUseCase.ts:51-60` / `UpdateGroupUseCase.ts:66-75`, and `DeleteGroupUseCase.ts:32-42` / `UpdateGroupUseCase.ts:47-57` (access-control + fetch-original boilerplate repeated across the three group use cases, mirroring the model side).
- `ObjectFieldType.ts:31-43,68-83` vs `BaseModelBuilder.ts:44-57,144-159` — the "process fields via registry / build fields" logic is duplicated between the object-field builder (nested fields) and the top-level model builder, since `ObjectFieldType` re-implements its own mini version of `fieldBuildersMap`/`buildFields` rather than reusing `BaseModelBuilder`.
- `LongTextFieldType.ts:32-142` vs `TextFieldType.ts:43-154` — 111 duplicated lines; the two field types share nearly their entire validator/renderer setup, which could be pulled into a shared base.
- `PrivateModelBuilder.ts:5-13` vs `PublicModelBuilder.ts:102-110` — duplicated `modelId`/`name`/`fields-required` guard checks (both concrete builders re-check what `BaseModelBuilder` could enforce once).

None of these duplications is a correctness bug; they're maintenance risk (a fix applied to one CRUD flow but not its sibling, as already partly happened — see Bug #1 vs. the DB-model path's `validateModelFields` call).

## Dead code
No dead exports found in this slice. Everything checked via codegraph (`LayoutBuilder`, `FieldBuilderRegistry`, `RefModelsGenerator`, `ComponentMapGenerator`) has active callers, either within `api-headless-cms` (GraphQL schema/resolvers) or from `app-admin`/`ai-powerups`/generated project code.

## Convention issues
- DI naming and one-abstraction-per-file conventions are followed consistently (impl classes named `*Impl`, exported const matches the abstraction name, `export namespace X { export type Interface = ... }` pattern used throughout).
- The repeated "Note: Repository handles domain validations..." / "Note: Entry validation and cleanup is handled by decorator" comments in `UpdateModelUseCase.ts`/`DeleteModelRepository.ts` are accurate for the DB path but, combined with Bug #1, are misleading about the `modelBuilder` path, which never goes through that validation at all — worth updating once #1 is fixed.

## Test gaps
- No unit/integration test exercises duplicate-`storageId` (or duplicate-`fieldId`) definitions on a code-defined (`modelBuilder`) model — `__tests__/modelBuilder/*.test.ts` covers comparison/all-fields/faulty-model scenarios but not this specific collision (Bug #1).
- No test deletes a database group that is still referenced by a plugin/code-defined model's `.group()` — `contentModelGroup.crud.test.ts` only asserts the plain "group not found" and successful-delete paths, not the `GroupHasModelsError` path at all, let alone the plugin-model gap in Bug #4.
- No test covers passing an explicit, colliding `id` to `createContentModelGroup` (Bug #3).
- The elaborate multi-level cache described in `ModelsFetcher.ts`'s docstring has no test asserting cache reuse across two calls in the same request (which is the only scope in which it actually applies) or documenting that it does *not* persist across requests.

## Recommendations
1. Route code-defined (`modelBuilder`) models through the same field-uniqueness validation (`validateModelFields`/`validateFields`) that DB-created models get — at minimum check `storageId`/`fieldId` collisions in `BaseModelBuilder.buildFields()` before returning, since that's shared by both `PrivateModelBuilder` and `PublicModelBuilder` (Bug #1).
2. Fix `DeleteGroupRepository`'s "has models" check to query the merged model set (`ModelsFetcher`/`ListModelsRepository`, which includes plugin/code-defined models) instead of raw `ListModelsStorageOperation`, so deleting a group in use by a code-defined model is correctly blocked (Bug #4).
3. Either make `ModelCache`/`GroupCache` genuinely cross-request (register the cache instance on the root/process container instead of the per-request container) or simplify the tenant-keyed cache machinery down to plain per-request memoization and correct the "cached per tenant" docstrings in `ModelsFetcher.ts` so the design intent is accurate (Bug #2). Also fix the `GroupSlugTakenError` mismatch in `CreateGroupRepository.ts` for id collisions (Bug #3), which is a small, low-risk fix.
