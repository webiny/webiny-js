# @webiny/api-headless-cms — Content entries

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice (`packages/api-headless-cms/src/features/contentEntry`, ~8.8k lines) is the CRUD/revision/publish-state engine for content entries: create, update, move, delete (soft "move to bin" and permanent), delete-revision, restore-from-bin, publish/unpublish/republish, plus a large family of read use cases (get-by-id(s), get-latest/-published/-previous revision, list, get-unique-field-values, singleton entry). It follows a consistent use-case → data-factory → repository → storage-operation pipeline, with events published before/after every mutation. The dominant, correctly-applied pattern is a **double access-control check**: a coarse model-level `accessControl.canAccessEntry({ model, rwd/pw })` check before doing any work, followed by a second, entry-scoped check (`{ model, entry, rwd/pw }`) once the target entry has been fetched, which is what enforces "own entries only" and rwd/pw (read/write/delete, publish/unpublish) permissions per entry. Tenant scoping is set once at creation time (`entry.tenant = tenantContext.getTenant().id`) and enforced transitively by the storage layer. A security finding was identified in this slice — see private notes. Otherwise the slice is generally well structured, if extremely repetitive.

## Public API
- `CreateEntryUseCase`, `UpdateEntryUseCase`, `PublishEntryUseCase`, `UnpublishEntryUseCase`, `RepublishEntryUseCase`, `MoveEntryUseCase`, `DeleteEntryUseCase`/`MoveEntryToBinUseCase`, `DeleteEntryRevisionUseCase`, `DeleteMultipleEntriesUseCase`, `RestoreEntryFromBinUseCase` — the mutation use cases, each wired to one GraphQL resolver in `~/graphql/schema/resolvers/manage/*` (e.g. `resolveCreate.ts`, `resolveRepublish.ts`). Each is also reused by `api-aco`'s folder-level-permission decorators (`*WithFlpDecorator.ts`) and by `api-headless-cms-bulk-actions-*`.
- `GetRevisionByIdUseCase`, `GetEntriesByIdsUseCase`, `GetLatestEntriesByIdsUseCase`, `GetPublishedEntriesByIdsUseCase`, `GetLatestRevisionByEntryIdUseCase` (+ `IncludingDeleted`/`GetLatestDeletedRevisionByEntryIdUseCase` variants), `GetPreviousRevisionByEntryIdUseCase`, `GetPublishedRevisionByEntryIdUseCase`, `GetRevisionsByEntryIdUseCase`, `ListEntriesUseCase` (+ Latest/Published/Deleted variants), `GetEntryByIdUseCase`, `GetEntryUseCase`, `GetUniqueFieldValuesUseCase`, `GetSingletonEntryUseCase` — the read side; consumed both by resolvers and, per codegraph, by ~20 external call sites across `ai-powerups`, `api-aco`, and this package's own bulk-actions/AI features.
- `ContentEntryTraverser` — a visitor over an entry's field values (used for reference-field/dynamic-zone traversal); consumed by validation and reference-mapping code elsewhere in the package.
- `entryDataFactories/*` (`CreateEntryDataFactory`, `UpdateEntryDataFactory`, `CreatePublishEntryDataFactory`, `CreateRepublishEntryDataFactory`, `CreateUnpublishEntryDataFactory`, `CreateEntryRevisionFromDataFactory`) — build the in-memory `CmsEntry` object for each mutation (defaults, meta fields, status/locked/live transitions); internal to this slice, not intended for outside consumption.

## Duplication
The jscpd report for `api-headless-cms` (131 clones repo-wide) shows 36 clone pairs touching this folder. Nearly all of them are the same structural pattern repeating across sibling use cases rather than copy-pasted business logic:
- The "fetch by ID (…IncludingDeleted / …Deleted variant)" query pattern is duplicated near-verbatim across `GetLatestRevisionByEntryId/BaseUseCase.ts` ↔ `GetPreviousRevisionByEntryId/BaseUseCase.ts` (20 lines), and across their `variations/*.ts` files.
- `GetEntriesByIdsUseCase`, `GetLatestEntriesByIdsUseCase`, and `GetPublishedEntriesByIdsUseCase` (and their repositories) are structurally identical (~22-line clones each), differing only in which storage operation/decorator they inject.
- The "transform → storage-op → transform-back" repository body is duplicated across `PublishEntryRepository.ts`, `RepublishEntryRepository.ts`, `RestoreEntryFromBinRepository.ts`, and `CreateEntryRevisionFromRepository.ts` (10–16-line clones each).
- `CreateEntryDataFactory.ts` (lines 142-175, 189-209) duplicates the same publishing-meta-field-population and access-control-on-status blocks found in `CreateEntryRevisionFromDataFactory.ts` (34 and 21 lines respectively) — this one is closer to genuine logic duplication (the same "if status is published/unpublished, re-check `pw` permission and stamp publishing meta fields" logic reimplemented rather than shared).
- `GetLatestEntriesByIdsNotDeletedDecorator.ts` / `GetPublishedEntriesByIdsNotDeletedDecorator.ts` / `GetEntriesByIdsNotDeletedDecorator.ts` are the same 17-line "filter out `wbyDeleted` entries" decorator repeated three times.
- `utils/incrementEntryIdVersion.ts` (outside this folder) duplicates 20 lines of the version-increment logic that also appears in `CreateEntryRevisionFromDataFactory.ts:26-45`.

None of these look accidental/harmful today, but the volume (a use case + repository + abstractions + events + feature file per operation, most only 10-20 lines different from a sibling) means a bug fix or behavior change (e.g. the return-value bug above) has to be applied N times by hand, which is presumably how bug #2 came to affect three of four "publish-family" use cases but not the fourth.

## Convention issues
- Inconsistent error typing in catch blocks: `CreateEntryUseCase`/`UpdateEntryUseCase`/`DeleteEntryUseCase` cast caught errors as `error as UseCaseAbstraction.Error`, while `PublishEntryUseCase`, `RepublishEntryUseCase`, `UnpublishEntryUseCase`, `MoveEntryUseCase`, `RestoreEntryFromBinUseCase`, `DeleteMultipleEntriesUseCase` all use `Result.fail(error as any)` — a weaker, silently-typed escape hatch that defeats the `Result<T, E>` type's purpose. Minor, but it is spread across most of the publish/delete family.
- `DeleteEntry/decorators/ForceDeleteDecorator.ts:37-41` builds a storage-operation param via `{ entry: { id, entryId } } as any` rather than an explicit partial type, another instance of the "no inline types"/no-`any` convention being bypassed to route around a storage-operation interface mismatch ("Not the nicest way to do it" per the file's own comment).
- Two different "not authorized" error classes are used within the same feature area: `~/domain/contentEntry/errors.js`'s `EntryNotAuthorizedError` (used by every use case in this slice) vs. `~/utils/errors.js`'s `NotAuthorizedError` (used only inside `CreateEntryDataFactory.ts` for the publish/unpublish-on-create permission checks). Not a functional bug, but it means the same failure mode surfaces as two different error codes depending on whether it's caught at the use-case layer or inside the data factory.

## Test gaps
- No unit tests exist under `features/contentEntry/**` for the individual use-case classes; coverage is exclusively at the GraphQL/integration level (`__tests__/contentAPI/contentEntry.*.test.ts`, `contentEntryHooks.test.ts`, `lifecycleHooks/onBeforeEntryPublish.test.ts`). This means bug #2 above (publish/republish/unpublish returning the pre-transform entry) would only be caught by an integration test that specifically asserts the *returned* entry's field values for a field type whose storage transform is non-identity — no such assertion was found.
- Security finding SEC-32 has no regression test (see private notes).

## Recommendations
1. Address the security finding — see private notes.
2. Make `PublishEntryUseCase`/`RepublishEntryUseCase`/`UnpublishEntryUseCase` return the repository's transformed result (`publishedEntry`/`storageEntry`) instead of the pre-storage `entry`, matching what `EntryAfterPublishEvent`/`EntryAfterRepublishEvent` already receive, and add an integration test asserting the returned value for a field type with a non-identity storage transform.
3. Consider collapsing the repeated "fetch by ID variant" and "transform → storage-op → transform-back" repository bodies (GetLatest/GetPrevious/DeletedVariant, Publish/Republish/Restore repositories) into a shared helper to reduce the number of places a fix like #2 needs to be applied by hand.
