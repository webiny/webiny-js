# @webiny/api-headless-cms — CRUD, utils, export and domain

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary

This slice covers `src/{crud,types,utils,export,domain,plugins,fieldConverters,exports,legacy}` plus the top-level `HeadlessCmsFeature.ts`/`createCmsRoute.ts`/`HeadlessCmsEndpointConfig.ts` (~11.3k lines). `crud/` is **not** dead legacy code superseded by `features/` — it is the anti-corruption layer that `HeadlessCmsFeature.ts` wires into the `HeadlessCms` DI facade: every `crud/*.crud.ts` function resolves the corresponding `features/**/UseCase` from the container, calls `.execute()`, and converts the `Result`'s failure branch into a thrown `WebinyError` for the (still `throw`-based) public facade contract. `domain/` holds the actual business-rule validation (zod schemas, error types, id/name rules) that the `features/` use cases call directly. `fieldConverters/` implements the field-value storage/GraphQL round-trip (object, dynamicZone, default), and `export/` implements CMS structure export/import (groups+models, with a separate, older zod validation path for imports). Overall health is decent — the facade/use-case split is consistent and the export/import flow has good test coverage — but the audit found one concrete correctness bug (content-model field-ID reserved-keyword validation is enforced on the import path only, not on normal create/update), one asymmetric-failure bug in the dynamic-zone field converter (deleting/renaming a template silently drops data on write but hard-crashes reads of existing entries), and three dead zod-schema exports left over from an incomplete migration of model validation from `crud/` to `domain/`. Other packages should reuse `utils/converters/ConverterCollection` and `utils/entryStorage.ts`'s storage-transform dispatch pattern (exact-type → base-type → default fallback) rather than re-deriving field-type dispatch, and should be aware that `utils/caching/Cache.ts`'s `get()`/`getOrSet()` treat any falsy cached value as a cache miss.

## Public API

- `HeadlessCmsFeature` (`src/HeadlessCmsFeature.ts:91`) — the package's DI feature; registers all sub-features and builds the `HeadlessCms` facade from `crud/`. Consumed by the package's own `index.ts`/handler wiring; ~13 other packages import from `@webiny/api-headless-cms` root (grep), e.g. `api-headless-cms-ddb`, `api-headless-cms-aco`, `api-website-builder`.
- `createModelsCrud`/`createContentEntryCrud`/`createModelGroupsCrud` (`src/crud/*.crud.ts`) and `createExportCrud`/`createImportCrud` (`src/export/index.ts`, `src/export/crud/importing.ts`) — build the `HeadlessCms` facade's `models`/`entries`/`groups`/`export`/`importing` namespaces; each delegates to one `features/**/*UseCase` per method.
- `CmsModelFieldConverterPlugin` and its 3 built-ins (`src/fieldConverters/*`, registered via `registerFieldConverters` in `src/fieldConverters/abstractions.ts`) — the field value ⇄ storage conversion contract used by `utils/converters/ConverterCollection`. No external package subclasses it (grep: zero hits outside this package) — it is an internal extension point today, not a cross-package API.
- `entryToStorageTransform`/`entryFromStorageTransform` (`src/utils/entryStorage.ts:105,116`) — whole-entry storage transform, exposed to the rest of the package via the `EntryToStorageTransform`/`EntryFromStorageTransform` DI abstractions in `src/legacy/abstractions.ts`. No consumers outside this package (grep).
- `PluginsContainer`/`CmsGroupPlugin`/`CmsModelPlugin`/`CmsGraphQLSchemaPlugin`/`StorageOperationsCmsModelPlugin` (`src/plugins/index.ts`) — legacy plugin-container extension points still bridged from `extraPlugins` in `HeadlessCmsFeature.register`; used by test infra and a handful of downstream storage packages.
- `types/index.ts` re-exports the package's whole public type surface (`CmsModel`, `CmsEntry`, `CmsModelField`, `CmsContext`, etc.) — consumed extremely broadly (every other `api-headless-cms-*` package and `app-headless-cms*`).

The most important finding in this slice's own duplication is the top pair by clone count: `src/crud/contentModel/validation.ts` ↔ `src/domain/contentModel/schemas.ts` (8 of the 19 crud↔domain clones, both files reproducing the same `fieldSchema`/`icon`/`shortString` zod building blocks). These aren't just copy-paste noise — they have **drifted apart** (see Bug #1 above, plus: `crud/contentModel/validation.ts:43` defines `longString = str.max(255)`, i.e. identical to `shortString`, while `domain/contentModel/schemas.ts:7` defines `longString = str` with no cap — so the "help" field text is capped to 255 chars on the import path but uncapped on the normal create/update path). This is a duplication-caused correctness drift, not just style debt.

Other duplication of note:
- `src/utils/converters/valueKeyFromStorageConverter.ts` and `valueKeyToStorageConverter.ts` are near-identical factories (same params, same `ConverterCollection` construction) differing only in calling `convertFromStorage`/`convertToStorage`; could be merged into one factory parameterized by direction.
- `src/crud/AccessControl/AccessControl.ts` (648 lines) implements the same `canAccessX`/`getXAccessControlList`/`hasFullAccessToX` shape three times (for groups, models, and entries — the "entries" copy wasn't fully read in this audit but is evident from the file's section comments and jscpd's third self-clone pair). This is a legitimate candidate for a generic `AccessControlList` builder parameterized by permission-name plugin, rather than a functional bug.

## Dead code

- `src/crud/contentModel/validation.ts` exports `createModelCreateValidation`, `createModelUpdateValidation`, and `createModelCreateFromValidation` — none are imported anywhere in `src/` outside this file (grep confirms only `dist/*.d.ts` declaration files reference them). Only the file's fourth export, `createModelImportValidation`, is actually used (by `src/export/crud/imports/validateModels.ts:1,204`). These three appear to be leftovers from before model create/update validation was migrated to `src/domain/contentModel/schemas.ts` (which now has its own, diverged copies of the same three functions, actively used by `CreateModelUseCase`/`UpdateModelUseCase`/`CreateModelFromUseCase`).
- `src/legacy/abstractions.ts` is small and every export (`PluginsContainer`, `SearchableFieldsProvider`, `EntryToStorageTransform`, `EntryFromStorageTransform`) is registered and resolved within `HeadlessCmsFeature.ts` itself — not dead, but worth flagging that its docstrings all say "legacy abstraction for the utility function," suggesting eventual removal once remaining consumers migrate to plain DI use-case calls.

## Convention issues

- `src/crud/contentModel/validation.ts` violates the "one abstraction per file" spirit less by mixing concerns and more by being a near-complete, silently-diverging duplicate of `src/domain/contentModel/schemas.ts` — per AGENTS.md's DI/duplication conventions this pair should be consolidated (or the dead exports removed) rather than left to drift further.
- No inline-type or barrel-export violations found in this slice: `src/utils/index.ts` only re-exports `caching`, `contentModelToJsonSchema`, and `modelFieldTraverser` (not every util file), consistent with the "minimal barrel exports" convention — most utils are imported via deep paths (e.g. `~/utils/entryStorage.js`), which is intentional here since they're package-internal.

## Test gaps

- No test exercises reserved-system-field-ID rejection on the create/update path (only relevant to Bug #1); `__tests__/validations/models/test.ts` and `__tests__/validations/fields/*` don't reference `fieldSystemFields` or "reserved keyword" at all.
- `__tests__/converters/dynamicZone/*` (21 field-type-specific test files) all appear to test the happy path of converting known templates; none tests a `_templateId` that no longer exists in the field's `settings.templates` on either `convertToStorage` or `convertFromStorage` (Bug #2).
- `export/crud/imports/*` has decent coverage via `__tests__/contentAPI/export.structure.test.ts` and `import.structure.test.ts`, but there's no test importing a model whose field IDs collide with system fields, which would additionally have caught the crud/domain validation drift in Bug #1 from the opposite direction (i.e., confirming import correctly rejects what create/update wrongly accepts).

## Recommendations

1. Fix Bug #1: either port the `fieldSystemFields` reserved-keyword check from `src/crud/contentModel/validation.ts` into `src/domain/contentModel/schemas.ts`'s `fieldSchema` (so it applies uniformly to create/update/import), or extract the check into a single shared zod refinement used by both — then delete the crud copy's redundant `createModelCreateValidation`/`createModelUpdateValidation`/`createModelCreateFromValidation` exports (dead code) so there is exactly one model-field-schema source of truth.
2. Fix Bug #2: make `CmsModelDynamicZoneFieldConverterPlugin.processFromStorage`'s unknown-template case fail the same way as `processToStorage` (return `undefined`/log a warning instead of throwing), or, if hard-failing on read is intentional, make writing an unknown `_templateId` also fail loudly instead of silently dropping the entry's data — the current asymmetry (silent data loss on write, hard crash on read) is the worse combination of the two.
3. Consolidate the `valueKeyFromStorageConverter.ts`/`valueKeyToStorageConverter.ts` pair into a single direction-parameterized factory, and document (or fix) the falsy-value cache-miss behavior in `utils/caching/Cache.ts` before any future caller relies on it for non-Promise values.
