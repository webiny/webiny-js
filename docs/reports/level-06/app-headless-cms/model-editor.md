# @webiny/app-headless-cms — Model editor UI

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers the "model structure" side of the headless-CMS admin app — everything under `packages/app-headless-cms/src/presentation/*` except `contentEntries` and `fieldRenderers`: content-model list/CRUD (`contentModels`, `newContentModel`, `cloneContentModel`), model groups (`modelGroup`, `contentGroupsMenu`, `menus`), JSON import (`importContentModels`), the per-field settings dialog (`fieldEditor`, `fieldValidators`), and the field-type registry used by the model editor's field-type picker and per-type settings forms (`fieldTypes`). It is a newer MobX-Presenter/DI rewrite that sits alongside (and in places still delegates into) the legacy `~/admin/components/FieldEditor` tree — e.g. `fieldTypes/types/object/ObjectFields.tsx` renders the legacy `FieldEditor` for nested object fields, so the actual field-tree drag/drop reordering and add/remove logic is out of this slice's scope. Health is mixed: the code is consistently structured (DI abstraction/implementation/feature per concern, MobX presenters, zod-validated form fields), but there are real gaps — most notably that nothing in this slice (or, as far as could be confirmed, in the legacy tree either) prevents two sibling fields from sharing the same `fieldId`, the Clone-model dialog silently drops the source model's required API names, and a validator's settings form makes a field required that legitimately should be optional. Test coverage for ~9.6k lines of code in this slice is essentially a single unit-test file.

## Public API
This slice is internal to `@webiny/app-headless-cms` (wired up via DI `feature.ts` registrations and consumed by the package's own `admin/` views and by `packages/webiny`'s admin re-exports), not a separately imported set of symbols. Notable internal contracts other parts of the model editor build on:
- `CmsFieldType` / `CmsFieldEditorGroup` / `CmsFieldValidator` / `CmsValidatorPatternFactory` (`fieldTypes/abstractions.ts`, `fieldEditor/abstractions.ts`, `fieldValidators/abstractions.ts`) — multi-registration DI abstractions that let field types, field-editor tabs, and validators be extended by other features; consumed by `FieldEditorPresenter` and the field-type registry.
- `ImportContentModelsPresenter`, `CloneContentModelPresenter`, `NewContentModelPresenter`, `ModelGroupPresenter` — MobX presenters behind the Import/Clone/New-model/Model-group dialogs, each wired through a `feature.ts` DI registration and a `useXxxPresenter` hook consumed by the corresponding dialog component in the same folder.

## Duplication
- `packages/app-headless-cms/src/presentation/newContentModel/NewContentModelPresenter.ts:9` redefines `const CMS_MODEL_SINGLETON_TAG = "singleEntry"` locally instead of importing the identical exported constant `CMS_MODEL_SINGLETON_TAG` from `@webiny/app-headless-cms-common` (`packages/app-headless-cms-common/src/constants.ts:1`), which the dependency's own audit flags as the canonical source other packages should reuse.
- jscpd confirms several near-identical field-validator files: `GteValidator.ts`/`MinLengthValidator.ts` share the same form-building shape as `LteValidator.ts`/`MaxLengthValidator.ts` (12-14 line clones each), and `DateGteValidator.ts`/`DateLteValidator.ts` are near-total duplicates of each other (lines 12-48 overlap almost completely) — same settings-form/label/description scaffold repeated per comparison direction rather than parameterized by operator.
- `fieldTypes/types/layout/SeparatorLayoutFieldType.tsx` and `AlertLayoutFieldType.tsx` both duplicate large chunks (40-63 lines each) of `TabsLayoutEditor.tsx`'s settings-form construction — three layout field types re-implement the same tab/tabs-settings scaffolding instead of sharing one helper.
- `fieldEditor/renderers/CmsConditionRulesRenderer.tsx` and `CmsAccessControlRulesRenderer.tsx` duplicate 9-12 line blocks from the legacy `admin/components/FieldEditor/EditFieldDialog/RulesEditor/RulesEditor.tsx` and `PermissionsEditor/PermissionsEditor.tsx` respectively — the new-presenter renderers were written by copying the legacy dialog's logic rather than extracting a shared helper, so the two field-permission/condition UIs can now drift independently.
- `contentModels/components/ContentModelsDataList.tsx` and `modelGroup/components/ContentModelGroupsDataList.tsx` share two near-identical 11-line blocks (list row rendering scaffolding) per jscpd.
- `cloneContentModel/CloneContentModelPresenter.ts` and `newContentModel/NewContentModelPresenter.ts` share a ~16-line constructor/`makeAutoObservable` block and an ~11-line `save()` try/finally block (jscpd) — expected given they are sibling dialogs, but a shared base presenter would remove the copy.
- Each of the six per-type field renderer registration files under `fieldTypes/renderers/*` (`TextInputsRenderer.ts`, `NumberInputsRenderer.ts`, `LongTextsRenderer.ts`, `LexicalTextInputsRenderer.ts`, `DateTimeInputsRenderer.ts`, `DynamicZoneRenderer.ts`/`ObjectAccordionRenderer.ts`) duplicate the same 7-12 line registration boilerplate; low-impact since it's a declarative registration pattern, but a shared factory (there is already a nearby `patternAbstractions`-style factory pattern used for validators) would remove it.

## Dead code
No exports in this slice were found unreachable; the two smallest folders were spot-checked with codegraph (`contentModelEditor/preview`'s `ContentModelFormPreviewPresenter`/`useContentModelFormPreview` are consumed by `admin/components/ContentModelEditor/PreviewTab.tsx`) and confirmed live. A full unused-export sweep of all ~13 folders was not performed given the tool budget; nothing else stood out as an obviously orphaned file during reading.

## Convention issues
- Barrel/DI naming is followed correctly throughout (impl class named `XxxImpl`, abstraction re-exported as `Xxx`, `feature.ts` per folder) — no violations of the project's DI-naming or one-per-file rules were found in the files read.
- `ModelGroupPresenter.ts` and both `NewContentModelPresenter.ts`/`CloneContentModelPresenter.ts` cast form data through `as unknown as string` repeatedly (e.g. `CloneContentModelPresenter.ts:96-101`, `ModelGroupPresenter.ts:163-177`) rather than typing the form's generic `submit<T>()` call with a concrete interface — this isn't the "inline object type" pattern the project conventions call out, but it does mean the exact same untyped-cast pattern is repeated 3 times across sibling files instead of being expressed once via a typed form-data interface.

## Test gaps
Of the ~9.6k lines in this slice, the only test file found is `fieldEditor/groups/GeneralGroup.test.ts`, and it covers only the `disabled` flag's `mapToForm`/`mapFromForm` round-trip — none of the following have any test coverage: `fieldId` validation/uniqueness behavior in `GeneralGroup`/`FieldEditorPresenter`, the JSON-import parsing/validation flow (`ImportContentModelsPresenter.parseFileContent`, `handleModelsValidation`, `getDataToImport`'s dependency-selection recursion `createSelected`), the clone/new-model presenters' save flows, `ModelGroupPresenter`'s slug-from-name auto-fill, or any of the eight `fieldValidators` (`GteValidator`, `PatternValidator`, etc.) settings-form/`mapToFieldBuilder` logic. The recursive `createSelected` in `ImportContentModelsPresenter.ts:27-48` (selecting a model also pulls in its related models transitively) is exactly the kind of logic that benefits from a unit test and currently has none.

## Recommendations
1. Add a `fieldId` uniqueness check in `FieldEditorPresenterImpl`/`GeneralGroup` (using the `model` already available in `context`) that rejects saving a field whose `fieldId` collides with another field in the same model — this is a real, currently-unguarded data-integrity gap in the shared field-editing path.
2. Fix `CloneContentModelPresenter.init()` to pre-fill `singularApiName`/`pluralApiName` (e.g. from the source model, with a suffix) so the required clone form isn't left half-empty on every clone; and relax `PatternValidator`'s `flags` field from `.required()` to optional to match the built-in presets that use empty flags.
3. Add unit tests for `ImportContentModelsPresenter`'s `parseFileContent`/`createSelected`/`getDataToImport` (pure, easily testable logic with no MobX/DOM dependencies) and fix the `data.groups.length` optional-chaining gap while doing so.
