# @webiny/app-headless-cms — Content entries UI and field renderers

> Level 6 · commit 19c9ca1b91 · audited 2026-09-26

## Summary

This slice (`packages/app-headless-cms/src/presentation/{contentEntries,fieldRenderers}`, ~7.4k lines) is the admin UI for browsing, editing, publishing and deleting content entries, plus the "ref" (reference) field renderer family (simple/detailed, single/multiple, autocomplete, inline create/edit drawers) and the icon-picker renderer. Everything follows the codebase's MobX Presenter + DI feature/abstraction/implementation pattern consistently, delegates list pagination/filtering to `@webiny/app-admin`'s `ListPresenter`/`FolderAwareDataSource` rather than reimplementing it, and correctly isolates inline "edit referenced entry" forms in their own child DI container (`EditEntryDrawer.tsx`) so they don't share state with the entry being edited on the main screen. The main issues found are two real async-race gaps — neither `ContentEntryFormPresenter.loadRevision` nor the ref-field autocomplete's `search()` guard against out-of-order responses, so a slow earlier request can silently overwrite a newer one — and a near-total lack of unit tests for this slice's most important logic (the save/publish/revision-switch presenter has zero tests). The app-admin form-model's `requiredWhen()` validation-cache bug (flagged at level 3) is not reachable here: this slice's forms only use static `.required()` calls, no conditional-required fields.

## Public API
This slice is internal to `app-headless-cms` (consumed by other modules inside the same package and by `packages/webiny`'s re-exports), not a separately published sub-package, so "consumers" below are other in-package modules.
- `ContentEntryFormPresenter` (`contentEntries/form/abstractions.js` / `ContentEntryFormPresenter.ts`) — drives the single-entry edit form (load/save/publish/unpublish/delete/create-revision); consumed by `ContentEntryFormView.tsx`, `RevisionSelector.tsx`, and reused (via a scoped child container) by `fieldRenderers/ref/editEntry/EditEntryPresenter.ts` for the inline "edit referenced entry" drawer.
- `ContentEntriesPresenter` (`contentEntries/list/abstractions.js`) — list/folder/search state for the entries table; consumed by `ContentEntriesView.tsx`, `RouteParamsSync.tsx`, `ContentEntriesListLayout.tsx`.
- `CmsFieldRendererFeature` (`fieldRenderers/feature.ts`) — registers all field renderers (text/number/date/ref/object/dynamicZone/etc.) into the DI container; consumed at admin bootstrap (`HeadlessCMS.tsx`, outside this slice).
- `RefSingleAutocompletePresenter` / `RefMultiAutocompletePresenter`, `RefSimplePresenter`, `RefDetailedPresenter`, `RefDialogPresenter`, `EditEntryPresenter`, `NewEntryPresenter` — the ref-field renderer family; each is wired into its own DI feature and consumed only by its matching `CmsRef*Renderer.tsx` component.

## Bugs

| # | Severity | Location (file:line) | Problem | Failure scenario | Confidence |
|---|----------|----------------------|---------|-------------------|------------|
| 1 | medium | `contentEntries/form/ContentEntryFormPresenter.ts:285-303` (`loadRevision`) | `loadRevision(id)` has no guard against out-of-order responses: it awaits `getEntryUseCase.execute`, then unconditionally does `runInAction(() => { this.entry = entry; this.buildAndPopulateForm(entry); })`, regardless of whether a *later* `loadRevision` call has since started. | User switches revisions/entries quickly (e.g. via browser back/forward on the `?id=` route param, which is not blocked by the `loading`-disabled dropdown button), or a slow network response for revision A arrives after a faster response for revision B. The presenter ends up showing/holding revision A's data and `entry.id`, while the UI (URL, revision selector highlight) reflects B — and a subsequent "Save" would write to revision A's id, not the one the user believes they are editing. | medium |
| 2 | medium | `fieldRenderers/ref/autocomplete/BaseAutocompletePresenter.ts:28-50` (`search`) | `search(query)` sets `this.searchQuery = query` synchronously but assigns the resolved `this.searchOptions` from whichever `searchUseCase.execute` call happens to resolve last, with no per-call token/id check. `RefSingleAutocompletePresenter`/`RefMultiAutocompletePresenter` both delegate straight to this method, and the renderers (`CmsRefInputRenderer.tsx:61`, `CmsRefInputsRenderer.tsx:62`) call `presenter.search(query)` on every keystroke with no debounce at this layer. | User types "a", "ab", "abc" quickly for a reference-field autocomplete; if the "a" request's response arrives after "abc"'s, `searchOptions` is overwritten with results for the stale "a" query while `searchQuery` (and the visible input) still shows "abc" — the dropdown displays options that don't match what's typed. | high |

## Duplication
- `fieldRenderers/ref/CmsRefSimpleSingleRenderer.tsx` and `CmsRefSimpleMultipleRenderer.tsx` are ~90% identical (jscpd: 48-line clone at lines 34-81/33-78, plus three smaller clones), differing mainly in single-vs-array value handling. Same pattern between `CmsRefDetailedSingleRenderer.tsx` and `CmsRefDetailedMultipleRenderer.tsx` (jscpd: a 40-line clone at lines 138-175/192-231, plus three smaller ones), and between `autocomplete/single/RefSingleAutocompletePresenter.ts` and `autocomplete/multi/RefMultiAutocompletePresenter.ts` (two clones, 8 and 10 lines — mostly the constructor/DI wiring, since both already delegate their real logic to the shared `BaseAutocompletePresenter`). These are consistent enough that a single parameterized ("multiple: boolean") renderer/presenter would remove most of the duplication without changing behavior.
- `contentEntries/preview/ComponentDiscoveryIframe.tsx` and `contentEntries/preview/PreviewPane.tsx` share three small clones (8/17/13 lines) around iframe/messenger setup — likely worth extracting a shared hook if this preview mechanism grows further, but low priority as-is.
- Within `ContentEntryFormPresenter.ts` itself, `publishRevision`/`unpublishRevision`'s try/`runInAction`/finally loading-flag boilerplate repeats near-verbatim (jscpd: 20-line self-clone at lines 208-227/235-254); minor and not worth a large refactor on its own.
- `bulkActions/{BulkPublishPresenter,BulkUnpublishPresenter,BulkDeletePresenter}.ts` share a ~12-line structural clone (constructor + `vm` getter + `execute` delegating to `BulkActionRunner`), but each is a thin, correct wrapper around the shared `BulkActionRunner`/use-case pair — this is acceptable boilerplate, not logic duplication.

## Dead code
None found. Checked several files that looked like plausible dead code and confirmed each has live consumers: `GenericModelLoader.tsx`/`ModelLoader.tsx` (both used, by `ContentEntriesView.tsx` and the ref-field drawers), `CmsAdvancedSearch.tsx` (used by `ContentEntriesListLayout.tsx`), and `CmsIconPickerRenderer.tsx` (registered separately in `HeadlessCMS.tsx`, outside this slice's own `fieldRenderers/feature.ts`, rather than being unused).

## Convention issues
- `contentEntries/form/getFieldBuilders.test.ts` is misplaced/mislabeled: despite its name and location (inside `contentEntries/form/`), it does not test anything in this folder — it tests `CmsFormModelBuilder` from `~/features/formModel` via `CmsFormModelFeature`. This makes it easy to miss when auditing or extending either module, since neither a `getFieldBuilders.ts` file nor that function exists in this directory.
- No other meaningful DI-naming, one-per-file, or barrel-export violations were found; the presenter/abstraction/feature split is applied consistently throughout the slice.

## Test gaps
Only two test files exist for the whole ~7.4k-line slice: `contentEntries/list/ContentEntriesPresenter.test.ts` (covers list/folder/search state reasonably well) and the misplaced `getFieldBuilders.test.ts` (covers `CmsFormModelBuilder`, not this slice). Entirely untested: `ContentEntryFormPresenter` (save, publish, unpublish, delete, create-new-revision, and the `loadRevision` race described above), `SingleEntryPresenter`, `RevisionsListPresenter`, all three bulk-action presenters, and the entire `fieldRenderers/ref` family (autocomplete, detailed/simple renderers, dialog, new/edit-entry drawers). This is the highest-risk gap in the slice, since `ContentEntryFormPresenter` is the one component whose bugs cause silent data loss or wrong-revision saves.

## Recommendations
1. Add a request-generation guard (e.g. an incrementing counter checked after each await) in `ContentEntryFormPresenter.loadRevision` and in `BaseAutocompletePresenter.search`/`resolveEntries`, so a stale response can never overwrite state for a request that has since been superseded.
2. Add unit tests for `ContentEntryFormPresenter` (save/publish/unpublish/delete/create-revision flows and the locked-vs-unlocked revision branching in `saveEntry`), since it currently has zero coverage despite being the slice's most consequential presenter.
3. Parameterize the single/multiple variants of the ref renderers (`CmsRefSimpleSingle/MultipleRenderer`, `CmsRefDetailedSingle/MultipleRenderer`) and autocomplete presenters into one implementation each, to remove the ~150 duplicated lines jscpd flags and reduce the risk of the two copies drifting apart.
