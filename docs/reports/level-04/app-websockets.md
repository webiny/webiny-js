# @webiny/app-websockets

> Level 4 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/app-websockets` is the admin-side real-time layer: a `WebsocketsContextProvider` that opens a single, window-cached `WebSocket` connection (via `WebsocketsConnection`/`WebsocketsManager`/`WebsocketsSubscriptionManager`), bridges every incoming message into `@webiny/app`'s `EventPublisher` as a `WebsocketEvent`, and exposes a `useWebsockets()` hook (`send`, `createAction`, `onMessage`, `onError`, `onClose`) for feature code to talk back over the socket via a request/response `WebsocketsAction`. The package correctly reuses `@webiny/app`'s `EventPublisher`/`BaseEvent`, `@webiny/feature`'s `createAbstraction`, and `@webiny/utils`'s `generateId` rather than reimplementing them. Overall health is mixed: the request/response action layer (`WebsocketsActions.run`) is solid, but the connection-lifecycle code has two confirmed, concrete bugs — a subscription-manager bucket mix-up that silently disables `onOpen` callbacks, and an unmount handler whose cleanup does not do what its own comment says it does, which (combined with the window-level connection cache) can leave a live connection wired to a stale subscription manager after a remount.

## Public API
- `Websockets` (`index.tsx`) — the `Provider` HOC that mounts `WebsocketsContextProvider`; registered once at the admin composition root (per `app-admin` wiring, not re-audited here).
- `useWebsockets()` (`hooks/useWebsockets.tsx`) — returns `{ send, createAction, onMessage, onError, onClose }`; the main surface feature code uses to react to server push events and send actions. `createAction(name)` returns an `IWebsocketsAction` (`trigger()`), used for typed request/response calls.
- `WebsocketEventHandler` abstraction (`events/abstractions.ts`, re-exported via `exports/admin/websockets.ts`) — DI abstraction for handlers that receive every incoming `WebsocketEvent`; this is the intended integration point for other packages instead of subscribing to the socket directly.
- `createWebsocketsManager`/`createWebsocketsConnection`/`createWebsocketsSubscriptionManager`/`createWebsocketsActions`/`createWebsocketsAction` (`domain/*`) — internal factory functions; per codegraph, all consumers are within this package (`WebsocketsContextProvider.tsx`), i.e. not used as a public extension point by other workspace packages today.

## Bugs
| # | Severity | Location (file:line) | Problem | Failure scenario | Confidence |
|---|---|---|---|---|---|
| 1 | high | packages/app-websockets/src/domain/WebsocketsSubscriptionManager.ts:29 | `onOpen()` stores its subscription in `this.subscriptions.close[value.id]` instead of `this.subscriptions.open[value.id]` (copy-paste from `onClose` below it). | Any code that calls `manager.onOpen(cb)` never has `cb` invoked by `triggerOnOpen` (which iterates `subscriptions.open`, which stays empty for these registrations); instead `cb` gets invoked on close events, receiving a `CloseEvent` instead of the expected open `Event`. Currently only internal code could call this (not exposed via `IWebsocketsContext`), but the manager's public `onOpen` method is part of `IWebsocketsManager` and any future/extension code that subscribes to socket-open will silently never fire, or fire with the wrong event shape. | high |
| 2 | high | packages/app-websockets/src/WebsocketsContextProvider.tsx:88-127 | The `useEffect`'s own comment says it "close[s] the websocket connection ... in case component is unmounted," but the cleanup function (124-126) only does `abortController.abort()` for the two `window` listeners — it never calls `socketsRef.current?.close(...)`. Meanwhile the actual `WebSocket` object is cached on `window.WebinyWebsocketsConnectionCache` (WebsocketsConnection.ts:34-40) and `getConnection()` only calls `addEventListener` the first time a socket is created (WebsocketsConnection.ts:121-171); if the socket is already OPEN/CONNECTING it is returned as-is with no new listeners attached. | If `WebsocketsContextProvider` ever unmounts and remounts while the cached socket is still open (e.g. the provider sits under a route/layout that gets torn down and recreated, or React StrictMode-style remount), the new mount creates a brand-new `subscriptionManager`/`WebsocketsConnection`, but `getConnection()` sees the cached socket is already OPEN and skips registering listeners for it — so the socket's real `open`/`close`/`error`/`message` DOM listeners stay bound to the *old*, discarded `subscriptionManager`. The new provider's `onMessage`/`onClose`/`onError` subscriptions (and the `WebsocketEvent` → `EventPublisher` bridge) are wired to the new manager and never receive anything: real-time updates silently stop working until a full page reload, with no error surfaced. | medium |
| 3 | medium | packages/app-websockets/src/WebsocketsContextProvider.tsx:66-82 | The auto-reconnect-on-close counter `currentIteration` is incremented on every `GOING_AWAY` close but is never reset after a successful reconnect, and the closure lives for the entire mounted lifetime of the provider (captured once in a no-deps `useMemo`). | After 6 `GOING_AWAY` closes in one session (e.g. laptop sleep/wake, tab backgrounding, or transient reverse-proxy idle timeouts recurring over a workday), `currentIteration > 5` becomes permanently true and the `onClose` auto-reconnect handler stops trying to reconnect for the rest of the session — the app relies only on the `window focus` handler from then on, and if the tab stays focused after that point (or is a background/no-focus context) the socket simply stays disconnected. | medium |

## Duplication
jscpd reports one clone: `domain/abstractions/IWebsocketsManager.ts:48-63` and `domain/abstractions/IWebsocketsSubscriptionManager.ts:35-51` (16 lines) — the `onOpen`/`onClose`/`onMessage`/`onError` method-signature declarations are repeated verbatim across the two interfaces (one re-declares the other's shape instead of `IWebsocketsManager` delegating to `IWebsocketsSubscriptionManager`'s type). Low-impact (type-only, no runtime cost) but a plausible source of the bug above: the interfaces read identically, and the implementation was written by pattern-matching one against the other.

## Dead code
- `WebsocketsConnection.setTenant()` (packages/app-websockets/src/domain/WebsocketsConnection.ts:68-70) — codegraph shows its only reference is the class's own declaration; no caller anywhere in the monorepo. Tenant switching in `WebsocketsContextProvider.tsx` (129-160) instead closes the old connection and constructs an entirely new `WebsocketsConnection` with the new tenant, so this method is unreachable dead code.

## Convention issues
None found beyond what's already noted — the domain/abstraction split (interfaces under `domain/abstractions/`, implementations under `domain/`) follows the repo's DI/abstraction-implementation convention, and factory functions (`createWebsocketsX`) are named per convention.

## Test gaps
There is no `__tests__` directory in this package at all. Given the focus area, the untested behavior that matters most: the auto-reconnect logic (both the `onClose`/`GOING_AWAY` path and the `window focus` path, including the iteration-cap bug above), the unmount/remount listener-wiring behavior, `WebsocketsSubscriptionManager`'s bucket routing (which would have caught bug #1 immediately), and `WebsocketsActions.run`'s timeout/response-matching logic.

## Recommendations
1. Fix `WebsocketsSubscriptionManager.onOpen` to store into `this.subscriptions.open`, not `.close` (WebsocketsSubscriptionManager.ts:29), and add a unit test asserting each of `onOpen`/`onClose`/`onMessage`/`onError` only fires for its own event type.
2. Either make the unmount cleanup actually close the cached connection (matching its own comment) or update the comment to describe the real (cache-reuse) behavior, and add a regression test/manual check for the remount-with-stale-listeners scenario, since it currently fails silently in production.
3. Reset `currentIteration` to 0 on a successful reconnect (e.g. inside the `open` handler) so long-running sessions don't permanently lose auto-reconnect after 5 disconnects; consider also reconnecting on close codes other than `GOING_AWAY` (e.g. abnormal closure) rather than relying solely on the `window focus` fallback.
