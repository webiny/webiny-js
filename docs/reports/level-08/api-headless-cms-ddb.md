# @webiny/api-headless-cms-ddb

> Level 8 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-headless-cms-ddb` is the DynamoDB storage-operations implementation of the entry/model/group storage-operation interfaces defined by `@webiny/api-headless-cms`, built on `@webiny/db-dynamodb`'s toolbox wrapper. Entries use a single-table design with one partition key per entry id (`createPartitionKey`) and three sort-key "views" (`REV#<version>` per-revision history, `L` latest, `P` published), plus a GSI (`GSI1`) used for tenant+model+type listing. A per-request-cached `DataLoader`-based batching layer (`CmsDdbDataLoaders`) correctly re-maps DynamoDB batch-get results back onto the originally requested ids by filtering on id/entryId after `execute()`, so it does not have the positional-misalignment risk that the level-4/5 audits found in the tenant loader (SEC-14). Health is otherwise solid — the publish/unpublish/move-to-bin/restore-from-bin operations correctly maintain the L/P/REV# record invariants — but one concrete cross-backend drift was confirmed: this package's "list an entry's revisions" query returns oldest-first, while `@webiny/api-headless-cms-sql`'s equivalent returns newest-first. The package's own test suite also spends real coverage on a dependency's dead code rather than on this package's own storage-operation classes.

## Public API
- `HeadlessCmsDdbFeature` (`src/index.ts:27`) — the top-level DI feature; creates the shared DynamoDB table/entity instances and registers `DdbEntryStorageOpsFeature`/`DdbModelStorageOpsFeature`/`DdbGroupStorageOpsFeature`. It is the DynamoDB storage-operations backend named as this package's role by the level-7 `@webiny/api-headless-cms-storage` report, and is wired into project API handlers that choose the DynamoDB deployment target.
- `DdbCreateEntry`/`DdbUpdateEntry`/`DdbPublishEntry`/`DdbUnpublishEntry`/`DdbMoveEntry`/`DdbMoveToBin`/`DdbRestoreFromBin`/`DdbDeleteEntry`/`DdbDeleteEntryRevision`/`DdbDeleteMultipleEntries`, and the read side `DdbGetEntry`/`DdbListEntries`/`DdbGetEntriesByIds`/`DdbGetLatestEntriesByIds`/`DdbGetPublishedEntriesByIds`/`DdbGetRevisions`/`DdbGetRevisionById`/`DdbGetLatestRevisionByEntryId`/`DdbGetPublishedRevisionByEntryId`/`DdbGetPreviousRevision`/`DdbGetUniqueFieldValues` (`src/operations/entry/*.ts`) — each implements one of `@webiny/api-headless-cms`'s `*StorageOperation` interfaces (`features/shared/storageOperations/entry/*`) and is consumed exclusively through that interface, one per corresponding use case in `api-headless-cms`'s `features/contentEntry/*` slice (per the level-6 content-entry report).
- `DdbCreateModel`/`DdbUpdateModel`/`DdbDeleteModel`/`DdbGetModel`/`DdbListModels` and `DdbCreateGroup`/`DdbUpdateGroup`/`DdbDeleteGroup`/`DdbGetGroup`/`DdbListGroups` — the model/group storage-operation equivalents, same consumption pattern.
- `CmsDdbDataLoaders`/`DataLoadersHandler` (`src/operations/entry/dataLoaders.ts:26`) — a request-scoped, tenant+modelId-keyed `DataLoader` cache wrapping four DynamoDB batch-read shapes (`getRevisionById`, `getLatestRevisionByEntryId`, `getPublishedRevisionByEntryId`, `getAllEntryRevisions`); internal to this package, used by nearly every entry read/write operation above (e.g. `DdbPublishEntry`/`DdbUnpublishEntry` use it to fetch the current latest/published records before writing).

## Bugs
| # | Severity | Location (file:line) | Problem | Failure scenario | Confidence |
|---|---|---|---|---|---|
| 1 | medium | `packages/api-headless-cms-ddb/src/operations/entry/dataLoader/getAllEntryRevisions.ts:14-23` (reached via `DdbGetRevisions.ts:23`) | `entity.queryAllClean({ partitionKey, options: { beginsWith: "REV#" } })` passes no reverse/`ScanIndexForward` option. Neither this call site nor `@webiny/db-dynamodb`'s `queryAllClean` helper (`packages/db-dynamodb/src/utils/query.ts`) ever sets a reverse flag, so DynamoDB returns items in ascending sort-key order — oldest revision (`REV#0001`) first, newest last. `@webiny/api-headless-cms-sql`'s equivalent, `SqlGetRevisions.ts:41`, explicitly does `.orderBy("version", "desc")`, returning newest-first. | A GraphQL client (e.g. the admin app's "revision history" panel, which calls `GetRevisionsByEntryIdUseCase`) gets its list of an entry's revisions in the opposite chronological order depending on whether the deployed API uses the DynamoDB or the SQL storage backend. Any consumer that assumes "the first item in the list is the current/latest revision" (a natural assumption for a "list" endpoint) shows the oldest revision first on DynamoDB deployments. | high |

## Duplication
jscpd reports 9.35% duplicated lines across 18 clones, all structural DI/constructor boilerplate rather than divergent logic: the three per-entry-type batch dataloader factories (`getPublishedRevisionByEntryId.ts:12-30`, `getLatestRevisionByEntryId.ts:12-32/33-55`, `getRevisionById.ts:10-23`) repeat the same `DataLoader`+`reader.get()` shape; `DdbCreateModel.ts:11-22`/`DdbUpdateModel.ts:10-22` and `DdbCreateGroup.ts:10-21`/`DdbUpdateGroup.ts:10-21` repeat constructor/DI wiring; `DdbPublishEntry.ts`, `DdbUnpublishEntry.ts` and `DdbUpdateEntry.ts` each redeclare a near-identical private `getLatestRevisionByEntryId`/`getPublishedRevisionByEntryId` helper instead of sharing one; and `DdbMoveToBin.ts:27-57,79-95`/`DdbRestoreFromBin.ts:29-58,80-99` are near-mirror images of each other (same write-batch shape, opposite meta-field set). None of this duplication is behavior-affecting.

The actual filter/sort logic used by `DdbListEntries.ts` (via `filter`/`sort`/`createFields` from `@webiny/api-headless-cms-storage`) is correctly shared with the SQL package rather than reimplemented here, consistent with that dependency's stated role.

## Dead code
No dead exports found via a targeted check of this package's own code. However, two of this package's own test files exercise dead code that lives in a dependency: `__tests__/plugins/dynamoDb/path/plainObject.test.ts` and `__tests__/plugins/dynamoDb/transformValue/datetime.test.ts` import `createPlainObjectPathPlugin`/`createDatetimeTransformValuePlugin` from `@webiny/api-headless-cms-storage`, which the level-7 report for that package identifies as an entire `Plugin`-class-based filter implementation that is "not wired into `FilterRegistriesFeature` at all and is effectively dead."

## Convention issues
No inline-type or barrel-export violations found; `src/index.ts` exports only the single `HeadlessCmsDdbFeature`, consistent with the repo's minimal-barrel-export convention. The repeated per-file helper declarations noted under Duplication are a side effect of the "one abstraction per file" convention rather than a violation of it.

## Test gaps
- Nothing in `packages/api-headless-cms-ddb/__tests__` directly exercises any of the `Ddb*` storage-operation classes (create/update/publish/unpublish/move-to-bin/restore-from-bin/delete/list/get-by-ids). The only entry-related tests (`operations/entry/filtering/*.test.ts`) exercise `@webiny/api-headless-cms-storage`'s shared `filter`/`createFields`/`createExpressions`/`createFilters`/`getValue` functions — dependency code, not this package's own. The two `plugins/dynamoDb/*.test.ts` files (see Dead code) exercise that same dependency's dead `Plugin` implementation.
- As a result, DynamoDB-specific key-building (`keys.ts`), the publish/unpublish/move-to-bin state machine, and the batch dataloaders have no automated coverage in this package.
- The revision-ordering drift (Bug #1) is exactly the kind of behavior a test asserting revision order would have caught.

## Recommendations
1. Resolve the revision-ordering drift against `@webiny/api-headless-cms-sql`: either request `ScanIndexForward: false` (descending) in `getAllEntryRevisions.ts` to match SQL's `orderBy("version", "desc")`, or change SQL to ascending — pick one canonical order and add a test (ideally shared/cross-backend) asserting it.
2. Add unit/integration tests for this package's own storage-operation classes — at minimum the publish/unpublish/move-to-bin/restore-from-bin lifecycle and the batch dataloaders — instead of relying on tests that only cover a dependency package's (partially dead) code.
3. Move or delete the two `__tests__/plugins/dynamoDb/*.test.ts` files; they test `@webiny/api-headless-cms-storage` code that isn't wired into this package (or, per that package's own report, into any package) and provide no coverage of anything this package ships.
