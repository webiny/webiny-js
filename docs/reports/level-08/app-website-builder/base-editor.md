# @webiny/app-website-builder — BaseEditor

> Level 8 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`BaseEditor` (`packages/app-website-builder/src/BaseEditor`, ~9.5k lines, of which `defaultConfig` alone is ~7.4k) is the visual page-editor shell: it defines the editor's command vocabulary (`commands.ts`), the command handlers that mutate the document via `editorSdk` (`commandHandlers/*`), the extension-point layout (`config/{Sidebar,Toolbar,Content,TopBar}`, built on `@webiny/react-composition`'s `makeDecoratable`), and the default, out-of-the-box UI for that layout (`defaultConfig/*`: element/style settings panels, insert-element toolbar, drag-and-drop preview, breakpoint switching). It consumes `editorSdk`'s `Editor`/`StateWithHistory` (undo/redo, selection, document state) and `@webiny/website-builder-sdk`'s bindings processors rather than reimplementing them. Health is mixed: the architecture and extension pattern are sound and consistently applied, but the box-model style editors (padding/margin/border) are copy-pasted four times instead of parameterized, there is a real cross-instance state-leak bug in the drag-preview cursor tracker, and the slice has almost no automated test or Storybook coverage for ~9.5k lines of UI logic.

## Public API
- `DefaultEditorConfig` (`defaultConfig/DefaultEditorConfig.js`) — the default editor UI composition; the main entry point consumed by `app-website-builder`'s page-editing routes/pages (used alongside a `SandboxConfig` variant for the sandbox/preview app).
- `Commands` (`commands.ts`) — the command-bus vocabulary (`CreateElement`, `MoveElement`, `CloneElement`, `DeleteElement`, `SelectElement`, `DeselectElement`, `HighlightElement`, `RefreshPreview`, `PreviewPatchElement`, `SendPreviewMessage`, `SetTheme`); consumed by `commandHandlers/*` in this slice and by `editorSdk/utils/*` (e.g. `$deleteElement` calling `Commands.DeselectElement`).
- `config/*` re-exports (`Sidebar`, `Toolbar`, `Content`, `TopBar`, `Element`, `Elements`) — the extension-point API other parts of `app-website-builder` (and downstream component-manifest authors) register UI into via `react-properties`-style composition.
- `ElementInputRendererProps` (type, `config/ElementInput.js`) — the contract for custom input renderers registered by component manifests.

## Duplication
Package-wide (`app-website-builder`), jscpd reports 164 clone pairs / ~2.3–2.5k duplicated lines. Grouped by area (counts = clone pairs involving that folder):

- **`features/pages` (self, 51 pairs)** and **`presentation/pages`/`presentation/redirects` (18+10+4 pairs)** — the largest clusters, entirely outside this slice (belongs to the package's `features`/`presentation` layers, audited separately).
- **`BaseEditor/assets/icons` (34 pairs, +7 with `inputRenderers/assets`)** — almost all of these are raw `.svg` files (e.g. `settings.svg` clone-matches a dozen other icons). This is jscpd matching generic SVG boilerplate (`<svg>`/`<path>` header lines), not real logic duplication; low-value noise, not worth deduplicating.
- **`BaseEditor/defaultConfig/Sidebar/StyleSettings` (14 pairs, real duplication)**:
  - `Groups/MarginPadding/Padding.tsx` and `Groups/MarginPadding/Margin.tsx` are near-line-for-line copies of the same "4-sided linked value editor" pattern (linked-editing toggle, per-side `onChange`/`onPreviewChange`/`onReset`, identical JSX layout), differing only by the `margin`/`padding` property names and margin's extra `isKeyword` branch. `Groups/Border/BorderWidth.tsx` and `Groups/Border/BorderRadius.tsx` repeat the same pattern again for border sides/corners. Four ~90-130 line components reimplement one generic concept instead of a single parameterized `SidedValueEditor(propertyPrefix, sides, options)`.
  - `Groups/Border/LinkedEditing.tsx` and `Groups/MarginPadding/LinkedEditing.tsx` are byte-identical (lines 1-26 in each) — a single small component copy-pasted into two folders instead of shared.
  - `UnitValuePicker.tsx` and `ValueSelector.tsx` share two near-identical blocks (parsing/formatting the numeric+unit value), suggesting one should wrap the other rather than both reimplementing the same logic.
  - `useInputValue.ts` has an internal duplicate: the value-building block in `onChange` (lines ~140-161) and in `onPreviewChange` (lines ~224-245) construct `InputValueObject`/`devFriendlyInputs` identically; the two functions could share a helper.
- **`BaseEditor/config` (3 pairs)** — `Sidebar/Sidebar.tsx`/`Toolbar/Toolbar.tsx` and `Sidebar/Tab.tsx`/`Toolbar/Tab.tsx` repeat the same "scoped `Element`/`Elements` factory + layout wrapper" boilerplate for each of the four extension zones (Sidebar/Toolbar/Content/TopBar); `createGetId` is already factored out, but the surrounding `makeDecoratable(...)` wiring per zone is not.
- **`BaseEditor/metadata` (1 pair)** — `InputMetadata.ts`/`StylesMetadata.ts` share the same `IMetadata` decorator boilerplate (constructor + `applyToDocument`/`get`/`set`/`unset` delegating with a prefix); acceptable given it's a deliberate decorator pattern, but a shared base class would remove ~10 duplicated lines.
- **`BaseEditor/hooks` (1 pair)** — `useActiveElement.ts`/`useHighlightedElement.ts` share the same `autorun`-over-`editorState`/`documentState` subscription pattern (see Bug #2); a shared `useEditorElementRef(selector)` hook would fix both the duplication and the effect-dependency issue at once.
- Long tail (1-2 pairs each) in `domain/Page`/`domain/Redirect`, `features/settings`/`features/ecommerce`, `ecommerce/createResourceListPicker.tsx`/`createResourcePicker.tsx`, `inputRenderers/{TextInput,TextareaInput,FragmentSelectorInput,SelectInput,ColorPickerInput}.tsx`, `Extension.tsx` (two separate self-clones) — all outside this slice.

Cross-package (not in jscpd, found via codegraph): `BaseEditor/components/Draggable.tsx` reimplements the same "wrap `react-dnd`'s `useDrag` behind a render-prop" pattern that `app-headless-cms/src/admin/components/Draggable.tsx` already implements independently; likewise `BaseEditor/components/DragPreview/*` duplicates the drag-layer-cursor-following concept in `app-headless-cms/src/admin/components/DragPreview.tsx`. Different concrete code (so jscpd doesn't flag it), same abstraction reinvented per package.

## Dead code
- `defaultConfig/Sidebar/ElementSettings/ExpressionRenderer.tsx` and `WithBindingToggle.tsx` are exported and fully implemented (a `Select`-of-known-state-paths renderer for expression bindings, and a static/expression toggle button), but their only call sites are commented-out code in `InputField.tsx:47-66` and `ElementInputs.tsx:59-91` (`// We'll implement expression bindings at a later stage.`). `useInputValue.ts`'s `setBindingType` return value (lines 255-278) is likewise never destructured by the only live consumer (`InputField.tsx`). Net effect: the free-text/expression-binding editing UI for component inputs is currently built but entirely disabled — component authors cannot enter binding expressions through this editor path today (only the pre-defined `$repeat.expression` binding, set via `useRepeatValue`, can carry an expression string, and that too has no UI wired to it — see next point). This is relevant context for `website-builder-sdk`'s privately-tracked SEC-2 (expression evaluation): the attack surface it describes is not reachable through `BaseEditor`'s current UI.
- `defaultConfig/Sidebar/ElementSettings/useRepeatValue.ts` exports `useRepeatValue`, which reads/writes `document.bindings[elementId].$repeat.expression`. Codegraph and a repo-wide grep both show zero callers anywhere in `app-website-builder` — codegraph: no consumers. Dead code; the repeat-binding editing UI does not exist yet.

## Convention issues
- Inconsistent relative vs. path-alias imports for the same module across sibling files: `commandHandlers/DeselectElement.tsx`, `SelectElement.tsx`, `HighlightElement.tsx` import `Commands` via `../commands.js`, while `CloneElement.tsx`, `MoveElement.tsx`, `CreateElement.tsx`, `DeleteElement.tsx` import the same thing via `~/BaseEditor/index.js` (the package barrel) — pulling in the whole `BaseEditor` barrel (including `DefaultEditorConfig`) just to get `Commands` is unnecessary and inconsistent with the sibling files in the same folder.
- `BaseEditor/components/Draggable.tsx` and `BaseEditor/metadata/*` are reasonably scoped (one abstraction per file), but the `Padding.tsx`/`Margin.tsx`/`BorderWidth.tsx`/`BorderRadius.tsx` quartet violates the spirit of "no reimplementation" more than file-per-abstraction — each file is its own abstraction, but the abstraction itself (a 4-sided linked style editor) is defined four times.

## Test gaps
The entire ~9.5k-line slice has exactly one test file (`defaultConfig/Sidebar/ElementSettings/StatePathsExtractor.test.ts`) and zero `.stories.tsx` files. In particular there is no test coverage for: the command handlers that apply create/move/clone/delete/select operations (`commandHandlers/*`), the drag-and-drop preview and its module-level singleton state (`components/DragPreview/*` — exactly where Bug #1 lives), the breakpoint-switching logic (`hooks/useBreakpoint.tsx`), the active/highlighted-element `autorun` hooks (Bug #2), and every style-settings component (`Padding`/`Margin`/`BorderWidth`/`BorderRadius`/`Layout`/etc.). Given how much of this code is copy-pasted (Duplication above), the lack of tests also means the four box-model editors can silently drift out of sync with each other over time.

## Recommendations
1. Fix the module-level singleton state in `components/DragPreview/useDragPosition.ts` (Bug #1) — move `dragPreviewRef`/`subscribedToOffsetChange` into a per-`DragPreview`-instance closure (e.g. a small class instantiated in the component, or React state/ref) instead of module-scope `let`s, so multiple concurrently-mounted editors don't fight over the drag cursor.
2. Extract the shared "4-sided linked value editor" logic out of `Padding.tsx`/`Margin.tsx`/`BorderWidth.tsx`/`BorderRadius.tsx` into one parameterized component/hook (property names + unit options + optional keyword handling as parameters); this removes the largest real (non-SVG) duplication cluster in the slice and would have caught drift between the four copies for free.
3. Add unit/interaction tests for `commandHandlers/*` and the breakpoint/active-element hooks before extending them further — right now a regression in undo-adjacent flows (select/deselect/move/delete) or breakpoint switching would ship with zero automated signal.
