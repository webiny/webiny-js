# @webiny/app-website-builder — Features (DI layer)

> Level 8 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers `packages/app-website-builder/src/features` (~7k lines): the gateway/repository/use-case DI layer for pages, redirects, settings, ecommerce settings, experiments, permissions and the preview-URL extension point. The package follows a consistent Gateway → Repository → UseCase(+WithLoading decorator) pattern per operation, backed by a small set of shared, MobX-observable `IListCache`/`ILoadingRepository`/`IMetaRepository` abstractions (from `@webiny/app-utils` and local `PageListCache`/`FullPageCache`/`PageRevisionsCache`). Overall health is decent and the pattern is applied uniformly, but cache-invalidation-after-mutation is inconsistently implemented: two page-revision mutations never touch the revisions cache they logically affect, one redirect mutation drops an item from cache instead of updating it in place, and the settings-update path writes to a plain (non-DI, non-rollback) global cache *before* the network call succeeds, so a failed save leaves the UI showing unsaved data as if it were persisted.

## Public API
This slice exports per-operation `*Feature` objects (e.g. `CreatePageFeature`, `PublishPageFeature`, `ListRedirectsFeature`, `GetSettingsFeature`, `ExperimentsFeature`) consumed directly by `~/presentation/pages/**` components and hooks (e.g. `useCreatePage.ts` imports `CreatePageFeature` from `~/features/pages/createPage/index.js`), and by `Extension.tsx`, which registers all of them into the app's DI container. `features/index.ts` only re-exports the settings/ecommerce/previewUrl features and the `PreviewUrlModifier` extension abstraction (multi-binding, resolved with `resolveAll`, intentionally left unimplemented in this package); page and redirect features are imported directly from their own sub-folders rather than through a barrel, which matches the "minimal barrel exports" convention. Shared cache/loading/meta abstractions (`PageListCache`, `FullPageCache`, `PageRevisionsCache`, `WbPageLoadingRepository`, `WbPageMetaRepository`) are registered once in `pages/shared/feature.ts` and injected into ~20 per-operation repositories.

## Duplication
jscpd clones touching `features/`:
- `features/settings/getSettings/GetSettingsRepository.ts:10-20` duplicates `features/ecommerce/settings/getSettings/GetEcommerceSettingsRepository.ts:9-18` almost verbatim (same cache-then-gateway-then-cache-set logic); the accompanying `updateSettings` repositories are likewise near-identical. Both pairs, plus `~/shared/settingsCache.ts`, could be collapsed into one generic settings-cache repository parameterized by cache key.
- The `*UseCaseWithLoading.ts` decorator (10-19 lines) is duplicated close to identically across ~9 operations (`createPage`, `duplicatePage`, `publishPage`, `unpublishPage`, `movePage`, `deletePage`, `updatePage`, `createPageRevisionFrom`, `getPage`) — same constructor/`runCallBack` shape each time, differing only in the injected loading-action constant.
- `UpdatePageRepository.ts:26-44`, `PublishPageRepository.ts:12-34` and `UnpublishPageRepository.ts:12-44` share the same 19-23 line "update both `PageListCache` and `FullPageCache` by id" block verbatim; a shared helper (e.g. `updatePageInCaches(listCache, detailsCache, id, page)`) would remove three copies of this logic (and would have made bug #3 above harder to miss).
- `createPage/PageGqlDto.ts:2-21` duplicates `updatePage/PageGqlDto.ts:2-21`, and `domain/Page/PageDto.ts:9-20` overlaps `updatePage/PageGqlDto.ts:7-18`.
- Large overlapping blocks across the page-mutation `*.test.ts` files (mock container/gateway setup), e.g. `PublishPage.test.ts`, `UnpublishPage.test.ts`, `UpdatePageRevisionDescription.test.ts`, `MovePage.test.ts`, `DuplicatePage.test.ts`, `GetPage.test.ts` — expected for parallel test suites, but the volume (dozens of matched fragments) suggests a shared test-harness builder would cut a lot of boilerplate.

## Dead code
None confirmed in this slice. Checked `WbPageRevisionsLoadingRepository` (registered in `pages/shared/feature.ts`) — it is consumed by `getPageRevisions/GetPageRevisionsUseCaseWithLoading.ts`, so not dead. `PreviewUrlModifier`/`WbPermissionsFeature` are intentional multi-binding extension points with no in-package implementation, not dead exports.

## Convention issues
- `features/experiments/` skips the Repository/UseCase layering used everywhere else in this slice: `ExperimentsFeature.resolve()` returns the raw `gateway` directly (`features/experiments/feature.ts`), and callers presumably talk to the gateway's 13 methods straight, unlike the page/redirect/settings features which always interpose a repository (for caching) and a use case. This is likely deliberate (experiments has no local cache), but it is an inconsistency worth flagging since every other operation in the slice follows Gateway→Repository→UseCase.
- `~/shared/settingsCache.ts` is a plain, un-abstracted, un-DI-registered global `Map`, whereas every other cache in this slice (`PageListCache`, `FullPageCache`, `PageRevisionsCache`, `RedirectsListCache`) is a `createAbstraction`-wrapped, mobx-observable `IListCache` registered through `container.registerInstance`. The settings caches don't participate in the DI container at all and aren't observable, which is inconsistent with the rest of the codebase's DI-naming/one-abstraction-per-file conventions and is part of why bug #1 above went unnoticed (no abstraction boundary to add a rollback/try-catch to).

## Test gaps
- `deletePageRevision`, `getPageRevisions`, `listPages`, `translatePage`, and the whole `trashBin`, `redirects/*`, `settings/*`, `ecommerce/*`, `permissions`, `previewUrl`, and `experiments` sub-trees have no `*.test.ts` files at all in this slice — none of the four bugs above (settings-cache rollback, revision-cache invalidation on delete/description-update, redirect-move cache handling) are covered by any test.
- `UpdatePageRevisionDescription.test.ts` (the one test file that exists for that feature) asserts against `listCache`/`detailsCache` only and never references `PageRevisionsCache`, so it would not have caught bug #3 even if the cache had been wired up incorrectly.

## Recommendations
1. Fix bug #1 first: wrap `UpdateSettingsRepository`/`UpdateEcommerceSettingsRepository` in try/catch (or reorder to cache only after a successful `gateway.execute`), since a failed settings save currently looks like a successful one for the rest of the session.
2. Add the missing `PageRevisionsCache` invalidation to `DeletePageRevisionRepository` (`removeItems`) and `UpdatePageRevisionDescriptionRepository` (`updateItems`), and add regression tests asserting on `PageRevisionsCache` state, not just `PageListCache`/`FullPageCache`.
3. Make `MoveRedirectRepository` consistent with `MovePageRepository` — either have the gateway return the updated redirect so the repository can `updateItems` its `folderId` in place, or explicitly document/confirm that removal-from-cache is the intended behavior for redirects' folder-scoped list views.
