# @webiny/api-website-builder — Pages, GraphQL and domain

> Level 8 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers `packages/api-website-builder/src/{features/pages,graphql,domain,exports,rest,utils}` (~6.9k lines): the full page CRUD/publish/trash/translate lifecycle (`features/pages/*`, 15 use-case/repository pairs), the GraphQL schema/resolvers for pages, redirects, experiments and the Next.js/Nuxt admin-config queries (`graphql/*`), the domain layer (page/redirect/experiment/variant CMS models, entry-to-domain mappers, the shared `WB_PERMISSIONS_SCHEMA`), the public barrel exports (`exports/api/website-builder/*`), the public redirects REST route (`rest/*`), and two small shared helpers (`utils/resolve.ts`, `utils/ensureAuthentication.ts`). The pages feature follows the repo's use-case/repository/DI pattern very consistently: every mutating and single-item read use case does a coarse `canX("page")` check followed by a per-record `canAccess`/`canEdit`/`canDelete`/`canPublish("page", page)` check, correctly gating "own"-scope access via `@webiny/api-core`'s already-audited `Permissions`/`OwnableItem` machinery. Public/unpublished-page-by-path is not a leak: `GetPageByPathRepository` always queries with `published: true`, so drafts can never surface through path lookup regardless of the permission outcome. The one concrete correctness bug found is that page path uniqueness is never enforced anywhere in the create/update/publish flow, and `GetPageByPath`'s underlying `GetEntryUseCase` silently returns whichever matching entry a `limit: 1`, unsorted list query happens to return first — so two published pages can permanently share a path with no error and no deterministic "winner." `utils/resolve.ts` also reimplements `@webiny/api-graphql`'s own `resolve` helper verbatim instead of importing it. Bindings/elements/expressions are stored and passed through this slice as opaque JSON with no server-side evaluation or interpolation, so the SEC-2 "expressions in bindings" concern does not apply to any code in this slice.

## Public API
- `CreatePageUseCase`/`UpdatePageUseCase`/`DeletePageUseCase`/`TrashPageUseCase`/`RestorePageUseCase`/`PublishPageUseCase`/`UnpublishPageUseCase`/`MovePageUseCase`/`DuplicatePageUseCase`/`TranslatePageUseCase`/`CreatePageRevisionFromUseCase`/`GetPageByIdUseCase`/`GetPageByPathUseCase`/`GetDeletedPageByIdUseCase`/`ListPagesUseCase`/`ListDeletedPagesUseCase`/`GetPageRevisionsUseCase`/`UpdatePageRevisionDescriptionUseCase` — re-exported from `exports/api/website-builder/page.ts`; wired into `graphql/pages/pages.gql.ts` (the admin GraphQL API) and, per `@webiny/languages`' own summary, `TranslatePageUseCase` is also consumed directly by `@webiny/languages`'s page-translation flow and by `@webiny/ai-powerups`'s translate-page decorator.
- `PageModelProvider` (`domain/page/abstractions.ts`) — supplies the tenant's `wbPage`/`wbyWbPage` CMS model; consumed by every page repository in this slice plus `graphql/pages/pages.gql.ts`'s `getPageModel` resolver.
- `WB_PERMISSIONS_SCHEMA`/`WbPermissions` (`domain/permissionsSchema.ts`, `features/permissions/abstractions.ts` — outside this slice but defined from this slice's schema) — the `wb.page`/`wb.redirect`/`wb.settings`/`wb.integrations` schema-typed permission entity every use case in the package injects.
- `resolve` (`utils/resolve.ts`) — thin try/catch → `Response`/`ErrorResponse` wrapper used by every resolver in `graphql/pages/pages.gql.ts`; duplicates `@webiny/api-graphql`'s own exported `resolve` (see Duplication).
- `WebsiteBuilderRedirectsRouteDefinition` (`rest/WebsiteBuilderRedirectsRoute.ts`) — the `GET /wb/redirects` HTTP route, registered on `@webiny/event-handler-core`'s router; consumed by frontend rendering integrations (e.g. `website-builder-nextjs`) for redirect resolution.

## Dead code
None found with high confidence. `PageBeforeCreateEventHandler`/`PageBeforeDuplicateEventHandler`-style "before" hook abstractions have no in-repo implementation for some operations, but this is the same "extension point with no default listener" pattern used consistently across the package (e.g. `PageAfterDuplicateEventHandler` *is* implemented, by `packages/api-audit-logs/src/subscriptions/websiteBuilder/pages/PageAfterDuplicateHandler.ts`), so flagging every unused "before" hook individually would be speculative rather than confirmed dead code.

## Test gaps
- No test exercises the duplicate-path scenario described in Bug #1: creating/publishing two pages (or duplicating one twice) with the same `properties.path` and asserting what `getPageByPath` returns. `packages/api-website-builder/__tests__/pages.test.ts`/`pages.gql.test.ts` cover permission scoping (`pages.permissions*.test.ts`) well but nothing on path collisions.
- No test hits `rest/WebsiteBuilderRedirectsRoute.ts` at all (`__tests__` only has `redirects.gql.test.ts`/`redirects.test.ts` against the GraphQL API), so Bug #2's unhandled-exception path is untested.

## Recommendations
1. Enforce page path uniqueness before create/update/publish (e.g. a repository-level check via `GetPageByPathUseCase`/a dedicated indexed lookup, rejecting the write with a domain error on collision), and give `GetPageByPathRepository`'s underlying list query a deterministic sort so behavior is at least predictable until uniqueness is enforced.
2. Fix `WebsiteBuilderRedirectsRoute.ts` to check `result.isFail()` before touching `.value` and return a proper 403 — the same fix the `experiments-and-redirects.md` slice recommends, since both slices touch this one file.
3. Replace `utils/resolve.ts` with a direct import of `@webiny/api-graphql`'s `resolve`, and consider extracting the repeated "load original → coarse permission → per-record permission → repository call" shape shared by ~15 page use cases into a small helper to shrink the largest jscpd cluster.
