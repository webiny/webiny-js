# @webiny/api-website-builder — Experiments, redirects, variants and integrations

> Level 8 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice covers `packages/api-website-builder/src/features/{experiments,redirects,variants,nextjs,nuxt,webhooks,installer,tenantManager,permissions}` (~6k lines), i.e. everything under `features/` except the `pages` feature. It implements: URL redirect CRUD (`redirects/`), A/B experiment lifecycle and variant management (`experiments/`, `variants/`), outbound webhook event definitions for page/redirect changes (`webhooks/`), admin-facing "copy this into your `.env`" config generators for the Next.js/Nuxt starter kits (`nextjs/`, `nuxt/` — these are *not* revalidation/ISR endpoints; that logic lives in the separate `website-builder-nextjs`/`website-builder-nuxt` packages), the `frontend-integration` read-only API key bootstrapped at tenant install time (`installer/`), a small per-tenant "website theme" content-model extension for `@webiny/tenant-manager` (`tenantManager/`), and the `WbPermissions` schema-typed permissions abstraction (`permissions/`) used by every use case in this slice. The code follows the repo's use-case/repository/DI pattern consistently, with a double permission check (a coarse `canX("redirect"/"page")` gate followed by a per-record `canEdit/canDelete/canAccess(entity, record)` check) applied uniformly across redirects and experiments. The most concrete problem found is a public REST route (`/wb/redirects`) that reads `Result.value` without checking `isFail()`, turning an expected 403 into an unhandled exception for any authenticated-but-unauthorized caller. Redirect creation/update also performs zero business-rule validation (no self-redirect/cycle check, no `redirectFrom` uniqueness), which is a real gap for the "redirect loops" concern this audit was asked to focus on. Test coverage for this whole slice is essentially zero (one test file, for a markdown string builder).

## Public API
- `CreateRedirectUseCase`/`UpdateRedirectUseCase`/`DeleteRedirectUseCase`/`MoveRedirectUseCase`/`GetRedirectByIdUseCase`/`ListRedirectsUseCase`/`GetActiveRedirectsUseCase` — wired into `graphql/redirects` (manage GraphQL) and, for `GetActiveRedirectsUseCase`, into the public REST route `rest/WebsiteBuilderRedirectsRoute.ts` (`GET /wb/redirects`, consumed by frontend rendering layers such as `website-builder-nextjs`).
- `CreateExperimentUseCase`/`StartExperimentUseCase`/`StopExperimentUseCase`/`PauseExperimentUseCase`/`ResumeExperimentUseCase`/`GraduateVariantUseCase`/`GetActiveExperimentForPathUseCase`/`GetActiveExperimentForRevisionUseCase` and the parallel `*VariantUseCase` set — all consumed from `graphql/experiments/experiments.gql.ts` (manage GraphQL only; no public REST surface for experiments in this package).
- `WbPermissions` (`features/permissions/abstractions.ts`) — the DI permissions abstraction every use case in `redirects/`, `experiments/`, `variants/` injects; also consumed by `graphql/*` resolvers and by the `pages` feature (out of this slice).
- `NextjsConfig`/`NuxtConfig` — resolved once each, from `graphql/nextjs/NextjsGraphQLSchema.ts` and `graphql/nuxt/NuxtGraphQLSchema.ts` (both admin-gated: `identity.isAdmin()` + `wb.settings` permission).
- `ApiKeyInstaller` — registered as a tenant `AppInstaller`; creates the `frontend-integration` read-only API key on tenant install (consumed indirectly by every frontend integration that authenticates with that key, e.g. `NextjsConfig`'s generated `.env` snippet).
- `TenantModelExtension` (default export) — plugs a `websiteTheme` field group into `@webiny/tenant-manager`'s `Tenant` content model; consumed only by `tenant-manager`'s model builder at model-definition time.

## Duplication
Within-package clones from the jscpd report that touch this slice's folders (all are the repo's standard create/update/repository boilerplate pattern, not logic bugs):
- `redirects/MoveRedirect/MoveRedirectUseCase.ts:30-43` ↔ `redirects/UpdateRedirect/UpdateRedirectUseCase.ts:30-43` (14 lines) — the "load original, run the second per-record permission check" block is identical between move and update.
- `redirects/GetRedirectById/GetRedirectByIdRepository.ts:19-31` ↔ `redirects/UpdateRedirect/UpdateRedirectRepository.ts:45-56` (13 lines) and `redirects/CreateRedirect/CreateRedirectRepository.ts:16-25` ↔ `redirects/UpdateRedirect/UpdateRedirectRepository.ts:36-45` (10 lines) — the entry-to-domain mapping/error-translation boilerplate repeated per use case.
- `redirects/DeleteRedirect/abstractions.ts:1-15` ↔ `redirects/MoveRedirect/abstractions.ts:1-15` (15 lines) — near-identical DTO/error-union declarations.
- `experiments/StartExperiment/StartExperimentUseCase.ts:21-35` ↔ `experiments/StopExperiment/StopExperimentUseCase.ts:18-32` (15 lines), and the matching `StartExperimentRepository.ts`/`StopExperimentRepository.ts` pair (two clone blocks, 14 and 17 lines) — start/stop are structurally the same status-flip operation.
- `experiments/GetExperimentById/GetExperimentByIdRepository.ts:20-33` ↔ `experiments/StopExperiment/StopExperimentRepository.ts:26-39` (14 lines).
- `experiments/ExperimentPause/PauseExperimentUseCase.ts:13-23` ↔ `experiments/ExperimentPause/ResumeExperimentUseCase.ts:9-19` (11 lines) — pause/resume are symmetric key-value-store writes.
- `nextjs/NextjsConfig.ts:7-20,33-73` ↔ `nuxt/NuxtConfig.ts:7-20,33-73` (14 + 41 lines) — the Next.js and Nuxt config generators are near-identical except for the markdown copy and starter-kit link; a shared `FrontendConfigBuilder` taking framework-specific strings would remove most of this.

None of these are dangerous duplication (each pair is independently correct), but the `NextjsConfig`/`NuxtConfig` pair in particular is large enough (41 duplicated lines) to be worth factoring into one parameterized implementation.

Cross-package: this slice correctly reuses `@webiny/api-core`'s `EventPublisher`/`DomainEvent` for before/after mutation events and `KeyValueStore` for the experiment pause kill-switch, rather than reimplementing either.

## Dead code
None found with high confidence. `nuxt/` looked at first glance like it might be an unfinished/unused mirror of `nextjs/` (99 lines vs. 693), but `NuxtFeature` is registered from `WebsiteBuilderFeature.ts:122` and `NuxtConfig` is wired into a real GraphQL resolver (`graphql/nuxt/NuxtGraphQLSchema.ts`, `WbQuery.getNuxtConfig`), symmetric with the Next.js path — it's simply a smaller, single-purpose config generator, not dead.

## Convention issues
- The `NextjsConfig`/`NuxtConfig` duplication (see Duplication) is the one place in this slice where the "reuse, don't duplicate" convention is visibly violated — a single parameterized builder would be more in line with the rest of the package's DI-per-concern structure.
- No inline-type or barrel-export violations found; every feature folder here follows the repo's one-abstraction-per-file / `abstractions.ts` + `feature.ts` + `index.ts` convention consistently.

## Test gaps
Test coverage for this entire ~6k-line slice is effectively nonexistent: the only test file under any of the audited folders is `features/nextjs/MarkdownContentBuilder.test.ts`, which tests a plain string-builder utility, not any business logic. In particular, there are no tests for: redirect create/update/move/delete and their permission checks; the experiment start/stop/pause/resume/graduate state machine (including the concurrency gap in Bug #3); variant CRUD; or the `ApiKeyInstaller`'s install/uninstall behavior. Given the permission double-check pattern and the several status-transition invariants (`draft`/`stopped` → `running`, `running` → `graduated`, etc.) are the main correctness surface of this slice, this is a significant gap.

## Recommendations
1. Fix `WebsiteBuilderRedirectsRoute.handle()` to check `result.isFail()` before touching `result.value` and return a proper 401/403 JSON error, matching the pattern already used for the anonymous-identity branch two lines above (Bug #1).
2. Add a same-source/cycle guard to `CreateRedirectUseCase`/`UpdateRedirectUseCase` (reject `redirectFrom === redirectTo`, and ideally detect chains against existing enabled redirects) so a redirect-loop can't be saved in the first place (Bug #2).
3. Add tests for the experiment status state machine (start/stop/pause/resume/graduate, including the concurrent-start race in Bug #3) and for the redirect CRUD permission double-checks — this slice currently has no safety net for either.
