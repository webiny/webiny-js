# @webiny/api-record-locking

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-record-locking` is the backend half of Webiny's optional ("recordLocking" feature-flag gated) content-entry locking mechanism: it stores one CMS entry per lock (id `wby-lm-<entryId>`, via the injected `RecordLockingModel`) and exposes GraphQL operations (`lockEntry`/`updateEntryLock`/`unlockEntry`/`getLockedEntryLockRecord`/`listLockRecords`/`requestEntryUnlock`) built entirely on top of `@webiny/api-headless-cms`'s own `CreateEntryUseCase`/`UpdateEntryUseCase`/`GetEntryByIdUseCase`/`DeleteEntryUseCase`, plus a websocket "kick out" notification (via `@webiny/api-websockets`' `SendToIdentity`) sent when a lock is force-released. The feature/use-case/repository structure is clean and consistently applied, but the audit found that lock acquisition is not atomic (a genuine two-user race), and — more importantly — that the lock is purely advisory: nothing in this package (or, as far as this audit's scope covers, in `api-headless-cms`) stops a normal `updateEntry`/`publishEntry`/`deleteEntry` GraphQL mutation on a locked entry from a non-lock-holder. Enforcement of "you can't edit what's locked" exists only in `@webiny/app-record-locking`'s client-side UI gating.

## Public API
- `LockEntryUseCase` / `UpdateEntryLockUseCase` / `UnlockEntryUseCase` / `GetLockedEntryLockRecordUseCase` / `ListLockRecordsUseCase` / `ListAllLockRecordsUseCase` / `UnlockEntryRequestUseCase` (`src/features/*/abstractions.ts`) — each wired to one GraphQL field in `src/graphql/schema.ts`; the only confirmed consumer is `@webiny/app-record-locking`'s gateways (`AcquireLockGateway` calls `updateEntryLock`, `ReleaseLockGateway`/`ForceUnlockGateway` call `unlockEntry`, `CheckLockStatusGateway` calls `getLockedEntryLockRecord`, `ListLockRecordsPresenter` calls `listLockRecords`).
- `RecordLockingFeature` / `RecordLockingAppFeature` (`src/features/RecordLockingFeature.ts`, `src/RecordLockingAppFeature.ts`) — DI wiring entry points; `RecordLockingAppFeature.register` checks the `recordLocking` `FeatureFlags` entitlement before registering anything (license gate).
- `createLockRecordDatabaseId`/`removeLockRecordDatabasePrefix` (`src/utils/lockRecordDatabaseId.ts`) — derives the deterministic lock-record entry id (`wby-lm-<id>`) from a target entry id; used by every repository in this package.

## Bugs
| # | Severity | Location | Problem | Failure scenario | Confidence |
|---|----------|----------|---------|-------------------|------------|
| 1 | critical | `src/features/LockEntry/LockEntryUseCase.ts:17-37`, `src/features/LockEntry/LockEntryRepository.ts:19-45` | Lock acquisition is check-then-act, not atomic. `LockEntryUseCase` calls `IsEntryLockedUseCase` (a read), and only if it returns "not locked" does it call `repository.create`, which calls `api-headless-cms`'s `CreateEntryUseCase`. The DynamoDB storage operation behind that (`packages/api-headless-cms-ddb/src/operations/entry/DdbCreateEntry.ts`) performs a plain `put` with no `ConditionExpression`/`attribute_not_exists` guard, so it is an unconditional overwrite, not a create-if-absent. | Two users open the same never-before-locked entry at the same instant. Both requests read "not locked" before either has written, both proceed to `create` the same deterministic lock-record id (`wby-lm-<entryId>`), and both writes succeed (last one wins in storage) — but both callers receive `Result.ok(...)` with themselves as `lockedBy`, so both clients believe they exclusively hold the lock while the DB only reflects one of them. | high |
| 2 | high | `src/features/RecordLockingFeature.ts` (whole file) and its sub-features — no decorator anywhere in this package registers on `api-headless-cms`'s `UpdateEntryUseCase`, `PublishEntryUseCase`, `UnpublishEntryUseCase`, or `DeleteEntryUseCase` | The lock record is a side-table with no server-side gate on the actual entry mutation. The only place "is this locked by someone else" is checked is in this package's own read-side use cases (`IsEntryLockedUseCase`, `GetLockedEntryLockRecordUseCase`), which nothing in `api-headless-cms`'s write path calls. | A user (or a script/second tab bypassing the admin UI) sends a normal `updateEntry`/`publishEntry`/`deleteEntry` GraphQL mutation for an entry that is currently locked by someone else. The mutation succeeds unconditionally — the lock has zero effect at the API layer; it only drives `@webiny/app-record-locking`'s client-side button-disabling (see that package's report, `ContentEntryFormPresenterDecorator.ts`). | high |
| 3 | medium | `src/features/UpdateEntryLock/UpdateEntryLockUseCase.ts:46-52`, `src/features/UpdateEntryLock/UpdateEntryLockRepository.ts:38-53` | Same non-atomic pattern as #1 applies to re-acquiring an *expired* lock: both branches check `record.isExpired()` then call `repository.update(record.id, true)` (an unconditional CMS entry update — no version/condition check was found in the equivalent DynamoDB update operation either). | Two users both hold entries whose 20s+ heartbeat has lapsed past the configured timeout and both call `updateEntryLock` (the "acquire" mutation, per `AcquireLockGateway`) within the same window; both observe the existing record as expired, both update it with themselves as the new `createdBy`/owner, and both get back a success result even though only one write persists. | medium |

## Duplication
jscpd found only small, unavoidable clones within the package: `LockEntryRepository.ts:4-12` vs `UpdateEntryLockRepository.ts:6-14` (constructor/import boilerplate), `LockEntryEventsDecorator.ts:19-31` vs `UnlockEntryRequestEventsDecorator.ts:26-38` (before/after event-publishing wrapper shape), `ListAllLockRecordsRepository.ts:26-56` vs `ListLockRecordsRepository.ts:25-55` (near-identical list-query construction for "all lock records" vs "lock records for one entry"), and three internal near-duplicate blocks inside `graphql/schema.ts` (lines ~205-298, repeated response-type field declarations for the different mutations). None of these are large enough to warrant extraction on their own merits; they're standard artifacts of the repo's use-case/repository/decorator-per-feature convention.

## Dead code
None found with the codegraph/grep checks performed — `LockEntryUseCase`, `UpdateEntryLockUseCase`, `UnlockEntryUseCase`, `ListLockRecordsUseCase`, `ListAllLockRecordsUseCase`, and `UnlockEntryRequestUseCase` are all wired into `graphql/schema.ts` and have external consumers via `app-record-locking`'s gateways.

## Convention issues
None found that violate `AGENTS.md`'s DI naming/one-abstraction-per-file/inline-types conventions — the package consistently follows the abstraction/implementation/feature-per-folder pattern used elsewhere in the repo.

## Test gaps
`__tests__/graphql/*.test.ts` covers the happy/error paths of each mutation and query individually (lock, unlock, updateEntryLock, requestEntryUnlock, isEntryLocked, getLockRecord, getLockedEntryLockRecord, listLockRecords), but nothing exercises concurrent/overlapping requests, so the two races above (#1 and #3) are untested and would not be caught by the existing suite. There is also no test asserting that a locked entry's `updateEntry`/`deleteEntry` mutation is (or, per finding #2, is not) rejected server-side.

## Recommendations
1. Make lock acquisition atomic: either add a conditional write (e.g. `attribute_not_exists(pk)` equivalent) on the lock-record create/expired-update path, or have `LockEntryRepository`/`UpdateEntryLockRepository` re-read the just-written record after `create`/`update` and verify `lockedBy` matches the current identity before returning success, and treat a mismatch as `EntryAlreadyLockedError` (finding #1 and #3).
2. Decide whether server-side enforcement is actually intended; if so, add a decorator on `api-headless-cms`'s `UpdateEntryUseCase`/`PublishEntryUseCase`/`UnpublishEntryUseCase`/`DeleteEntryUseCase` that checks `IsEntryLockedUseCase`/`GetLockedEntryLockRecordUseCase` and rejects the mutation for non-owners, matching the "double access-control check" pattern already used elsewhere in `api-headless-cms` (finding #2 — this is the single highest-impact gap, since it means the whole feature is currently a UX convenience rather than a real lock).
3. Add an integration test that fires two concurrent `updateEntryLock`/`lockEntry` calls for the same never-locked (and separately, expired) entry and asserts only one succeeds, to guard against regressing #1/#3 once fixed.
