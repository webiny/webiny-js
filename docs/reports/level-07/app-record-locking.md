# @webiny/app-record-locking

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/app-record-locking` is the admin-UI client of the record-locking feature: a MobX `RecordLockingPresenter` that acquires a lock on entering a content-entry form (via `@webiny/api-record-locking`'s `updateEntryLock` GraphQL mutation), heartbeats it every 20s, releases it on unmount, listens for a `recordLocking.entry.kickOut.<id>` websocket message (via `@webiny/app-websockets`' `onMessage`, not `onOpen` — the level-4 `app-websockets` `onOpen`/close bug does not affect this package), and disables save/publish/unpublish/delete via a `ContentEntryFormPresenter` decorator when the entry is locked by someone else. A separate `ListLockRecordsPresenter`/`ContentEntriesPresenterDecorator` shows a lock icon in the content-entry list view. The package correctly reuses `@webiny/app`'s DI/router/websockets primitives rather than reimplementing them, but all of its "lock enforcement" is client-side button-disabling — the actual server-side gap this depends on is documented in `@webiny/api-record-locking`'s report (finding #2) — and the same content/kick-out wiring is implemented three times with meaningful duplication, one of those three (`RecordLockingGuard.tsx`) appearing unused. There are no automated tests anywhere in this package.

## Public API
This is a leaf admin-app package (registered as a module via `RecordLockingModule`/`RecordLockingFeature`/`SecurityPermissions`), not one consumed by other workspace packages beyond `packages/webiny`'s app composition. Its main pieces:
- `RecordLockingModule` (`src/RecordLockingModule.tsx`) — mounts three decorators: an inline `ContentDecorator` (wraps `ContentEntryFormContent`), `SingleEntryContentDecorator` (wraps `SingleEntryFormContent`, for single-entry models), and `RecordLockingCellActionsDecorator` (adds the lock icon to the entries table).
- `ContentEntryFormPresenterLockingDecorator` (`src/presentation/entryLocking/ContentEntryFormPresenterDecorator.ts`) — decorates `@webiny/app-headless-cms`'s `ContentEntryFormPresenter` to gate `canSave`/`canPublish`/`canUnpublish`/`canDelete` on `RecordLockingPresenter.vm.canEdit`.
- `RecordLockingPresenter` (`src/presentation/entryLocking/RecordLockingPresenter.ts`) — the core lock lifecycle state machine (`init`/`refreshLock`/`forceUnlock`/`handleKickOut`/`dispose`), consumed by all three decorators above.

## Duplication
jscpd flags two clone pairs, and reading the three files confirms a third, larger duplication jscpd's threshold didn't catch: `RecordLockingModule.tsx`'s inline `ContentDecorator` (lines 21-107), `SingleEntryContentDecorator.tsx` (the whole file), and the apparently-dead `RecordLockingGuard.tsx` (the whole file) all implement the same sequence — resolve `RecordLockingPresenter` from the container, call `presenter.init(entryId, modelId)` in a `useEffect`, subscribe to `websockets.onMessage(\`recordLocking.entry.kickOut.${id}\`, ...)`, show a "forcefully unlocked" dialog and call `router.unblockTransition()` when status becomes `kicked-out`, and render `LockedEntryOverlay`/`OverlayLoader` based on `presenter.vm.status`. This is ~80 lines duplicated three times (jscpd catches two of the three pairings: `RecordLockingModule.tsx:43-52` ↔ `SingleEntryContentDecorator.tsx:47-56`, and `RecordLockingModule.tsx:59-80` ↔ `RecordLockingGuard.tsx:59-82`). Extracting a shared `useRecordLockingGuard(entryId, modelId)` hook (or a single shared wrapper component parameterized by `onNavigateBack`) would remove the triplication and the associated risk of the three copies diverging (as they already have — `RecordLockingGuard.tsx` isn't even wired up, per Bugs #3).

## Dead code
`RecordLockingGuard.tsx` — see Bugs #3. No other unused exports were found; `AcquireLockUseCase`/`ReleaseLockUseCase`/`ForceUnlockUseCase`/`CheckLockStatusUseCase`/`ListLockRecordsUseCase` are all consumed by `RecordLockingPresenter`/`ListLockRecordsPresenter`.

## Convention issues
None found that violate `AGENTS.md`'s DI naming/one-abstraction-per-file/inline-types conventions — features consistently follow the abstraction/gateway/use-case/feature-per-folder pattern (e.g. `features/acquireLock/{abstractions,AcquireLockUseCase,AcquireLockGateway,feature}.ts`).

## Test gaps
There are no `__tests__` anywhere in this package (confirmed by directory search) — none of the presenter lifecycle logic (heartbeat, dispose-during-init race, kick-out handling, force-unlock's two-step "unlock then re-acquire" sequence) has any automated coverage. Given this package's logic is almost entirely about time- and network-ordering (heartbeats, races on mount/unmount, websocket timing), the complete absence of tests is a significant gap relative to sibling packages like `app-admin`'s `presentation` slice, which has dedicated presenter tests for comparable MVP logic.

## Recommendations
1. Treat the server-side enforcement gap (api-record-locking finding #2) as the priority — this package's `canEdit` gating is only as meaningful as the server check backing it, and today there is none.
2. Consolidate `ContentDecorator` (in `RecordLockingModule.tsx`), `SingleEntryContentDecorator.tsx`, and `RecordLockingGuard.tsx` into one shared hook/component; delete `RecordLockingGuard.tsx` if confirmed unused, or wire it in if it was meant to replace one of the other two.
3. Add a `_disposed` guard in `RecordLockingPresenter` that `init()`'s continuation checks before applying `runInAction`, so a lock acquired after unmount is immediately released instead of leaking until the server-side timeout; and add unit tests for the presenter's init/dispose/heartbeat/kick-out state machine, including the unmount-during-init race.
