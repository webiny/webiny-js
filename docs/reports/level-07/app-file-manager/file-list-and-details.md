# @webiny/app-file-manager — File list and details UI

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
This slice (`packages/app-file-manager/src/presentation/{FileList,FileDetails}`, ~5.8k lines) is the MobX-presenter/DI-driven UI for browsing files (table/grid views, search, filters, tags, bulk actions) and viewing/editing a single file's details in a drawer. It follows the codebase's presenter+abstraction+feature DI pattern consistently, correctly reuses `@webiny/app-admin`'s generic `ListPresenter`/`FolderAwareDataSource` rather than reimplementing pagination/selection, and renders all user-supplied file names/descriptions/tags as plain React text (no `dangerouslySetInnerHTML` anywhere in the slice, so no XSS was found here). Health is otherwise mixed: `FileDetailsPresenter.loadFile` has no guard against out-of-order responses, so rapidly opening two different files' details can leave the drawer showing (and let the user save over) the wrong file's data, and `FileManagerPresenter.dispose()` doesn't reset transient view state (`_fileDetails`, `_showingFilters`, `_dragging`) even though the same singleton presenter is re-initialized when its owning view's `scope`/`accept` props change without a remount.

## Public API
This slice is internal to `@webiny/app-file-manager` (only reached through `~/index.js` and the package's own `FileManagerView`), not separately imported by other workspace packages.
- `FileManagerPresenter` / `IFileManagerPresenter` (`FileList/FileManagerPresenter.ts`, `FileList/abstractions.ts`) — the file-browser view-model; resolved once per `FileManagerView` mount (`presentation/FileManager/FileManagerView.tsx`) and consumed by every component under `FileList/components/*` via `useFileManagerPresenter()`.
- `FileDetailsPresenter` / `IFileDetailsPresenter` (`FileDetails/FileDetailsPresenter.ts`, `FileDetails/abstractions.ts`) — the single-file edit view-model; also consumed by `packages/app-file-manager/src/modules/AiEnrichment/ReenrichWithAiPresenter.ts` (calls `setFile` after an out-of-band AI re-enrichment).
- `FileListDataSource` (`FileList/FileListDataSource.ts`) — extends `@webiny/app-admin`'s `FolderAwareDataSource` with file-specific `where` building (mime-type accept filters, tag AND/OR rules, scope-based tag prefixing); used only by `FileManagerPresenter.init()`.
- `FileManagerPresenterProvider` / `useFileManagerPresenter` (`FileList/FileManagerPresenterProvider.tsx`) — React context plumbing, used by essentially every component in both folders.

## Duplication
- `FileList/components/Table/Cells/CellSize.tsx:5-13` and `CellType.tsx:4-12` — identical row-guard boilerplate (`isFolderRow` check + `"-"` fallback) around a one-line value formatter; jscpd reports a 9-line clone. Low-value duplication, could share a `useCellValue` helper but not urgent.
- `FileList/components/BulkActions/BulkActionDelete.tsx:31-57` and `BulkActionMove.tsx:40-66` — the `processInSeries` try/catch/report block (success/error reporting per item) is duplicated near-verbatim (jscpd: two clones of 13 and 14 lines). A shared `runBulkOperation(worker, fn)` helper in `useBulkActionWorker.ts` would remove both copies.
- The remaining jscpd hits inside this slice (`jscpd-app-file-manager/jscpd-report.json`) are all test-to-test clones (`FileGrid.test.ts` ↔ `FileTable.test.ts` fixture setup, `FileListPresenter.test.ts` internal repeats, `FileDetailsPresenter.test.ts` ↔ `FileListPresenter.test.ts` mock scaffolding) — not production duplication, not flagged further.
- No reimplementation of lower-level dependency utilities was found: `FileListDataSource` correctly extends `@webiny/app-admin`'s `FolderAwareDataSource` instead of rebuilding pagination/folder-expansion logic, and no local `ListCache`-style class (as seen triplicated in `admin-ui` and again in `app-admin`) appears in this slice.

## Dead code
- `FileDetails/FileDetailsPresenter.ts:24` — the constructor injects `deleteFileUseCase: DeleteFileUseCase.Interface` but the class never calls it (codegraph: no references to `this.deleteFileUseCase` outside the constructor parameter). `IFileDetailsPresenter` (`FileDetails/abstractions.ts:24-30`) also has no `deleteFile()` method, so there is no way to trigger it from this presenter.
- Relatedly, `vm.permissions.canDelete` (`FileDetailsPresenter.ts:43`, `IFileDetailsViewModel.permissions.canDelete`) is computed and unit-tested (`FileDetailsPresenter.test.ts:329-338`) but has no consumer: `grep` across `FileDetails/components/*` shows no component reading `permissions.canDelete` (only `permissions.canEdit` gates the drawer's Update button in `FileDetailsDrawer.tsx:92`). Together these look like the remnant of a "delete from the details drawer" feature that was removed or never finished, leaving an unused DI dependency and a dangling, untriggerable permission flag.

## Convention issues
- `FileList/components/Table/Actions/MoveFile.tsx` renders its `OptionsMenuItem` unconditionally, with no `vm.permissions.canEdit`/`canEditFile` gate, unlike its sibling `DeleteFile.tsx` (`if (!vm.permissions.canDeleteFile(file)) return null;`) and `BulkActionDelete.tsx` (`if (!vm.permissions.canDelete) return null;`). This is an inconsistency in the row-actions family rather than a confirmed security gap (the backend enforcement of the move/update mutation was not checked as part of this slice), but it means the "Move" menu item is shown to users regardless of edit permission while every other mutating action in the same menu is gated.

## Test gaps
- `FileList/FileListDataSource.ts` has zero direct test coverage (no `FileListDataSource.test.ts`, and it is not exercised through `FileListPresenter.test.ts`, which mocks the data source rather than using the real one). Its `customizeWhere` method builds non-trivial `where` clauses (mime-type accept splitting into `type_in`/`type_startsWith`/`OR`, tag `AND`/`OR` rule composition, scope-based `tags_startsWith`/`tags_not_startsWith`), and a regression here would silently over- or under-fetch files rather than throw.
- No test exercises two overlapping `loadFile()` calls on `FileDetailsPresenter` (see Bug #1) — all tests in `FileDetailsPresenter.test.ts` await one `loadFile` call to completion before issuing the next.
- No test covers `FileManagerPresenter.dispose()` followed by a second `init()` on the same instance with the file-details drawer open (see Bug #2); `FileListPresenter.test.ts` only tests `init()` in isolation.

## Recommendations
1. Guard `FileDetailsPresenter.loadFile` against out-of-order responses (e.g. track a request id/generation counter and ignore stale resolutions) — this is the one finding with a concrete data-corruption path (editing/saving the wrong file).
2. Have `FileManagerPresenter.dispose()` reset `_fileDetails`, `_showingFilters`, and `_dragging` alongside the reaction teardown, so re-`init()` on the same singleton starts from a clean UI state.
3. Remove the unused `deleteFileUseCase` dependency and the orphaned `vm.permissions.canDelete` from `FileDetailsPresenter`, or finish wiring a delete action into the details drawer if one was intended — as is, it's dead weight and a source of confusion for future maintainers.
