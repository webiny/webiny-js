# @webiny/api-headless-cms-storage

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary

`@webiny/api-headless-cms-storage` is the storage-agnostic, in-memory implementation of CMS entry `where`-filtering, sorting, and field-path/value-transform resolution: it turns a GraphQL-style `where` object into a tree of `Expression`/`Filter` nodes (`filtering/expressions/createExpressions.ts`), evaluates them against already-fetched entries using `@webiny/db-utils`'s `ValueFilterRegistry` (`filtering/filter.ts`), sorts a single field at a time (`filtering/sort.ts`), and exposes a small set of DI registries (`FieldFilterCreateRegistry`, `FieldFilterPathRegistry`, `FieldFilterValueTransformRegistry`, `FieldSortingRegistry`) that field-type-specific storage packages (`api-headless-cms-ddb`, `-sql`) plug into. It does not talk to a database or build a physical query itself, and it has no tenant/locale scoping or index-naming concerns of its own — those live one layer up in the consumer packages. Overall health is mixed: the actively-wired DI-handler code path (`handlers/*.ts` + `features/*Registry.ts`) is reasonable, but the package also carries an entire second, near-verbatim, `Plugin`-class-based implementation of the same filter/path/transform logic (`filtering/plugins/*.ts`, `plugins/*.ts`, `path/*.ts`, `transforms/datetime.ts`) that is not wired into `FilterRegistriesFeature` at all and is effectively dead. Test coverage of the actual filter/sort evaluation logic is thin.

## Public API

- `filter` (`src/filtering/filter.ts:93`) and `sort` (`src/filtering/sort.ts:22`) — the two entry points that consumer storage packages call to apply a `where`/`sort` in memory. Codegraph: consumed by `api-headless-cms-ddb`'s entry storage operations and `api-headless-cms-sql`'s equivalent (this audit did not re-verify every call site, per cost rules, but both are named as consumers in the `db-utils` level-1 report).
- `createFields` (`src/filtering/fields/createFields.ts:96`) — builds the `Record<string, Field>` map (system fields + model fields) that `filter`/`sort` operate against; consumed by the same storage packages when constructing a query context per model.
- `FieldFilterCreateRegistry` / `FieldFilterPathRegistry` / `FieldFilterValueTransformRegistry` / `FieldSortingRegistry` (`src/features/*/abstractions.ts`) and `FilterRegistriesFeature` (`src/features/FilterRegistriesFeature.ts:18`) — the DI wiring point; registers the `*`, `ref`, `object`, `searchable-json` filter-create handlers, the `plainObject`/`text` (folderId) path handlers, and the `datetime` value-transform handler.
- `createStorageModelAccessor` / `createStorageTransformCallable` / `aggregateUniqueFieldValues` (`src/cms/storageHelpers.ts`) — small helpers used by consumer storage-operations packages to resolve a model's storage shape and aggregate unique field values.
- `createFilterCreatePlugins` (`src/filtering/plugins/index.ts:6`) and `CmsEntryFieldFilterPlugin`/`CmsEntryFieldFilterPathPlugin`/`CmsEntryFieldSortingPlugin`/`CmsFieldFilterValueTransformPlugin` — a legacy `Plugin`-based API, still exported from `index.ts`; codegraph shows `createFilterCreatePlugins` has exactly one caller (its own re-export in `src/index.ts`) — see Dead code.

## Duplication

The package contains two complete, parallel implementations of the same filter/path/transform logic:
- **Wired (used) path:** `handlers/defaultFilterCreateHandler.ts`, `handlers/objectFilterCreateHandler.ts`, `handlers/refFilterCreateHandler.ts`, `handlers/searchableJsonFilterCreateHandler.ts`, `handlers/plainObjectPathHandler.ts`, `handlers/locationFolderIdPathHandler.ts`, `handlers/datetimeTransformHandler.ts`, registered via `features/FilterRegistriesFeature.ts`.
- **Unwired (dead) legacy path:** `filtering/plugins/defaultFilterCreate.ts`, `filtering/plugins/objectFilterCreate.ts`, `filtering/plugins/refFilterCreate.ts`, `filtering/plugins/searchableJsonFilterCreate.ts`, `path/plainObject.ts`, `path/locationFolderId.ts`, `transforms/datetime.ts`, plus the `Plugin`-based base classes in `plugins/CmsEntryFieldFilterPlugin.ts`, `plugins/CmsEntryFieldFilterPathPlugin.ts`, `plugins/CmsEntryFieldSortingPlugin.ts`, `plugins/CmsFieldFilterValueTransformPlugin.ts`.

jscpd confirms heavy internal duplication in this second set — `filtering/plugins/searchableJsonFilterCreate.ts` (71.8% duplicated lines, 3 clones), `filtering/plugins/objectFilterCreate.ts` (66%), `filtering/plugins/refFilterCreate.ts` (57.8%) — each clone-pairing with its `handlers/*.ts` counterpart (verified by direct comparison of `path/plainObject.ts` vs `handlers/plainObjectPathHandler.ts`, which implement identical logic through two different plugin interfaces). This is exactly the class of "reimplementation of a lower-level utility" the audit is meant to flag, except here it's an internal fork rather than a cross-package one: any future fix to filter-creation logic (e.g. the missing type guard in finding #1) must be made in two places to stay consistent, and only one of them is exercised at runtime.

## Dead code

- `createFilterCreatePlugins` (`src/filtering/plugins/index.ts:6`) and everything it composes (`createDefaultFilterCreate`, `objectFilterCreate`, `createRefFilterCreate`, `searchableJsonFilterCreate`, and the `CmsEntryFieldFilterPlugin`/`CmsEntryFieldFilterPathPlugin`/`CmsEntryFieldSortingPlugin`/`CmsFieldFilterValueTransformPlugin` base classes) — codegraph: `createFilterCreatePlugins` has exactly one caller, its own re-export in `src/index.ts`; no production code instantiates these plugins, and `FilterRegistriesFeature` (the actual DI wiring) only uses the `handlers/*.ts` variants. This whole legacy `Plugin`-based surface (spanning `filtering/plugins/`, `plugins/`, `path/`, and `transforms/`) appears to be superseded by the `handlers/`+`features/*Registry` DI approach but was never removed, and is still part of the public barrel export in `src/index.ts`.

## Convention issues

`filtering/plugins/*.ts` (`defaultFilterCreate.ts`, `objectFilterCreate.ts`, `refFilterCreate.ts`, `searchableJsonFilterCreate.ts`) each define one factory function per file, which is fine per AGENTS.md's "one abstraction per file", but because they duplicate the `handlers/*.ts` implementations rather than being alternate DI implementations of the same abstraction registered under a different name, they read as leftover migration debris rather than intentional structure. No other meaningful convention violations found (no inline types beyond small local interfaces, DI naming follows the class-name convention in `features/*Registry.ts`).

## Test gaps

`__tests__/` only covers `filtering/getValue.test.ts`, `path/plainObject.test.ts`, and `transforms/datetime.test.ts` (plus a fixture in `filtering/mocks/entry.noModel.ts`). There is no test coverage for: `filtering/filter.ts` (`filter`/`executeFilter`/`executeExpressions`), `filtering/sort.ts`/`extractSort.ts`, `filtering/expressions/createExpressions.ts` (AND/OR nesting, the `wbyAco_`/`not_` key-parsing in `where.ts`), or any of the four `handlers/*FilterCreateHandler.ts` (default/ref/object/searchable-json) — i.e. none of the actual `where`-clause-to-filter-tree translation logic that this package exists to provide, including the `searchable-json` path implicated in Bug #1, is exercised by a test in this package.

## Recommendations

1. Add a type guard in the filter-creation path (or in the shared `ValueFilterRegistry.get(...)` consumption pattern used here) so a `compareValue` of the wrong type for the chosen operator is rejected with a clean validation error instead of reaching `db-utils`'s `matches()` and throwing — this closes both this package's `searchable-json` exposure (Bug #1) and the underlying `StartsWithFilter` gap flagged at level 1.
2. Delete the unwired legacy `Plugin`-based filter/path/transform code (`filtering/plugins/*`, `plugins/CmsEntryFieldFilterPlugin.ts` and its siblings, `path/*.ts`, `transforms/datetime.ts`) and their exports from `src/index.ts`, keeping only the `handlers/*`/`features/*Registry` implementation that is actually wired — this removes the dead code and eliminates the largest source of internal duplication in one pass.
3. Add unit tests for `filter.ts`, `sort.ts`/`extractSort.ts`, and `createExpressions.ts` covering AND/OR nesting, negation (`not_`/`_not_`), and each of the four filter-create handlers, since this is the package's core responsibility and is currently the least-tested part of it.
