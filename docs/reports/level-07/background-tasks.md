# @webiny/background-tasks

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/background-tasks` is the long-running-job framework built on top of `@webiny/api-core`'s `TaskDefinition`/`TaskService`/`TaskController` DI abstractions: it stores tasks and their logs as CMS entries, drives a task through a Lambda/Step-Functions-style "run, maybe continue, maybe timeout" loop (`TaskRunner`/`TaskControl`/`TaskManager`), exposes a GraphQL API (`triggerTask`/`abortTask`/`deleteTask`/`listTasks`/`listLogs`/`listDefinitions`/`getSettings`/`updateSettings`) and a matching Admin UI (task list, task detail, task-definitions catalogue, retention settings screen). The runner's timeout check correctly delegates to an injected `Timer` abstraction (in production, `background-tasks-aws`'s `LambdaTimer`, which reads the real `context.getRemainingTimeInMillis()`), so it does **not** reproduce the "hardcoded 900s remaining time" defect found in the level-4 `api-sync-ddb-to-opensearch`/`api-sync-pg-to-opensearch` adapters. However, task execution has no re-entrancy guard: a task already in the `RUNNING` state can be run a second time concurrently (no check for that status, and no optimistic locking on the underlying CMS-entry update), any single thrown error inside a task iteration permanently marks the task `FAILED` with no automatic retry, and there is no rate limiting anywhere on task triggering. Overall the code is clean, consistently uses the DI use-case/repository pattern, and is reasonably well tested for the happy paths, but the concurrency gap is a real correctness risk for a framework whose entire purpose is orchestrating long-running, resumable work.

## Public API
- `TasksCrud`/`TaskService` (`packages/background-tasks/src/api/TasksCrud.ts`) — the CRUD/service facade for tasks and logs; ~20 call sites, mostly within the package itself and `api-headless-cms-bulk-actions` (`createBulkActionTasks.ts`, `ChildTasksCleanup.ts`).
- `TriggerTaskUseCase`/`AbortTaskUseCase` (`src/api/features/{TriggerTask,AbortTask}`) — used by the GraphQL resolvers and directly by other packages that programmatically trigger background work (e.g. `api-headless-cms-bulk-actions`, `api-file-manager-s3`'s cache-invalidation task).
- `TaskController.runtime` (`isCloseToTimeout`, `isAborted`, `getRemainingSeconds`/`getRemainingMilliseconds`) — the API every registered `TaskDefinition.run()` implementation is expected to poll; consumed by task definitions across the monorepo (bulk actions, file-manager cache flush, headless-cms ES sync tasks).
- GraphQL: `triggerTask`/`abortTask`/`deleteTask`/`listTasks`/`listLogs`/`listDefinitions`/`getSettings`/`updateSettings` (`src/api/graphql/BackgroundTasksContextualSchema.ts`) — consumed by the package's own Admin UI presentation layer.
- Admin UI presentation components (`src/admin/presentation/{TaskExecutions,TaskDetail,TaskDefinitions,BackgroundTaskSettings}`) — registered into `app-admin`'s menu/routes; not consumed outside this package.

## Duplication
- `packages/background-tasks/src/api/features/GetBackgroundTaskSettings/GetBackgroundTaskSettingsRepository.ts:40-59` and `packages/background-tasks/src/api/features/UpdateBackgroundTaskSettings/UpdateBackgroundTaskSettingsRepository.ts:53` (jscpd): near-identical "ensure the settings singleton CMS entry exists, resolve its model" logic duplicated between the get and update repositories instead of the update repository reusing the get repository's entry-resolution helper (it does call `GetBackgroundTaskSettingsRepository.execute()` for existence-checking, but re-derives the model/entry lookup itself right after).
- `packages/background-tasks/src/admin/presentation/TaskExecutions/TaskExecutionsDataSource.ts:50-71` vs `73-97` (jscpd, self-duplication): `query()` and `loadMore()` build the same `sort` transform and result-mapping logic almost verbatim, differing only in whether rows are replaced or appended.
- `packages/background-tasks/src/admin/features/listLogs/ListLogsGateway.ts:50-62` and `packages/background-tasks/src/admin/features/listTasks/ListTasksGateway.ts:59` (jscpd): duplicated GraphQL-response-to-domain-object mapping between the logs and tasks list gateways.
- Conceptual (not jscpd-flagged, different code per site): the "which task statuses allow further action" guard is independently re-implemented three times with slightly different status sets — `TaskControl.run()` (`ABORTED`/`SUCCESS`/`FAILED`), `TaskManager.run()` (`ABORTED`/`PENDING`/max-iterations), and `service.tasks.ts`'s `abort()` (`PENDING`/`RUNNING` only) — instead of a single shared state-machine helper, which is part of why finding #1's `RUNNING` case falls through unnoticed.

## Dead code
None confirmed. Codegraph checks on the main exports used in this audit (`TasksCrud` — 20 callers, `Task` domain type — 14 callers, `IBackgroundTaskSettings` — 11 callers) all show live consumers; no unused exports were identified within the scope investigated.

## Convention issues
- `updateSettings` (`packages/background-tasks/src/api/graphql/BackgroundTasksContextualSchema.ts:393-404`) is the only mutation resolver in this schema that does not call `checkPermissions()` at the resolver boundary the way `abortTask`/`triggerTask`/`deleteTask` do. It is not currently exploitable — `UpdateBackgroundTaskSettingsUseCase` independently enforces `permissions.canEdit("task")` — but it breaks the package's own established "check permissions in the resolver, then again in the use case" pattern, so the resolver has no defense-in-depth if the use-case-level check is ever changed.
- Otherwise the package follows the repo's DI abstraction/implementation/feature convention consistently (one abstraction + one `*Impl` class + `feature.ts` per use case, abstraction and implementation names matching).

## Test gaps
- No test exercises a task whose status is already `RUNNING` being handed to `TaskControl.run()`/`TaskManager.run()` a second time (the concurrent/duplicate-execution path in finding #1); `taskRunnerAbort.test.ts` only covers aborting before a run starts, and `taskRunnerErrorFailedState.test.ts`/`taskRunnerErrorSuccessState.test.ts` don't re-invoke a task after it reaches a terminal or in-progress state.
- No test covers the "transient error permanently fails the task" behavior in `DatabaseResponse.error()` (finding #2).
- No test covers repeated/rapid `triggerTask` calls or any throttling expectation (finding #3).

## Recommendations
1. Add a re-entrancy guard: reject (or safely no-op) a run when `TaskManagerStore.getStatus()` is already `RUNNING` at entry, and make `TaskManagerStore.save()`/`TasksCrud.updateTask()` a conditional write (e.g. compare against the last-read revision) instead of a blind read-then-write, so a redelivered/retried invocation can't execute the same task twice or silently overwrite another invocation's update.
2. Add rate limiting / a max-concurrent-tasks-per-tenant setting (surfaced through the existing `WebinyBackgroundTaskSettings`/`updateSettings` machinery, which currently only has `retentionDays`) so `triggerTask` can't be used to exhaust Step Functions concurrency or overload storage.
3. Add the resolver-level `checkPermissions()` call to `updateSettings` for consistency with the other five permission-checked resolvers in the same file, even though the use case currently double-checks.
