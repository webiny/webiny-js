# @webiny/api-scheduler

> Level 7 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/api-scheduler` is the backend engine behind Webiny's "schedule publish/unpublish for later" feature: it exposes a small GraphQL API (`scheduleAction`, `cancelScheduledAction`, `getScheduledAction`, `getTargetScheduledAction`, `listScheduledActions`), persists each pending schedule as a CMS entry via a dedicated private content model, delegates the actual timer creation/update/deletion to a pluggable `SchedulerService` (EventBridge in `api-scheduler-aws`, a no-op `VoidSchedulerService` here), and — when the timer fires — resolves a namespace-specific `NamespaceHandler`/`ScheduledActionHandler` (implemented by consumers such as `api-headless-cms-scheduler`) to actually perform the publish/unpublish. The use-case/DI structure is consistent with the rest of the backend (Result-based error handling, feature/abstraction/implementation split), the schedule-vs-reschedule flow correctly deduplicates by deriving a deterministic id from `namespace+targetId+actionType` (so re-scheduling the same target/action updates the existing timer instead of creating a duplicate), and the package has essentially no exports other CMS packages would be tempted to reimplement. However, this audit found two confirmed, serious authorization gaps in the schedule-creation and cancellation paths (see Bugs; full detail in the private security notes), one resource-leak bug in cancellation's error handling, and a comment/code mismatch in past-date handling. Test coverage is minimal — only `ScheduledActionId` has a unit test.

## Public API
- `ScheduleActionUseCase` / `CancelScheduledActionUseCase` / `GetScheduledActionUseCase` / `GetTargetScheduledActionUseCase` / `ListScheduledActionsUseCase` (`src/features/*/abstractions.ts`) — each wired to exactly one resolver in `src/graphql/SchedulerGraphQLFactory.ts`; the GraphQL mutations/queries are the only realistic external consumers (confirmed via codegraph: `GetTargetScheduledActionUseCase` has exactly its own `feature.ts` DI registration and the GraphQL resolver as callers).
- `NamespaceHandler` / `ScheduledActionHandler` abstractions (`src/features/NamespaceHandler/abstractions.ts`, `src/shared/abstractions.ts`) — the extension points implemented by app-specific scheduler packages; currently implemented by `api-headless-cms-scheduler` (`PublishEntryActionHandler`, `UnpublishEntryActionHandler`, `NamespaceHandler`) and `api-website-builder-scheduler` (page/redirect handlers).
- `SchedulerService` abstraction (`src/shared/abstractions.ts`) — implemented by `VoidSchedulerService` here (used as the default/test double) and by `EventBridgeSchedulerService`/`LazySchedulerService` in `api-scheduler-aws` (11 callers per codegraph, including that package's own test suite).
- `ScheduledActionLambdaHandler` (`src/ScheduledActionLambdaHandler.ts`) — the composition-root entry point consumed by the AWS Lambda wiring in `api-scheduler-aws`, dispatches to `ExecuteScheduledActionUseCase` inside the correct tenant context.

### End-to-end timezone question (informational, not a separate row)
Tracing `scheduleFor` from the wire to execution confirms the level-6 finding is not cosmetic: `SchedulerGraphQLFactory.ts` declares `scheduleAction(..., scheduleFor: DateTime, ...)`, and the `DateTime` scalar (`packages/api-core/src/graphql/ApiCoreSchemaFactory.ts:25,48` → `packages/api-graphql/src/builtInTypes/DateTimeScalar.ts`) is `graphql-scalars`' standard `DateTimeResolver`, which parses the incoming ISO-8601 string with ordinary `Date` semantics — a trailing `Z` is taken as literal UTC, with no client-timezone reinterpretation. `ScheduleActionUseCaseImpl` then takes that `Date` completely at face value: it is stored via `scheduleFor.toISOString()` (`ScheduleActionUseCase.ts:164,245`) and handed unmodified to `schedulerService.create/update({ scheduleFor: new Date(scheduleFor) })` (lines 197-202, 259-264), which is what ultimately becomes the EventBridge schedule's trigger time in `api-scheduler-aws`. Nothing in this package inspects or corrects for a client timezone. So the admin-ui `DateTimePicker` bug (local wall-clock time mislabeled as UTC via the `.000Z` suffix, per `docs/reports/level-06/app-scheduler.md`) flows through unmodified: the scheduled publish/unpublish genuinely fires at the wrong wall-clock instant for any non-UTC user, exactly as the level-6 report predicted, with no server-side correction anywhere in this pipeline.

## Duplication
`jscpd` reports 4 clones (2.77% of lines) within the package, all minor structural repetition rather than copy-paste of business logic:
- `GetScheduledActionUseCase.ts:25-41` / `GetTargetScheduledActionUseCase.ts:27-44` and `GetScheduledActionUseCase.ts:51-69` / `GetTargetScheduledActionUseCase.ts:48-66` — the two "fetch by id" use cases share near-identical permission-check and CMS-entry-fetch boilerplate (expected, since they differ only in how the CMS entry id is derived).
- `CancelScheduledActionUseCase.ts:42-54` / `ExecuteScheduledActionUseCase.ts:57-68` — both repeat the same "`getScheduledActionUseCase.execute()` fails with `NotFound` → map to `ScheduledActionNotFoundError`" block.
- `SchedulerGraphQLFactory.ts:176-194` / `SchedulerGraphQLFactory.ts:197-215` — the `getScheduledAction` and `getTargetScheduledAction` resolvers are near-identical (same `Result`-to-`Response`/`ErrorResponse` mapping).

No reimplementation of lower-level package utilities was found; the package correctly reuses `@webiny/utils`' `parseIdentifier`, `@webiny/api-core`'s permissions/identity abstractions, and `@webiny/api-headless-cms`'s entry use cases rather than rolling its own.

## Dead code
None found with high confidence. `VoidSchedulerService` and `GetTargetScheduledActionUseCase` both looked like plausible dead-code candidates but codegraph confirms real consumers (`VoidSchedulerService` is extended/used by `api-scheduler-aws`'s `LazySchedulerService` and several of that package's tests; `GetTargetScheduledActionUseCase` is wired to the `getTargetScheduledAction` GraphQL query, its only expected consumer).

## Convention issues
None significant found — the feature/abstraction/implementation split, one-class-per-file, and DI naming conventions (implementation named after the abstraction, e.g. `ScheduleActionUseCase`/`ScheduleActionUseCaseImpl`) are followed consistently throughout.

## Test gaps
The package has only one test file, `__tests__/ScheduledActionId.test.ts`. None of `ScheduleActionUseCase`, `CancelScheduledActionUseCase`, `ExecuteScheduledActionUseCase`, `GetScheduledActionUseCase`, `isValidDate`, or the permission-check logic have any unit tests. In particular, a test asserting that `scheduleAction` rejects a caller lacking `scheduler.action` permission, or that `cancelScheduledAction` rejects a caller with only `own`-scoped permission trying to cancel someone else's schedule, would have caught both authorization gaps in this report — and their complete absence is itself evidence for how these gaps went unnoticed.

## Recommendations
1. Address security findings SEC-36 and SEC-37 (see private notes).
2. Add unit tests for every use case in `src/features/*`, especially permission-check branches (both "no permission" and "own-scope" cases) and the create-vs-reschedule branching in `ScheduleActionUseCase`, since this package currently has essentially zero coverage of its core logic.
3. Reconcile `isValidDate`'s past-date handling with its own doc comment (either implement the documented "treat past dates as immediate" fallback, or fix the comment), and consider what should happen when `schedulerService.delete()` fails during cancellation instead of silently continuing to delete the CMS tracking entry.
