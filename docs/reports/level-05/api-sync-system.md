# @webiny/api-sync-system

> Level 5 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
api-sync-system replicates DynamoDB writes (and a handful of side-effecting operations: S3 file copies, Cognito user create/delete) from a "source" blue/green deployment to one or more "target" deployments, via three legs: (1) an in-request hook (`attachToDynamoDbDocument`/`Handler`) that intercepts application DynamoDB writes and republishes them as an EventBridge event; (2) a resolver Lambda (`SyncResolverLambdaHandler`) that consumes those events from SQS, bundles them by table/command to preserve ordering, re-fetches current item state from the source table, and re-applies Put/Delete to the target table(s); and (3) a worker Lambda (`SyncWorkerLambdaHandler`) that performs non-DynamoDB side effects (file copy/delete, Cognito user create/update/delete) dispatched by the resolver. The ordering/bundling design (`CommandBundle`/`TableBundle`) is sound, but there are two real correctness bugs: writes made through the DynamoDB Document client's convenience methods (`put`/`delete`/`update`/`batchWrite`) are captured twice because the package wraps both those methods and the underlying `.send()` they internally delegate to, and the Cognito-side worker actions (`CreateUser`/`DeleteUser`) swallow the actual write failure and report success, silently dropping the replication.

## Public API
- `attachToDynamoDbDocument`/`decorateClientWithHandler` (`src/sync/attachToDynamoDbDocument.ts:20,81`) — wraps a `DynamoDBDocument` client so that every write made through it is captured into a per-request `Handler` and, on `flush()`, published as a single EventBridge event (`src/sync/handler/Handler.ts`).
- `SyncResolverLambdaHandler` (`src/resolver/SyncResolverLambdaHandler.ts:192`) — the SQS-triggered Lambda handler that consumes those events and replicates the write to the target deployment(s); built from `RecordHandler`/`Fetcher`/`Storer`/`Bundler` and the `put`/`delete` `CommandHandlerPlugin`s.
- `SyncWorkerLambdaHandler` (`src/worker/SyncWorkerLambdaHandler.ts`) — the Lambda invoked by the resolver (via `LambdaTrigger`) for non-DynamoDB side effects: `createUser`/`updateUser`/`deleteUser` (Cognito) and `copyFile`/`deleteFile` (S3), each a `WorkerActionPlugin`.
- Command converters (`src/sync/handler/converter/*CommandConverter.ts`) — turn intercepted SDK command objects (`Put`/`Delete`/`Update`/`BatchWrite`, plus `NullCommandValue` for `Get`/`Query`/`Scan`/`BatchGet`/anything unrecognized) into the `{command, PK, SK, tableName}` shape carried in the EventBridge event's `detail.items`.

These exports are consumed only by the generated project's own sync-system Lambda functions and by whatever deployment code wires `attachToDynamoDbDocument` into the "source" deployment's DynamoDB document-client factory; no other package in the monorepo imports from `api-sync-system`.

## Bugs

| 1 | high | src/sync/attachToDynamoDbDocument.ts:33-76 | `decorateClientWithHandler` overrides `client.send` AND `client.put`/`client.delete`/`client.update`/`client.batchWrite` on the same client instance. The AWS SDK's own `DynamoDBDocument.put/delete/update/batchWrite` (`node_modules/@aws-sdk/lib-dynamodb/dist-es/DynamoDBDocument.js:50-79,110-139,215-229`) are thin wrappers that build a command and call `this.send(command)`. Since `this` is the already-decorated client, calling e.g. `client.put(...)` invokes the overridden `put` (which does `handler.add(new PutCommand(params))`) and then, via `originalPut.apply(client, ...)`, re-enters the overridden `send` (which does `handler.add(params)` again) — every write issued through the convenience methods is captured twice. | An application write via `documentClient.put(...)` (or `.delete`/`.update`/`.batchWrite`) results in two identical command-value items pushed into `Handler.commands`, and thus two copies of the same write in the "synchronization-input" EventBridge detail. The resolver then applies the same Put/Delete/Update twice to the target table — each individual replicated write is idempotent on its own, but every side effect triggered off it (e.g. `StorerAfterEachPlugin`, worker Lambda invocations for file/user actions) runs twice per real application write. | high |
| 2 | medium | src/resolver/app/fetcher/Fetcher.ts:62-99, src/resolver/app/fetcher/types.ts:17-27, src/resolver/app/RecordHandler.ts:69-83 | `Fetcher.exec()` is typed to return `IFetcherExecResult = {items} \| {error}`, and `RecordHandler.handle` branches on `if (error) { ...; continue; }`, expecting to skip just the failed table bundle and keep processing the rest. Source and target Cognito pools silently diverge with no operator-visible failure signal beyond logs. | high |

## Duplication
- `PutCommandValue`/`DeleteCommandValue`/`UpdateCommandValue` (`src/sync/handler/converter/commands/*.ts`) are ~60% identical per jscpd, each hand-rolling the same `{command, PK, SK, tableName, tableType, input}` construction from `input.Key`/`input.Item`; could share a small base helper.
- The worker action layer repeats the same parse/handle scaffolding across `createUserAction.ts`/`deleteUserAction.ts`/`copyFileAction.ts`/`deleteFileAction.ts` (jscpd flags `updateUserAction.ts:24-35` as ~98% duplicated against all three siblings), and the `*Schema.ts` files are near-identical zod wrappers (e.g. `updateUserSchema.ts` vs `deleteUserSchema.ts`/`createUserSchema.ts`). `CopyUser.ts`/`DeleteUser.ts` (`resolver/recordTypes/users`) and `CopyFile.ts`/`DeleteFile.ts` (`resolver/recordTypes/fileManager`) likewise share large blocks (e.g. `CopyFile.ts:33-47,64-82` vs `DeleteFile.ts:33-48,60-78`). This follows the repo's "one action per file" convention, so it reads as deliberate boilerplate rather than a bug, but a shared base class for the common validate → look-up-source → look-up-target → act → log-failure shape would remove most of it.

## Dead code
Not evaluated with codegraph in this audit — the tool-call budget was spent confirming the bugs above via direct source reads (including the actual `@aws-sdk/lib-dynamodb` implementation for Bug #1), so no dead-code claims are made here rather than reporting unconfirmed guesses.

## Convention issues
- `attachToDynamoDbDocument.ts:28-76` uses six `@ts-expect-error` suppressions to attach `__webinyHandler` and re-wrap methods on the SDK's `DynamoDBDocument` type; combined with Bug #1, this masks a real overlap (the compiler would otherwise complain that `send` and `put`/`delete`/`update`/`batchWrite` are being independently reassigned) rather than being a pure style nit.
- `CommandType`/`ExtendedCommandType`/`AllCommandType` (`src/types.ts:1-3`) are three overlapping string-union types for what is conceptually one "which write happened" concept. `BaseBundle.getCommand` (`src/resolver/app/bundler/BaseBundle.ts:28-30`) silently collapses `"update"` into `"put"` (intentional — an update is resolved by re-fetching full item state and re-putting it), but this isn't documented near the type definitions, so a reader who only looks at `CommandType` will assume "update" is unhandled.

## Test gaps
- No test exercises the double-add scenario in Bug #1 — `__tests__/sync/attachToDynamoDbDocument.test.ts` only checks that decoration is skipped when the same handler/client pair is reused, not that a single `.put()`/`.delete()`/`.update()`/`.batchWrite()` call only registers one command.
- No test drives `Fetcher.exec` into an exhausted-retries path to confirm the `{error}` branch in `RecordHandler` is reachable (per Bug #2, it isn't).
- `CreateUser`/`DeleteUser` have no test asserting that a Cognito API failure is surfaced (propagated or reported as a failure) rather than swallowed (Bug #3); existing tests cover only the happy path and the "already exists"/"not found" idempotent-skip paths.

## Recommendations
1. Fix the double-capture bug in `attachToDynamoDbDocument.ts`: either wrap only `client.send` (every convenience method funnels through it already) or have the `put`/`delete`/`update`/`batchWrite` wrappers call `originalSend` directly instead of `originalPut`/`originalDelete`/etc., so each logical write is captured exactly once.
2. Make `Fetcher.exec` actually return `{error}` on failure (wrap the retrying `execute()` call in try/catch) so `RecordHandler`'s per-bundle skip-and-continue logic is reachable — or, if whole-batch failure is in fact the desired behavior, remove the dead `IFetcherExecErrorResult` branch and the misleading `continue` in `RecordHandler` so the code stops implying a partial-failure tolerance it doesn't have.
3. Stop swallowing `AdminCreateUserCommand`/`AdminDeleteUserCommand` failures in `CreateUser`/`DeleteUser` — at minimum rethrow so the worker Lambda invocation is marked failed and retried/DLQ'd, since a failed Cognito replication is currently indistinguishable from a successful one to anything monitoring the pipeline.
