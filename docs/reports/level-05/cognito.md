# @webiny/cognito

> Level 5 · commit 19c9ca1b91 · audited 2026-09-26

## Summary
`@webiny/cognito` is the Cognito-backed authentication extension for Webiny: an admin sign-in UI (username/password, forced password change, TOTP/MFA setup and verification, password reset, and federated social/SAML login via `aws-amplify`), a backend OIDC identity provider that maps a verified Cognito ID token into a Webiny admin identity, and a set of use cases that keep admin users (`adminUsers.user`) synced between the local api-core database and an actual Cognito User Pool (create/update/delete/list, first-user bootstrap). The package is architecturally consistent with the rest of the monorepo (one abstraction/implementation/feature per file, DI naming followed correctly throughout), but it has two concrete, confirmed defects in the Cognito-sync paths (a wrong-username bug when password and email are updated together, and no rollback/compensation when a Cognito call fails after the local database has already been mutated), plus a security finding tracked privately (SEC-21). It also inherits, via `@webiny/api-core`'s `JwksCache`, the already-reported issue that JWKS keys are cached forever and never refreshed — a Cognito signing-key rotation would make admin logins fail until the API process restarts.

## Public API
- `Cognito` (`src/Cognito.tsx` → `src/index.ts`) — the top-level extension component that wires the admin sign-in screen, the backend `CognitoApiFeature`, and Pulumi federation config together; consumed by project setup as the single package entry point.
- `CognitoIdpConfig` (`src/api/index.ts`, optional DI token) — lets a project customize `getIdentity`/`verifyTokenClaims` for the Cognito-issued token; consumed by `CognitoIdentityProviderImpl` (`src/api/features/CognitoIdp/CognitoIdentityProvider.ts`).
- `CognitoSignInConfig`, `CognitoComponents` (`src/admin/index.ts`) — customization points (title/description/federated providers, component overrides) for the sign-in screen; consumed by `CognitoPresenter` and `CognitoLoginScreen`.
- `CreateUserUseCase` / `UpdateUserUseCase` / `DeleteUserUseCase` / `GetUserUseCase` / `ListUsersUseCase` (`src/api/features/*`) — admin-user CRUD synced with Cognito; consumed by `CognitoApiFeature`'s GraphQL wiring and by `UserInstaller` (system-install first-admin-user bootstrap, ~1 caller each per codegraph).
- `CognitoService` (`src/api/features/CognitoService/*`) — thin wrapper over `@webiny/aws-sdk`'s `CognitoIdentityProvider` admin API (`adminCreateUser`/`adminUpdateUserAttributes`/`adminSetUserPassword`/`adminDeleteUser`/`adminGetUser`); consumed only by the four use cases above.

## Duplication
- `src/admin/presentation/Cognito/components/ConfirmTotpCode.tsx`, `RequestPasswordResetCode.tsx`, and `SetNewPassword.tsx` share large near-identical blocks (per jscpd: lines 1-7, 24-41/44, 48-67 respectively) — the same form-wrapper/description/submit-button boilerplate copy-pasted per screen instead of factored into a shared layout component.
- `src/api/features/CreateUser/schema.ts:9-17` and `src/api/features/UpdateUser/schema.ts:8-16` duplicate the same Zod field definitions (password/roles/teams/avatar shape) between create and update validation.
- `CreateUserUseCase.ts:37-45` and `UpdateUserUseCase.ts:47-55` duplicate the identical `safeParse` → `UserValidationError` mapping pattern.
- `CognitoPresenter.ts` duplicates its own try/catch/finally error-handling block three times almost verbatim (`confirmNewPassword` ~212-237, `confirmTotpCode` ~316-338, `verifyTotpSetup` ~340-362) — same `formLoading`/`message` bookkeeping around a single `confirmSignIn` call, differing only in the error message title.
- `src/admin/presentation/shared/createPasswordValidator.ts` hand-rolls password-policy regex checks (length/lowercase/uppercase/number/symbol) instead of using `@webiny/validation`'s existing `password` rule; this may be intentional since Cognito's policy flags are configurable per-project, but it duplicates logic the dependency already centralizes (low confidence this is avoidable without knowing whether `@webiny/validation`'s rule supports per-flag configuration).

## Dead code
None found with confidence — `federatedIdentityProviders` and `SecurityPermission` (both single-use, admin-only helpers) each have exactly one consumer per codegraph, and all other checked exports (`CognitoIdpConfig`, `CognitoSignInConfig`, `CognitoComponents`, the five admin-user use cases) have live consumers.

## Convention issues
- `src/admin/presentation/Cognito/CognitoPresenter.ts:102-104` declares an inline anonymous object type for `oauthConfig` (`{ Cognito: { userPoolId: string; userPoolClientId: string; loginWith: any } }`, including a bare `any` for `loginWith`) instead of a named interface, violating the "no inline types" convention.
- Minor DI-wiring inconsistency: `DeleteUserUseCase` (`src/api/features/DeleteUser/DeleteUserUseCase.ts:51-55`) constructs its implementation with the verbose `createImplementation({ abstraction, implementation, dependencies })` form, while every sibling use case (`CreateUserUseCase`, `UpdateUserUseCase`, `GetUserUseCase`, `ListUsersUseCase`) uses the shorthand `UseCaseAbstraction.createImplementation({...})`. Cosmetic, but inconsistent within the same feature family.

## Test gaps
- `UpdateUserUseCase` has separate tests for "update profile fields", "update password", and "update when email changes", but no test exercises password and email changed together in the same call — the exact scenario that trips Bug #1, so the regression would not be caught by the existing suite.
- `CognitoIdentityProviderImpl` (`getIdentity`/`isApplicable`/`verifyTokenClaims`, `src/api/features/CognitoIdp/CognitoIdentityProvider.ts`) has no tests at all (confirmed via codegraph: no tests within 3 caller hops) — the code that turns a Cognito token's claims into an admin identity, including the federated-vs-local `external` flag and the `custom:id`/`sub` fallback, is entirely unverified.
- `CognitoServiceImpl` (`src/api/features/CognitoService/CognitoService.ts`) is never exercised directly — all use-case tests substitute `MockCognitoService`, so the real AWS SDK call shapes (attribute names, `ForceAliasCreation: false`, `MessageAction: "SUPPRESS"`) have no regression coverage.
- `CognitoPresenter` (the entire admin sign-in flow: password login, forced new password, TOTP challenge, TOTP setup/QR, password-reset request/confirm, session restore) has no unit tests in the package; the MVP/presenter pattern used elsewhere in the monorepo (e.g. `admin-ui`) is normally covered by presenter-level tests, but none exist here despite this being the most security-sensitive UI code in the package.

## Recommendations
1. Fix `UpdateUserUseCase.ts:99-102` to use `Username.fromUser(originalUser)` (the actual, stable Cognito username) for the password update too, and add a test that changes email and password in the same request.
2. Make the local-database vs. Cognito mutations consistent on failure: either perform the Cognito call first and only commit the local database change after it succeeds, or add a compensating action (delete/re-create/mark-for-repair) when the Cognito call fails in `UpdateUserUseCase`/`DeleteUserUseCase`, and extend `CreateUserUseCase`'s existing rollback to also delete the Cognito user when a post-creation step fails.
3. Address SEC-21 (private security notes) and add presenter-level tests for `CognitoPresenter`'s TOTP/MFA and password-reset flows.
