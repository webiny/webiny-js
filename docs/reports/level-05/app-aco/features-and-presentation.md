# @webiny/app-aco — Features, presentation and dialogs

> Level 5 · commit 19c9ca1b91 · audited 2026-09-26

## Summary

This slice covers app-aco's folder feature layer (DI use cases/repositories/gateways under `src/features/folders`), the newer MobX presenter-based folder tree (`src/presentation/folderTree`), the create/edit/move/delete/set-permissions dialogs (`src/dialogs`), the field/action/column configuration objects (`src/config`), the folder domain model (`src/domain/folder`), the folder context and the public barrel (`src/index.ts`, `src/exports/admin/ui.ts`). Overall the DI wiring (use case → decorators → repository → GraphQL gateway, one class per file) is applied very consistently and is well covered by tests for the use-case layer. The main issues are: the client-side folder-permission cache decorator reproduces the same stale-`inheritedFrom` merge bug documented for `@webiny/shared-aco`'s `Permissions.create` (masked in the common move flow by an immediate full reload, but real), and a large, fully-built presentational `UncontrolledFolderTree` component + its DI feature appear to have no real consumers anywhere in the monorepo even though the underlying `FolderTreePresenter` it was built on top of is now the standard folder view-model reused by app-file-manager, app-headless-cms and app-website-builder.

## Public API

- `FolderTreePresenter` / `FolderTreePresenterFeature` (`src/presentation/folderTree/abstractions.ts`, `feature.ts`) — the MVP presenter that owns the folders cache, tree building, move/create/edit/delete operations and permission checks. Consumed as a DI dependency well beyond this package: `app-file-manager`'s `FileManagerPresenter`, `app-headless-cms`'s `ContentEntriesPresenter` and `NewEntryPresenter`, and `app-website-builder`'s `RedirectListPresenter` and `PageListPresenter` all register `FolderTreePresenterFeature` and inject `FolderTreePresenter` to drive their own folder browsing UI.
- `UncontrolledFolderTree` (`src/presentation/folderTree/FolderTree.tsx:144`) — the reference tree component built on top of the presenter above (drag/drop, confirmation dialogs, sorting, permission-gated drag/drop). Only reference in the repo is its own export barrel and a `.d.ts` under `dist/`; no consuming package imports it (see Dead code).
- Folder feature hooks (`useCreateFolder`, `useUpdateFolder`, `useDeleteFolder`, `useGetFolder`, `useListFolders`, `useListFoldersByParentIds`, `useLoadFolderHierarchy`, `useGetFolderAncestors`, `useGetDescendantFolders`, `useGetFolderLevelPermission`, `useFolderExtensionsFields`) — re-exported from `src/index.ts`; used across `app-file-manager`, `app-headless-cms` and `app-website-builder` (e.g. `useMoveToFolderDialog`, `useGetFolderLevelPermission`, `sortFolders` are imported directly from `@webiny/app-aco` by those packages).
- Dialog hooks (`useCreateDialog`, `useEditDialog`, `useDeleteDialog`, `useMoveToFolderDialog`, `useSetPermissionsDialog`, `useConfirmMoveFolderDialog`) and `AcoConfig`/`FolderActionConfig` (`src/config/AcoConfig.tsx`) — consumed by the same three downstream apps for folder CRUD dialogs and per-folder action menus.
- `FolderDto` / `FolderDtoMapper` (`src/domain/folder/*`) — the read-model handed to every consumer; `hasNonInheritedPermissions`, `canManagePermissions`, `canManageStructure`, `canManageContent` are passed straight through from the server response (or from whatever the cache currently holds) rather than recomputed client-side (relevant to Bugs #1).

## Bugs

**Main-session verification:** the backend equivalent was found unreachable (see level-0 `shared-aco`). This client-side cache effect remains a transient UI inconsistency at most, already masked by the reload.

| 1 | ~~medium~~ low | `src/features/folders/updateFolder/decorators/RepositoryWithPermissionsChange.ts:52-64` | When a folder is re-parented, this decorator recomputes each descendant's permissions in the local cache via `Permissions.create(f.permissions, parentFolder)`, where `f.permissions` is the child's *cached* permissions array (still tagged with `inheritedFrom: "parent:<OLD_PARENT_ID>"` from before the move). `Permissions.create` (`@webiny/shared-aco`) only strips an inherited entry when its marker equals `parent:<the id passed in>`; since the id changed, the stale entry survives the filter and is treated as a folder-owned permission. This is the exact same bug shared-aco's own audit flagged, reproduced here on the client. | User drags folder A (which inherited a permission from its old parent) into folder B. `moveFolder` (`FolderTreePresenter.ts:125-142`) updates A via the use case, which triggers this decorator to walk A's cached descendants and recompute their permissions against A's *new* effective permissions — any descendant whose permissions array still carries an `inheritedFrom: "parent:<A-or-ancestor>"` tag from a stale ancestor keeps that entry as if it were its own override, and `hasNonInheritedPermissions` (untouched by this decorator — see `Folder.ts`) is not recomputed either, so the tree can briefly show a folder as having custom permissions with the wrong entries. This is a client-side UX gap, not a security issue by itself — the actual authorization decision is made server-side when the mutation runs — but it does mean a to-be-rejected move briefly reorders the tree until the error path recovers. | medium |

## Duplication

- `src/presentation/folderTree/FolderTree.tsx` (the new, presenter-driven tree, only ever used in its own test suite — see Dead code) duplicates significant drag/drop and rendering structure from `src/components/FolderTree/List/List.tsx` (outside this slice, the legacy tree actually wired into every dialog): `FolderTree.tsx:226-241` vs `List.tsx:114-128` (16 lines) and `FolderTree.tsx:300-312` vs `List.tsx:157-169` (13 lines). Two parallel tree-rendering implementations exist side by side.
- `src/config/folder/Action.tsx` and `src/config/record/Action.tsx` are near-identical action-menu-item components (`Action.tsx:2-25` and `:31-51`, ~24 and ~21 duplicated lines) — one for folder actions, one for record/content actions, differing mainly in which config registry they read from.
- Three feature hooks reimplement the same "subscribe to `FoldersCache` + subscribe to loading state" boilerplate with `mobx.autorun`: `src/features/folders/listFolders/useListFolders.ts:11-53`, `src/features/folders/loadFolderHierarchy/useLoadFolderHierarchy.ts:13-62`, and `src/features/folders/listFoldersByParentIds/useListFoldersByParentIds.ts:39-55`. All three set up an identical `useState` + two `autorun`-driven `useEffect`s pattern; only the use case they call and the loading-state accessor differ. A shared `useFoldersCacheViewModel(useCase)` helper would remove ~40 duplicated lines.
- `src/components/AdvancedSearch/domain/FilterRepository.ts:72-108` and `FilterMapper.ts:10-38` each contain an internal near-duplicate block (outside this slice's primary folders/permissions focus, noted only because jscpd flagged them inside the audited folder tree).
- Test-only duplication (lower priority): `GetDescendantFolders.test.ts:10-63` and `GetFolderAncestors.test.ts:10-63` share a 54-line near-identical setup block; `UpdateFolder.test.ts` and `ListFoldersByParentIds.test.ts` each have internal repeated setup blocks (per jscpd report).

## Dead code

- `UncontrolledFolderTree` (`src/presentation/folderTree/FolderTree.tsx:144`, exported from `src/presentation/folderTree/index.ts:16`) has no consumers anywhere in the monorepo outside its own barrel/tests — codegraph and a repo-wide grep for `UncontrolledFolderTree` only turn up the definition, its type export, and the compiled `.d.ts` in `dist/`. The component (344 lines) plus its heavily-tested presenter (368 lines + a 704-line `FolderTreePresenter.test.ts`) form a fully built, well-tested folder tree that nothing renders; every real consumer (`app-file-manager`, `app-headless-cms`, `app-website-builder`) injects `FolderTreePresenter` into its own bespoke view components instead of using this one. Worth a decision: either wire it in somewhere (it looks intended to eventually replace `components/FolderTree`) or remove the component/tests and keep only the presenter, which is genuinely load-bearing.
- `src/presentation/folderTree/FolderTreeFieldRenderer.tsx` renders the *legacy* `components/FolderTree` (imported from `~/components/FolderTree/index.js`, `FolderTreeFieldRenderer.tsx:4`), not the presenter-based `UncontrolledFolderTree` that lives in the same `presentation/folderTree` folder — despite the name/location suggesting it renders the new tree. This isn't dead code but is a naming/location trap worth flagging alongside the dead-code finding above.

## Convention issues

- DI naming/one-class-per-file conventions (AGENTS.md) are followed consistently throughout this slice — every `*Impl` class matches its exported abstraction name and each use case/repository/decorator/gateway lives in its own file.
- `src/index.ts` re-exports essentially everything under `features/folders/*` (all `use*` hooks) and all of `config`, `contexts`, `hooks`, `dialogs` via `export *`, rather than a curated public surface — this is closer to "export everything" than the "minimal barrel exports" convention, though in practice most of it is genuinely consumed by the three downstream apps identified above, so the barrel is broad but not obviously wrong.

## Test gaps

- `src/dialogs/*` (create/edit/delete/move/set-permissions dialogs, `ParentFolderField`, `UsersTeamsSelection` and friends) has zero test files — none of the move/delete confirmation flows or the set-permissions dialog's user/team selection logic is covered.
- `src/config/*` (AcoConfig, folder/record `Action.tsx`, advanced-search `FieldRenderer`, `DropConfirmation`, table `Column`/`Sorting`) has zero test files.
- `src/domain/folder/*` (`Folder`, `FolderDto`, `FolderDtoMapper`, `FolderIdentity`, `RootFolder`) has no dedicated unit tests; mapping correctness (e.g. the pass-through of `hasNonInheritedPermissions`/`canManage*` flags noted in Bugs #1) is only exercised indirectly through other features' tests.
- `RepositoryWithPermissionsChange` and `RepositoryWithPathChange` (the two decorators responsible for cascading cache updates to descendants on move) are not covered by `UpdateFolder.test.ts` — that suite exercises the base update flow but not the recursive children-permission/path cascade, so the stale-`inheritedFrom` bug in Bugs #1 has no regression test.
- `UncontrolledFolderTree`/`FolderTree.tsx` itself has no component-level test (only the presenter is tested), consistent with it not being used anywhere yet.

## Recommendations

1. Fix `RepositoryWithPermissionsChange` (`src/features/folders/updateFolder/decorators/RepositoryWithPermissionsChange.ts:52-64`) to strip any `inheritedFrom` marker referencing an ancestor no longer on the folder's path (not just the immediate new parent id) before recomputing descendant permissions, and add a regression test that moves a folder with a deeper permission-inheritance chain and asserts the cache (not just the post-reload server state) is correct.
2. Resolve the `UncontrolledFolderTree` situation: either adopt it as the tree UI for at least one of its intended call sites or delete the unused component and its 700-line test file, keeping only `FolderTreePresenter`/`FolderTreePresenterFeature`, which are the parts every downstream package actually depends on.
3. Extract the shared "cache items + loading state via autorun" pattern out of `useListFolders`, `useLoadFolderHierarchy` and `useListFoldersByParentIds` into one helper, and consolidate `config/folder/Action.tsx` / `config/record/Action.tsx` behind a shared component parameterized by config registry.
