# @webiny/app-admin — Form model

> Level 3 · commit 19c9ca1b91 · audited 2026-09-26

## Summary

`packages/app-admin/src/features/formModel` (~12.6k lines) is a self-contained, MobX-backed form/model
framework used to build the admin app's dynamic content-editing forms (headless CMS content forms,
settings screens, etc.): a fluent `FieldBuilder`/`ObjectFieldBuilder` DSL registers typed fields
(text, number, boolean, date, file, object/list, and extension-defined types) into a `FormModel`
instance, which owns value storage, required/computed/visibility rules, a layout DSL (rows,
separators, tabs, nested objects with templates), and validation (per-field `required` + Zod
schema + form-level rules). This is a full, independent reimplementation of form and validation
logic rather than a consumer of the lower-level `@webiny/form` (MVP `Form`/`Bind` component) or
`@webiny/validation` (string-rule `Validation` class) packages — neither is imported anywhere in
this folder. The architecture is coherent and heavily tested (two ~450–4400 line test suites
covering rules, builders, and form behavior), but the validation-result cache has a real
correctness gap around conditional-required fields, and one layout-builder feature (tab
reordering at initial-build time) is a silent no-op.

## Public API
- `FormModelFactory` (DI abstraction, `FormModelFactory.ts`) — creates `FormModel` instances; the primary entry point re-exported as `webiny/admin/form` and consumed by `app-headless-cms` (content model forms), `app-aco`, `ai-powerups`, and multiple `extensions/*` packages (e.g. `extensions/customFormFieldType/MonthFieldType.ts` extends `FieldBuilder` directly).
- `Field` / `ObjectField` (`Field.ts`, `ObjectField.ts`) — the runtime field implementations (`IField`/`IObjectField`), exported for extension authors building custom field types.
- `FieldBuilder`, `IFieldBuilder`, `IObjectFieldBuilder` and the whole `abstractions.ts` type surface — exported wholesale from `index.ts`; this is the DSL consumers use to define fields/layouts (`fields.text()`, `layout.row()`, `layout.tabs()`, `layout.object()`, etc.).
- `FormView`, `FormErrors`, `PresenterErrors`, `createFieldRenderer`/`createObjectFieldRenderer`, `useFieldRenderers`/`useLayoutRenderers` — the React rendering layer, consumed by every screen that hosts a generated form.
- `ConditionRuleEvaluator` — the built-in `IRuleEvaluator` for `hidden`/`disabled` conditional rules based on another field's value; `app-headless-cms`'s access-control rules use a separate custom evaluator with `type: "accessControl"`.

## Duplication
- Within this slice: `ObjectField.ts:908-921` (list-schema `safeParseAsync` check) and `ObjectField.ts:923-936` (object-schema `safeParseAsync` check) are near-identical blocks (jscpd: 14 lines) that could share a small helper.
- `LayoutResolver.ts` self-duplicates the tabs-resolution logic: `resolveTabsNode` (lines 99-151) and `resolveChildNode`'s tabs branch/`resolveChildTabsNode` (lines 169-250) are structurally the same walk (evaluate rules, resolve tab visibility, compute `hasErrors`, track `activeTabId`) once for the top-level `_fields` map and once for a child `Map<string, IField>`; likewise `resolveRowNode`/`resolveObjectNode` duplicate `resolveChildNode`'s "row"/"object" cases almost verbatim. jscpd flags the two internal 9–26 line clones at `LayoutResolver.ts:68-79`/`173-181` and `99-153`/`204-252`.
- `FieldBuilder.ts`'s `createFieldBuilderRegistry()` (lines 235-251) and `FieldBuilderRegistry.ts`'s `FieldBuilderRegistryImpl` (lines 8-28) both independently implement the same "Proxy over a `Map<type, IFieldTypeFactory>`" pattern to build a field-builder registry. Only the DI-registered `FieldBuilderRegistry` is actually wired up (`feature.ts`); see Dead code.
- `FormModel.ts:211-219`/`58-65` (a 9-line internal clone, jscpd) and `FormModel.ts:475-481` vs `LayoutBuilderFactory.ts:473-479` (7-line clone in the recursive builder-collection code) are minor structural repeats of the "iterate map/record entries, skip non-object builders" pattern already visible in `LayoutBuilderFactory.collectBuilders`/`collectBuildersFlat`.
- The `demo/` folder (`FormModelDemo.tsx`, `FormModelDemoPresenter.ts`, `FormModelPhase8c1Presenter.ts`, `FormModelPhase11Presenter.ts`, `FieldRenderersDemoPresenter.ts`) accounts for the bulk of jscpd's remaining hits in this slice (~11 of 20), including a 67-line clone inside `FormModelDemo.tsx` itself. This is scratch/demo code exercising the framework, not production logic, so it's lower priority, but worth trimming or consolidating since it roughly triples the amount of code an unfamiliar reader has to skip past to find the real model.
- No reuse of `@webiny/validation`'s `Validation` class for the `required`/basic checks in `Field.ts:539-560` and `ObjectField.ts:882-906` — both hand-roll an "is empty" check (`null`/`undefined`/`""`/empty array) that duplicates logic already centralized in `@webiny/validation`'s `required` rule (per its level-0 summary). Given the framework's Zod-based design this may be an intentional simplification rather than an oversight, but it is a second, subtly-different definition of "empty" living in the codebase.

## Dead code
- `createFieldBuilderRegistry` (`FieldBuilder.ts:235`), exported from the package barrel (`index.ts:92`), has zero consumers repo-wide (grep across `packages/` and `extensions/` found only its own definition and re-export) — the DI-registered `FieldBuilderRegistry` (`FieldBuilderRegistry.ts`) is what `feature.ts` actually wires up and what every consumer receives via `container.resolve`.
- `LayoutMutator.createModifierAPI`'s `tabs()` handle (`LayoutMutator.ts:36-50`) accepts `config.id` and builds an `ITabsNode`, but `LayoutMutator.removeFromLayout`/`nodeMatchesTarget` only match a tabs node by `node.id === target` (`LayoutMutator.ts:119`, `171`) — consistent, but note this means a tabs node added via `layout(factory)` modifications without an explicit `id` can never be targeted for removal or reordering later (`LayoutBuilderFactory.tabsNodeKey` is only used for the *active-tab* observable map key, not as a removable target). Not verified as unused by any current caller, so listed as a design gap rather than confirmed dead code.

## Convention issues
- Barrel export breadth: `index.ts` re-exports essentially the entire `abstractions.ts` type surface (60+ named types) plus every concrete class. Given this package is meant to be an extensible DSL for building custom field types (as `extensions/customFormFieldType/MonthFieldType.ts` does), broad exports are largely justified, but `createFieldBuilderRegistry` (dead, see above) and the `@deprecated` aliases `IRowNodeHandle`/`ITabsHandle`/`ITabHandle` (abstractions.ts:430-431, 650-654) are exported without any internal or external consumer, which is at odds with the "minimal barrel exports" convention.
- `ObjectField.fields()` (`ObjectField.ts:538-542`) does `this.config.childBuilders[name] = undefined as unknown as IFieldBuilder; delete this.config.childBuilders[name];` — assigning `undefined` immediately before `delete`-ing the same key is redundant (the assignment has no observable effect); harmless but reads like leftover code from an earlier version.

## Test gaps
- No test exercises the interaction covered by Bug #1: a `requiredWhen` dependency changing while the dependent field's own value stays constant, followed by a non-forced (blur) `validate()` call. The existing "validation memoization" suite (`FormModel.test.ts:3739-3814`) only varies the field's *own* value/`resetValidation()`, not a cross-field required-state change.
- No test calls `.before()`/`.after()` on the tabs builder returned by `layout.tabs(id)` at initial-layout-build time (only on `TabsAccessBuilder` via `form.layout(id).as("tabs")`), which is why Bug #3 (silent no-op) was never caught.
- `ConditionRuleEvaluator`'s `"matches"` branch (Bug #2) has no direct unit test with `type: "condition"`; the only `"matches"` tests in `Rules.test.ts` exercise a custom `accessControl` evaluator, not `ConditionRuleEvaluatorImpl` itself.
- `LayoutMutator.ts`, `LayoutResolver.ts`, and `FocusManager.ts` have no dedicated unit test files; their behavior is only indirectly exercised through `FormModel.test.ts`'s layout/focus-related `it()` blocks, so edge cases inside their private helpers (e.g. `LayoutResolver.childTabHasErrors` recursing into nested tabs, `FocusManager.diveIntoObjectNode`'s per-template `inner` resolution) rely on whatever the higher-level tests happen to hit rather than targeted coverage.

## Recommendations
1. Fix the validation-cache key in `Field.ts` to also account for the current `resolveRequired()` result (or simply always pass `force: true` from `vm.onBlur` once the form has been submitted, matching the existing "revalidate after submit" intent) — this is the one confirmed, user-visible correctness bug (Bug #1).
2. Either implement real reordering in `TabsBuilder.before`/`.after` (`LayoutBuilderFactory.ts:141-147`) to match `TabsAccessBuilder`'s behavior, or remove the methods from the initial-build `ITabsBuilder` surface so the API doesn't silently promise something it doesn't do (Bug #3).
3. Delete the unused `createFieldBuilderRegistry` export (and its barrel re-export) now that `FieldBuilderRegistry`/DI is the one true implementation, and decide `ConditionRuleEvaluator`'s `"matches"` semantics (implement regex matching or drop the operator from `RuleOperator`) before anything starts relying on it.
