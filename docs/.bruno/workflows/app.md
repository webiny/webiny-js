# Workflows: admin UI (app-workflows)

Notes for `packages/app-workflows` and how the CMS and WB admin packages consume it. Everything below describes the code as built in phases 8a, 8b, 9a and 9b (2026-10-16 to 2026-10-18, D157-D177); section 3 is the workflow editor of 9a and 9b. The 2026-10-01 discovery notes on the old editor went with it.

Path roots:

- `[AW]` = `packages/app-workflows/src`
- `[CMS]` = `packages/app-headless-cms-workflows/src`
- `[WB]` = `packages/app-website-builder-workflows/src`
- `[API]` = `packages/api-workflows/src`
- `[AWE]` = `[AW]/editor` (the 9a workflow editor; `[AW]/review/editor` is the 8a review session)

## 1. Layout, entry points, registration, gating

- Layout of `[AW]`:
  - The workflow editor, `editor/` (section 3), and the shared `components/picker/` (`WorkflowPicker`, `WorkflowMultiPicker`, `PickerOption`, `limitPickerOptions`).
  - The permission code that stays: `domain/permissionsSchema.ts`, `features/permissions/`, `presentation/permissions/` (the old editor's `hooks/canUseWorkflows.ts` was deleted with it).
  - The shared review core, `review/`: `domain/` (types, enums, error codes, constants, pure functions), `gateway/` (the gateway interface `IReviewGateway`, DTOs, field fragments, mappers), `useCases/` (the use-case interfaces and the one implementation `ReviewUseCases`), `events/`, `cache/`, `activity/`, `toasts/`, `notifications/`, `content/` (the content adapter interface), `presentation/{targetReview,actionDialog,reviewerPicker,requestReview,reviewDetails,reviewList,reviewWidget}/`, `editor/` (editor session and `EditorReviewBar`), `mounting/` (row provider, notification handler, route, menu and widget components), `trash/` (block collector, guard, warning presenter and dialog), `testing/` (fixtures and fakes), `feature.ts`.
- Mounting: `packages/app-serverless-cms/src/Admin.tsx` renders `<WorkflowsAdminApp/>`, `<CmsWorkflows/>`, `<WebsiteBuilderWorkflows/>` in that order, so the shared features are registered before the app features resolve them.
- All three roots return `null` unless `featureFlags.isEnabled("advancedPublishingWorkflow")` (tied to the licence). `WorkflowsAdminApp` registers the permissions, editor and shared review features and `SecurityPermissions`; it has no review route, menu or widget of its own.
- Public API (`[AW]/index.tsx`): `WorkflowsAdminApp`, `useWorkflowsPermission` and `WorkflowsPermissionsFeature` (nothing else; the old editor's exports went with it in 9a). Phases 8a and 9a add nothing to this barrel: the review core (use-case and gateway types, `ReviewUseCases`, `EditorReviewSession`, `EditorReviewBar`, `ReviewListView`, the widgets, the mounting components, `AppReviewRowProvider`, `ReviewNotificationHandler`, `ReviewCacheSyncHandler`, `ActiveReviewGuard`, ...) is imported by deep `.js` paths (every admin package exports `"./*": "./*"`); the editor (`WorkflowEditorRoute`, `WorkflowEditorMenu`, `WorkflowEditorView`, `WorkflowEditorAppAdapter`, the editor use-case interfaces) is imported the same way by the CMS and WB packages.
- Routes: none in `[AW]`. The editor routes are per app (`/cms/workflows` in `[CMS]`, `/website-builder/workflows` in `[WB]`, each shown only when `useWorkflowsPermission().editor` is true), and so are the Content Reviews routes: `Routes.ContentEntries.ContentReviews` (`/cms/content-reviews`, `[CMS]/routes.ts`) and the Website Builder one in `[WB]/routes.ts` (`/website-builder/pages/content-reviews`; its key is a historical name). Permissions: `createPermissionSchema({ prefix: "workflows", fullAccess: { editor: true } })` (`[AW]/domain/permissionsSchema.ts`), shown through `Security.Permissions`.

- Permissions in the admin (8b, D162): `getWorkflowsPermissionSet(identity)` (`[AW]/review/domain/getWorkflowsPermissionSet.ts`) returns `{ fullAccess, editor, reassign }` (`fullAccess` is `workflows.*` or `*`; several roles combine). `useWorkflowsPermission` returns `{ editor, reassign }` over it; `IWorkflowsSecurityPermission` is `{ name, editor?, reassign? }` and `WorkflowsSecurityPermissionAccessLevel` is gone (the stored values are booleans, the old comparison with the enum was a bug). Presenters read the identity through `IdentityContext`. The server keeps every check; these are display gates (the Failed steps tab, the Background task link).

## 2. Architecture pattern

- DI: `@webiny/feature/admin` `createAbstraction` / `createFeature`, `X.createImplementation({ implementation, dependencies })`. Gateways call `MainGraphQLClient` (`@webiny/app/features/mainGraphQLClient/abstractions.js`). No Apollo.
- Layering (D159): shared presenters and components depend on use-case interfaces (`IReviewUseCases` and its parts) and never on a gateway; the one `ReviewUseCases` class calls an app's gateway through `IReviewGateway`. Each app registers `<App>ReviewGateway`, `<App>ReviewUseCases` (a per-app subclass of the shared class, `<App>ReviewUseCasesImpl`, bound to its gateway, singleton, own workflow cache; the shared class is never bound itself) and `<App>ReviewContentAdapter` under its own tokens (`Cms/Workflows/...`, `WebsiteBuilder/Workflows/...`, `Wb/Workflows/ReviewContentAdapter`). Shared presenters receive `useCases` as an `init(...)` argument; app glue resolves its token and passes it in. The editor follows the same rule (9a): the shared `WorkflowEditorUseCases` class (R237) is subclassed per app (`CmsWorkflowEditorUseCasesImpl`, a WB mirror), and the view receives `useCases`, `reviewUseCases` and the app's `WorkflowEditorAppAdapter` as props and passes them to `WorkflowEditorPresenter.init`.
- Presenters: MobX `makeAutoObservable`, a `vm` of render-ready values only, transient (a new instance per `useFeature` resolve) so two views never share state; components are `createReactiveComponent`.
- Errors: gateways return the `{ data, error }` envelope; `ReviewUseCases` throws `GraphQLOperationError` (`@webiny/app/errors/GraphQLOperationError.ts`, code, message, data) and presenters map it by code ("Someone else acted first", field errors, no access, transport failure).
- Events and cache: `ReviewChangedEvent` (`workflows.review.changed`) after a target review loads; the app's `<App>ReviewCacheSyncHandler` (a subclass of the shared `ReviewCacheSyncHandler`) hands `toSystemWorkflow(review)` to the app's cache writer (`CmsReviewCacheWriter`, `WbReviewPageCacheWriter`) so the content lists show the review state. A writer updates only the review's own revision.
- Live updates: `ReviewActivity` signals `{ namespace, source, reviewId, targetRevisionId }` (the two ids are `null` when the caller has none). Own actions, every incoming `workflows.notification` (`ReviewNotificationHandler` per app, `ReviewNotificationService`, with a toast) and every silent `workflows.reviewChanged` (`ReviewChangeMessageHandler`, a shared plain class in `[AW]/review/mounting/`, subclassed per app as `CmsReviewChangeMessageHandlerImpl` and `WbReviewChangeMessageHandlerImpl`; source `remote`, no toast) notify it. Lists and widgets refetch once per signal of their namespace, and a signal that arrives during a load is queued and applied once after it. `TargetReviewPresenter` (the bar) refetches on a signal for its review or its revision and `ReviewDetailsPresenter` (the drawer) on one for its review (it subscribes after its first successful load, because its init params carry no namespace; a failed first load does not subscribe and Try again subscribes on success, and an action taken in the drawer refreshes the bar only through the signal, its `onChanged` stays for conflicts); both ignore a signal raised by their own `notify` call, so their own action refreshes once, and both keep at most one refetch queued during a load. A later `init` or `dispose` drops the subscription. No polling (D160).
- Toasts: `ReviewToasts` and `ReviewNotificationService` use the admin `Notifications` stack with link, duration, position, dismissible and the error variant.
- Extensibility: decorators on each app's extension points (editor components, `ContentEntryFormPresenter`, list field selections and row mappers, the delete use cases), each point decorated once.
- Tests: fixtures and fakes are in `[AW]/review/testing/` (imported as `@webiny/app-workflows/review/testing/...` by the app packages); all three packages have jsdom vitest setups; the review core, the editor and the app packages are covered. The editor's pure builders and vitest fakes are in `[AWE]/testing/`. The shared `review/testing` helpers cover the 8b views: `createWorkflowsIdentityContext` (a test identity with teams and permissions), `at` (one clock for the view tests), `createRunningAiStep`, `createRunningAutomationStep` and `createFailedAutomationStep` (in `createAutomatedStep.ts`), `createStepRunInfo` and `createStepRunInfoDto` (in `reviewFixtures.ts`), and `createFakeActivity` (a fake activity bus).

## 3. Workflow editor (9a and 9b, as built)

The editor of 9a replaced the discovery-era one (deleted in 9a, D168). `[AWE]` is `[AW]/editor`; `[AW]/review/editor` is the unrelated review session of 8a.

- Mounting and gate: `WorkflowEditorView` (`[AWE]/presentation/editor/components/`) is one shared view. The route and the menu item are written once in `[AWE]/mounting/components/` (`WorkflowEditorRoute`: `AdminConfig.Route`, layout, title "Workflows", breadcrumbs, the view; `WorkflowEditorMenu`: the pinnable "Workflows" menu link); both render nothing without the `editor` permission (`useWorkflowsPermission().editor`, D162) and there is no `SecureRoute`. Each app adds a mount component (`CmsWorkflowEditor` in `[CMS]/Routes/`, `/cms/workflows`; `WebsiteBuilderWorkflowsMenu` in `[WB]/Routes/`, `/website-builder/workflows`) and a mounting feature in `features/editorMounting/` (`CmsWorkflowEditorMountingFeature`, `WbWorkflowEditorMountingFeature`) whose `resolve` returns `{ useCases, reviewUseCases, app }`; these are passed to the view as props and on to `WorkflowEditorPresenter.init`. The server keeps its checks. Without the `advancedPublishingWorkflow` flag nothing is registered; the editor features are registered in `[AW]/app.tsx` (`WorkflowEditorServicesFeature`, `WorkflowEditorPresenterFeature`, `StepDrawerPresenterFeature`, `WorkflowEditorConfig`).
- `WorkflowEditorAppAdapter` (`[AWE]/WorkflowEditorAppAdapter.ts`) is what differs per app: `{ appKind: "cms" | "wb", panelLabel, appliesToLabel, init(), renderModelIcon(modelId), contentAdapter }`. The CMS adapter (`CmsWorkflowEditorAppAdapter`, `[CMS]/features/editorMounting/`; `panelLabel` "Content models", `appliesToLabel` "Headless CMS model"; its `init` swallows a failure, the icon is cosmetic) lists the models once into the admin `ModelsCache` in `init()` and renders the icon through the CMS icon component (`app-workflows` has no icon library); the WB adapter's `init()` is a no-op and its `panelLabel` is `Website Builder` (shown uppercase by the panel's style). `contentAdapter` is the app's existing `IReviewContentAdapter`, used to link the reviews of the blocked-delete dialog. 9b adds `getFolderType(modelId)` (CMS `cms:<modelId>`, WB `wb:page`) and `listFolders(modelId)` returning `AppFolder { id, path }` (the folders the admin can see, root excluded, `/A/B` paths built from titles); the CMS and WB adapters implement them over `ListFoldersGateway` of `@webiny/app-aco`, registered through `ListFoldersGqlGateway` in each `features/editorMounting/feature.ts`. `app-workflows` never imports `app-aco` (D173).
- Gateways and use cases: `IWorkflowEditorGateway { listModels, getWorkflow, storeWorkflow, deleteWorkflow }` per app (`[CMS]/features/editorGateway/` over the `cms` root, `[WB]/features/editorGateway/` over `websiteBuilder`; the WB `listModels` returns the single `wb.page` row `Pages` with its bound workflow from `listWebsiteBuilderPageWorkflows`). The shared `WorkflowEditorUseCases` (`[AWE]/useCases/`, a plain class, R237) maps the gateway's DTOs to the domain types (`EditorWorkflow`, `EditorStep`, `WorkflowModelRow`, ...) and throws `GraphQLOperationError` for an envelope error. The shared configuration operations run through one `WorkflowConfigGateway` and `WorkflowConfigUseCases` (tokens, one implementation each, `[AWE]/gateway/` and `[AWE]/useCases/`, over `MainGraphQLClient` on the `workflows` root): `listStepTypes`, `listAutomationDefinitions`, `listNotificationTransports`, `listTeams`, `listAiModels` and `listAiTools` (the last two are called only when the AI type is available). 9b adds `inspectRouting(params)` and `folderExists(params)` to the per-app gateway and use cases (CMS sends the bare model id; WB ignores `modelId` and the folder type) and `listUsers({ search, ids, teamIds, limit })` to the shared `WorkflowConfigGateway` and `WorkflowConfigUseCases` (D170, D172). The shared `WorkflowEditorUseCases` class carries the new methods and the per-app subclasses inherit them (R237).
- Domain and model: `[AWE]/domain/` holds the types, `WorkflowErrorCode` (`NotFound`, `Conflict`, `Validation`, `Persistence`, `HasActiveReviews`, `NotAuthorized`) and `stepColours.ts` (ten theme presets stored as CSS variable strings, D169). `[AWE]/model/WorkflowDraft.ts` is the MobX draft (name, steps, baseline; `isDirty`; a draft for a new workflow has no baseline and is dirty; `toInput()` emits the review defaults, keeps unknown transport ids, unknown AI tools and `assignment`); next to it are the pure helpers `createNewStep`, `validateWorkflowDraft` (the client rules of R276), `getStepTypeOptions` (availability, with `matchesAutomationScope` mirroring the server's scope rule `*`, `<app>.*`, exact namespace), `getStepSummary` and `getStepWarnings`. The draft stays inside the presenters; the view gets render-ready VMs (R234). 9b adds the typed assignment (`[AWE]/model/assignment/`: `AssignmentValue`, `RuleValue`, `RuleFolderValue`, `RuleTargetValue`; `readAssignment`, `assignmentToConfig`, which keep every key the editor does not edit in `preserved`), `createRuleId`, the rule helpers (`[AWE]/model/rules/`: add, move, remove and update a rule, `getReferenceLabel`, `describeRule`, `getRuleIssues`), `getStepErrorTab`, and the Test routing composer (`[AWE]/model/testRouting/`: `composeTestRoutingResult`, `getTestRoutingSignature`). `validateWorkflowDraft` adds the rule target errors (D174), `getStepSummary` names the strategy, the rule count and the requester pick, and `getStepWarnings` adds the `Rule {n}: ` lines and the teams-off line.
- Presenters: `WorkflowEditorPresenter` (`[AWE]/presentation/editor/`) owns the model list (search debounced 250 ms, 20 per page for the CMS, Load more), option loading (a failure shows the banner "Could not load the step options." with Try again), the draft, the dialogs (`vm.dialog`, one render-ready kind at a time) and the banners, and resolves the team ids of a loaded workflow with one `listTeams({ ids })`. While a save is in flight `setName`, `updateStep`, `addStep`, `moveStep` and `deleteStep` do nothing (the view disables the controls). The editor presenter owns `openStep`, `closeStep`, `vm.openStepId` and `vm.scrollRequest` (the step to scroll to after a failed save; adding a step opens it). The step drawer has its own presenter (`StepDrawerPresenter`, `[AWE]/presentation/stepDrawer/`) that reads the editor presenter through `StepDrawerSource`; closing by Done, X, Escape or the scrim keeps the edits, and an unfinished hex keeps the old colour (only Done is blocked by it). The drawer: one FormModel form per step (`[AWE]/presentation/stepForm/`: `buildCommonFields`, `buildPeopleStepForm`, `buildAutomationStepForm`, `buildAiStepForm`), a server error on a field or at the top of the drawer until the step is edited, Done applies the form to the draft, and a step of an unknown type opens read-only. 9b: the editor presenter resolves the saved user, team and folder ids of rules (users in chunks of 200, rule teams, folders from the adapter's list then `folderExists`; a run token drops stale responses; a failure shows the banner "Could not load the step options." with Try again), loads the user, member and folder options, exposes `getModelId()`, `inspectRouting` and the inspection name lookup, and maps rule errors by `ruleId` in `mapSaveError`. The drawer presenter holds the People assignment, the tabs (`showErrorTab`, opening on the tab of an error), the live rule issues, the `Check this step` warnings, the teams-off read-only state and the Test routing state of the open step (a run token, a signature taken when the request is sent, cleared when another step opens).
- Save and errors (R276, D165): the store mutation carries the loaded `savedOn` string unchanged (null for a new workflow and for Save as new). `mapSaveError` maps the result: a `Validation` error with a `stepId` marks that step and field; `name` or `steps` mark the name input or the "No steps yet" box; a `workflowId` reads the other workflow's name with `getWorkflow` and shows the duplicate banner with Reload (the CMS says "{Model} already has a workflow", the WB "Pages already have a workflow"); `Conflict` opens "Someone else changed this workflow"; `NotFound` opens "This workflow was deleted" (Discard changes, Save as new workflow); a transport error shows the banner "Could not save the workflow" with Try again. The draft stays dirty after every failure. After a save and after a delete the presenter calls `reviewUseCases.invalidateWorkflows()` (R277), which clears the shared `ReviewUseCases` cached workflow list including a pending load. Delete maps `HasActiveReviews` to the blocked dialog (count, up to five reviews linked through `contentAdapter.getContentUrl`, the closing sentence by the viewer's `reassign`).
- Step forms and renderers: the field renderers are registered by the JSX config component `WorkflowEditorConfig` (`AdminConfig.Form.FieldRenderer` entries, mounted in `WorkflowsAdminApp`): `StepColourRenderer`, `TeamsPickerRenderer`, `TransportCheckboxesRenderer`, `AutomationCardsRenderer`, `AiModelPickerRenderer`, `AiToolsRenderer`. They read their option VMs (items, `loading`, `failed`, `retry`) from `StepFormOptionsContext`, which the drawer provides from the presenter's data. The Automation settings form is generated by `buildFieldsFromJsonSchema` from `@webiny/app-admin` with `uiRenderers: { team: <the teams picker renderer> }`; stored settings are checked with `createJsonSchemaValidator`, and the card shows "Saved settings no longer validate: {error}" only while the admin has not changed them in the session. The pickers are the shared `WorkflowPicker` and `WorkflowMultiPicker` (`[AW]/components/picker/`): at most 50 visible options then "More matches. Keep typing to narrow the list.", an unknown selected id as "Unknown item", and a per-option warning. 9b: a People form has the FormModel layout tabs General, Assignment and Test routing; `assignment` is a form object with `strategy`, `allowManualPick` and `rules`, where `rules` is a plain-JSON array field edited by `RoutingRulesRenderer` (its cards are under `renderers/routingRules/`); the strategy cards are `AssignmentStrategyRenderer` over the stock `RadioGroup`; the Test routing tab is the layout element `workflowTestRouting` (`TestRoutingRenderer`, under `renderers/testRouting/`), which reads its data from `StepFormOptionsContext`; `UserPickerRenderer` and `FolderPickerRenderer` serve the rule fields and the Automation `user` hint. The shared `PickerOption` gained `muted`, `disabled` and `icon`, and `WorkflowPicker` the `anyLabel` clear row.
- Cards, drawer and dialogs: `WorkflowFlow` and `StepCard` (reorder by drag through the admin `SortablePresenter`, registered by the admin's `SortableFeature`, or by the up and down buttons; a keyboard move restores focus to the moved card and announces "Step moved to position {position} of {total}." in a polite live region), `StepTypePicker`, `StepDrawer` (560 px), the dialogs under `components/dialogs/` (destructive actions use the admin-ui `Button` `destructive` variant, added in 9a), the banners under `components/banners/` and toasts through `IWorkflowEditorToasts` (`[AWE]/toasts/`, over the admin `Notifications`, D125; the 8a `ReviewToasts` stays review-only). `useLeaveGuard` registers `useRouter().addTransitionGuard` once (the `ContentModelEditor.tsx` pattern; its guard returns true only while the draft is dirty) and a `beforeunload` listener only while the draft is dirty.
- Known limits: model rows carry no step count (QBZ-20 forbids counts per row), so the sub line of an unopened bound model is the bound workflow's name. Deviations from the design in 9b: a new rule targets the pool of the first reviewing team, not its first member (that needs a member lookup before the card appears); a tab with an error shows FormModel's asterisk after the label, not the design's dot; picker rows have an icon column but no avatar and no right-hand note; a rule with a condition the editor cannot show (`modelId`, unknown keys) reads "... and other conditions". Read access and exclusions are shown only by Test routing. The automation cards use `RadioGroup` and the AI tools list `CheckboxGroup` again (9b closed the 9a gap, D177).

## 4. Content review flows (as built)

- Editor session: one `IEditorReviewSession { presenter, useCases }` per app (`CmsEntryReview` with `CmsEntryReviewImpl`, `WbPageReview` with `WbPageReviewSessionImpl`; both subclass the shared `EditorReviewSession`), singleton, reset on `dispose()`; `EditorReviewBar` renders `ReviewBar` and the details drawer. The CMS form presenter decorator (`CmsEntryFormPresenterReviewDecorator`) and the WB top bar, layout, autosave and publish button (`PageEditorTopBar`, `PageEditorLayout`, `PageEditorAutoSave`, `PageReviewPublishButton`) init the presenter for the open revision and apply `allowsEditing` / `allowsPublishing`.
- `TargetReviewPresenter` statuses: `loading | failed | noWorkflow | none | active`; actions come from the server's `flags`. Dialogs (start, take over, approve, reject, cancel, reassign) load the review by id and share `ReviewActionDialogPresenter`; each takes an optional conflict callback so its host (bar, drawer, list) refreshes, and a dialog opened from Content Reviews ends a conflict with "The list has been refreshed.". The request dialog (`RequestReviewPresenter`) previews the steps and takes picks; `ReviewDetailsPresenter` drives the drawer.
- Lists: `ReviewListPresenter` over `IReviewListUseCases` and an `IReviewRowProvider` (app-neutral rows, per-namespace link and actions); `ReviewListView` has up to five tabs (Assigned to me, Team pool, Team in review, My requests, and Failed steps for viewers with `reassign` or full access; `?tab=failedSteps` without the permission opens the default tab), filters, sorting by last change, load more and the live-update notice; widgets: `ReviewWidgetPresenter` with `ReviewForMeWidget` and `ReviewMyRequestsWidget` (names `workflows.{cms,wb}.{review,requested}`). The Content Reviews menu item is the shared `ReviewContentReviewsMenu` (wrapped in `AdminConfig`, name `workflows.{cms,wb}.contentReviews`).
- Trash and delete: `ActiveReviewGuard` (`run`, `runBulk`) with `ActiveReviewBlockCollector` and `ActiveReviewWarningDialog` (a named dialog); each app's `features/trash` decorates its delete use cases and the bulk delete presenter (D157). For the CMS bulk trash of all loaded rows the bulk decorator asks `listBlockingReviews` per chunk of 200 entry ids first and shows the warning through `ActiveReviewGuard.confirmBlocking` (D164); `runBulk` is built on it. The base `BulkDeletePresenter.execute` reports whether the background task started (Q39): the trash action's toast and deselection follow only `true`, and a failed pre-check shows the error toast.
- Restart (8b): the action kind `restart` (label Restart, icon `refresh`) is offered from the server flag `canRestart` in the bar, the drawer and the Content Reviews row; `ReviewActionDialogPresenter` calls `restartStep`, shows the toast "Restarted “{Step}”" and treats `Workflows/Review/TargetSync` as a success with a refresh; `getConflictMessage` has a restart branch for a step someone else already restarted. `getRestartDialogBody` builds the dialog text from the step's `finishedOn` and `comment` and drops one trailing "." of the server reason before " Restarting runs the step again from the beginning.". `isStepRunning(step)` (in review with a non-user owner) drives the running messages and tags and the cancel dialog's running suffix.
- Drawer additions (8b): `getAttempts` and `getAiIssues` build the `Attempts` and `Issues reported by the AI` sections; operators get a "Background task" link per attempt, which opens the task panel (`openStepRun`, `closeStepRun`, `getStepRunPanel`) over `getStepRun` (a row without a value is left out, times through `formatReviewTimeFull`).
- Content reload (8b, D163): `TargetReviewInitParams.contentReloader` (`IReviewContentReloader { reload(): Promise<boolean> }`) is built by the app glue: the CMS reloader `CmsEntryContentReloader` (`[CMS]/presentation/CmsEntryContentReloader.ts`, built in `CmsEntryFormPresenterReviewDecorator` over the undecorated presenter's `loadRevision`, skipped while the form is dirty; the form's loading overlay shows briefly during the reload, accepted, Q40), the WB reloader `WbPageContentReloader` (evicts the page from `FullPageCache`, reads it, applies it with `updateDocument`). `TargetReviewPresenter` calls it once when a non-user step stops being in review and sets `vm.contentNotice`, which the shared `ReviewBar` shows as a success strip inside the bar (`EditorReviewBar` is unchanged). The reload is skipped when the presenter was disposed or initialised again during the refresh.

## 5. GraphQL operations

- Per-app review operations live only in the app packages, one document per file: CMS `[CMS]/features/gateway/graphql/` over the `cms` root (`listCmsEntryWorkflows`, `getCmsEntryTargetReview`, `getCmsEntryReview`, `listCmsEntryReviews`, `listCmsEntryStepCandidates`, `listCmsEntryReviewStepCandidates`, `requestCmsEntryReview`, `startCmsEntryReviewStep`, `takeOverCmsEntryReviewStep`, `reassignCmsEntryReviewStep`, `approveCmsEntryReviewStep`, `rejectCmsEntryReviewStep`, `cancelCmsEntryReview`, `cancelCmsEntryReviewsForDelete`); WB `[WB]/features/gateway/graphql/` over the `websiteBuilder` root (the same set with `WebsiteBuilderPage`, no `modelId`). The shared field fragments are `[AW]/review/gateway/reviewFields.ts`.

- Added in 8b: per app `restartCmsEntryReviewStep` and `restartWebsiteBuilderPageReviewStep`, `getCmsEntryReviewStepRun` and `getWebsiteBuilderPageReviewStepRun` (documents in the same folders), and CMS only `listCmsEntryBlockingReviews` (the WB gateway's `listBlockingReviews` returns an empty list, the WB bulk delete runs per item). The fragments `STEP_RUN_INFO_FIELDS` and `BLOCKING_REVIEW_FIELDS` are in `reviewFields.ts`.
- Editor operations (9a), one document per file: CMS `[CMS]/features/editorGateway/graphql/` over the `cms` root (`listCmsEntryWorkflowModels`, `getCmsEntryWorkflow`, `storeCmsEntryWorkflow`, `deleteCmsEntryWorkflow`); WB `[WB]/features/editorGateway/graphql/` over the `websiteBuilder` root (`listWebsiteBuilderPageWorkflows`, `getWebsiteBuilderPageWorkflow`, `storeWebsiteBuilderPageWorkflow`, `deleteWebsiteBuilderPageWorkflow`). The shared fields are `EDITOR_WORKFLOW_FIELDS` (`[AWE]/gateway/editorFields.ts`, including `notifications { id }`, `savedOn`, `createdOn`, `savedBy`, `createdBy`); `savedOn` travels as the string the server returned and is sent back unchanged. The configuration operations of the `workflows` root (`listStepTypes`, `listAutomationDefinitions`, `listNotificationTransports`, `listTeams`, `listAiModels`, `listAiTools`) go through one `WorkflowConfigGateway`.

## 6. Consumer contract

CMS and WB use: `ReviewUseCases` through their own tokens, `EditorReviewSession` and `EditorReviewBar`, the presenters' use-case-typed `init` arguments, `ReviewListView` and the widgets through the mounting components, `ReviewCacheSyncHandler` with their cache writer, `ReviewNotificationHandler` and `ReviewChangeMessageHandler` subclasses with their content adapter, an `IReviewContentReloader` passed to `TargetReviewPresenter.init` as `contentReloader`, `ActiveReviewGuard` (`run`, `runBulk`, `confirmBlocking`), and, for the editor, `WorkflowEditorView` with a per-app `WorkflowEditorAppAdapter` and a per-app subclass of `WorkflowEditorUseCases` (bound to the app's editor gateway), plus `useWorkflowsPermission` for the editor gate. The `system.workflow` shape on content is `{ workflowId, reviewState, stepId, stepName, stepState }` (`SystemWorkflowValue`). Details in `integrations.md`.
