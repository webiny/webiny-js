# Workflows admin layers: presenter, use case, repository, gateway

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The three workflows admin packages (`app-workflows`, `app-headless-cms-workflows`, `app-website-builder-workflows`) follow the Webiny admin convention presenter → `XUseCase` (one class, one `execute()`) → area `XRepository` (DTO ↔ domain mapping and caching) → area `XGateway` (GraphQL call and error conversion). The four multi-method bundles (`ReviewUseCases`, `WorkflowEditorUseCases`, `WorkflowConfigUseCases`, `WorkflowSettingsUseCases`) become 32 use cases, one per operation, that live once in `app-workflows`; the 33rd operation (`invalidateWorkflows`) stops being an operation and becomes a repository call the store and delete use cases make. Only the gateway varies per app: CMS and Website Builder each register an app gateway under one shared multi-registration token, and an app-neutral routing gateway picks it by the review's namespace or the editor's app. Presenters, services and decorators inject exactly the use cases they call; no use case travels through `init()`, props, the Content Reviews row binding or an editor session any more. Users see no change: the same GraphQL documents and variables, the same values, the same errors (class, message, code, data), the same cache and refetch behaviour.

**Architecture:** Five sub-phases, one area at a time (Q75, G15).

1. **L1 Settings** (`[AWS]`): the shared error helper moves to `[AW]/gateway/`; `WorkflowSettingsGateway` throws; `WorkflowSettingsRepository`; `GetWorkflowSettingsUseCase`, `UpdateWorkflowSettingsUseCase`; then the three settings presenters inject them.
2. **L2 Config** (`[AW]/config`, new area folder): `WorkflowConfigGateway` moves out of the editor and throws; `WorkflowConfigRepository`; seven use cases; then the editor and settings presenters inject them.
3. **L3 Editor** (`[AWE]`): `WorkflowAppKind`; the per-app editor gateways become `WorkflowEditorAppGateway` registrations behind the routing `WorkflowEditorGateway`; `WorkflowEditorRepository`; six use cases; then the editor presenter injects them and the per-app editor use-case bundles go.
4. **L4 Review** (`[AW]/review`): the per-app review gateways become `ReviewAppGateway` registrations behind the routing `ReviewGateway`; `ReviewRepository` with the workflow-list cache; seventeen use cases; then the consumers move group by group: target and request (with the cache and its invalidation), details and action dialogs, list and widgets, trash.
5. **L5 Cleanup and docs**: the old bundles, their interfaces, fakes and per-app tokens and the review bridge classes are deleted; `app.md`, the spec and `decisions.md` (D183-D187) are updated.

**Tech Stack:** as 9c: `@webiny/feature/admin` DI (`createFeature`, `createAbstraction`, `X.createImplementation`), `@webiny/di` 2.0.0 multi-injection (`dependencies: [[Token, { multiple: true }]]`, the `ToolRegistry` precedent in `packages/app-admin/src/features/tools/ToolRegistry.ts:34-37`), MobX presenters with render-ready VMs, `useFeature` + `createReactiveComponent`, `MainGraphQLClient`, `GraphQLOperationError` (`@webiny/app/errors/index.js`), vitest with jsdom. No new package dependency.

## Rulings

- R342. **Scope** (Q69-Q76). A structural refactor of the admin data layer of the three workflows admin packages. Out: API, base packages, copy, VMs, refetch rules, any bug fix found on the way (write it down in the task report; do not fix it here).
- R343. **Layers** (Q71, Q72, G5, G7, research-conventions 7). Gateway: runs the GraphQL call (an app gateway) or routes to the app gateway and unwraps its envelope (a routing gateway), throws `GraphQLOperationError` through `toOperationError` and lets a transport rejection pass; returns DTOs; no mapping, no caching; singleton. Repository: calls its area gateway, maps DTO → domain (and domain → DTO for settings), owns the area's cache (review only); singleton; never swallows an error (R350's failed-load cleanup rethrows). Use case: one class, one `execute(params)`, transient, the decoration point; it depends on its area repository (a use case may also depend on another area's repository, R350) and holds a business rule only where R351 says so; never catches except where R350 says so. Presenters and services depend on use cases only (no repository, no gateway). One repository and one gateway per area (Q72): `WorkflowSettingsRepository` / `WorkflowSettingsGateway`, `WorkflowConfigRepository` / `WorkflowConfigGateway`, `WorkflowEditorRepository` / `WorkflowEditorGateway`, `ReviewRepository` / `ReviewGateway`; review and editor add a per-app `ReviewAppGateway` / `WorkflowEditorAppGateway` (R347). No per-operation repository or gateway.
- R344. **Names and layout** (Q76, G8). Tokens are scoped `Workflows/<Name>` and named after the export (`"Workflows/GetReviewUseCase"`, `"Workflows/ReviewRepository"`). An area has `gateway/` (the area gateway: `abstractions.ts` and its implementation file; the existing `dto.ts`, field fragments and mappers stay in this folder), `appGateway/` (review and editor: the multi-registration token and the app contract), `repository/` (`abstractions.ts`, `<Area>Repository.ts`, `feature.ts` named `<Area>RepositoryFeature` registering the area gateway and repository as singletons, the Dashboard precedent), `useCases/<operation>/` per operation (`abstractions.ts`, `<Name>UseCase.ts`, `feature.ts`, `<Name>UseCase.test.ts`; no `index.ts`). A new abstraction declares its interface, its `Params` types and its token in its `abstractions.ts` with `export namespace X { export type Interface = IX; export type Params = XParams; }` (WB template); the existing `IWorkflowSettingsGateway.ts` and `IWorkflowConfigGateway.ts` keep their separate interface file. Per-operation `feature.ts`: name `Workflows/<Name>` (without `UseCase`), `register` = `container.register(XUseCase)` (transient), `resolve` = `{ useCase: container.resolve(UseCaseAbstraction) }`; exported as `<Name>Feature` without `UseCase`, matching the `name` string (`GetReviewFeature`, `ListWorkflowUsersFeature`, the WB `DeletePageRevisionFeature` form). No `index.ts`: the admin packages export `./*`, consumers import `abstractions.js` and `feature.js` directly, and the minimal-barrel rule applies. **Exception for multi-registration tokens:** an app's implementation of `ReviewAppGateway` or `WorkflowEditorAppGateway` keeps its app name (`CmsReviewGateway`, `WbReviewGateway`, `CmsWorkflowEditorGateway`, `WbWorkflowEditorGateway`), because their names, files and the four large gateway tests stay unchanged, the two registrations of one token stay distinguishable in DI errors and in the multi-registration tests, and the `Tool` implementations set the precedent; the same holds for the R356 bridge subclasses `CmsReviewAppGateway` / `WbReviewAppGateway` until Task 14; each still aliases the abstraction (`ReviewAppGateway as GatewayAbstraction`). Mappers and DTO files do not move (they are pure and already tested; the repository imports them).

An app gateway's contract file keeps the wire parameter types it declares today (they are what an app sends): `[AW]/review/appGateway/IReviewAppGateway.ts` (moved from `[AW]/review/gateway/IReviewGateway.ts`, Task 7), `[AW]/editor/appGateway/IWorkflowEditorAppGateway.ts` (moved from `[AWE]/gateway/IWorkflowEditorGateway.ts`, Task 5), `[AW]/config/gateway/IWorkflowConfigGateway.ts` (moved, Task 3), `[AWS]/gateway/IWorkflowSettingsGateway.ts`. ## Assumptions

- A113. The plugin list renders before route content, and the three workflows roots are plugins in the order `WorkflowsAdminApp`, `CmsWorkflows`, `WebsiteBuilderWorkflows` (`app.md` section 1, `packages/app/src/App.tsx:124-136`), so every `RegisterFeature` of every app runs before any route element resolves a presenter (R349).
- A114. `@webiny/di` 2.0.0 resolves `[[Token, { multiple: true }]]` to every registration of the token in registration order, singletons shared (`Container.resolveMultiple`, `node_modules/@webiny/di/dist/index.js:216-236`); a second registration of the same class (a double render of `RegisterFeature`) yields a second, equivalent instance, which first-match routing tolerates.
- A115. The CMS and WB namespace claims are disjoint (`cms.<modelId>` with exactly two parts, and `wb.page`), so the first-match rule never chooses between two claimants.
- A116. No GraphQL server rejects a request because a variable it used to receive is missing or a new one is present; R347 still forbids any variable change, so this only matters if a task gets it wrong.
- A117. `WorkflowEditorAppAdapter.appKind` is always `"cms"` for the CMS editor and `"wb"` for the WB editor, the same values the app gateways declare as `app`.

## Decisions

Recorded by Task 15 (no SEC ids).

- **D183. Admin data layer per operation.** The workflows admin follows presenter → use case → area repository → area gateway: one use case per operation (32), living once in `app-workflows`; one repository and one gateway per area (settings, config, editor, review); the gateway converts error envelopes to `GraphQLOperationError` through one helper and lets transport errors pass; the repository maps DTOs and caches; the use case is thin and is the decoration point. Refines D159. Source: Q70, Q71, Q72, Q76, R343, R344, R346.
- **D184. Per-app gateways behind a routing gateway.** CMS and Website Builder register their review and editor gateways under the shared `ReviewAppGateway` / `WorkflowEditorAppGateway` tokens; the app-neutral `ReviewGateway` / `WorkflowEditorGateway` pick one by the review's namespace (`canHandle`) or the editor's and list's app. Q69's namespace key serves review-bound operations; app-wide operations (editor, lists and widgets, the workflow list) route by app, the namespace's app. App gateways keep resolving with the envelope (R204); the routing gateway unwraps it once, so CMS and WB share the conversion and the null rules. No per-app use case, token or subclass in the data layer; nothing passes use cases at runtime; mounts pass `app` or `namespace`. Refines D159, R204 and R237. Source: Q69, Q70, Q71, R346, R347, R348, R349, R353.
- **D185. The workflow list is cached in `ReviewRepository`.** One cached list per app, the same dedupe, retry and invalidation semantics as before; the store and delete workflow use cases clear their app's list after success and after a `NotFound`, so the editor no longer does it. Refines R277. Source: Q73, R350.
- **D186. Workflows admin tests follow the layers.** Gateway tests with a fake client, routing tests with fake app gateways, use-case tests with a fake gateway and the real repository and cache, presenter tests with one fake per injected use case; no aggregate fakes (the setup kits are rewritten wiring helpers under their old names, not kept as bundles). Refines R243. Source: Q74, R355.
- **D187. Configuration is its own area.** The shared configuration lookups (step types, automations, transports, teams, users, AI models and tools) move from `editor/` to `[AW]/config/` with their own repository and services feature, used by the editor and the settings page. Source: Q72, Q75, R344.
