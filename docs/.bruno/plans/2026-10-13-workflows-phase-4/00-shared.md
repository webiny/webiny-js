# Workflows Phase 4: Routing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Review steps get a real owner when they are reached: the requester's pick, then the first matching rule, then the step's strategy (round-robin or least loaded), then the team pool, with every decision and skip written to the assignment log (spec 6). Reassign arrives as a transition with per-app wrappers. The editor gets the routing inspector, step candidates, folder existence and the shared user list (D104, D117, D128, D133).

**Architecture:** Four sub-phases, built bottom up.

1. **Routing core** (`packages/api-workflows`, 4.1): a `RoutingEvaluatorService` (DI service: candidates, rule matching, strategies, skip records, trace) used by the step-reach resolver and by the inspector; a `RoutingStepAssignmentResolver` replacing `PoolStepAssignmentResolver`; a per-app folder port; assignment records written after the review is saved (also for start and take over).
2. **Engine operations** (`packages/api-workflows`, 4.2): the reassign transition and `ReassignReviewStepUseCase`; `InspectRoutingUseCase` and `ListStepCandidatesUseCase` (internal, explicit inputs); save-time validation of rule user targets; the shared `listUsers` operation (use case behind `editor` + `workflows` GraphQL).
3. **CMS** (`packages/api-headless-cms-workflows`, 4.3): the CMS folder port and folder-level read check, wrappers for reassign, step candidates, the inspector and folder existence, `excludedReason` redaction, and their GraphQL on the `cms` root.
4. **Website Builder** (`packages/api-website-builder-workflows`, 4.4): the same for pages on the `websiteBuilder` root, and the docs.

**Tech Stack:** TypeScript, `@webiny/feature` DI, `@webiny/api-core` (`ListUsersUseCase`, `ListUserTeamsUseCase`, `IdentityContext`), `@webiny/api-aco` (`GetFolderRepository`, `GetAncestorsUseCase`) in the app packages only, `@webiny/api-graphql`, vitest, `@webiny/api-headless-cms-testing`.

**Spec:** `docs/.bruno/specs/2026-10-05-workflows-refactor-design.md` sections 6, 4.3, 4.4, 5.1, 8, 10. Decisions: `docs/.bruno/workflows/decisions.md` D20-D22, D43, D45, D46, D48, D61, D63, D69, D89, D95, D97, D104-D106, D111, D117, D118, D127, D128, D133, D137. Roadmap: phase 4 row. ## Global Constraints

Pure functions (no dependency, no I/O) are allowed. Inline duplication of dependency calls is intended.

## Review Focus

1. **Routing picks someone who must not review** (spec 6, D21, D61). The requester, an excluded user, a non-member of the step's teams, or a user who cannot read the target must never become the owner by pick, rule or strategy. Pinned by Task 2 "never selects the requester, an excluded user or a user without read access" and Task 3 per source.
2. **Routing breaks the review** (spec 6). Any error in resolution (user/team lookup, settings, folders, read checks, load or log queries) falls through to the pool with a logged reason; a failed log write never fails the request. Pinned by Task 3 "falls through to the pool when <dependency> fails" and Task 1 "keeps the review when writing the assignment log fails".
3. **Round-robin or least loaded drifts** (D20, D137). Stable order by user id, wrap-around, a last assignee who is no longer a candidate, load counted per app only, ties to the least recently assigned. Pinned by Task 3 strategy tests with seeded logs and reviews of both apps.
4. **Assignment details leak** (D89, D97, D127). Exclusion free-text reasons never go into a log record; `excludedReason` only for `editor` / `reassign` viewers; skip records stay redacted (R96). Pinned by Tasks 9 and 12 candidate tests and Task 1 record tests.
5. **Reassign bypasses the checks** (D25, D54). Reassign needs `reassign` and read access; the chosen user is validated like a pick; same-owner reassign is refused. Pinned by Task 4 and the wrapper tests in Tasks 9, 12.

## Rulings

- R109. **Assignment sources.** `ReviewStepAssignment.source` and `AssignmentRecord.source` take exactly: `picked`, `rule`, `roundRobin`, `leastLoaded`, `pool`, `poolStart`, `takeOver`, `reassign`. A rule decision sets `source: "rule"` and `ruleId` (user target), or the strategy name / `pool` with `ruleId` set (team target narrowing). The assignment record model gains a `ruleId` text field (unreleased model, allowed). Existing comments listing "rule id" or "strategy" as a source are updated.
- R110. **Order** (spec 6): pick (if the step allows picks and `pickedUserId` is set) → rules (first whose conditions all match and whose target is valid) → strategy over the candidates (or the team-narrowed candidates) → pool. First owner wins.
- R111. **Candidates.** Members of `candidateTeamIds` (default the step's teams; a team-target rule narrows to that team): `ListUsersUseCase({ where: { teams_in } })` inside `withoutAuthorization` (only that call), minus the requester, minus active exclusions (`GetWorkflowSettingsUseCase({ includeExpired: true })` filtered with `filterActiveExclusions(exclusions, now)`), minus users without read access. Read access is checked lazily, in the order a source needs (pick and rule targets: one check; strategies: in their candidate order, stopping at the first readable). Stable candidate order: sorted by user id.
- R112. **Validity of a person target** (pick, rule user target, reassign target): member of `candidateTeamIds` (via `ListUsers` `teams_in`), not excluded, not the requester, and `canUserRead` true. An invalid pick or rule target writes a skip record with a fixed reason and the evaluation continues. A rule whose **team** target is not one of the step's teams is invalid too (spec 6): the rule is skipped (trace `skipped`, skip record `{ kind: "skip", userId: null, source: "rule", ruleId, reason: "Not one of the step's teams." }`) and evaluation continues; save-time validation and the inspector (R121) refuse such a rule, so the skip appears only for a stored workflow whose teams changed or that was written without validation. Rule conditions that need no lookup (`requesterUserId`, `modelId`, folder `type`) are checked before the requester's teams or the folder chain are read; each lookup runs at most once per evaluation. Fixed reasons (exact strings): `"Not a member of the step's teams."`, `"Excluded from reviews."`, `"The requester cannot review."`, `"Cannot read this content."`. An exclusion's own free-text reason never goes into a record (D89, D97).
- R113. **Rule conditions** (spec 6). `requesterUserId` = requester id; `requesterTeamId` ∈ the requester's teams (`ListUserTeamsUseCase(requester.id)`, failure or API key → no teams); `modelId` = the review's `model` namespace's model id (CMS `cms.<modelId>`; WB `wb.page` matches `modelId` `"page"`); `folder`: the target's folder id and its ancestor ids from the per-app folder port at reach time; `includeDescendants` matches when the rule folder id is in the chain, else when it equals the target folder id; the rule folder `type` must equal the target folder type; a target in the root (`folder: null`) matches no folder condition. A rule with no conditions always matches.
- R114. **Folder port.** New engine abstraction `ReviewTargetFolderChain` (`features/review/ReviewTargetFolderChain/`), one per namespace like `ReviewTargetLoader`: `canHandle(model): boolean`, `listFolderChainIds({ model, folderId }): Promise<string[]>` (the folder and its ancestors, nearest first). Apps implement it with ACO `GetFolderRepository` (no FLP) + `GetAncestorsUseCase`. No implementation for the namespace, or a failure, → resolution falls through to the pool (R116).
- R115. **Strategies.** `roundRobin`: latest record with `kind: "outcome"` and a non-null `userId` for `workflowId` + `stepId` (any source with a user, incl. `poolStart`, `takeOver`, `reassign`); next candidate by user id after it, wrapping around; none → first candidate. `leastLoaded` (D137): load = active reviews with `currentStepState: "inReview"` owned by the candidate, in namespaces of the same app as the review (app = namespace prefix before the first `.`, pure `getNamespaceApp`); the review being routed is not counted (`reviewId` on `RoutingStrategyOrderParams`; a candidate who owned its previous step is not penalised by it); fewest wins; ties at the **lowest** load → least recently assigned: one `AssignmentRepository.list({ where: { userId, workflowId_in, kind: "outcome" }, limit: 1 })` per candidate tied at the lowest load, among the same app's workflows (never assigned = least recent; still tied → user id order); ties at higher loads read no history and go by user id. New repository reads: `ReviewRepository.listInReviewByOwners(ownerIds)` (paged, `currentOwnerId_in`, `currentStepState: "inReview"`, `isActive: true`, no model filter; app filter in code) and `AssignmentRepository.list` gains `kind` and `workflowId_in` filters. Lag (A29) accepted.
- R116. **Never blocks** (spec 6). Any thrown or failed dependency during resolution → pool, `reason: "Routing failed; the step went to the pool."`, the error logged with `Logger`. The step still reaches. **Refined:** a failure keeps what was decided so far: `RoutingDependencyError.decided` carries the candidate teams (narrowed when a team-target rule matched, else the step's teams), that rule's id and the skip records gathered; the pool is of those teams, the records are those skips then the pool outcome (with the rule id). A throwing folder port is caught and keeps them too; a throwing read check gives the pool of the step's teams without skips.
- R117. **Records after save.** The resolution carries the outcome and skip records; they travel on the `stepReached` fact and `ReviewSaver` writes them after the review save (`AssignmentRepository.create` per record). Start (`poolStart`) and take over (`takeOver`, `by`) also write an outcome record; reassign writes `reassign` with `by`. A failed record write is logged and never fails the request. `assignedOn` = the reach `now`.
- R118. **Determinism.** `StepAssignmentResolverParams` gains `now: Date`; the reacher passes its `now`. No `new Date()` inside routing.
- R119. **Reassign** (spec 5.1, D25). Aggregate `Review.reassign({ stepId, actor, owner, now })` uses `guardReassign`; same user as the current owner → `ReviewAlreadyOwnerError`; `awaiting` → `inReview` with `startedOn`; assignment `{ source: "reassign", by: actor }`; new `stepReassigned` fact (with `previousOwner`) → `ReviewStepReassignedEvent`. Engine `ReassignReviewStepUseCase({ reviewId, stepId, userId, actor })` validates the user per R112 (owner Actor from the `AdminUser`: `{ type: "user", id, displayName, identityType: "admin" }`). Wrappers need `reassign` (1b predicate) and target read access.
- R120. **Step candidates** (D97, D104, D128). Engine `ListStepCandidatesUseCase` takes either `{ workflowId, stepId, model, targetId, targetRevisionId, requesterId }` (request dialog; the step config from the stored workflow) or `{ reviewId, stepId }` (reassign; from the review snapshot). Returns every member of the step's teams except the requester, sorted by `displayName`: `{ id, displayName, excluded: boolean, excludedReason: string | null }`; `excluded` true for active exclusions or no read access; `excludedReason` = the exclusion's reason or `"Cannot read this content."`. No workload counts. The wrappers null `excludedReason` unless the viewer has `editor` or `reassign`.
- R121. **Inspector** (D45, D95, D104, D118). Engine `InspectRoutingUseCase({ stepConfig, model, requesterId, folder: { id, type } | null, now })` (the wrapper derives the folder type: CMS `cms:<modelId>`, WB `wb:page`) runs the same `RoutingEvaluatorService` on unsaved config and returns `{ owner: { id, displayName } | null, source, ruleId, strategy, trace: RoutingTraceEntry[] }` (`strategy` is the step's configured strategy; `source` says what decided) with `RoutingTraceEntry { ruleId, outcome: "matched" | "notMatched" | "skipped", reason: string | null }` — no load numbers. With no target revision, read access uses the new port method `ReviewTargetReadAccess.canUserReadInFolder({ userId, model, folderId })` (model read + folder content read as that user; root folder → model read only).
- R122. **Save-time rule targets** (spec 6, 1a A7). `StoreWorkflowUseCase` checks user targets inline: `ListUsersUseCase({ where: { id_in: userTargets, teams_in: step.teams } })` inside `withoutAuthorization`; a user target not returned → `WorkflowValidationError` ("Rule <ruleId> targets a user who is not a member of the step's teams."). A failed lookup → `WorkflowPersistenceError`.
- R123. **Shared `listUsers`** (D48, D117). `ListWorkflowUsersUseCase({ search?, ids?, limit? })` in `features/config/` checks `canEdit()` first (refusal action `"list users"`), then `ListUsersUseCase` inside `withoutAuthorization`; `ids` → `{ users, missingIds }` (D117); `search` case-insensitive on `displayName` and email, sorted by `displayName`, `limit` default 50 max 200 (guarded like R92). Users are `{ id, displayName }`. GraphQL `workflows.listUsers`.
- R124. **Per-app GraphQL names.** CMS (`cms` root): `listCmsEntryStepCandidates(workflowId, stepId, modelId, revisionId)`, `listCmsEntryReviewStepCandidates(reviewId, stepId)`, `inspectCmsEntryRouting(stepConfig: JSON!, modelId, requesterId, folderId)`, `cmsEntryFolderExists(id, type)`, mutation `reassignCmsEntryReviewStep(reviewId, stepId, userId)`. WB (`websiteBuilder` root): `listWebsiteBuilderPageStepCandidates(workflowId, stepId, revisionId)`, `listWebsiteBuilderPageReviewStepCandidates(reviewId, stepId)`, `inspectWebsiteBuilderPageRouting(stepConfig, requesterId, folderId)`, `websiteBuilderPageFolderExists(id)`, `reassignWebsiteBuilderPageReviewStep(reviewId, stepId, userId)`. R107 applies to every `revisionId` argument.
- R125. **Per-app permissions.** Step candidates for a request: write access to the target (as the request wrapper). Step candidates for reassign and reassign itself: `reassign` + read access. Inspector and folder existence: `editor`. Folder existence (D69) runs the ACO repository without folder-level permissions and returns only a boolean; the type must belong to the app (`cms:<modelId>` for a bindable model / `wb:page`).

- R126. **Small engine choices (4.2 drafting).** Request-form step candidates for an unbound model, unknown or non-review step fail with `ReviewValidationError` (the `Review.request` messages for an unbound model and an unknown step; a non-review step: `Step "<title>" is not a review step.`). `listUsers` `ids` is capped at 200 (more → `WorkflowValidationError` "Too many user ids."); with `ids`, `search`/`limit` are ignored. Reassign to the current owner returns `ReviewAlreadyOwnerError` unchanged (the admin shows its own text). Tests that need a workflow with an invalid user target (to test skips at reach) seed it with `WorkflowRepository.create`, never through `StoreWorkflowUseCase` (R122 is not relaxed). The inspector passes `workflowId: null`; round-robin needs a workflow id and treats null as no history.

- R127. **Cross-task placement (4.3 drafting).** `redactStepCandidates(candidates, permissions)` is a pure function in api-workflows `domain/routing/redactStepCandidates.ts`, owned by 4.2 Task 5 (not 4.3). The WB test helper `NoAcoFolders.ts` and its `handler.ts` registration are created by 4.3 Task 8 (the WB harness registers the CMS feature, whose folder chain needs ACO); 4.4 Task 11 does not recreate them. The inspector's folder-level read check reads the model as the request identity (the editor); an editor who cannot read the model sees every candidate as "Cannot read this content." (accepted). Refusal actions: `"reassign this step"`, `"list the step's candidates"`, `"inspect routing"`, `"check folders"`.

- R128. **Request candidates check the workflow's app (R46).** The per-app request-candidate wrappers read the workflow (`GetWorkflowUseCase`) and check it belongs to the app (`isCmsWorkflow` / `isWbWorkflow`) before the engine; another app's workflow → `Workflows/Workflow/NotFound` with `{ id }`. The folder chain params type is `ReviewTargetFolderChain.Params` everywhere.

- R129. **Inspector trace shows the exclusion's own reason** (D118). The inspector (editor only) marks a rule whose user target is excluded as `skipped` with the exclusion's own reason (or `"Excluded from reviews."` when it has none). Assignment records keep the fixed R112 reasons (D89, D97); the free text never goes into a record. `RoutingInspection` also lists the skipped people (D118): `skipped: { userId, displayName, reason }[]` (pick, rule targets and strategy candidates refused read access), with the same reasons as the trace.
- R130. **Folder at reach = the review's target folder** (spec 6). The folder id comes from `targetContext.folder` (moves are refused while a review is in progress, D84/R55, so it is the target's current folder); its ancestors are read at reach through the folder port, so a moved parent is seen as it is then.

## Assumptions

- A46. Load counts and the round-robin "latest assignee" read OpenSearch; two quick reaches can pick the same person (A29). Accepted.
- A47. Read checks for strategy candidates are lazy; the inspector checks folder-level access only (no entry), so a candidate it shows as readable can still lack access to a specific entry; step reach re-checks.
- A48. `ListUsersUseCase` returns every user of a team (DDB scans the tenant). Teams are expected to be small enough; no paging in v1.
- A50. Strategy candidates that are excluded or the requester are dropped without a skip record; only candidates asked for read access and refused get one. A strategy that finds nobody readable goes to the pool with reason `"No eligible candidate; the step went to the pool."`.
- A49. Records for start, take over and reassign are written after the save like step reach records (R117); before phase 4 these transitions wrote none.
