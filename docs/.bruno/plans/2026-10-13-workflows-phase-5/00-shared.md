# Workflows Phase 5: Step types, automation, tasks

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Steps are no longer review-only. A public `StepType` extension point and a public `AutomationDefinition` abstraction let developers define automations in code (a zod schema for what the workflow author fills in, a handler returning an outcome). The engine runs an automation step as a private background task attributed to the requester (the identity is the requester, but authorization is off, so the automation is not limited by the requester's permissions, D36), applies its outcome through the base approve/reject use cases with an `automation` actor, and fails the step with a reason when anything goes wrong. Failed steps are restartable (per-app wrappers, GraphQL, `canRestart`). Cancel aborts the running task. The SEC-68 bug (GraphQL `triggerTask` runs private definitions) is fixed in `packages/background-tasks`. No built-in automation ships (the "Send webhook" built-in is dropped) and there are no secret settings.

**Architecture:** Five sub-phases, built bottom up.

1. **Step types and automation definitions** (`packages/api-workflows`, 5.1): the `StepType` abstraction and registry with the `review` built-in (the workflow validator and `listStepTypes` go through it; the other `step.type === "review"` checks, in `StoreWorkflowUseCase`, `ListStepCandidatesUseCase` and `canPickReviewer`, keep parsing the review config and only import `REVIEW_STEP_TYPE` from its new file); the `AutomationDefinition` abstraction, registry, scope matching and the `automation` step type (save-time validation); `listStepTypes` from the registry and the shared `listAutomationDefinitions` operation.
2. **Run data and transitions** (`packages/api-workflows`, 5.2): `taskId` and `runs` on review steps; `Review.reachRun`, `Review.fail`, `Review.restart` with facts and events; the restart permission predicate and `canRestart`.
3. **Task runner** (`packages/background-tasks`, `packages/api-workflows`, `packages/api-headless-cms-workflows`, `packages/api-website-builder-workflows`, 5.3): the SEC-68 fix; the workflow bypass context; the task abort service (abort when the save fails), with the requester-identity trigger inline in the automation reach (trigger before save); step-reached dispatch by step type with the automation reach; the private `workflowsStepRun` task definition, stale guard and failure hooks (with the `@webiny/background-tasks` dependency); the run handler; cancel and delete abort the task; stuck detection on single reads; `RestartReviewStepUseCase`.
4. **CMS** (`packages/api-headless-cms-workflows`, 5.4): restart wrapper, `restartCmsEntryReviewStep` GraphQL, `taskId`/`runs` exposed on the review step.
5. **Website Builder and docs** (`packages/api-website-builder-workflows`, 5.5): the same for pages, then the docs task (developer guide, stale "phase 5" comments, spec/roadmap/decisions updates).

**Tech Stack:** TypeScript, `@webiny/feature` DI, zod 4 (`z.toJSONSchema`), `@webiny/api-core` (`TaskService`, `TaskDefinition`, `TaskController`, `IdentityContext`), `@webiny/background-tasks` (`GetTaskUseCase`, `GetRunnableTaskDefinitionUseCase`, the GraphQL schema), `@webiny/api-graphql`, vitest, `@webiny/api-headless-cms-testing`.

**Spec:** `docs/.bruno/specs/2026-10-05-workflows-refactor-design.md` sections 4.1, 4.2, 5.1, 5.2, 5.3, 7.1, 7.2, 7.4, 8, 9.2, 10 (7.2 loses the "Send webhook" built-in and the secret settings bullet in Task 18). Decisions: `docs/.bruno/workflows/decisions.md` D6-D8, D14, D25-D28, D34-D38, D56, D57, D62, D65, D81, D82, D86, D87, D100, D107-D112, D119, D122, D129, D130, D132, D133 (D67 secret part and D86 "Send webhook" part are superseded by R154, R155). Roadmap: phase 5 row. Earlier rules keep applying: phase 1a R1-R28 / A1-A12, phase 1b R29-R44 / A13-A19, phase 2 R45-R87 / A20-A39, phase 3 R88-R108 / A40-A45, phase 4 R109-R130 / A46-A50. ## Global Constraints

- **No helper functions or private methods that wrap a dependency call** (use case, service, reader, repository, logger). Call dependencies inline in the owning class with the Result pattern or an inline `try`/`catch`. Shared logic that needs dependencies becomes a DI service named `...Service`. Pure functions (no dependency, no I/O) are allowed. Inline duplication of dependency calls is intended.
- **R87:** app wrappers turn every dependency throw into a failed Result with the persistence error type, never `NotAuthorized`, never a rejected promise.
- **D132:** engine use cases take explicit inputs (actor, viewer ids) and check no permissions. Wrappers read identity and check permissions; GraphQL resolvers call only wrappers or shared configuration use cases.
- **SEC-66:** `canUserRead` / any candidate read check runs as the request identity, never inside `withoutAuthorization`. `ListUsersUseCase` / `GetUserUseCase` need `withoutAuthorization` (they require `adminUsers.user`): wrap only those calls, never a read check.
- DI conventions: one abstraction or implementation per file; implementation file named after its class; namespace types; no inline object types; minimal barrels.
- Before every commit: `git add .`, `yarn > /dev/null 2>&1`, `node scripts/generateTsConfigsInPackages.js`, `yarn adio`, `yarn check-ts-configs`, `yarn format:fix > /dev/null 2>&1`, `yarn lint:fix`, `yarn webiny sync-dependencies`, `yarn build -p <package> --no-cache 2>&1 | tail -30` for changed packages, `git add .`. Restore `.gitleaks.toml` (`git checkout -- .gitleaks.toml`); never commit it, `docs/.reports` or `.superpowers`.
- Commits: Conventional Commits, ending with exactly:
  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_01U31bVptN4E9cWVxet6Tjxn
  ```
  Never push, amend or revert.
- **Tests are targeted:** run the test files you add or change and the files covering the changed code, by path (`yarn test packages/<pkg>/__tests__/<file>.test.ts`, the same with `yarn test:os`). Never a whole package suite unless the dispatch asks. Run `test:os` runs one at a time (parallel runs clash on port 8001). `packages/background-tasks` tests use `yarn test` by path.
- Type-check tests: `yarn check:test:types 2>&1 | grep -iE "api-workflows|headless-cms-workflows|website-builder-workflows|background-tasks" | head` prints nothing.
- TDD: failing test first, record RED before source.
- `@webiny/api-aco` stays app-package only. `api-workflows` gains one dependency: `@webiny/background-tasks` (R156), in the first task that imports it (Task 11).
- **Test automations are test-only.** No automation definition ships in a source package. Tests register a small one from `__tests__/__helpers/` (R157).

## Review Focus

1. **A stale or forged task writes to a review** (D7, D27, SEC-68). A late `onError`, a restarted step's old task, or a task triggered through GraphQL for a private definition must write nothing. Pinned by Task 7 "refuses a private definition as unknown" and Task 11 guard tests per hook (wrong task id, wrong creator, inactive review, other current step).
2. **Task and save race** (D57, R143). The task is triggered before the review is saved; it must wait for its `taskId` to appear (bounded), and a failed save must abort the task. Pinned by Task 12 "waits for the review and step to carry its task id, at most 3 tries" (also when the review is not found yet) and Task 9 "aborts the triggered task when the save fails".
3. **Automation runs as the wrong identity or leaves the bypass open** (D87, D133 point 4b, D36). The trigger runs under `withIdentity(requester)` also when reached inside a task or on restart; the bypass flag exists only inside the handler's automation call, is restored in `finally`, and exempts only the save block (R150). Pinned by Task 10 "triggers as the requester", Task 12 "the automation and the engine calls it makes see the requester identity" (R161) and Task 8 "restores the flag when the callback throws".
4. **A step ends up failed without a reason, or restart works when it must not** (D8, D34, D82). Every failure path writes a fixed reason (including a step config that no longer parses, R146, and no error from `review.fail` is swallowed, R159); restart only from `failed`, never from `rejected`; requester or `reassign` plus read access. Pinned by Task 5 transition tests, Task 10 "fails the step when the automation is missing / its settings are invalid", Task 15 and the wrapper tests in Tasks 16 and 17.
5. **A workflow saves with an automation step that cannot run** (D35, D37). Definition must exist, its models must cover the workflow's models, the step's settings must pass the definition's zod schema; the same check runs again on reach and restart. Pinned by Task 2 save-time tests and Task 10.

## Rulings

- R131. **`StepType` shape.** Multi-registered abstraction `StepType` (`features/stepTypes/StepType/`): `type: string`, `title: string`, `configSchema: zod.ZodType | null`, `describeAvailability(): Promise<{ available: boolean; unavailableReason: string | null }>`, `validate({ step, workflow }): Result<WorkflowStep, WorkflowValidationError>` (pure of I/O; a type that needs a registry gets it injected), `reach({ review, step, actor, now }): Promise<Result<void, ReviewInvalidStateError | ReviewStepNotCurrentError>>` (R159). `StepTypeRegistryService` (`get(type): StepType.Interface | null`, `list(): StepType.Interface[]`) returns the last registration per `type`. `WorkflowsFeature` registers `review` and `automation`; `ai` is registered by phase 6 only. Constants `REVIEW_STEP_TYPE = "review"` and `AUTOMATION_STEP_TYPE = "automation"` live in `domain/workflow/stepTypes.ts`. Done in phase 6 (R164-R180).
- R132. **`ai` placeholder and unknown types.** While no `ai` type is registered, `listStepTypes` still returns the `ai` row (D122, D130) exactly as today: `available` is the `aiPowerups` feature flag (read through `FeatureFlags`, a throwing read is a `WorkflowPersistenceError`), `unavailableReason` is `"AI powerups are not enabled."` when the flag is off and `null` when on, `configSchema: null`. Save refuses an `ai` step with `Step "<title>" uses the step type "ai", which is not available.` and any other unregistered type with `Step "<title>" uses an unknown step type "<type>".` (both `WorkflowValidationError`).
- R133. **Automation definition and step config** (spec 7.2, D14, D35, D86; names align with the spec). An automation is a developer-written class registered against the multi-registered abstraction `AutomationDefinition`: `id: string`, `name: string`, `models: string[]` (the D35 scope: `["*"]`, `["cms.*"]`, or namespace ids), `settingsSchema: zod.ZodType` (what the workflow author passes in, e.g. a URL for a developer's own "webhook" automation), `maxIterations?: number`, `run(params): Promise<AutomationOutcome>`. The step's stored config is `{ automationId: string; settings: Record<string, unknown> }` (`automationStepConfigSchema`, `domain/automation/`). The workflow author adds the automation as a step in the editor and fills `settings`; `settings` are validated against the chosen definition's `settingsSchema` at save time and again on reach and restart. The schema reaches the editor as JSON schema (`z.toJSONSchema`) through `listAutomationDefinitions`. Credentials stay in the definition's own code or config, never in step config (R154).
- R134. **Public exports.** Developers import from `@webiny/api-workflows/features/automation/AutomationDefinition/index.js` (`AutomationDefinition`, `AutomationOutcome`, `AutomationRunParams`) and `@webiny/api-workflows/features/stepTypes/StepType/index.js`; the package `exports` already allow `./*`. Nothing else becomes a documented public surface. Editor-side counterparts belong to the admin phases.
- R135. **Outcomes** (spec 7.2, 7.4). `AutomationOutcome` is `{ type: "approved" | "rejected"; comment?: string }` or `{ type: "continue"; wait?: number; state?: Record<string, unknown> }` (`wait` in seconds, applied as the task's continue delay; `state` is written with `controller.state.updateOutput({ state })` and read back with `controller.state.getOutput()` as `run` params `state` on the next iteration; only the handler writes the output). A `rejected` outcome needs a comment of 10 or more characters (D100), else the step fails with `The automation rejected without a comment.`
- R136. **Scope matching** (D35). Pure `matchesAutomationScope(automationModels, workflowModels): boolean`: true when every workflow model is covered: `"*"` covers all; `"<app>.*"` covers namespace ids starting with `"<app>."`; otherwise an exact id. A workflow with no models is never covered. Save refuses an uncovered workflow with `Automation "<id>" is not available for this workflow's models.`
- R137. **Save-time automation validation** (D35, D37). Messages (`WorkflowValidationError`): unknown definition `Step "<title>" uses the automation "<automationId>", which is not defined.`; settings `Step "<title>" settings are not valid: <first issue path>: <message>.` (path omitted when empty); malformed shell `Step "<title>" needs an automation.`. The stored `settings` are the ORIGINAL value the author submitted, not zod's parsed output (a transform schema, e.g. `z.string().transform(Number)`, must save and re-parse): save validation, reach and run each parse the stored settings again (`parseAutomationSettings`, defaults applied at use).
- R138. **`listStepTypes` and `listAutomationDefinitions`** (D122, D129, D130, D133 point 2). `listStepTypes` rows come from the registry plus the `ai` placeholder row (R132) if no `ai` type is registered, in the fixed display order `review`, `ai`, `automation`, then any other registered type in registration order (the order of the existing test); `configSchema` is `zod.toJSONSchema(schema, { io: "input", unrepresentable: "any" })` of the type's schema (the author-facing input form; a conversion error is a `WorkflowPersistenceError`, R87). `automation` is `available: false` with the existing text `"No automation is defined."` when the definition registry is empty; per-model availability is a UI string over the `models` data. New shared `ListAutomationDefinitionsUseCase` (`editor` only, refusal action `"list automations"`; a throwing permission read is a `WorkflowPersistenceError`, like `ListWorkflowStepTypesUseCase`) and GraphQL `WorkflowsQuery.listAutomationDefinitions`, rows `{ id, name, models, settingsSchema }` (`settingsSchema` is `zod.toJSONSchema(definition.settingsSchema, { io: "input", unrepresentable: "any" })` so a schema never makes the list throw, a remaining conversion error is a `WorkflowPersistenceError` (R87); a field with `.default()` is not required), sorted by `name`.
- R139. **Step run data** (D57, D82). `ReviewStep` gains `taskId: string | null` (the current attempt's background task id; also the run id) and `runs: ReviewStepRun[]` (earlier attempts only). `ReviewStepRun { taskId: string | null; startedOn: string; finishedOn: string | null; outcome: "approved" | "rejected" | "failed" | null; reason: string | null }`. `taskId` is null on a run whose reach failed before a task started. Review steps and reviews written earlier read as `taskId: null`, `runs: []` (mapper default, no migration). GraphQL `WorkflowsStepRun` type and `taskId`, `runs` on the review step.
- R140. **Transitions** (spec 5.1, D8, D82, D119). `Review.reachRun({ actor, owner, taskId, now })` reaches the next pending step of an automation: `pending` to `inReview`, owner = the automation actor (R141), `startedOn` and `reachedOn` = now, `assignment` and `assignmentSource` null, records none, `taskId` stored; it records the existing `stepReached` fact (its `assignment` becomes `ReviewStepAssignment | null`, new field `taskId: string | null`). `Review.fail({ stepId, reason, now })` fails the current `pending` or `inReview` step (`comment` = reason, `finishedOn` = now); an already `failed` step is a no-op `Result.ok` with no fact (idempotent); the fact actor is the step's owner, else the requester. `Review.checkRestart` / `Review.restart({ stepId, actor, now })`: only a `failed` current step (a `rejected` step fails with `ReviewInvalidStateError`, transition `"restart"`); appends the failed attempt to `runs` (`taskId` = the step's `taskId`, `startedOn` = the step's `startedOn`, else its `reachedOn`, else its `finishedOn`; `finishedOn`; `outcome: "failed"`, `reason` = the comment), clears `comment` and `taskId`, sets `pending`, keeps the owner, then the caller re-reaches. New `ReviewTransitionName` values `fail`, `restart`. Facts `stepFailed { actor, change, reason }` and `stepRestarted { actor, change, previousTaskId }`; events `Workflows/Review/StepFailed`, `Workflows/Review/StepRestarted` (`ReviewStepFailedEvent`, `ReviewStepRestartedEvent`).
- R141. **Automation actor** (spec 5.2, D58, D107). `{ type: "automation", id: <requester id>, displayName: <requester displayName> }` for the step owner, approve, reject and `fail` facts; `identityType` omitted. Approve and reject by the runner pass `actorTeamIds: []`.
- R142. **Task definition** (spec 7.4, D57). One private definition, id `workflowsStepRun` (constant `STEP_RUN_TASK_DEFINITION_ID`), title `Workflow step run`, `isPrivate: true`, `selfCleanup: "never"`, a high `maxIterations` ceiling (`STEP_RUN_MAX_ITERATIONS = 10000`), task name `Workflow step: <step title>`, input exactly `StepRunTaskInput { reviewId: string; stepId: string }` (validated with `createInputValidation`). The handler reads nothing else from input (R148).
- R143. **Trigger before save, bounded wait, abort on failed save** (user answer Q1). The reach path triggers the task before the review is saved and stores its id on the step in the one save (`reachRun`). The handler, when the review is not found yet (a new review is created by that one save) or the step does not carry a matching `taskId` yet, returns `controller.response.continue(data, { seconds: STEP_RUN_TASKID_WAIT_SECONDS })` (2 seconds; R162 for the signature), while `controller.state.getTask().iterations <= STEP_RUN_TASKID_WAIT_TRIES` (3, so at most 3 waits), then treats the run as stale (R144). `ReviewSaver.save`, when persisting fails, aborts the tasks named by the `taskId` of the recorded `stepReached` facts through `ReviewTaskAbortService` (best effort, logged, never changes the returned error). A save that fails after the task finished is covered by the stale guard discarding the orphan's result.
- R144. **Stale guard** (D7, D27, D57). Pure `getStaleStepRunReason(review, stepId, task): string | null` (`task: { id: string; createdById: string }`): returns a reason unless the review `isActive`, `state === "inProgress"`, the current step id equals `stepId`, that step is `inReview` with `taskId === task.id`, and `task.createdById === review.createdBy.id`. The handler and every hook (`onError`, `onMaxIterations`, `onAbort`) and stuck detection use it: stale means log at info, write nothing, return done. A guarded `fail` on an already failed step is a no-op (R140).
- R145. **maxIterations** (user answer Q5). The task definition has one high ceiling (R142). The handler enforces the automation definition's own `maxIterations` (default `DEFAULT_AUTOMATION_MAX_ITERATIONS` = 50) against the automation's own run count (R163: `iteration`, the task's `iterations` minus the id-waits), never against the runner ceiling: when the run count would exceed it, the handler fails the step with the R146 reason (`<n>` = that definition's `maxIterations`) instead of running again. The task's `onMaxIterations` hook (the 10000 ceiling) fails the step through the guard with the same reason text, `<n>` again the automation definition's own `maxIterations` (P4), looked up from the review snapshot; never `STEP_RUN_MAX_ITERATIONS`.
- R146. **Fail reasons** (fixed texts, stored in `comment` and `runs[].reason`). Missing definition: `The automation "<automationId>" is not available.`; invalid settings: `The automation settings are not valid: <first issue path>: <message>.`; step config that no longer parses against `automationStepConfigSchema` at reach (own fixed reason, never reuses the missing-definition text; P3): `The automation step configuration is not valid.`; automation not covering the models (at reach): `The automation "<automationId>" is not available for this workflow's models.`; trigger failed or threw: `The automation could not be started.`; run error (the automation threw, a use case failed, or the task ended with an error): `The automation failed.`; unknown outcome: `The automation failed: It returned an unknown outcome.` (a deliberate fixed text); max iterations: `The automation did not finish in <n> iterations.`; stuck: `The automation task ended without a result.`; abort: `The automation was aborted.`; rejected without comment: R135; step type not registered: `The step type "<type>" is not available.`. Raw thrown or trigger error messages NEVER reach `comment` or `runs[].reason` (they can carry internals): any error that is not a deliberate `StepRunFailure` stores the fixed text (`The automation failed.` / `The automation could not be started.`) and the full error is logged with `Logger.error`. Only the `<first issue path>: <message>` of the author's own settings validation (R146 invalid settings) carries a message, and it comes from the zod schema, not from a thrown error.
- R147. **SEC-68 is a bug, fixed in the platform** (user answer Q4; `packages/background-tasks`). The GraphQL mutation `WebinyBackgroundTaskMutation.triggerTask` refuses a private definition exactly as an unknown one (`TaskDefinitionNotFoundError`, code `BackgroundTasks/TaskDefinition/NotFoundError`, message `Task definition not found.`, data `{ id }`), so a caller cannot tell them apart. Today `TaskService.trigger` throws a `WebinyError` with code `TASK_DEFINITION_ERROR` and message `Task definition was not found!` for an unknown id; the GraphQL resolver now checks unknown and private ids itself (`GetRunnableTaskDefinitionUseCase`, `isPrivate`) and returns `TaskDefinitionNotFoundError` for both, before `TriggerTaskUseCase`. `TriggerTaskUseCase` and internal `TaskService.trigger` calls (the engine triggering the private definition) are unaffected. Out of scope: `abortTask`, `deleteTask`, `getTask` and `listTasks` stay open for private tasks to holders of `task.entry` (the `workflowsStepRun` stale guard makes abort and delete safe); the fix commit body mentions that the SDK's `triggerTask` (which goes through this mutation) now refuses private ids. A commit `fix(background-tasks): ...` of its own (Task 7). The runner defences stay regardless (R144, R148).
- R148. **Runner defences** (SEC-68). The handler never trusts input: it reads the review by `reviewId`, applies the stale guard with the task's own id and `createdBy` (which must be the requester), and takes everything else (definition id, settings, models) from the review snapshot. Before every `run` call it parses the step's settings with the definition's schema (`parseAutomationSettings`); invalid settings fail the step with the R146 reason, and `run` receives the parsed value (answers: validated at save and before run). A task created through any other path matches no step `taskId` and writes nothing. `createdBy` equals the requester because the trigger runs under `withIdentity(requester)` (R149).
- R149. **Requester identity** (D87, D133 point 4b). `AutomationStepType.reach` (the only trigger call site, so no wrapper service) builds `new AuthenticatedIdentity({ id, displayName, type: identityType ?? "admin", context: { canAccessTenant: true } })` from `review.createdBy` (as `CandidateReadAccess` does) and calls `TaskService.trigger({ definition: STEP_RUN_TASK_DEFINITION_ID, name, input })` inside `IdentityContext.withIdentity` only, with the Result pattern inline (a failed or thrown trigger becomes the fixed R146 reason `The automation could not be started.`, the error logged with `Logger.error`). Reach runs the same way inside a task (R161), on restart (always the requester, never the restarter) and on a later step reached by approve. `TaskService.trigger` is unchanged; `AutomationStepType` takes the task id from the returned task.
- R150. **Bypass context** (D36, D62, spec 9.2). `WorkflowBypassService` (`features/bypass/`): `run<T>(callback: () => Promise<T>): Promise<T>` sets a flag on the request-scoped container, restores it in `finally`; `isActive(): boolean`. Only the run handler enters it, around `AutomationDefinition.run`, never wrappers or GraphQL. It does not touch `IdentityContext` and does not widen permissions. Only the save block `BlockUpdateWhileInReview` (CMS; it also covers WB pages) skips when `isActive()`, as a check before the binding lookup: D36, D62 and spec 9.2 exempt only the save block (`EntryBeforeUpdate`). The move rule (D84: `BlockMoveWhileInReview`, `BlockFolderChangeWhileInReview`, WB `BlockPageMoveWhileInReview`) and the delete and trash blocks (D134) are not exempted by any decision and do not skip.
- R151. **Cancel and delete abort the task** (spec 5.1, D25, D57). `CancelReviewUseCase` calls `ReviewTaskAbortService.abort` for the current step's `taskId` after the save, and `DeleteTargetReviewsUseCase` for every deleted review's in-review automation step; abort failures are logged and never fail the request. The abort message is `The review was cancelled.` / `The review was deleted.`
- R152. **Stuck detection** (D28, D57). Only `GetReviewUseCase` and `GetTargetReviewUseCase` (never lists): a current automation step `inReview` with a `taskId` whose task (`GetTaskUseCase`) is `success`, or is `failed` / `aborted` AND finished more than `STEP_RUN_STUCK_GRACE_MS` (300000, 5 minutes) ago (`task.finishedOn`, falling back to `savedOn`), or is missing (`null`) AND the step started (`startedOn`, falling back to `reachedOn`, then the review's `lastChangedOn`) more than the same grace ago, and passes the stale guard, is failed with the stuck reason (R146) through `ReviewSaver`, and the failed review is returned. The grace exists because the runner may still call `onError` / `onAbort` (which fail the step with the proper reason) shortly after the platform marks a task `failed` / `aborted`; a `pending` or `running` task is never stuck, and a missing task gets the same grace because `GetTaskUseCase` answers `null` on any read failure, not only not-found, so a storage hiccup must not fail a live step. A thrown task lookup or a failed write leaves the review as read and is logged; a read never fails because of it. RULING (accepted): this write happens inside the engine read, before the app wrapper's authorization check, so a caller without access to the review can trigger it. That is accepted: it only moves a truly stuck step to `failed` (a correct, idempotent state change that the hooks or any other read would make anyway), returns no extra data to the caller (the wrapper still decides what is returned), and engine use cases carry no permission checks by design (D132).
- R153. **Restart** (spec 5.1, D8, D34, D82). Engine `RestartReviewStepUseCase({ reviewId, stepId, actor })` (explicit actor, no checks): load, `review.restart`, re-reach through `ReviewStepReacher` (definition lookup, settings re-validation, new task as the requester), save; if the re-reach fails the step ends `failed` with the new reason (never left `pending`). Wrong state: `Workflows/Review/InvalidState` with `transition: "restart"`. Wrappers authorize with `canRestartByPermission` (requester or `reassign`, same body as `canCancelByPermission`) plus read access; refusal `WorkflowsNotAuthorizedError` action `"restart a review step"`. `canRestart` = `review.checkRestart` and the predicate, ANDed with target access like the other flags (R33).
- R154. **No secret settings** (user answer Q6; supersedes the secret part of D67). Step config has no secret fields: no `.meta({ secret: true })` handling, no encryption, no write-only marker, no stripping on reads. Credentials belong to whoever writes the automation definition, in their own code or config, never set or seen by workflow editors.
- R155. **No built-in automation** (user answers Q2, Q3). "Send webhook" was only an example of a custom automation; no webhook step ships and nothing signs requests. Phase 5 builds the abstraction. Task 18 removes the "Send webhook built-in" wording from spec, roadmap and decisions (D86).
- R156. **Dependency.** `api-workflows` gains `@webiny/background-tasks` (for `GetTaskUseCase` and the `TaskController` state augmentation), declared in Task 11 (the first task that imports it: the `TaskController` augmentation) with the workspace version like the other deps, `adio` and `sync-dependencies` clean. ## Assumptions

- A51. The trigger/save race and the stuck-detection write race stay unlocked beyond R143 (D27); two concurrent writers on one step are accepted.
- A52. A review's id is assigned before its first step is reached (`RequestReviewUseCase` passes `mdbid()` to `Review.request`, then reaches, then saves), so the reach path can put it in the task input. The first save is a create, so a task can start before the review exists (R143).
- A53. A review whose workflow was edited or whose automation definition was removed mid-run keeps running from its snapshot; only reach and restart look the definition up again (D37, D81). The handler looks the definition up by id for `run`; a missing one fails the step (R146).
- A54. An automation step in `inReview` is owned by the automation actor, so `currentOwnerId` is null (D74) and the step never appears in "my reviews"; it appears in the failed list only once failed (D112).
- A55. Delay between iterations (`wait`) is honoured by the task runner as the continue delay; very short waits are subject to the runner's own scheduling.
