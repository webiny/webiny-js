> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Read first:** `../00-shared.md` — Global Constraints, Rulings R253-R266, Assumptions A92-A96, Task order, Interfaces by task (Tasks 12-15), and `../00-answers.md` (Q32-Q37). Decisions D82, D90, D107, D161, D163. Everything there binds every task here.

**Goal:** What the review bar, the progress popover and the details drawer show about AI and automation steps, and how they keep it current. A running step reads `{Step} running since {hh:mm}`, a failed one `{Step} failed: {reason}`, with the `Running` tag and tooltips; the bar and the drawer refetch when the websocket change message (Task 10) or an own action says the review changed, without refetch storms; when an automated step finished while the editor was locked, the bar reloads the content through the app's reloader and says "Content updated by {step}"; the drawer lists each step's attempts and the issues the AI reported, and operators open an attempt's background task in a panel. In `packages/app-workflows` (plus one extra icon in `packages/icons`).

**Depends on:** 8b.4 (Task 8 domain types, DTOs and `getStepRun`; Task 10 the permission set, the widened activity signal and the change message handler; Task 11 `isStepRunning` and the restart action). The API of 8b.1-8b.3 need not run. Tasks 17 and 18 (8b.7) implement `IReviewContentReloader`; Task 13 adds `contentReloader: null` to the two app init-params builders so every package keeps compiling, and those tasks replace the `null`.

## Review Focus for this sub-phase

Review Focus 5 (refetch storm or missed update: Task 13 the bar refetches once for a signal of its own review or revision, queues one during a load, its own `actionDone` refreshes once, a second `init` and `dispose` unsubscribe; Task 14 the same for the drawer), Review Focus 6 (the content reload: Task 13 the reloader runs once per finished non-user step, never re-initialises the presenter, a throwing or `false` reloader sets no notice, the notice shows only after a reload that changed the revision). Also check: R263 texts character for character in Tasks 12 and 14 (running, failed, tooltips, `Running` tag with `progress_activity`); the attempts rule R261 (people steps list none, the current attempt is last, running reads `since {start}`) and the operator gate on `showTaskLink` (R258, with several roles and `workflows.*`); R146 in the client (the panel and the view models never carry task input, output, logs, a raw error or, as text, a task id); the 8a expectations these tasks change on purpose (`getReviewMessage` failed text, the `getReviewProgress` segments, the drawer R203 tests) are replaced, not weakened; no logic is written twice (the run message and tooltip come from `getStepRunMessage` and `getStepTagTooltip`, the permission rule from `getWorkflowsPermissionSet`).
