# Workflows Phase 8b: Admin automation, AI and live updates

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The admin shows AI and automation steps as they run and fail, and lets the people allowed to restart a failed step do so. The bar, the progress popover and the details drawer show "{Step} running since {hh:mm}" and "{Step} failed: {reason}". Restart is offered in the bar, the drawer and the Content Reviews rows, with a confirmation dialog, a toast and conflict handling. The details drawer lists each step's attempts and the AI issues, and operators (workflows `editor` or `reassign`) can open each attempt's background task. Workflows reads the task, which is now kept until its review is deleted. Content Reviews gets the Failed steps tab, for viewers with `reassign` only. A new silent websocket message `workflows.reviewChanged` makes the bar, drawer, lists and widgets refetch when a review is requested and when a step starts, finishes partway, restarts or fails. When an AI or automation step changes the content while the editor is locked, the editor reloads the revision and says so ("Content updated by {step}…"). The CMS bulk trash of all loaded rows checks for reviews in progress before it starts its background task and shows the 8a warning.

**Architecture:** Eight sub-phases, bottom up; each ships and tests alone. 8b.1-8b.3 are API work, 8b.4-8b.6 are shared admin work in `app-workflows` (8b.4 also adds the app gateway methods so every package keeps building), 8b.7 is CMS and WB glue, 8b.8 is docs.

1. **8b.1 Live change message** (`api-workflows`): the tenant-scoped websocket send loop moves out of `ReviewNotifierService` into `ReviewWebsocketSender`; `ReviewChangeNotifierService` and five event handlers send `workflows.reviewChanged`.
2. **8b.2 Step run tasks** (`api-workflows`, `api-headless-cms-workflows`, `api-website-builder-workflows`): run tasks are kept and deleted with their review; the engine `GetReviewStepRunUseCase`, the CMS and WB wrappers and the `getCmsEntryReviewStepRun` / `getWebsiteBuilderPageReviewStepRun` queries.
3. **8b.3 Blocking reviews query** (`api-headless-cms-workflows`): `listCmsEntryBlockingReviews(modelId, entryIds)`.
4. **8b.4 Client core** (`app-workflows`, then the CMS and WB gateways): DTOs, fragments, mappers, gateway and use-case methods (`restartStep`, `getStepRun`, `listBlockingReviews`) and their app gateway implementations; the permission set; the widened activity signal and the change message handler; the restart action through every action table, dialog, conflict text and toast.
5. **8b.5 Review view** (`app-workflows`): running and failed messages, tags, tooltips and popover; the bar subscribes to activity and shows the content notice; the drawer subscribes and shows attempts and AI issues; the task panel.
6. **8b.6 Content Reviews** (`app-workflows`): the Failed steps tab and the row restart.
7. **8b.7 App glue** (CMS and WB packages, plus the shared guard for the bulk pre-check): the change message handler subclasses, the content reloaders and the CMS bulk pre-check.
8. **8b.8 Docs.**

**Tech Stack:** as phase 8a (`docs/.bruno/plans/2026-10-16-workflows-phase-8a/00-shared.md`), plus `@webiny/background-tasks` on the API side (`GetTaskUseCase`, `CleanupTaskSubtreeUseCase`) and `@webiny/api-websockets` (`WebsocketsListConnectionsUseCase`, `WebsocketsSendToConnectionsUseCase`).

5. **A refetch storm or a missed update** (R254, R260). Pinned by Task 13 (the reloader runs once per finished non-user step and never re-inits the presenter) and Task 17 (CMS: no reload while the form is dirty; the bar is not re-initialised; the notice shows only when the revision timestamps changed). 7. **Restart offered or sent when it must not be** (D34, D82). Pinned by Task 11 (Restart only with `flags.canRestart`; the conflict text when the step is no longer failed; `TargetSync` is a success) and Task 16 (row action).
8. **The Failed steps tab shows to viewers the server refuses** (R259). Pinned by Task 16 (tab hidden without `reassign` or full access; `?tab=failedSteps` falls back to the default tab) and Task 10 (permission set over several roles, `workflows.*` and `*`).
9. **The bulk pre-check leaks unreadable entries or skips the warning** (R265). Pinned by Task 7 (unreadable or missing entries never listed; unbound model returns `[]`; 201 ids refused) and Task 19 (all loaded rows: pre-check per chunk of 200, warning, cancel, then the bulk task; empty pre-check goes straight to the bulk task; a dismissed warning or a failed pre-check runs nothing).
10. **Workflows features active without the flag** (R211). Pinned by the flag-off mount tests of Tasks 10, 17, 18.

- R253. **`workflows.reviewChanged`** (user answer Q32). No title, no body, no toast (ids and namespace only, R200). One handler class per event in `[AWF]/features/notifications/handlers/` (`Review<Event>ChangeNotifications`); the `stepApproved` handler sends nothing unless `review.state === "inProgress"` (the final approval already sends `approved`). The 8 existing notification events do not also send it.
- R254. **Change recipients.** The requester (`review.createdBy.id`) and the current user owner (`review.currentOwnerId`), de-duplicated, minus the fact's actor when `actor.type === "user"` (pure `getReviewChangeRecipients(review: ReviewData, actor: Actor): string[]`, the phase 7 `dropActor` rule). The acting user's own tab refreshed through its own action; their other tabs update on reload. This keeps one refetch per action (R260). The `failed` handler removes the requester, who already gets the `failed` notification. No pool lookup (`NotificationRecipientService.listPool` is too heavy for a silent refetch). So pool members, and the people who get no toast for a take-over, reassign, reach or final decision, see those changes on reload or after their own action. API-key requesters have no connections; nothing is sent to them.
- R255. **One websocket sender.** The tenant-scoped, batched send loop of `ReviewNotifierService` (D149, R188, A63: current tenant only, `NOTIFICATION_SEND_CONCURRENCY` = 10, never throws, the existing log text and fields) moves into `ReviewWebsocketSender` (`[AWF]/features/notifications/ReviewWebsocketSender/`, own `ReviewWebsocketSenderFeature`, registered in `[AWF]/features/notifications/feature.ts`). The sender takes recipient ids, de-duplicates them and returns at once for none; the notifier keeps building its recipients and its frame. `ReviewNotifierService` and `ReviewChangeNotifierService` both depend on the sender. The phase 7 notifier tests keep their assertions; their setup gains the one `ReviewWebsocketSenderFeature.register(container)` line (`ReviewNotifierService.test.ts` registers features one by one), and the feature test's registration list gains the sender.
- R256. **Run tasks are kept and deleted with their review** (user answer Q33). `WorkflowStepRunTaskDefinition` drops `selfCleanup = "always"` (so no self cleanup; `databaseLogs` stays false) and its R179 comment says so. `DeleteTargetReviewsUseCase` gains the dependencies `CleanupTaskSubtreeUseCase` (from `@webiny/background-tasks/api/features/CleanupTaskSubtree/index.js`; Task 3 verifies the deep path, else uses `@webiny/background-tasks/api`) and `Logger`. After its existing abort it calls `CleanupTaskSubtreeUseCase.execute(taskId)` for every non-null `step.taskId` and `step.runs[].taskId` of every deleted review. Each call has its own `try`/`catch`: the use case documents that it never throws, but a decorator may; a catch logs `Could not clean up the background task of a deleted review.` with `reviewId` and `taskId`, and the delete still succeeds. A cleanup that fails is never retried (the review is already gone); accepted. Cancel keeps aborting only. `StuckStepService` already handles kept tasks (pending and running alive, failed and aborted after the grace, success stuck at once); no change.
- R257. **The step run read** (user answer Q33: "whatever is required for some user to determine if something was wrong or ok"). Engine `GetReviewStepRunUseCase` (internal, D132) input `GetReviewStepRunInput { reviewId: string; stepId: string; taskId: string }`. It loads the review (one more read after the wrapper's guard; accepted), finds the step and requires `taskId === step.taskId` or `taskId` in `step.runs[].taskId`, else `ReviewStepRunNotFoundError` (code `Workflows/Review/StepRunNotFound`, data `{ reviewId, stepId, taskId }`). It reads the task with `GetTaskUseCase.execute(taskId)` inside `try`/`catch` (a throw is a failed `ReviewPersistenceError`, R87). It returns `ReviewStepRunInfo | null`, `null` when the task record is gone. `ReviewStepRunInfo { taskId: string; status: StepRunTaskStatus; startedOn: string | null; finishedOn: string | null; iterations: number; outcome: StepRunOutcome | null; reason: string | null }`, with `StepRunTaskStatus = "pending" | "running" | "done" | "failed" | "aborted"` mapped from `TaskDataStatus` (`success` -> `done`, the others by name). `iterations` is the automation's own run count, computed as the task handler does (`WorkflowStepRunTaskHandler.ts`: `iteration = task.iterations - idWaits`, where `idWaits` defaults to `task.iterations - 1`): `task.iterations - (typeof output?.idWaits === "number" ? output.idWaits : task.iterations - 1)`, never below 0 (Task 4 re-reads the handler and copies its rule). `outcome` and `reason` come from the review step: the `runs[]` record of that `taskId`, or, for the current attempt, the step's state (`failed` -> outcome `failed`, reason `step.comment`; `approved`/`rejected` -> that outcome, reason `null`; still running -> both `null`). Times prefer the review's record (run record, or the step's `startedOn`/`finishedOn`) and fall back to the task's, `undefined` mapped to `null`. GraphQL `type WorkflowsStepRunInfo { taskId: ID! status: String! startedOn: DateTime finishedOn: DateTime iterations: Int! outcome: String reason: String }` (the existing `WorkflowsStepRun` stays the attempt record). The client mirrors the type and the status union under the same names.

## Decisions

Recorded in `docs/.bruno/workflows/decisions.md` by Task 20 (no SEC ids).

- **D160. Silent review change message.** Workflows sends `workflows.reviewChanged` (ids and namespace, no text) to the requester and the current owner (never to the acting user) when a review is requested and when a step starts, is approved partway, restarts or fails; the client refetches what shows that review. No pool lookup. Refines D60 (a websocket message is no longer always a toast). Source: Q32, R253-R255.
- **D161. Run tasks are kept, and workflows reads them.** A step's background task is kept until its review is deleted, and then cleaned up with the review. Workflows reads it through its own per-app query, gated on `editor` or `reassign` plus read access, and exposes only status, times, iterations, outcome and the fixed reason. **Supersedes** D90's link into the Background Tasks admin (that admin hides private tasks and has no link by id). Source: Q33, R256-R258.
- **D162. Client gates mirror the workflows permissions.** The Failed steps tab and the Background task link show only for viewers whose `workflows` permission allows them (full access, `reassign`; `editor` also for the link); the server keeps every check. Source: Q34, R259.
- **D163. Content reload after an automated step.** When an AI or automation step finishes while the editor is locked and the revision changed, the editor reloads it and says "Content updated by {step}". Source: Q35, R262.
- **D164. Pre-check before the CMS bulk trash.** Before trashing all loaded rows through the background task, the admin asks for the reviews in progress of those entries and shows the D157 warning first. **Closes** the D157 gap for the CMS (the WB bulk delete is per item). Source: Q38, R265.
