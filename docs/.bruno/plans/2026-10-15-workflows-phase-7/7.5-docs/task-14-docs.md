Create `docs/.bruno/workflows/notifications.md`, same style and depth as `docs/.bruno/workflows/automations.md` and `ai-tools.md` (numbered `##` sections, plain statements, rule ids in parentheses, one full example). Content, in this order (sections 1-9; verify every name, path, text and number against the as-built code; texts in quotes below are fixed texts from the plan and must be re-checked against `MailNotificationTransport.ts`, `features/notifications/ReviewNotifierService/ReviewNotifierService.ts` and `domain/notifications/`):

1. **What a notification is and what a transport is.** Review events notify their recipients (D44, R181, listed in section 8 of the guide) through two channels: a websocket message, always, and the transports configured on the step where the event happened (D103, R186). The engine ships one transport, e-mail. A transport is a class you register; it receives the recipients and one message per event and delivers it somewhere (an e-mail, a chat webhook, an SMS). The websocket message is not a transport and cannot be switched off (D96). Notifications are sent only when `advancedPublishingWorkflow` is on (R199).
2. **The abstraction.** `NotificationTransport` from `@webiny/api-workflows/features/notifications/NotificationTransport/index.js` (verify the path against the package `exports` map and the existing barrel), with the types `NotificationTransport.Interface`, `NotificationTransport.SendParams`, `NotificationTransport.User` and `NotificationTransport.Message` and the I-prefixed interfaces they alias (`INotificationTransport`, `INotificationTransportSendParams`, `INotificationTransportUser`, `INotificationTransportMessage`). Rule for your own code: write the class against the namespace types (`implements NotificationTransport.Interface`), never an inline object type. Fields: `id` (stable, stored on workflow steps as `notifications[{ id }]`; a rename breaks stored workflows; the e-mail transport is `"e-mail"`), `title` (shown in the editor's "Notify via" list), `description` (optional, shown next to the title), `send(params)`. The editor reads them through the shared `listNotificationTransports` operation (R191), which lists every registered transport.
3. **What `send` receives.** `{ users, message }`. `users` is a non-empty array of `{ id, email, displayName }` exactly as the user store holds them: the engine does not clean or validate addresses (R194), so a transport decides what it can use (an external identity provider user can have its identity id as `email`; the e-mail transport keeps an address only if it has exactly one `@` with text on both sides and no whitespace, comma, semicolon or angle bracket, R193). `message` is `{ title, body, url, linkLabel }`: `title` is the subject line, `body` is plain text with `\n` line breaks, `url` is the admin link to the content (admin host + path + a `tenantId` query parameter holding the current tenant's id) or `null` (no admin host, no link adapter for the app or no current tenant, R195), `linkLabel` is the text for the link (`Open content`). There is no HTML: a transport that sends HTML escapes it itself. One `send` call per event and per transport carries every recipient (R197); the text is the same for every recipient, so there is no per-recipient greeting (D44). Send blind (bcc) when the channel shows other recipients to each other.
4. **Escaping and user text.** Titles, step titles, display names and the rejection comment are user text (R146 mirror, R200). Escape everything you put in markup (`escapeHtml` and `toSingleLine` in `domain/notifications/` are internal helpers; copy the idea, do not import a private path), keep header values on one line (the e-mail transport collapses CR, LF and whitespace runs in the subject, R193) and never build a URL from message text: use `message.url`.
5. **Failure handling: `send` never throws.** `send` returns `Promise<void>`. It catches, logs once with `Logger.error` and returns; a notification never fails a review action (R190, R196, R87): the saver publishes after the save and handler exceptions propagate, so an uncaught throw would fail an approve that already happened. The engine wraps each transport call in its own try/catch as a last resort and logs `Could not send a workflow notification through a transport.` (verify the text); a transport still must not rely on that. A failure of one transport does not stop the websocket message or the other transports. There is no retry and no queue (A64, A65): a notification that fails is lost, the review state is the truth.
6. **Logging: no addresses.** Log with `Logger.error({ ... }, "<fixed text>")` using ids, the transport id and `error.code` and `error.name` only. Never log an address, the message, the error object or `error.message`: an SMTP or provider error often embeds the addresses it refused (R193, R196). The e-mail transport is the reference: it logs `{ errorCode, errorName, userIds }` under `Could not send a workflow notification e-mail.` once per failed chunk (verify against `MailNotificationTransport.ts`). Latency: `send` runs inside the user's request (A65), so keep it quick, chunk big recipient lists (the e-mail transport sends one mail per 50 bcc recipients, `MAIL_BCC_CHUNK_SIZE`, and a failed chunk does not stop the next) and put a timeout on every network call.
7. **Writing and registering a transport.** A transport is registered as a class (`NotificationTransport.createImplementation({ implementation, dependencies })`) in a feature (`createFeature` from `@webiny/feature/api`, `container.register(...)`) that is registered in the project's API like any API feature; use a new `id` for a new transport. Two registrations with one `id`: the notifier keeps the last resolved transport per id (a `Map`, override semantics), while the editor list (`ListNotificationTransports`) shows every registration, so a duplicate id appears twice in "Notify via" (verify both against the as-built Tasks 1 and 10). To override the built-in e-mail transport, register your class (id `"e-mail"`) in a feature that is registered after `WorkflowsFeature`. `container.resolveAll` returns `registerInstance` registrations before class registrations, and within each kind in registration order (verified in `node_modules/@webiny/di/dist/index.js`, `Container.resolveMultiple`: parent container first, then `instanceRegistrations`, then `registrations`, then factories), so an override must be a class registered later; an instance registration of the abstraction would come first and lose to any class. A workflow author picks transports per step in the editor; the choice is stored as the transport id. A transport unregistered later is skipped at send time and logged once with `A step names a notification transport that is not registered.`; it never blocks editing or saving a workflow (R192). Full example, a chat webhook transport (class with `Logger`, `createImplementation`, feature), copied into a scratch file and compiled before it is pasted (`yarn tsc` in the guide's example folder is not needed: place the scratch file inside `packages/api-workflows/src`, run `yarn check:test:types -p api-workflows --report cli 2>&1 | tail -40`, delete it afterwards):

   ```ts
   import { createFeature } from "@webiny/feature/api";
   import { Logger } from "@webiny/api-core/features/logger/index.js";
   import { NotificationTransport } from "@webiny/api-workflows/features/notifications/NotificationTransport/index.js";

   class ChatWebhookTransportImpl implements NotificationTransport.Interface {
       public readonly id = "chat-webhook";
       public readonly title = "Team chat";
       public readonly description = "Posts to the review channel in the team chat.";

       private readonly logger: Logger.Interface;

       public constructor(logger: Logger.Interface) {
           this.logger = logger;
       }

       public async send(params: NotificationTransport.SendParams): Promise<void> {
           const { users, message } = params;
           const text = message.url
               ? `${message.title}\n${message.body}\n${message.linkLabel}: ${message.url}`
               : `${message.title}\n${message.body}`;

           try {
               const response = await fetch(process.env.WEBINY_CHAT_WEBHOOK_URL as string, {
                   method: "POST",
                   headers: { "Content-Type": "application/json" },
                   body: JSON.stringify({ text }),
                   signal: AbortSignal.timeout(5000)
               });
               if (!response.ok) {
                   this.logger.error(
                       { status: response.status, userIds: users.map(user => user.id) },
                       "Could not send a workflow notification to the chat."
                   );
               }
           } catch (error) {
               this.logger.error(
                   { errorName: (error as Error).name, userIds: users.map(user => user.id) },
                   "Could not send a workflow notification to the chat."
               );
           }
       }
   }

   export const ChatWebhookTransport = NotificationTransport.createImplementation({
       implementation: ChatWebhookTransportImpl,
       dependencies: [Logger]
   });

   export const ChatWebhookTransportFeature = createFeature({
       name: "MyProject/ChatWebhookTransport",
       register(container) {
           container.register(ChatWebhookTransport);
       }
   });
   ```
