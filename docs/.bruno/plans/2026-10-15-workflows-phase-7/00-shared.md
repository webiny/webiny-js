# Workflows Phase 7: Notifications

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The review engine tells people what happened. Every review event in the D44 table (plus the take-over notice, D111) notifies exactly its recipients through two channels: a websocket message always (sent to the recipient's connections in the review's own tenant only, R188; one action with the event in `data`, carrying the review's namespace so the client opens the right app, D60, D133) and the transports configured on the step where the event happened (e-mail today, D103). Messages name AI and automation deciders by their step title (D107, D126). E-mails link to the content in the admin through the admin host from service discovery. The shared `listNotificationTransports` operation (`editor` only, D129, D133) lists the registered transports with an optional description. The take-over action carries `notifyPreviousOwner` (default true) through the fact, the engine use case, the CMS and Website Builder wrappers and their GraphQL (D111). A failing mailer or websocket never fails a review action. No stored inbox, no per-user setting, no client work.

**Architecture:** Five sub-phases, built bottom up. Each ships and tests alone; every one ends green on the phase 2-6 tests it touches.

1. **Transports operation** (`packages/api-workflows`, 7.1): `ListNotificationTypes*` becomes `ListNotificationTransports*`, `description` on `NotificationTransport`, the unused `NotificationType*` leftovers deleted, the new transport message shape, the shared `listNotificationTransports` operation, and the e-mail transport fixed (HTML escaping, `Logger`, link, bare addresses).
2. **Take-over opt-out** (`packages/api-workflows`, `api-headless-cms-workflows`, `api-website-builder-workflows`, 7.2): `notifyPreviousOwner` on the engine input and on `ReviewStepTakenOverFact`, then on both wrappers and both GraphQL mutations. Independent of every other sub-phase (needed by 7.4).
3. **Messages, recipients and links** (`packages/api-workflows`, CMS and WB adapters, 7.3): the pure message builders (one file per event), the `NotificationRecipientService` (pool members, e-mail lookup), the admin URL service and the `ReviewTargetLink` port with its CMS and WB adapters.
4. **Notifier and handlers** (`packages/api-workflows`, 7.4): the `@webiny/api-websockets` dependency, the `ReviewNotifierService` (websocket plus step transports, bounded fan-out, nothing thrown), one event handler per notifying event, and the end-to-end tests through the real saver and the background-task identity.
5. **Docs** (7.5): the developer guide for notification transports, spec, roadmap, decisions, stale "phase 7" comments.

**Why five and not the four the notes proposed (7.3 handlers+websocket+take-over flag):** the take-over flag crosses three packages, two GraphQL schemas and two wrapper test suites and has no dependency on the notifier; folding it into the handlers sub-phase would make that sub-phase's review span engine, CMS, WB and websocket code at once. It is its own sub-phase (7.2) and can land before or after 7.1. The CMS and WB link adapters (Task 9) are in 7.3 because the engine cannot know admin routes (D133: the client opens the right app by namespace; the same port pattern as `ReviewTargetEditor`).

**Tech Stack:** TypeScript, `@webiny/feature` DI, `@webiny/api-core` (`Logger`, `IdentityContext`, `ListUsersUseCase`, `ServiceDiscovery`, event publisher), `@webiny/api-mailer` (`MailerService`), `@webiny/api-websockets` (`WebsocketsListConnectionsUseCase`, `WebsocketsSendToConnectionsUseCase`), `@webiny/api-graphql`, vitest.

## Global Constraints

- **No helper functions or private methods that wrap a dependency call** (use case, service, reader, repository, logger, websocket, mailer). Call dependencies inline in the owning class with the Result pattern or an inline `try`/`catch`. Shared logic that needs dependencies becomes a DI service named `...Service`. Pure functions (no dependency, no I/O) are allowed, and the message builders are exactly that. Inline duplication of dependency calls is intended.
- **R87:** a dependency throw becomes a failed Result (config and wrapper use cases) or a logged and swallowed failure (notifier, handlers, transports), never a rejected promise out of an event handler. `ReviewSaver` publishes after the save and lets handler exceptions propagate (`ReviewSaver.ts` "Handler exceptions propagate"), so an uncaught throw would fail a request whose review is already saved.
- **R146 mirror (raw errors never reach a message):** a thrown error, a provider or mailer error, a storage error and a stack are logged with `Logger.error` and never put in a websocket message, e-mail subject, body or link. The only free text in a message is the content title, the step title, a person's display name, the rejection comment (R189) and the step failure `reason`, which is already a fixed text (R146, R170).
- **D132:** the engine never checks permissions for notifications; the notifier and handlers read no identity for access decisions. The shared `listNotificationTransports` operation checks `editor` and nothing else (D133). Only the wrappers pass `notifyPreviousOwner`; the engine use case defaults it.
- **SEC-66:** `ListUsersUseCase` needs `adminUsers.user`: wrap only that lookup in `identityContext.withoutAuthorization`, never a read check. `RoutingEvaluatorService.listMembers` computes `canRead` (its read check runs per member, R111-R113 of phase 4) but filters nothing: `NotificationRecipientService.listPool` must itself keep only members with `!member.exclusion && member.canRead`; do not re-implement the read check, only use its flag.
- DI conventions: one abstraction or implementation per file; implementation file named after its class (never `implementation.ts`); export name matches the abstraction; namespace types; minimal barrels (export only what an external package consumes); no inline object types (named interfaces); registries are `Map` by key, last registration wins; `@webiny/di` resolves `registerInstance` before class registrations, so a test override by instance beats the feature's class.
- **Storage key formats are frozen.** No model, key or schema change in this phase. `notifyPreviousOwner` lives on the in-memory fact and the event only (R185).
- Before every commit: `git add .`, `yarn > /dev/null 2>&1`, `node scripts/generateTsConfigsInPackages.js`, `yarn adio`, `yarn check-ts-configs`, `yarn format:fix > /dev/null 2>&1`, `yarn lint:fix`, `yarn webiny sync-dependencies`, `yarn build -p <package> --no-cache 2>&1 | tail -30` for changed packages, `git add .`. Restore `.gitleaks.toml` (`git checkout -- .gitleaks.toml`); never commit it, `docs/.reports` or `.superpowers`.
- Commits: Conventional Commits, one `-m` for the subject and a separate `-m` for the trailer block, ending with exactly:
  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_01EWvjsBXWqViJPTrgbzhYr4
  ```
  Never push, amend or revert.
- **Tests are targeted:** run the test files you add or change and the files covering the changed code, by path (`yarn test packages/<pkg>/__tests__/<file>.test.ts`, then the same with `yarn test:os`: workflows assume OpenSearch, D63). Never a whole package suite unless the dispatch asks. Run `test:os` runs one at a time (parallel runs clash on port 8001).
- Type-check tests, per package the task touched: `yarn check:test:types -p <folder> --report cli 2>&1 | tail -40` (folder name, e.g. `api-workflows`; several as `-p a,b`) prints no errors.
- TDD: failing test first, record RED before source.
- **No mail is sent and no websocket frame leaves a test.** Tests register stub instances for `MailerService`, `WebsocketsListConnectionsUseCase` and `WebsocketsSendToConnectionsUseCase` (Task 10 adds `__tests__/__helpers/RecordingMailer.ts`, `FakeWebsocketConnections.ts` and `RecordingWebsocketsSend.ts`, with failing and throwing variants); the registration test stubs both. Nothing reads real service discovery: tests set a fake loader and call `ServiceDiscovery.clear()` after.
- `api-workflows` gains `@webiny/api-websockets` (Task 10). `api-headless-cms-workflows` and `api-website-builder-workflows` gain no new dependency in this phase. The client packages (`app-workflows` and the app packages) are not touched (stale `listWorkflowNotificationTypes` gateway: flag only, client phases 8-9).

## Review Focus

1. **A failing mailer or websocket breaks a review action** (R196, R87). The saver publishes after the save and handler exceptions propagate. A notifier or handler that throws, or a failed Result from `MailerService`, the websocket list and send use cases, `ListUsersUseCase`, `RoutingEvaluatorService.listMembers` or `ServiceDiscovery.load` that is not caught, fails an approve, reject, take over or cancel that already happened. Pinned by Task 10 (every dependency throwing and failing, one at a time, the notifier resolves and logs once) and Tasks 11-12 (each handler with a throwing notifier and a throwing recipient service resolves), and Task 13 (the real saver with a throwing mailer and websocket returns the saved review).
2. **Notifying the actor themselves, or skipping the wrong people** (R184). The AI and automation actors carry the requester's id (D58), so a naive "recipient is the actor" skip would drop the requester's own "Review rejected" and "Step failed" notices. The skip applies only when `fact.actor.type === "user"`, and never to `stepFailed`. Pinned by Tasks 11-12 (the same user as actor and recipient: skipped; an `ai` or `automation` actor with the requester's id: the requester is notified; `stepFailed` with a user actor equal to the requester: notified).
3. **Leaking another tenant's or a private model's data** (R188, R189, A63). A user id can have live connections in another tenant; websocket delivery is therefore filtered to connections whose `tenant` equals the current tenant (R188). The message also carries only ids, the namespace, the content title, the step title and display names of people already part of the review; no field values, no target data, no tenant data. Pool members are the members `listPool` keeps (`!exclusion && canRead`), never the whole team and never `listMembers`' raw result. Pinned by Task 6 (message texts contain only the listed inputs), Task 7 (`listPool` keeps only `!exclusion && canRead`: an excluded member and a member who cannot read get nothing, the requester is not returned), Task 10 (the websocket data keys are exactly the contract of R187; a recipient with connections in two tenants: only the current tenant's connection receives the frame, and a recipient connected only in another tenant gets nothing and no error) and Task 13 (the same through the real saver and inside the background-task step run).
4. **Raw error text in a message** (R146 mirror, R196). Pinned by Task 10 (a mailer, websocket and lookup failure with a recognisable secret string: the string is in the logs, in no sent message) and Task 12 (the failed-step message uses only `fact.reason`).
5. **Duplicate or stray notifications** (R181, R183, A64). One save can publish several facts (approve of the last step: `stepApproved` then `approved`; approve of a step: `stepApproved` then `stepReached`). Only the D44 events notify, each once. Pinned by Task 13 ("approve of a middle step notifies the next owner only", "approve of the last step notifies the requester once", "pool Start, restart, requested and a middle-step approve send nothing"). Restarts and stuck detection publish through the same saver, never twice per fact, except the accepted A64 race (concurrent stuck detection or a late hook publishing `stepFailed` twice); there is no dedupe store (A64).
6. **Unescaped HTML in e-mail, header injection, a raw URL in the body** (R193). Content titles, step titles, display names and comments are user text. Header values are user text too: the subject is collapsed to one line (R193). Pinned by Task 3 (`<script>`, `"`, `&`, newlines in title, body and display name: escaped in `html`, untouched in `text`; CR, LF and whitespace runs in a subject collapsed to single spaces; no raw newline or quote in an address header) and Task 8 (the link is built from the admin host and an encoded path, never from message text).
7. **The take-over opt-out leaks or defaults wrong** (R185, R198). Missing flag means notify. Pinned by Task 4 (engine default true, the fact carries the flag, `false` suppresses the notice) and Task 5 (both wrappers and both GraphQL mutations pass `true` when the argument is omitted and `false` when given).
8. **The step channels of the wrong step are used** (D103, R186). Approved uses the last step, rejected the rejecting step, cancelled the step the review was on, failed the failed step, reached and reassigned their own step. Pinned by Task 10 (transport selection by step) and Tasks 11-12 (one test per event with different `notifications` on two steps).
9. **Latency added to the user's action** (A65). Handlers are awaited by the saver; a pool of hundreds costs hundreds of connection lookups. Bounded concurrency (R197) and a single e-mail per event bound it; there is no queue. Bulk cancels when content is trashed or deleted notify each review's owner serially inside the request (A65), a known latency cost.

## Rulings

- R181. **Which events notify** (user answer Q1). Exactly the D44 rows plus the take-over notice (D111): `stepReached` (pool: candidate team members; owner: the owner), `stepReassigned` (old and new owner), `stepTakenOver` (previous owner), `approved` (requester), `stepRejected` (requester, "Review rejected"), `stepFailed` (requester), `cancelled` (current owner, if any). `requested`, intermediate `stepApproved`, pool `stepStarted` and `stepRestarted` send nothing. There is no refetch-only message to non-recipients (D60: every message is a notification to a recipient).
- R182. **Architecture** (notes). One event handler class per notifying event in `features/notifications/handlers/`, thin: pick recipients, build the message, call the one shared `ReviewNotifierService`. Handlers catch everything (try/catch around the whole body, `Logger.error`, return). Registered by a `ReviewNotificationsFeature` that `WorkflowsFeature` registers (it replaces the "recipient rules arrive in phase 7" comment). The notifier is a DI service; handlers do not call transports or websockets directly. No handler subscribes to `stepStarted`, `stepRestarted`, `stepApproved` or `requested`.
- R183. **Recipient rules** (D44, D111, notes). Owner means the step owner when `owner.type === "user"` (AI and automation owners carry the requester's id, D58, and are never notified as owners, which also keeps D107). Table (`review` is the saved review, `step` the step named in the row):

  | Event (fact) | Recipients | Step for channels (R186) |
  |---|---|---|
  | `stepReached`, `fact.owner` is a user | that owner | `fact.change.stepId` |
  | `stepReached`, `fact.owner` is `null` (pool) | `NotificationRecipientService.listPool`: `RoutingEvaluatorService.listMembers` of the step's `candidateTeamIds` (params built like `ListStepCandidatesUseCase`), keeping only members with `!member.exclusion && member.canRead` (`listMembers` returns every team member except the requester with `exclusion` and `canRead` flags and does not filter on them, R194) | `fact.change.stepId` |
  | `stepReached`, `fact.owner` is `ai` or `automation` | nobody | n/a |
  | `stepReassigned` | new owner (`fact.owner`) and old owner (`fact.previousOwner`, when a user) get two different messages (R189) | `fact.change.stepId` |
  | `stepTakenOver` | `fact.previousOwner`, only when `fact.previousOwner.type === "user"` and `fact.notifyPreviousOwner` is true (R185) | `fact.change.stepId` |
  | `approved` | requester (`review.createdBy`) | the last step of `review.steps` (the one that approved) |
  | `stepRejected` | requester | `fact.change.stepId` |
  | `stepFailed` | requester | `fact.change.stepId` |
  | `cancelled` | the owner of step `fact.stepId` when `fact.stepState === "inReview"` and that owner is a user; the cancel does not clear `step.owner`, so the owner is read from `review.steps` (verified in `Review.cancel`), never from `review.currentOwnerId` | `fact.stepId` (nobody when `null`) |

  A recipient is always a user id; duplicates are removed.
- R184. **Never notify yourself** (notes). A recipient whose id equals `fact.actor.id` is dropped only when `fact.actor.type === "user"`. AI and automation actors carry the requester's id (D58), so they never drop the requester. `stepFailed` never drops anyone (its actor can be the requester as a user, R140, and the requester must still hear about the failure). Applied by a pure function `dropActor(recipients, actor)` in `domain/notifications/`.
- R185. **Take-over opt-out** (user answer Q2, D111). Only the per-action flag. `TakeOverReviewStepUseCase.Input` gains `notifyPreviousOwner?: boolean` (default `true`, `undefined` counts as true); `Review.takeOver` params gain the same; `ReviewStepTakenOverFact` gains `notifyPreviousOwner: boolean` (always set). The flag is not stored on the review or anywhere else (storage keys frozen); the event is the only carrier. No stored per-user setting; `WorkflowSettings` exclusions (D105) are not reused. Reassign has no flag (D111).
- R186. **Channels** (D44, D103, notes). Every message is sent to every recipient through the websocket (always, not an option, D96) and through every transport id in `step.notifications[].id` (`WorkflowStepNotification { id }`) of the step in the R183 table, in that step's own order, deduplicated on `id`. No workflow-level channel. An unknown transport id (a transport unregistered later) is skipped and logged once per notification with a fixed text (R192).
- R187. **Websocket contract** (user answer Q4). One action `workflows.notification` (constant `WORKFLOWS_NOTIFICATION_WEBSOCKET_ACTION` in `domain/notifications/constants.ts`), `data` of type `WorkflowNotificationWebsocketData`:
  ```ts
  { event: WorkflowNotificationEvent; reviewId: string; stepId: string | null; namespace: string; targetId: string; targetRevisionId: string; title: string; body: string }
  ```
  `namespace` is `review.model` (so the client opens the CMS or WB app, D133), `stepId` is the step the event concerns (`null` only for a cancel with no step; such a cancel notifies nobody, so it is never sent), `title` and `body` are the in-app texts (R189). `WorkflowNotificationEvent = "poolReached" | "assigned" | "reassigned" | "takenOver" | "approved" | "rejected" | "failed" | "cancelled"`. No `messageId`, no `error`. Sent only to recipients. The client also fires `WorkflowStateChangedEvent` for every message (D60, client phase).
- R188. **Websocket sending** (verified in `packages/api-websockets`; revised: delivery stays inside the review's tenant). `WebsocketsSendToIdentityUseCase` is NOT used: it lists connections by identity id only (`ListConnectionsUseCase`, `where: { identityId }`) with no tenant filter, so a user connected in another tenant would receive the frame. The notifier instead, per recipient, skips a recipient whose id is empty or not a string (no list call: `where: { identityId: "" }` would fall through to listing every connection, `ListConnectionsUseCase` tests the id for truthiness) and otherwise calls `WebsocketsListConnectionsUseCase.execute({ where: { identityId: recipient.id } })` (rows `ConnectionRegistry.Data { connectionId, identity, tenant, connectedOn, endpoint }`, only connections newer than 3 hours), keeps the rows whose `tenant` equals `TenantContext.getTenant().id` (`@webiny/api-core/features/tenancy/TenantContext/index.js`, the current tenant, which is set inside a request, an event handler and the background-task step run alike; read inside the same try/catch as the sends, and when there is no current tenant or the read throws nothing is sent and it is logged once), maps them to `{ connectionId, endpoint }` and calls `WebsocketsSendToConnectionsUseCase.execute(connections, { action, data })` once per recipient (no kept connection: no send, no error). Both imports come from `@webiny/api-websockets/exports/api.js`. Both use cases return a failed Result for a list or transport error and do not throw for those; the notifier still wraps each in a try/catch. A recipient connected only in another tenant gets nothing. `WebsocketsFeature` is registered in the per-request stack with a `NullWebsocketsTransport` default (`registerApiRequestStack`), so the abstractions always resolve; a project without a real-time transport sends nothing and that is not an error. A failure is logged once per recipient (`Logger.error` with ids only) and never retried.
- R189. **Message texts** (D107, D111, D126; copy from the design `Notifications.dc.html`, simplified in A62). Inputs: `T` = `review.title`, `S` = the step title, `D` = decider (R189a), `C` = the rejection comment (always present: a reject needs a comment of at least `REJECT_COMMENT_MIN_LENGTH`, D100, and the AI and automation runners enforce it too, so there are no "rejected without a comment" variants), `R` = the step failure `fact.reason` (a different field from the cancel reason `ReviewCancelledFact.reason`). Typographic quotes `“ ”` around `T` and `C` as in the design. Each builder returns `NotificationMessage { title, body, subject, text, linkLabel }`: `title` and `body` are the websocket (in-app) texts; `subject`, `text` and `linkLabel` go to the transports (`subject` becomes the transport message `title`, `text` its `body`).

  | Event | `title` | `body` | `subject` | `text` | `linkLabel` |
  |---|---|---|---|---|---|
  | `poolReached` | `“{T}” is waiting in the team pool` | `{S} · requested by {requester}` | `Team pool: {T} ({S})` | `“{S}” is waiting in the team pool. Anyone in the team can start it.` | `Open content` |
  | `assigned` (reached, owner is a user) | `You’re reviewing “{T}”` | `{S} · {reason}` | `You’re reviewing: {T} ({S})` | `You are the owner of {S}. Open the content to approve or reject it.` | `Open content` |
  | `assigned` (reassign, new owner) | `You’re reviewing “{T}”` | `{S} · reassigned to you by {operator}` | same as above | same as above | `Open content` |
  | `reassigned` (old owner) | `“{T}” was reassigned to {newOwner}` | `{S} · reassigned by {operator}. You no longer own this step.` | `Reassigned: {T} ({S})` | `{operator} reassigned this step to {newOwner}. You don’t need to review it any more.` | `Open content` |
  | `takenOver` | `{taker} took over {S} on “{T}”.` | `You no longer own this step.` | `Taken over: {T} ({S})` | `{taker} took over {S} on “{T}”. You don’t need to review it any more.` | `Open content` |
  | `approved` | `“{T}” was approved` | `All steps approved. It’s ready to publish.` | `Approved: {T}` | `Every step approved this revision. It’s ready to publish.` | `Open content` |
  | `rejected` | `“{T}” was rejected at {S}` | `{D}: “{C}”. Create a new revision to fix it.` | `Rejected: {T} ({S})` | `{D} rejected this revision at {S}: “{C}”. This revision can’t be changed; create a new revision, fix it and request a new review.` | `Open content` |
  | `failed` | `{S} failed on “{T}”` | `{R} You can restart the step.` | `Step failed: {T} ({S})` | `{S} hit a technical error. {R} The review is paused at this step until it is restarted.` | `Open content` |
  | `cancelled`, `fact.reason` is `null` or unknown | `The review of “{T}” was cancelled` | `Cancelled by {canceller}. You no longer need to review {S}.` | `Review cancelled: {T}` | `{canceller} cancelled this review. You don’t need to review {S} any more.` | `Open content` |
  | `cancelled`, `fact.reason === "content trashed"` | `The review of “{T}” was cancelled` | `The content was moved to the trash. You no longer need to review {S}.` | `Review cancelled: {T}` | `The content was moved to the trash, so this review was cancelled. You don’t need to review {S} any more.` | `Open content` |
  | `cancelled`, `fact.reason === "content deleted"` | `The review of “{T}” was cancelled` | `The content was deleted. You no longer need to review {S}.` | `Review cancelled: {T}` | `The content was deleted, so this review was cancelled. You don’t need to review {S} any more.` | `Open content` |

  The cancel reasons are the two constants `REVIEW_CANCEL_REASON_CONTENT_TRASHED = "content trashed"` and `REVIEW_CANCEL_REASON_CONTENT_DELETED = "content deleted"` (`domain/review/getDeleteCancelReason.ts`, set by `getDeleteCancelReason` for the delete and trash wrappers, D134; a normal cancel has `reason: null`). The builder switches on those constants; any other non-null reason falls back to the `Cancelled by {canceller}` text and is never printed (R146 mirror). `dropActor` (R184) is unchanged: the owner who cancels their own step's review is not notified.
  R189a. **Naming** (D107, D126): `getActorName(actor, stepTitle)` is `actor.displayName` for `type "user"` (trimmed; a blank name reads `A user`) and `stepTitle` for `ai` and `automation`, so `{D}`, `{operator}`, `{taker}`, `{canceller}`, `{requester}` and `{newOwner}` never show an automation's or a model's name. Every person name a message shows (`{D}`, `{operator}`, `{taker}`, `{canceller}`, `{requester}`, `{newOwner}` and the reassigner in `assigned`) goes through `getActorName` with the actor, never a raw `displayName`, so a blank name reads `A user` (Tasks 11-12 pass actors). The D107 and D126 no-comment rejection texts are not needed here (a rejection always has a comment); they stay a client display concern. `{requester}` is `review.createdBy.displayName`. `{reason}` for `assigned` by `fact.assignment?.source`: `picked` → `picked by {requester}`, `rule` → `assigned by a routing rule`, `roundRobin` → `assigned by round-robin`, `leastLoaded` → `assigned by least-loaded`, anything else → `assigned to you`. `{R}` is the fixed reason, already a sentence ending in a full stop (R170, R146). The rejection comment `C` is clamped to at most `NOTIFICATION_COMMENT_MAX_LENGTH = 300` code points including the `…` (trimmed; when cut, 299 code points are kept, `trimEnd` is applied and `…` appended; counted by code point so an emoji is never split); the websocket and the e-mail use the same clamp. One pure builder file per event row in `domain/notifications/messages/`, unit tested with exact strings. `buildAssignedMessage` takes `reason: string | null` (null reads "assigned to you") and `getAssignmentReason(source: AssignmentSource | null | undefined, …)` accepts a missing source.
- R190. **Transport interface** (D129, D133, notes). `NotificationTransport` gains `description?: string` and its `send` contract is stated: it never throws and never fails the notification (it catches, logs once with `Logger.error` and returns). `send({ users: NonEmptyArray<NotificationTransport.User>, message: NotificationTransport.Message })` where `NotificationTransport.Message` is `{ title: string; body: string; url: string | null; linkLabel: string }` (`title` = subject, `body` = text, R189). Everything stays `void`-returning. - R191. **Transports operation** (D129, D133, notes). ## Assumptions

- A62. The design copy (`Notifications.dc.html`) is simplified where the data is not at hand: no `{team}` name (the pool text says "the team pool"; no team lookup), no `{rule}` name in the assignment reason (the rule id is not a name), no per-recipient greeting and no detail card in the e-mail (one mail, many `bcc` recipients, plain paragraphs), and every link opens the content, also where the design says "review details" (the review bar is on the content). A cancel caused by trashed or deleted content (R189) links to content that may be in the trash; accepted. Richer e-mail and the exact "review details" deep link are a later refinement.
- A63. Websocket delivery is tenant-scoped by the notifier (R188), not by the websockets layer: `ListConnectionsUseCase` can list an identity's connections across tenants, so the notifier filters on `connection.tenant === TenantContext.getTenant().id` before `WebsocketsSendToConnectionsUseCase`. This costs one connection lookup plus at most one send per recipient. Only connections younger than 3 hours receive a message (`ListConnectionsUseCase`); an older tab is missed until it reconnects, matching D60 (no stored inbox). The message still carries no tenant data (R200).
- A64. Delivery is at most once per published fact: the saver publishes once after the save, there is no dedupe store and no retry. A request retried by the client that fails after the save and is repeated is refused by the engine guards, so it publishes nothing twice. Two exceptions are accepted: concurrent stuck detection, or a late task hook racing it, can both save the failure and publish `stepFailed` twice, which notifies the requester twice (rare; D27 has no optimistic lock). A process that dies between the save and the notification loses that notification; the review state is the source of truth and the lists refetch (D47, D60).
- A65. Handlers are awaited inside the user's request (an un-awaited promise is lost in Lambda), so mail and websocket latency adds to approve, reject, cancel and take over. Bounded concurrency (R197) and one mail per event keep it small; a queue is a later optimisation. Bulk cancels when content is trashed or deleted (`CancelTargetReviews`, `DeleteTargetReviews`, D134) publish one `cancelled` event per review and notify each review's owner serially inside the request, with the same per-notification failure handling; accepted for now and a known latency cost to revisit (no new mechanism in phase 7).
- A66. A recipient who lost read access since (an old owner after a reassign, the previous owner after a take-over) still gets the message: it carries only the content title and step title, which they saw when they held the step (R200). The pool is filtered by read access (R183).
- A67. The requester of a review started with an `api-key` identity (D133) has no user, so no e-mail and a websocket send that finds no connection; both are silent, not errors.
