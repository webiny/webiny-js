# Workflows Phase 9b: People step assignment and Test routing

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The People step drawer gets its Assignment and Test routing tabs. On the Assignment tab an admin with the workflows `editor` permission picks the strategy (radio cards), switches "Let the requester pick a reviewer", and edits an ordered list of routing rules: up/down reorder, delete, conditions (requester user, requester team, folder with subfolders) and a target (a reviewing team's pool or a member of the reviewing teams), each rule with a readable summary and its warnings and errors. Saved user, team and folder references resolve by id, so a value is never shown empty (D117: "Deleted user", "Deleted team", "Restricted folder", "Deleted folder"). Stale targets (a user or team outside the reviewing teams, a deleted user) block Save on the client and on the server, and a server rule error lands on its rule card. The Test routing tab runs the server's routing evaluator on the unsaved step and shows the owner, the trace of every rule, the strategy line and the skipped people, and marks the result out of date when anything it depends on changes. The step card and the drawer show `Rule {n}:` warnings and errors, the card summary names the strategy, rule count and requester pick, and a tab with an error shows it with a banner. The API gains the team filter on `listUsers`, the rule id on validation errors, the team-target save check, the richer `inspectRouting` answer and the teams-off behaviour. The admin-ui `RadioGroup`, `CheckboxGroup` and `Checkbox` are fixed first and the 9a forms switch back to them.

## Rulings

- R285. **Scope** (Q50, Q56). 9b is the People step's Assignment and Test routing tabs, the Test routing inspector, saved-reference resolution, the People hint's full text, the People card summary and `Rule {n}:` lines, the admin gateways and the per-app folder list, the API changes of Q49, Q51, Q52, Q55, Q58, and the admin-ui fix of Q57. The Automation step's `user` ui hint gets its picker (9a R271). Not in 9b: any `listStepCandidates` work and any change to the 8a `ReviewerPicker` (the roadmap row 9b is stale; Task 25 corrects it and `app.md`). Warnings 9b can compute: deleted user or team, user outside the reviewing teams, team target outside them, deleted or restricted folder. Not shown in the editor: read access ("{Name} can't read {Model} content."), exclusions ("{Name} is unavailable (excluded until ...)..." and the picker's "Unavailable" note); Test routing reports both through the server's skipped people.
- R286. **`listUsers` team scope** (Q49, Q58). `workflows { listUsers(search: String, ids: [String!], limit: Int, teamIds: [String!]) }` gains the optional `teamIds`; a user matches when any of the user's teams is in `teamIds` (the `teams_in` filter `StoreWorkflowUseCase` already uses), combined with `search` and the limit rules unchanged (default 50, max 200, sorted by display name then id). An `ids` lookup ignores `search`, `limit` and `teamIds`, so a saved target that left the teams still resolves. The result type becomes `WorkflowsListedUser { id: ID! displayName: String! teamIds: [String!]! }` (new, like `WorkflowsTeamSummary`; `WorkflowsUser` stays for owners and candidates) and `WorkflowsUserListResult.users` uses it. With teams off: no team lookup, `teamIds` is `[]` on every user, and a request with `teamIds` returns no users. The use case reads each user's team ids from the admin user it already lists; it exposes ids only, never team names.
- R287. **Teams-enabled check** (Q58, A101). No wrapper abstraction. `ListWorkflowUsersUseCase`, `ListWorkflowTeamsUseCase` and `ReviewStepType` inject the api-core `FeatureFlags` abstraction (`api-workflows` already injects it in `WorkflowsFeature.ts` and `ListWorkflowStepTypesUseCase.ts`) and call `featureFlags.get().isEnabled(TEAMS_FEATURE_FLAG)` on every request (the value is re-read per call; never cached at registration). `TEAMS_FEATURE_FLAG = "advancedAccessControlLayer.teams"` is defined once in `[AWF]/constants.ts`.
- R288. **Rule error data** (Q51, Q52). `WorkflowValidationErrorData` gains `ruleId: string | null` (default `null`); the GraphQL error `data` is untyped `JSON`, so no schema type changes. The team-target and no-target checks already exist in `ReviewStepType.validate` (via `findReviewStepConfigProblem`, which already returns the rule id) and the user-target membership check in `StoreWorkflowUseCase`; Q51 and Q52 change their message, field and data, they are not new checks. Rule-level failures name the rule field `config.assignment.rules.target` and set `ruleId` and `stepId`: a rule without a target (message unchanged), a user target who is not a member of the step's teams (`The target user is not a member of the step's teams.`), a team target outside the step's teams (`The target team is not one of the step's reviewing teams.`). The three strings live in one constants module `[AWF]/domain/workflow/ruleErrorMessages.ts` used by `ReviewStepType`, `StoreWorkflowUseCase` and `InspectRoutingUseCase` (which today has its own wording for the no-teams and team-target checks and no field data): the inspector's rule failures use the same messages and set `field` and `ruleId`, so Test routing shows them as `Could not test routing: {server message}`. Schema failures keep `config.assignment.rules.<index>.<path>` (no `ruleId`). The whole-list field `config.assignment.rules` is no longer emitted.
- R289. **`inspectRouting` extension** (Q55). Shared SDL (`[AWF]/graphql/WorkflowsSchemaFactory.ts`): `WorkflowsRoutingTraceOutcome` gains `notEvaluated` (rules after the deciding rule; `reason` null); `WorkflowsRoutingTraceEntry` gains `failedConditions: [WorkflowsRoutingCondition!]!` where `enum WorkflowsRoutingCondition { requesterUser requesterTeam folder }` (non-empty only for `notMatched`; a failed `modelId` condition adds nothing); `WorkflowsRoutingInspection` gains `narrowedTeamId: ID` (the team a matched team-target rule narrowed to, else null; derived from `ruleId` and the step's teams), `candidateIds: [ID!]!` (the first `INSPECTION_CANDIDATE_LIMIT` = 3 candidate ids in the order the strategy considers them, empty when the rule chose the owner or nobody is eligible) and `candidateCount: Int!` (all candidates, so the editor can say `and others`). Existing fields, reasons and errors are unchanged. The trace lists every rule in order. No per-person load numbers (D104). **Inspector mode only:** `RoutingEvaluateParams` gains `explain: boolean`; with it the evaluator evaluates every condition of every rule (including requester teams and the folder chain) to fill `failedConditions`, and keeps walking the rules after the deciding one, marking them `notEvaluated` without assigning. Without it (live assignment at reach) the evaluator stays lazy and unchanged. `RoutingEvaluation` and `domain/routing/toRoutingEvaluation.ts` carry the new fields; the strategy order is returned from the evaluator.
- R290. **Teams off** (Q58, Q59.5). `listStepTypes` reports the `review` type `available: false` with `unavailableReason` `Teams are not enabled.`; `listTeams` returns `{ teams: [], missingIds: [] }` without querying (still `editor`-gated; more than 200 ids is still refused); `listUsers` per R286. The editor presenter does not call `listTeams` for a People step of an unavailable `review` row. The editor lists People disabled with that reason (D122); a saved People step loads read-only with the card warning and the drawer notice `This step needs teams, which are not enabled. It can't be edited.` (move and delete stay enabled, QBZ-47); Automation and AI steps work as before. The People step is read-only exactly when the `review` row of `listStepTypes` is not available (Task 16).
- R291. **Admin gateways** (D133). Shared `IWorkflowConfigGateway` and `IWorkflowConfigUseCases` gain `listUsers(params: ListUsersParams): Promise<…WorkflowUserList>` with `ListUsersParams { search: string | null; ids: string[] | null; teamIds: string[] | null; limit: number | null }`. The per-app `IWorkflowEditorGateway` and `IWorkflowEditorUseCases` gain `inspectRouting(params: InspectRoutingParams)` and `folderExists(params: FolderExistsParams)`; `InspectRoutingParams { stepConfig: RoutingStepConfig; requesterId: string; folderId: string | null; modelId: string | null }` (CMS sends the bare model id and `null` folder as root; WB ignores `modelId`), `FolderExistsParams { id: string; type: string }` (WB ignores `type`; the type is always `wb:page`). Envelope and error rules as 9a (R204); `NotAuthorized` is a display state only. The shared use-case class stays a plain class with the per-app subclass binding (R237); no new token in `app-workflows`.
- R292. **Folders through the app adapter** (Q54). `WorkflowEditorAppAdapter` gains `getFolderType(modelId: string | null): string` (CMS `cms:<modelId>`, WB `wb:page`) and `listFolders(modelId: string | null): Promise<AppFolder[]>` with `AppFolder { id: string; path: string }`: the folders of that type the admin can see (the ACO list is permission-filtered), root excluded, path built from folder titles through `parentId` as `/A/B` (the ACO `path` is slug-based). CMS and WB implement them over the data-returning `ListFoldersGateway.execute(type)` of `@webiny/app-aco`, inside their own packages; `app-workflows` never imports `app-aco`. `modelId` is the selected model row's bare `modelId` (`getModelId()`, R300), never derived from the namespace in shared code. The folder control is the shared `WorkflowPicker` over these paths with client-side search over the loaded list (the list is complete), options `Any folder` / `Root (no folder)` as the clear row. A saved folder id resolves to its path when listed; when not listed, `folderExists({ id, type: folder.type })` true is "Restricted folder" and false is "Deleted folder" (one call per distinct unresolved id). A rule's `folder.type` comes from `getFolderType` when the admin picks a folder; a saved folder keeps its own `type` (R295).
- R293. **Rule list is a form field** (controller). `assignment` is a form `object()` (the 9a `settings` precedent) with children `strategy` (text), `allowManualPick` (boolean) and `rules`; `getData()` returns `{ assignment: { strategy, allowManualPick, rules } }`. `rules` is a plain-JSON array field: the field type is `permissions` (value `Record<string, unknown>[]`, default `[]`) with its `.min(1)` schema replaced by `z.array(z.record(z.string(), z.unknown()))`, and the renderer `RoutingRulesRenderer` (registered in `WorkflowEditorConfig`, `fieldType: "permissions"`) owns the card UI. Task 18 starts with a short spike proving the type carries `RuleValue[]` unchanged through `setData` and `getData`; if it cannot, Task 18 uses the fallback without stopping (controller ruling: no app-admin change; the rule array lives in the drawer presenter and the form holds a text field that carries only the summary error) and reports it. `strategy` and `allowManualPick` have their own renderers (strategy radio cards, the stock switch). Tabs are FormModel layout tabs `General`, `Assignment`, `Test routing`, only on People steps; the Test routing tab holds the layout element `workflowTestRouting` (registered as `element:workflowTestRouting`), which reads the drawer presenter's data through `StepFormOptionsContext`. `getPeopleFormData` and `getPeopleStepPatch` now read and write `assignment`. Per-rule errors are not form validation: the drawer presenter holds `ruleErrors` (R303) and the renderer reads them from the options context; the form field `assignment.rules` carries only a summary validation message so the tab shows its error mark.
- R294. **Rule ids** (controller). `createRuleId(): string` in `[AWE]/model/createRuleId.ts` is the only generator (`r` followed by a random lowercase-alphanumeric suffix of 12 characters, unique within the draft by retry). Ids are created when a rule is added, never on load, never on reorder; a loaded rule keeps its stored id.
- R295. **Preserved data** (controller, D42, D69). `RuleValue` is `{ id; requesterUserId: string | null; requesterTeamId: string | null; folder: RuleFolderValue | null; target: RuleTargetValue | null; preserved: Record<string, unknown> }`; `preserved` holds every stored condition key the editor does not edit (`modelId` and any unknown key) and every unknown rule key, and `assignmentToConfig` writes them back unchanged. A folder whose `type` differs from the app's is kept unchanged (its `type`, id and `includeDescendants` stay as stored unless the admin removes the condition). A restricted folder is preserved unchanged (D69). Absent optional conditions are omitted from the emitted object, never emitted as `null`.
- R296. **Add rule** (design deviation). A new rule has no conditions and the target `{ type: "team", id: <first reviewing team> }`, or no target when the step has no teams. The design preselects the first member of the first reviewing team; that needs a member lookup before the card appears, so 9b preselects the team pool (the same card, one tap from a person). A rule with no target is a client error (R299) until chosen.
- R297. **Strategy** (UI copy). Stored `none`, `roundRobin`, `leastLoaded`; card names and descriptions as the design: `None (team pool)` / `The step waits in the team pool until a team member starts it.`, `Round-robin` / `Takes turns across eligible team members.`, `Least-loaded` / `Picks the eligible member with the fewest open reviews.`. Summary names: `Team pool`, `Round-robin`, `Least-loaded`. Strategy and the toggle are independent.
- R298. **Saved-reference resolution** (D117, Q54, Q59.1). Resolution is the editor presenter's: on workflow load and whenever a draft step's references change it collects the distinct user ids (rule `requesterUserId` and user targets), rule team ids (`requesterTeamId`, team targets; the steps' own teams stay on the 9a path) and folder ids, then resolves users with `listUsers({ ids })` in chunks of 200 ids, teams with `listTeams({ ids })`, folders from the adapter's list then `folderExists`. Labels: found -> name or path; user in `missingIds` -> `Deleted user` (muted, `person_off`); team in `missingIds` -> `Deleted team` (muted, `group_off`); folder -> `Restricted folder` (muted, `lock`, picker disabled) or `Deleted folder`. A picked value is known locally and is never re-resolved. Each resolution run carries a token (as the 9a search guard): a stale response is dropped (workflow switch, newer step edit), a reference removed from every step is not looked up again, concurrent chunks merge, and retry resolves only the unresolved ids. After a successful save the maps are rebuilt from the saved ids. A resolution failure shows the R281 banner (`Could not load the step options.` + `Try again`) and the unresolved ids keep their raw label `Unknown item` with `This item no longer exists.` only for ids the lookup confirmed missing; unresolved because of the failure show the picker's neutral loading label until retry.
- R299. **Rule issues** (Q50, Q53, Q59.1, QBZ-12). `getRuleIssues` returns issues of two kinds. Errors (block Save, strip `Rule {n}: {message}`, mark the rule card and the target field, toast `Fix the highlighted steps before saving.`): no target `Choose who this rule assigns to.`; user target not a member of the reviewing teams `{Name} is no longer in the reviewing teams.`; team target not a reviewing team `{Team} is not a reviewing team.`; user target deleted `The assigned user was deleted.`; team target deleted `The team was deleted.`. A user target's membership is known from its `teamIds` (R286) against the step's `teams`; a user whose teams are unknown (lookup failed) is not flagged. Error issues are live: they are shown on the rule card, on the step card and in the drawer top as soon as they are computed (once references resolve; recomputed when the step's teams or rules change; destructive styling, the design's warning placement), and Save is blocked by the same set; a server or Save-time error on the same rule and field replaces the live message, never doubles it. Warnings (never block Save, shown on the rule card without the prefix, on the step card and at the top of the drawer with the `Rule {n}: ` prefix): deleted folder `The folder no longer exists.`; deleted requester team `The team was deleted.`. A restricted folder has the field hint only (no warning). A deleted requester user shows the `Deleted user` label and no warning (the design warns only for targets).
- R300. **Test routing state** (controller). Lives in `StepDrawerPresenter` per open step: `requesterId: string | null`, `folderId: string | null`, `status: "idle" | "running" | "done" | "failed"`, `result`, `errorMessage`, `signature` of the last run. Opening another step clears it; closing and reopening the same step clears it too. The button is disabled with no requester, with the hint `Choose a requester to test.`; running shows `Testing…` and disabled. The request is `inspectRouting({ stepConfig: { teams, assignment }, requesterId, folderId, modelId })` where `stepConfig` is exactly what `toStepInput` emits for the draft step with the drawer's current form values applied, and `modelId` comes from `getModelId()` (the selected row's bare model id; `getNamespace()` is the namespace `cms.article` and is not used for it; the WB gateway ignores `modelId`). A run carries a token: a response with an old token (another step opened, drawer closed, a newer run) is dropped. The signature is taken when the request is sent and the `TestRoutingResultVm` is composed when the response arrives from the rules of the request, so a stale result keeps its old numbering and an edit made while `running` makes the result arrive stale. `runTest` while `running` is a no-op. Both inputs are disabled while running. A done result is stale when `getTestRoutingSignature` of the current teams, strategy, toggle, rules, requester and folder differs from the stored signature; stale shows the design copy, keeps the old result at reduced emphasis and is never re-run automatically. ## Decisions

Recorded by Task 25 (no SEC ids).

- **D170. `listUsers` can be scoped to teams.** `workflows.listUsers` takes `teamIds`, returns each user's team ids, never queries teams when teams are off, and an `ids` lookup ignores the filter. Source: Q49, Q58, R286.
- **D171. Rule errors name the rule.** Validation error data carries `ruleId`; rule-level failures use `config.assignment.rules.target`; a team target outside the step's teams is rejected on save. Refines D165, D46. Source: Q51, Q52, R288.
- **D172. The routing inspector answers for every rule.** `inspectRouting` lists all rules (`notEvaluated` after the decision), names failed conditions, and returns the narrowed team and the first candidate ids; the editor composes the sentences. Refines D95, D118. Source: Q55, R289, R301.
- **D173. Apps supply their folders.** The editor adapter lists the app's folders and the folder type; `app-workflows` does not depend on `app-aco`; restricted and deleted folders are told apart with `folderExists`. Refines D69, D133. Source: Q54, R292.
- **D174. Stale rule targets block Save.** A user or team target outside the reviewing teams and a deleted user or team are rule errors on the client and the server; folder warnings never block. Refines D46, D61. Source: Q50, Q52, Q53, R299.
- **D175. 9b is editor-only.** No `listStepCandidates` work, the 8a `ReviewerPicker` stays; exclusions and read access are shown only by Test routing. Source: Q50, Q56, R285.
- **D176. Teams off disables People.** `listStepTypes` reports People unavailable (`Teams are not enabled.`), saved People steps load read-only, `listTeams` and `listUsers` skip team data. Source: Q58, Q59, R290, R309.
- **D177. The stock admin-ui groups hold items by reference.** `RadioGroup`, `CheckboxGroup` and `Checkbox` accept JSX labels; the 9a workarounds are removed. Source: Q57, R305.
