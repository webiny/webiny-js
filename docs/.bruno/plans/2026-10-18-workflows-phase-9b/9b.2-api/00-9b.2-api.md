## Review Focus for this sub-phase

Review Focus 1 (stale or invalid rule target, server half: Task 3), 3 (server rule error lands on the wrong rule: Task 3), 5 (team data and teams off: Tasks 2 and 5), 7 (Test routing prose against the server's answer: Task 4) and 8 (`listUsers` scope: Task 2). Also:

- **Live assignment unchanged (Task 4).** The explain-only code paths are guarded by `params.explain`; the evaluator tests prove the live lookup counts (requester teams and folder chain read lazily and once, no `notEvaluated` entries, no `failedConditions`, no `strategyOrder`) and the existing resolver, candidate and strategy tests run unchanged.
- **Teams flag read per request (Tasks 2 and 5).** `TEAMS_FEATURE_FLAG` is read through `FeatureFlags` inside `execute` or `describeAvailability`, never at registration; each use case has a test that flips the switch between two requests and one where the flag read throws (a `WorkflowPersistenceError`, R87).
- **No team data with teams off (Tasks 2 and 5).** `listUsers` returns `teamIds: []` and makes no lookup for a team filter; `listTeams` queries nothing; both are asserted by recorded fake calls, not only by the result.
- **Error data shape (Task 3).** Every validation error `data` has the `ruleId` key; every existing assertion on error data in three API packages and `ai-powerups` is updated in the same commit, so no test is left comparing the old three-key shape.
- **Messages in one place (Task 3).** The save checks and the inspector use the strings of `ruleErrorMessages.ts`; no rule-level message is spelled twice.
- **Base packages untouched.** No file outside `api-workflows`, `api-headless-cms-workflows`, `api-website-builder-workflows` and (one test helper) `ai-powerups/__tests__` changes in this sub-phase.
