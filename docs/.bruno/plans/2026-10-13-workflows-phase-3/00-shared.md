> **Status note (after phase 4):** routing, the assignment-log writes, reassign, `listUsers`, `inspectRouting`, `listStepCandidates`, `folderExists` and the save-time check of rule user targets landed in phase 4 (`docs/.bruno/plans/2026-10-13-workflows-phase-4/`, R109-R130); the "Not in this phase" items marked (4) are done there.

**Goal:** Put the phase 2 wrappers behind GraphQL on the main `/graphql` endpoint and add the review lists. Each app gets its review lists (Assigned to me, Pool, Team in review, My requests, Failed steps) with filters, row viewer flags, a target-read predicate and the rewritten pagination (D47, D76, D94, D112, D119, D133), `getTargetReview`, the request title (D135), the assignment-log entries per step with redaction (D89, D127), and the CMS editor model list (D116). The shared configuration operations (settings, step types) land in api-workflows behind `editor` (D133). Website Builder's own page resolvers keep the workflows error codes (A26).

**Architecture:** Four sub-phases, built bottom up.

1. **Engine additions** (`packages/api-workflows`, 3.1): `currentStepType` on the review; the request title and the minimum lengths (D100, D135); `ListReviewsUseCase` (one internal use case for all five lists, explicit viewer ids, a `canRead` predicate, an item-level cursor, a scan cap, no `totalCount`); the assignment-log read with a `kind` on each record; the shared configuration use cases (settings for editors, step types).
2. **Shared GraphQL** (`packages/api-workflows`, 3.2): the `workflows` root on `/graphql`, the shared GraphQL types every app schema reuses (workflow, review, step, assignment entry, viewer flags, error, list meta), the settings and step types operations, and the GraphQL test harness.
3. **CMS** (`packages/api-headless-cms-workflows`, 3.3): new wrappers (review list, target review, editor model list), the request title and the assignment entries with redaction in the existing wrappers, every CMS operation on the existing `cms` root (`CmsQuery` / `CmsMutation`), and the corrected `system.workflow` GraphQL type on the CMS endpoints.
4. **Website Builder** (`packages/api-website-builder-workflows`, `packages/api-website-builder`, `packages/api-website-builder-scheduler`, 3.4): the same new wrappers for pages, every WB operation on the existing `websiteBuilder` root (`WbQuery` / `WbMutation`), `WbPage.system.workflow` on `/graphql`, the WB page resolvers and the scheduler's publish action keeping the workflows error code and data, and the docs.

**Tech Stack:** TypeScript, `@webiny/feature` DI (`createFeature`, `createAbstraction`, `createImplementation`), `GraphQLSchemaFactory` / `CoreGraphQLSchemaFactory` and the response classes (`Response`, `ListResponse`, `ErrorResponse`, `ListErrorResponse`) from `@webiny/api-graphql`, CMS use cases from `@webiny/api-headless-cms`, `WbPermissions` from `@webiny/api-website-builder`, `FeatureFlags` from `@webiny/api-core`, zod 4 (`z.toJSONSchema`), vitest, `@webiny/api-headless-cms-testing` (`createCmsTestHandler`: `invoke`, `getContext`).

## Global Constraints

- **No helper functions or private methods that wrap a dependency call** (use case, service, reader, repository, logger). Call the dependency inline in the owning class with the Result pattern (or an inline `try`/`catch`). Shared logic that needs dependencies becomes a DI service named `...Service`. Pure data functions (no injected dependency, no I/O) are allowed. Duplicating inline dependency calls across classes is intended; do not extract helpers to remove it. This applies to GraphQL resolvers too: each resolver calls its use case inline.
- **R87 (wrapper error contract):** app wrappers return a failed Result for every dependency throw (target reader, access checks, folder permissions, model list); a throw becomes the persistence error type of that use case, never `NotAuthorized` and never a rejected promise.
- **D132:** api-workflows engine use cases take an explicit actor and check nothing. GraphQL resolvers depend only on app wrapper use cases (CMS, WB) or on the shared configuration use cases (R97), never on an engine use case directly.
- DI conventions: one abstraction or implementation per file; implementation file named after its class (no `implementation.ts`); export name matches the abstraction; types via namespace (`X.Interface`); no inline object types (extract named interfaces); minimal barrel exports (only what external consumers need).
- Before every commit, run from the repo root, in order: `git add .`, `yarn > /dev/null 2>&1`, `node scripts/generateTsConfigsInPackages.js`, `yarn adio`, `yarn check-ts-configs`, `yarn format:fix > /dev/null 2>&1`, `yarn lint:fix`, `yarn webiny sync-dependencies`, build the changed packages with the cache off (`yarn build -p <package> --no-cache 2>&1 | tail -30`), `git add .`. ## Review Focus

1. **A list shows a review whose target the viewer cannot read** (spec 11, D76, D133). Titles from restricted folders and models must not leak. Pinned by Task 3 "skips reviews the predicate rejects and still fills the page", "counts a throwing predicate as unreadable", and per app by Task 7 / Task 10 "does not list a review of an entry in a folder the viewer cannot read" (and "... a page ...").
2. **The pagination loses or repeats rows across pages** (D76, R92). The cursor is item-level; a page that stops mid CMS page must resume at the next item. Pinned by Task 3 "returns every matching review exactly once across pages when the predicate skips rows" and "stops at the scan cap with hasMoreItems true and resumes from the cursor".
3. **Failed steps without `reassign`, or a list other than My requests filtered by review or step state** (D94, D112, R91, R95). Pinned by Task 3 "rejects reviewState and stepState outside myRequests" and Task 7 / Task 10 "refuses the failed steps list without reassign".
4. **Assignment details leak to a viewer without `editor` or `reassign`** (D89, D127, R96). Pinned by Task 4 "keeps skip entries for editor and reassign and drops them for everyone else" and Task 7 / Task 10 "drops skip entries from the review read for a plain reviewer".
5. **A GraphQL operation loses the error code or data** (spec 10, R100). Every resolver maps a failed Result with `ErrorResponse` / `ListErrorResponse`. Pinned by Task 6 "returns the settings validation error with code and data", Task 9 "returns Workflows/NotAuthorized with data through GraphQL", Task 11 "returns Workflows/NotAuthorized with data to a user without editor" and "cancels a review as its requester and refuses another user with data", Task 9 / Task 11 "returns the revision id validation error for a malformed revision id" (R107), and Task 12 "returns the publish-blocked code and data from publishPage".
6. **A WB item reachable through the CMS operations or the reverse** (D133, R46). Pinned by Task 9 "lists only CMS reviews" and Task 11 "lists only page reviews", and the get-review not-found tests through GraphQL.

## Rulings

Binding for this plan. Where they refine the spec, the ruling wins for phase 3.

- R88. **GraphQL placement and names** (D136). Everything is on `/graphql`.
  - `workflows` root (new, `WorkflowsQuery` / `WorkflowsMutation`, `extend type Query { workflows: WorkflowsQuery! }`, `extend type Mutation { workflows: WorkflowsMutation! }`): `getSettings`, `updateSettings`, `listStepTypes`.
  - `cms` root (existing `CmsQuery` / `CmsMutation`, extended with `extend type CmsQuery` / `extend type CmsMutation`): queries `listCmsEntryWorkflows`, `getCmsEntryWorkflow(id)`, `getCmsEntryReview(id)`, `getCmsEntryTargetReview(modelId, revisionId)`, `listCmsEntryReviews(list, where, sort, limit, after)`, `listCmsEntryWorkflowModels(search, limit, after)`; mutations `storeCmsEntryWorkflow(data, savedOn)`, `deleteCmsEntryWorkflow(id)`, `requestCmsEntryReview(modelId, revisionId, title, picks)`, `startCmsEntryReviewStep(reviewId, stepId)`, `takeOverCmsEntryReviewStep(reviewId, stepId)`, `approveCmsEntryReviewStep(reviewId, stepId, comment)`, `rejectCmsEntryReviewStep(reviewId, stepId, comment)`, `cancelCmsEntryReview(reviewId)`, `cancelCmsEntryReviewsForDelete(modelId, entryId, revisionId, action)`.
  - `websiteBuilder` root (existing `WbQuery` / `WbMutation`, extended): the same set with `WebsiteBuilderPage` in place of `CmsEntry` and no `modelId` (`getWebsiteBuilderPageTargetReview(revisionId)`, `requestWebsiteBuilderPageReview(revisionId, title, picks)`, `cancelWebsiteBuilderPageReviewsForDelete(pageId, action)`, ...); there is no WB model list (D116).
  - Operations that take a review id never take a model (D136). The entry id for a request comes from the revision id (`<entryId>#<version>`), so neither request takes `targetId`: the resolver passes `targetId: parseIdentifier(revisionId).id` (`@webiny/utils`, pure) and, for CMS, `model: toCmsNamespace(modelId)` (pure) to the unchanged wrapper inputs. Pure argument mapping in a resolver is allowed; anything that needs a dependency is not.
- R89. **Request title** (D135, D100). `RequestReviewInput.title?: string | null`. Trimmed; when non-empty it must be at least 5 characters, else `ReviewValidationError` ("The review title must have at least 5 characters."); when missing or empty the target's title is used (as today). The title is fixed afterwards. Both request wrappers and both GraphQL request operations take the optional `title`.
- R90. **Reject comment** (D100). Rejecting needs a comment of at least 10 characters after trimming, else `ReviewValidationError` ("A rejection needs a comment of at least 10 characters."). Checked in `Review.reject` (the aggregate; `checkReject` drives the `canReject` flag and takes no comment), so every caller gets it. Approve comments stay optional with no minimum.
- R91. **List kinds and filters** (spec 11, D47, D94, D112, D119, D75). `ReviewListKind = "assignedToMe" | "pool" | "teamInReview" | "myRequests" | "failedSteps"`. All require `isActive: true`.
  - `assignedToMe`: `currentOwnerId = viewerUserId`, `currentStepState = "inReview"`.
  - `pool`: `currentStepState = "awaiting"`, `currentCandidateTeamIds` intersects `viewerTeamIds`, `requester.id != viewerUserId`. An empty `viewerTeamIds` returns an empty page without a query.
  - `teamInReview`: `currentStepState = "inReview"`, `currentOwnerId != viewerUserId`, `currentCandidateTeamIds` intersects `viewerTeamIds`. Empty `viewerTeamIds` returns an empty page.
  - `myRequests`: `requester.id = viewerUserId`. The only list that accepts `where.reviewState` and `where.stepState` (`isActive` still applies: finished reviews show only while they are the target's active review).
  - `failedSteps`: `currentStepState = "failed"`, `currentStepType` in `["ai", "automation"]`. The engine does not check `reassign`; the wrappers do (R95).
  - `where.titleContains` on every list (`title_contains`). `where.model` is the namespace filter: the engine takes `models: string[]` from the wrapper (WB `["wb.page"]`; CMS the requested model or every bindable readable `cms.*` model, R94) and queries `model_in`.
  - Conditions a storage cannot express (`_not`, list intersection, nested `requester.id`) may be applied in code after the query; Task 3 tests every list on both storages and records which conditions run in code.
- R92. **Pagination** (D76). `limit` default 20, max 100 (larger values are clamped). The engine pages the repository with `values_lastChangedOn_ASC|DESC` (the `values_` prefix the CMS sort mapper needs), applies the list conditions that run in code, then `canRead(review)` per row (a throw counts as unreadable), until `limit` rows are kept or `MAX_REVIEW_LIST_SCAN = 200` rows were examined. The cursor is opaque: base64 of JSON `{ after: string | null, skip: number }` (the repository cursor of the page being read and how many rows of it were already examined), so a page can stop mid repository page and the next call resumes at the next row. `meta = { cursor: string | null, hasMoreItems: boolean }`; no `totalCount` (D76). An invalid cursor fails with `ReviewValidationError`. Sort default: `lastChangedOn_ASC` for assignedToMe, pool, teamInReview, failedSteps; `lastChangedOn_DESC` for myRequests (D119); the caller may pass either.
- R93. **`currentStepType`** (D112). New top-level text field on the review model (unreleased, allowed), kept by the aggregate wherever `currentStepId` changes, null when there is no current step, mapped in `ReviewEntryMapper` and in `ReviewData`. Failed-step test data is seeded through `ReviewRepository.save` (nothing produces `failed` before phase 5). Done in phase 5 (R131-R158).
- R94. **List wrappers.** `ListCmsEntryReviewsUseCase` and `ListWebsiteBuilderPageReviewsUseCase`: read the viewer (`CurrentReviewViewer.get()`), pass `viewerUserId = viewer.actor.id`, `viewerTeamIds = viewer.teamIds`, the app's `models`, and a `canRead` arrow that reads the target and checks read access inline (CMS `CmsEntryTargetReader.read` + `entryId` match + `CmsEntryAccess.canRead`; WB the same with `WbPageTargetReader` / `WbPageAccess`), then attach viewer flags per row (`getReviewViewerFlags(review, viewer)`). CMS `models`: when `where.modelId` is given, `["cms.<modelId>"]` if that model is bindable (public, publishable, readable), else an empty page; otherwise every bindable model the viewer can read (`ListModelsUseCase`, filtered like the bindable check). Results are `ReviewWithViewerFlags[]` plus meta.
- R95. **Failed steps needs `reassign`** (D112). The list wrappers refuse `list: "failedSteps"` without `reassign` with `WorkflowsNotAuthorizedError({ action: "list failed steps" })` before calling the engine.
- R96. **Assignment entries and redaction** (D89, D127). `AssignmentRecord` gains `kind: "outcome" | "skip"` (stored; existing records read as `"outcome"`). Engine `ListReviewAssignmentsUseCase({ reviewId })` returns every record of the review, newest first, paging the repository to the end. The get-review wrappers (by id and by revision) read them, attach `assignments: AssignmentRecord[]` to each step (by `stepId`) and drop `kind: "skip"` records unless the viewer has `editor` or `reassign` (pure function `redactAssignmentRecords(records, permissions)` in api-workflows, allowed: no dependency). A failed read of the log fails the get with the assignment persistence error (R87). Records are seeded in tests (nothing writes them before phase 4).
- R97. **Shared configuration use cases** (D133 point 2). New, in api-workflows, each checks `WorkflowsPermissions.canEdit()` first (`WorkflowsNotAuthenticatedError` / `WorkflowsNotAuthorizedError({ action })`) and then calls the engine inline: `GetWorkflowSettingsForEditorUseCase({ includeExpired? })`, `SaveWorkflowSettingsForEditorUseCase(settings)`, `ListWorkflowStepTypesUseCase()`. These and the app wrappers are the only use cases resolvers call.
- R98. **Step types in phase 3** (D130). `ListWorkflowStepTypesUseCase` returns a static list, replaced by the `StepType` registry in phase 5: `{ type: "review", title: "Review", available: true, unavailableReason: null, configSchema: <z.toJSONSchema(reviewStepConfigSchema)> }`, `{ type: "ai", title: "AI", available: <FeatureFlags aiPowerups>, unavailableReason: available ? null : "AI powerups are not enabled.", configSchema: null }`, `{ type: "automation", title: "Automation", available: false, unavailableReason: "No automation is defined.", configSchema: null }`. The workflow validator still accepts only `review` (phase 5). Done in phase 5 (R131-R158).
- R99. **Editor model list** (D116, D130). `ListCmsEntryWorkflowModelsUseCase({ search?, limit?, after? })`: `canEdit()` first; `ListModelsUseCase` (readable models), keep bindable ones (not private, not tagged `$publishing:false`), filter by `search` (case-insensitive on name and `modelId`), sort by name then `modelId`, page with an offset cursor (base64 JSON `{ offset }`, limit default 20, max 100), attach the bound workflow `{ id, name } | null` per row from one `ListCmsEntryWorkflowsUseCase` call (one model per workflow, D15). Meta `{ cursor, hasMoreItems }`.
- R100. **GraphQL conventions.**
  - Every operation returns an envelope `{ data, error }` (lists `{ data, meta, error }`); a failed Result is returned with `new ErrorResponse(result.error)` / `new ListErrorResponse(result.error)`, which keeps `code`, `message` and `data` (spec 10). A thrown error from a wrapper is a bug (R87); resolvers do not catch it.
  - Shared types live in api-workflows' schema factory and are reused by the app factories: `WorkflowsError { code message data stack }`, `WorkflowsListMeta { cursor hasMoreItems }`, `WorkflowsBooleanResponse`, `WorkflowsWorkflow`, `WorkflowsWorkflowInput`, `WorkflowsStep` / `WorkflowsStepInput` (step `config` as `JSON`), `WorkflowsReview`, `WorkflowsReviewStep`, `WorkflowsAssignmentEntry`, `WorkflowsViewerFlags`, `WorkflowsReviewWithFlags { review flags }`, `WorkflowsActor`, the list enums `WorkflowsReviewListKind`, `WorkflowsReviewListSort`, `WorkflowsReviewListWhere` (CMS list; the WB list uses its own where input without `modelId`), the request pick input `WorkflowsReviewPickInput { stepId userId }` and the enum `WorkflowsReviewsForDeleteAction { trash delete }`. App factories add only their envelopes and root fields.
  - Factories are registered inside the license-gated features (`WorkflowsFeature`, `CmsWorkflowsFeature`, `WebsiteBuilderWorkflowsFeature`), so without `advancedPublishingWorkflow` nothing is added (test this per factory).
  - Resolvers take only arguments; actor, teams and permissions come from the wrappers.
- R101. **Dependencies.** `@webiny/api-graphql` is added to `api-workflows` and `api-headless-cms-workflows` `dependencies` (WB already has it). `@webiny/wcp` may be added to `api-workflows` `devDependencies` (test licenses; the app packages already have it). `@webiny/utils` may be added to `api-headless-cms-workflows` and `api-website-builder-workflows` `dependencies` (`parseIdentifier`, R88). No other new dependency.
- R104. **GraphQL input dates are `String`.** `savedOn` and other date inputs compared as strings (D131) are `String` in input types, not `DateTime` (the scalar turns input into a `Date`). Output dates may be `DateTime`.
- R106. **Review reads with assignments.** 3.1 Task 4 owns `ReviewStepWithAssignments`, `ReviewWithAssignments`, `ReviewWithAssignmentsAndViewerFlags` (api-workflows `domain/assignment/types.ts`) and the pure `attachAssignmentRecords(review, records)`; the get-review wrappers of both apps (by id and by revision) return `ReviewWithAssignmentsAndViewerFlags`. Refusal actions: `"list failed steps"` (R95), `"view this review"` (target review).
- R107. **Malformed revision ids in resolvers.** Every resolver that takes a `revisionId` (request, target review, cancel-for-delete when given) checks it with a pure function first (non-empty entry id before `#`, numeric version); a malformed id returns `new ErrorResponse(new ReviewValidationError("The revision id is not valid."))` (data `{ revisionId }` if the error class takes data, else none), never a thrown error.
- R108. **Target review semantics (both apps).** `getCmsEntryTargetReview` / `getWebsiteBuilderPageTargetReview`: a model of another app → `Workflows/Review/TargetNotFound` (CMS only; WB has one model); a revision that does not exist, is trashed or is not readable by the viewer → `Workflows/NotAuthorized` with action `"view this review"` (does not reveal existence); a readable revision without an active review → `data: null`, no error; a read that throws → `Workflows/Review/Persistence` (R87).
- R105. **Shared config refusal actions:** `"view the workflow settings"`, `"change the workflow settings"`, `"list the step types"` (Task 5 and Task 6 tests use these exact strings).
- R102. **CMS `system.workflow` on the CMS endpoints.** The legacy `CmsEntrySystemWorkflow` type (`api-headless-cms-workflows/src/graphql/entrySystemSchema.ts`) is corrected to the stored shape `{ workflowId: String, reviewState: String, stepId: String, stepName: String, stepState: String }` (no `state`); the test reads a stored value through `/cms/manage`. On `/graphql`, `WbPage.system` gets a `workflow` field of type `WbPageSystemWorkflow` with the same fields (replacing the `CmsEntrySystem` placeholder reference).
- R103. **WB page resolvers keep the error** (A26). In `api-website-builder` `pages.gql.ts`, operations that today `throw new Error(result.error.message)` on `Result.fail` make `resolve()` produce `new ErrorResponse(result.error)` instead (they `throw result.error` inside it; code and data kept); rejections from before-event handlers keep flowing through `resolve()` (already kept). The scheduler's `PublishPageActionHandler` and `UnpublishPageActionHandler` rethrow the original error (keeping `code` / `data`) instead of wrapping it in a plain `Error`. These are Website Builder changes; run that package's suites.

## Assumptions

- A40. CMS where filters on the review model: `model_in`, `isActive`, `currentStepState`, `currentOwnerId`, `title_contains`, `currentStepType_in` work on ddb and ddb-os; `currentOwnerId_not`, `currentCandidateTeamIds_in` and the nested `requester.id` may not. Task 3 measures it; whatever does not work runs in code before the predicate (R91), still bounded by the scan cap.
- A41. The scan cap (200 rows per call) means a viewer with many unreadable rows can get a short page with `hasMoreItems: true`; the client pages on. The item cursor is exact only while the listed data does not change: on ddb the CMS cursor is an offset, so a row that leaves the list between calls can make the next call skip one row, and a row whose `lastChangedOn` moves can repeat (ddb-os uses `search_after` with an `id` tie-breaker and is stable). A cursor is valid only with the same list, where and sort it was issued for. Accepted (D76: no exact count, fill best effort).
- A42. Lists read the review's own fields; each kept row costs one target read for the predicate. With `limit` 20 and the cap 200, a call costs at most 200 primary reads of reviews (R18) plus 200 target reads. Accepted for v1.
- A43. `getReviewViewerFlags` with `canRestart` always false until phase 5 and `canReassign` from the 1b predicate are what rows carry; no target access is folded into the row flags beyond the predicate (a listed row is readable by construction). Done in phase 5 (R131-R158).
- A45. Correcting `system.workflow` (R102) breaks the old admin's entry and page field selections that still select `state` (`app-headless-cms-workflows`, `app-website-builder-workflows`). Accepted: the old admin is already broken against the new API since phase 1a (roadmap Cutover); phase 8a rewrites it. No admin package is changed in phase 3.
- A44. The assignment log is empty until phase 4; the redaction is tested with records written through `AssignmentRepository.create` in tests. Phase 4 writes them after each save (R117); tests that need exact records still seed them.
