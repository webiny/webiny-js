# Workflows Phase 8a: Admin review experience for review steps

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The admin speaks the new review API. In the CMS entry editor and the Website Builder page editor a review bar (loading and failed states, review state tag, all six step states, progress popover, tooltip, server-driven actions) lets people request a review (with picks), start (confirmed, D114), take over (notify checkbox, D111), reassign, approve, reject, cancel and open the Review details drawer (D88). Saving, publishing, moving and scheduling follow the review state (D121; WB "create new revision" on a rejected page, D24). Content Reviews exists once per app as a shared list view over app-neutral rows (four tabs, filters, `lastChangedOn` sort, load more, live refetch, "New reviews are available." notice), plus two dashboard widgets per app. Every workflows toast goes through the admin `Notifications` stack (D125). Trashing, deleting (also one revision) and bulk deleting content with a review in progress shows the D134 warning driven by the server refusal (new D157). Review steps carry `candidateTeams: [{ id, name }]` (Q7), skipped-by-assignment entries carry the person's display name (Q21) and a cancelled review says who cancelled it (Q23). The Website Builder gets the revision delete it lacked (`deletePageRevision`, Q14). The old admin review UI is deleted. 8b (Restart, running/failed messages, `runs`, AI issues, Background task link, Failed steps tab) and 9a-9c (editor, settings, permissions) are out of scope.

**Architecture:** Ten sub-phases, bottom up; each ships and tests alone. Only 8a.1 touches API packages. **Almost everything lives in `app-workflows`** (R202): domain, DTOs, fragments, mappers, the gateway interface, the shared use-case implementation, presenters, views, dialogs, toasts, activity and notification handling, list, widget and details logic, the trash/delete warning flow, the editor session, the cache-sync handler and the mounting components. The CMS and WB packages hold only what differs: GraphQL operation documents plus the gateway that runs them, the DI registration binding their gateway to the shared use cases, a content adapter (URL and content-type label), a cache writer, and thin glue at app-specific extension points.

## Global Constraints

Server (8a.1 only):

- **R87 / D132:** a dependency throw becomes a failed Result or a logged and swallowed failure, never a rejected promise out of a resolver; shared resolvers check no permissions (the wrappers authorized the read).
- **SEC-66 pattern (R208, R251):** `GetTeamUseCase` needs `security.team` and `GetUserUseCase` needs a users permission; wrap only the team or user lookup in `identityContext.withoutAuthorization`, never a read check, expose only `id` and `name` (a user's display name).
- **Storage key formats are frozen.** `candidateTeams` and the skipped-entry display names are resolved at read time, never stored; the WB revision delete (Tasks 3-5) goes through the existing CMS entry-revision path and changes no model, key or schema (R236, A86). The one stored addition of 8a.1 is the optional `cancelledBy` data field of the review (Task 5c, R252, A91): a data field of the private review model, no key, no key format, nothing migrated; if Task 5c finds it needs more, it stops and records an open question.

Everywhere:

- **No helper functions or private methods that wrap a dependency call** (use case, service, repository, logger, gateway, presenter, event publisher, notification service, confirmation). Call dependencies inline with an inline `try`/`catch` (admin) or the Result pattern (API). Shared logic that needs dependencies is a DI service. Pure functions are allowed (message tables, mappers, view-model builders).
- **Subclass rule (R237, binding):** `createImplementation` writes the abstraction and the dependencies as metadata on the class and returns the same class, so **never call `createImplementation` on a shared `app-workflows` class**. Each app subclasses it once in its own file and binds the subclass.
- DI conventions (R238): **one abstraction, implementation or feature per file**; the token file is named after the token (`CmsReviewGateway.ts` holds only the token `CmsReviewGateway`, never one `abstractions.ts` with several tokens) and the implementation file is `<Token>Impl.ts` holding class `<Token>Impl` exported under the token's name (`DeleteEntryGateway.ts` / `DeleteEntryGatewayImpl.ts` in the base packages' style); **one named import per line**; namespace types (`Foo.Interface`, `Foo.ViewModel`, never the `IFoo` outside the declaring file, R238); minimal barrels (the package `index` is the one listed barrel, and **app packages import `app-workflows` through deep paths** `@webiny/app-workflows/<path>.js`, never through the barrel; a barrel addition nobody imports is dropped); no inline object types (named interfaces everywhere, also parameters and generics); no inline class in `createImplementation`, the class declares `implements`.
- **No logic duplicated across the CMS and WB packages; app packages contain only app-specific gateways and glue** (R202). If a CMS task and a WB task would contain the same logic, it belongs in `app-workflows` and the app tasks only register or mount it.
- **Layering (R202):** shared presenters and components depend only on the shared use-case interfaces (`IReviewUseCases` and its parts), never on a gateway (`no-mixed-layers-in-dependencies.md`); use cases go through the gateway interface (`use-cases-go-through-repositories.md`).
- **Desktop only (Q26):** the admin is not for tablets or mobiles. No touch behaviour is built (no tap-to-toggle tooltip, QBZ-36's tap part is dropped) and no `@webiny/admin-ui` change is made for touch; mouse and keyboard only.

Admin code style (`ai-context/code-style/*.md`, `AGENTS.md`; read every file in the folder before writing code):

- One class per file; one exported function per file (unexported helpers stay in it); one named import per line; ES modules; comments end with a period; `//` and `/* */` only.
- **No container as service locator**: constructor `dependencies`; `container.resolve` only in a feature's `resolve()`.
- **Prefer a provider over a resolved value:** no abstraction that only holds another's result and is filled by `registerInstance`. Per-view parameters travel as `init(...)` arguments or props.
- **Presenters own component state** (`makeAutoObservable`, a `vm` getter of **render-ready values only: strings, numbers, booleans, plain arrays of those; no domain objects, no presenters, no callbacks** (R234); mutations after an `await` in named private methods; non-rendered machinery excluded from the observable map). Components are `createReactiveComponent` (never `observer`, `useState` only for one visual flag); presenters come from `useFeature(...)`. A singleton presenter's `dispose()` resets state.
- No stateless private methods; no multiline ternaries; no nested call arguments; no inline conditional spreads or casts in object literals; prefer annotation over cast; `cn` from `@webiny/admin-ui` for class names; no backwards compatibility on refactors.

Process:

- **Tests are targeted**, by path: admin `yarn test packages/<pkg>/src/<path>/<file>.test.ts`; API `yarn test packages/<pkg>/__tests__/<file>.test.ts` then the same with `yarn test:os` (workflows assume OpenSearch; one `test:os` run at a time, parallel runs clash on port 8001). Storage runs apply only to the four API packages of 8a.1 (`api-workflows`, `api-headless-cms-workflows`, `api-website-builder-workflows`, `api-website-builder`). Admin tests are co-located `*.test.ts(x)` (precedents `packages/app-headless-cms/src/presentation/contentEntries/list/ContentEntriesPresenter.test.ts`, `packages/app-website-builder/src/features/pages/deletePage/DeletePage.test.ts`, `packages/app-admin/src/presentation/listPresenter/ListPresenter.test.ts`): `Container` from `@webiny/di`, dependencies replaced by `vi.fn()` objects through `registerInstance`, a fake `MainGraphQLClient` for gateways, jsdom for presenters and components. A package without tests gets `vitest.config.ts` = `createTestConfig({ path: import.meta.dirname, vitestConfig: { environment: "jsdom", fileParallelism: true } })` (copy of `packages/app-admin/vitest.config.ts`), `vitest` `^4.1.11` and (component tests) `@testing-library/react` `^16.3.2` as devDependencies (R222, A75).
- Type-check tests per touched package: `yarn check:test:types -p <folder> --report cli 2>&1 | tail -40` prints no errors. **`check:test:types` lists only packages that have a `__tests__/**/*.test.ts` file** (`scripts/utils/getPackages.js`, `hasTests`), so for an admin package without one (`app-workflows`, `app-headless-cms-workflows`, `app-website-builder-workflows`) the type check of its co-located tests is `yarn build -p @webiny/<package> --no-cache 2>&1 | tail -30` (R243).
- **Test fixtures and fakes (R243):** shared fixtures that other packages import live in `packages/app-workflows/src/review/testing/` (it ships in `dist`, and a co-located test importing from `__tests__/` fails the build with TS6059 because `tsconfig.build.json` has `rootDir: ./src`): pure builders (data only, no vitest, mobx or `@webiny/di` imports) and vitest fakes in separate files. ## Rulings

- R202. **Shared core, app-owned gateways** (user answers Q1, Q11, Q13; D159). `app-workflows` knows no app and has no namespace registry. It holds every app-neutral piece: domain types and enums, the DTO types, the field fragments and mappers of the shared `Workflows*` types, the gateway interface `IReviewGateway`, the use-case interfaces and their **one shared implementation** `ReviewUseCases` (orchestration, mapping, error mapping, the workflow list cached per namespace, A74), and everything built on them. Each app package owns only: (a) its GraphQL operation documents and the `CmsReviewGateway`/`WbReviewGateway` that runs them (argument mapping such as `modelId` + `entryId` versus `pageId`, unwrapping its own root field into the shared envelope, nothing else); (b) the registration binding its gateway to the shared use cases under **its own tokens** (`CmsReviewGateway`, `CmsReviewUseCases`, and likewise `Wb...`), so both apps coexist in the one admin container; (c) the content adapter (R224) and a cache writer (R213); (d) thin glue at app-specific extension points. Tokens are `createAbstraction<IReviewGateway>("Cms/Workflows/ReviewGateway")`, `createAbstraction<IReviewUseCases>("Cms/Workflows/ReviewUseCases")` (WB: `"WebsiteBuilder/Workflows/..."`); the use cases are registered through **a one-line subclass per app** (R237): `class CmsReviewUseCasesImpl extends ReviewUseCases implements CmsReviewUseCases.Interface {}` in `CmsReviewUseCasesImpl.ts`, whose `createImplementation({ implementation: CmsReviewUseCasesImpl, dependencies: [CmsReviewGateway] })` result is exported under the token's name (token file `CmsReviewUseCases.ts`), singleton, so each app has its own cache and the shared class stays unbound (`WbReviewUseCasesImpl.ts` likewise). Shared presenters take `useCases` as an `init(...)` argument and shared components as a prop; app glue resolves its token with `useFeature(<App>ReviewFeature)` and passes it in. Gateways never throw for an envelope error: they return the shared `ReviewEnvelope`; the shared use cases turn `error` into `GraphQLOperationError` (R204, A81) and let transport `Error`s pass.
- R203. **Scope** (Q2). 8a ships the Review details drawer (D88: header, timeline with owner, "Why this owner" (hidden for AI and automation, QBZ-63), times, comment, skipped-by-assignment box exactly as received (D89), footer actions) and all six step states in tag, popover and details. A `failed` step renders its state with the generic in-review message; no Restart, Failed steps tab, attempts list, issues table or Background task link. `runs`, `issues`, `taskId` are mapped by the shared mapper but not rendered.
- R204. **Typed error and the eight gateways** (Q3). `@webiny/app` gains `GraphQLOperationError` (`packages/app/src/errors/GraphQLOperationError.ts`, exported from `errors/index.ts`, imported `@webiny/app/errors/index.js`). These eight gateways throw it when their envelope has an error, each keeping its own throw condition and message fallback and selecting `code message data`: CMS `packages/app-headless-cms/src/features/contentEntry/{deleteEntry/DeleteEntryGateway,deleteEntryRevision/DeleteEntryRevisionGateway,permanentlyDeleteEntry/PermanentlyDeleteEntryGateway,bulkAction/BulkActionGateway}.ts`; WB `packages/app-website-builder/src/features/pages/{deletePage/DeletePageGateway,deletePageRevision/DeletePageRevisionGateway,trashBin/WbTrashBinDeleteGateway,trashBin/WbTrashBinBulkActionGateway}.ts` (the two trash-bin gateways do not select `data` today, they add it; the bulk one keeps `if (error || !data)`). Other gateways keep `throw new Error`. Workflows decorates the **use cases**/presenters: CMS `DeleteEntryUseCase`, `DeleteEntryRevisionUseCase`, `PermanentlyDeleteEntryUseCase` (`.../contentEntry/*/abstractions.ts`), the CMS `BulkDeletePresenter` (`.../presentation/contentEntries/bulkActions/abstractions.ts`); WB `DeletePageUseCase`, `DeletePageRevisionUseCase` (`packages/app-website-builder/src/features/pages/{deletePage,deletePageRevision}/abstractions.ts`) and the WB `BulkDeletePresenter` (`.../presentation/pages/bulkActions/abstractions.ts`, token `"WB/BulkDeletePresenter"`); the WB trash-bin delete path is deliberately not decorated (R249), and the CMS trash-bin permanent delete is covered by the `PermanentlyDeleteEntryUseCase` decorator. Task 32 notes: `DeletePageGateway` declares only `$id` (it always trashes, unchanged), and the WB server has no `bulkActions` mutation (`WbTrashBinBulkActionGateway` calls an operation the API does not define, A72). The base callers of these use cases are fixed where they mishandle `false` (R228; the base fixes are separate `fix`/`refactor` commits in Tasks 35, 36).
- R205. **Warning flow** (Q4, D157). The normal confirmation runs first. A decorated use case runs the action; a `GraphQLOperationError` with code `Workflows/Review/ActiveReviewOnTrash` (data `ActiveReviewOnTrashData`) opens the warning dialog listing each review as "{title} · Step {stepPosition} of {stepCount} ({stepName})" under D134's text ("This content has a review in progress.
