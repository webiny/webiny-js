# Workflows Phase 8a: Admin review experience for review steps

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The admin speaks the new review API. In the CMS entry editor and the Website Builder page editor a review bar (loading and failed states, review state tag, all six step states, progress popover, tooltip, server-driven actions) lets people request a review (with picks), start (confirmed, D114), take over (notify checkbox, D111), reassign, approve, reject, cancel and open the Review details drawer (D88). Saving, publishing, moving and scheduling follow the review state (D121; WB "create new revision" on a rejected page, D24). Content Reviews exists once per app as a shared list view over app-neutral rows (four tabs, filters, `lastChangedOn` sort, load more, live refetch, "New reviews are available." notice), plus two dashboard widgets per app. Every workflows toast goes through the admin `Notifications` stack (D125). Trashing, deleting (also one revision) and bulk deleting content with a review in progress shows the D134 warning driven by the server refusal (new D157). Review steps carry `candidateTeams: [{ id, name }]` (Q7). The Website Builder gets the revision delete it lacked (`deletePageRevision`, Q14). The old admin review UI is deleted. 8b (Restart, running/failed messages, `runs`, AI issues, Background task link, Failed steps tab) and 9a-9c (editor, settings, permissions) are out of scope.

**Architecture:** Ten sub-phases, bottom up; each ships and tests alone. Only 8a.1 touches API packages. **Almost everything lives in `app-workflows`** (R202): domain, DTOs, fragments, mappers, the gateway interface, the shared use-case implementation, presenters, views, dialogs, toasts, activity and notification handling, list, widget and details logic, the trash/delete warning flow, the editor session, the cache-sync handler and the mounting components. The CMS and WB packages hold only what differs: GraphQL operation documents plus the gateway that runs them, the DI registration binding their gateway to the shared use cases, a content adapter (URL and content-type label), a cache writer, and thin glue at app-specific extension points.

## Global Constraints

Server (8a.1 only):

- **R87 / D132:** a dependency throw becomes a failed Result or a logged and swallowed failure, never a rejected promise out of a resolver; shared resolvers check no permissions (the wrappers authorized the read).
- **SEC-66 pattern (R208):** `GetTeamUseCase` needs `security.team`; wrap only the team lookup in `identityContext.withoutAuthorization`, never a read check, expose only `id` and `name`.
- **Storage key formats are frozen.** `candidateTeams` is resolved at read time, never stored; the WB revision delete (Tasks 3-5) goes through the existing CMS entry-revision path and changes no model, key or schema (R236, A86).

Everywhere:

- **No helper functions or private methods that wrap a dependency call** (use case, service, repository, logger, gateway, presenter, event publisher, notification service, confirmation). Call dependencies inline with an inline `try`/`catch` (admin) or the Result pattern (API). Shared logic that needs dependencies is a DI service. Pure functions are allowed (message tables, mappers, view-model builders).
- DI conventions: one abstraction, implementation or feature per file; implementation file named after its class or, in the base packages' style, after the abstraction it implements (`DeleteEntryGateway.ts` holds `DeleteEntryGatewayImpl` exported as `DeleteEntryGateway`); namespace types (`Foo.Interface`, never the `IFoo` outside the declaring file); minimal barrels (the package `index` is the one listed barrel); no inline object types (named interfaces everywhere, also parameters and generics); no inline class in `createImplementation`, the class declares `implements`.
- **No logic duplicated across the CMS and WB packages; app packages contain only app-specific gateways and glue** (R202). If a CMS task and a WB task would contain the same logic, it belongs in `app-workflows` and the app tasks only register or mount it.
- **Layering (R202):** shared presenters and components depend only on the shared use-case interfaces (`IReviewUseCases` and its parts), never on a gateway (`no-mixed-layers-in-dependencies.md`); use cases go through the gateway interface (`use-cases-go-through-repositories.md`).

Admin code style (`ai-context/code-style/*.md`, `AGENTS.md`; read every file in the folder before writing code):

- One class per file; one exported function per file (unexported helpers stay in it); one named import per line; ES modules; comments end with a period; `//` and `/* */` only.
- **No container as service locator**: constructor `dependencies`; `container.resolve` only in a feature's `resolve()`.
- **Prefer a provider over a resolved value:** no abstraction that only holds another's result and is filled by `registerInstance`. Per-view parameters travel as `init(...)` arguments or props.
- **Presenters own component state** (`makeAutoObservable`, a `vm` getter of **render-ready values only: strings, numbers, booleans, plain arrays of those; no domain objects, no presenters, no callbacks** (R234); mutations after an `await` in named private methods; non-rendered machinery excluded from the observable map). Components are `createReactiveComponent` (never `observer`, `useState` only for one visual flag); presenters come from `useFeature(...)`. A singleton presenter's `dispose()` resets state.
- No stateless private methods; no multiline ternaries; no nested call arguments; no inline conditional spreads or casts in object literals; prefer annotation over cast; `cn` from `@webiny/admin-ui` for class names; no backwards compatibility on refactors.

Process:

## Rulings

- R202. **Shared core, app-owned gateways** (user answers Q1, Q11, Q13; D159). `app-workflows` knows no app and has no namespace registry. It holds every app-neutral piece: domain types and enums, the DTO types, the field fragments and mappers of the shared `Workflows*` types, the gateway interface `IReviewGateway`, the use-case interfaces and their **one shared implementation** `ReviewUseCases` (orchestration, mapping, error mapping, the workflow list cached per namespace, A74), and everything built on them. Each app package owns only: (a) its GraphQL operation documents and the `CmsReviewGateway`/`WbReviewGateway` that runs them (argument mapping such as `modelId` + `entryId` versus `pageId`, unwrapping its own root field into the shared envelope, nothing else); (b) the registration binding its gateway to the shared use cases under **its own tokens** (`CmsReviewGateway`, `CmsReviewUseCases`, and likewise `Wb...`), so both apps coexist in the one admin container; (c) the content adapter (R224) and a cache writer (R213); (d) thin glue at app-specific extension points. Tokens are `createAbstraction<IReviewGateway>("Cms/Workflows/ReviewGateway")`, `createAbstraction<IReviewUseCases>("Cms/Workflows/ReviewUseCases")` (WB: `"WebsiteBuilder/Workflows/..."`); the use cases are registered as `CmsReviewUseCases.createImplementation({ implementation: ReviewUseCases, dependencies: [CmsReviewGateway] })`, singleton, so each app has its own cache. Shared presenters take `useCases` as an `init(...)` argument and shared components as a prop; app glue resolves its token with `useFeature(<App>ReviewFeature)` and passes it in. Gateways never throw for an envelope error: they return the shared `ReviewEnvelope`; the shared use cases turn `error` into `GraphQLOperationError` (R204, A81) and let transport `Error`s pass.
- R203. **Scope** (Q2). 8a ships the Review details drawer (D88: header, timeline with owner, "Why this owner" (hidden for AI and automation, QBZ-63), times, comment, skipped-by-assignment box exactly as received (D89), footer actions) and all six step states in tag, popover and details. A `failed` step renders its state with the generic in-review message; no Restart, Failed steps tab, attempts list, issues table or Background task link. `runs`, `issues`, `taskId` are mapped by the shared mapper but not rendered.
- R204. **Typed error and the eight gateways** (Q3). `@webiny/app` gains `GraphQLOperationError` (`packages/app/src/errors/GraphQLOperationError.ts`, exported from `errors/index.ts`, imported `@webiny/app/errors/index.js`). These eight gateways throw it when their envelope has an error, each keeping its own throw condition and message fallback and selecting `code message data`: CMS `packages/app-headless-cms/src/features/contentEntry/{deleteEntry/DeleteEntryGateway,deleteEntryRevision/DeleteEntryRevisionGateway,permanentlyDeleteEntry/PermanentlyDeleteEntryGateway,bulkAction/BulkActionGateway}.ts`; WB `packages/app-website-builder/src/features/pages/{deletePage/DeletePageGateway,deletePageRevision/DeletePageRevisionGateway,trashBin/WbTrashBinDeleteGateway,trashBin/WbTrashBinBulkActionGateway}.ts` (the two trash-bin gateways do not select `data` today, they add it; the bulk one keeps `if (error || !data)`). Other gateways keep `throw new Error`. Workflows decorates the **use cases**/presenters: CMS `DeleteEntryUseCase`, `DeleteEntryRevisionUseCase`, `PermanentlyDeleteEntryUseCase` (`.../contentEntry/*/abstractions.ts`), the CMS `BulkDeletePresenter` (`.../presentation/contentEntries/bulkActions/abstractions.ts`); WB `DeletePageUseCase`, `DeletePageRevisionUseCase` (`packages/app-website-builder/src/features/pages/{deletePage,deletePageRevision}/abstractions.ts`), the trash-bin delete path and the WB `BulkDeletePresenter` (`.../presentation/pages/bulkActions/abstractions.ts`, token `"WB/BulkDeletePresenter"`).
- R205. **Warning flow** (Q4, D157). The normal confirmation runs first. A decorated use case runs the action; a `GraphQLOperationError` with code `Workflows/Review/ActiveReviewOnTrash` (data `ActiveReviewOnTrashData`) opens the warning dialog listing each review as "{title} · Step {stepPosition} of {stepCount} ({stepName})" under D134's text ("This content has a review in progress. Trashing it cancels the review.", "Deleting it cancels the review." for `delete`). **Confirm** calls the app's `cancelForDelete` once per distinct (`model`, `targetId`), passing the revision id for a revision delete (CMS `cancelCmsEntryReviewsForDelete(revisionId)`, WB `cancelWebsiteBuilderPageReviewsForDelete(revisionId)` after Task 5) and none otherwise, then repeats the action once, no second confirm; **dismiss** resolves `false`; any other error is rethrown unchanged. One shared `ActiveReviewGuard` (Task 33). D134's "warning first, then the normal dialog" is revised by D157.
- R206. **Content Reviews per app, list neutral** (Q5). Route, menu item, sidebar entry and widgets are mounted per app, reusing `Routes.ContentEntries.ContentReviews` (name `Cms/ContentEntries/WorkflowStateList`, `/cms/content-reviews`, `packages/app-headless-cms-workflows/src/routes.ts`) and `Routes.Pages.WorkflowStateList` (name `WebsiteBuilder/Pages/WorkflowStateList`, `/website-builder/pages/content-reviews`, `packages/app-website-builder-workflows/src/routes.ts`), names unchanged. The shared `ReviewListView` takes `{ useCases: IReviewListUseCases; rowProvider: IReviewRowProvider; namespaces: string[]; showContentType: boolean; contentTypeFilter: IReviewContentTypeFilter | null; initialTab?: ReviewListTab }` over app-neutral `ReviewListRow`; row links and actions resolve per row namespace through `IReviewRowProvider.getBinding(namespace)`, so a later global view passes a provider over several apps and a combining `useCases`. `namespaces` is a list throughout (list presenter, widget presenter, `ReviewActivity.subscribe`). No global route. CMS shows the "Content type" column and filter (D113), WB neither.
- R207. **Toasts** (Q6, D125). `INotificationInput` gains `link?: INotificationLink` (`{ label, url }`), `duration?: number`, `position?: NotificationPosition`, `dismissible?: boolean` (the close button; admin-ui shows it only when set); `NotificationVariant` gains `"error"`; `INotifications` gains `error`. - R208. **Candidate teams** (Q7, D158). `ListReviewCandidateTeamsUseCase` (api-workflows): de-duplicates ids, reads each with `GetTeamUseCase` (cached successes via `TeamsRepositoryCachingDecorator`, A69) inside one `withoutAuthorization` around the lookups only, keeps `{ id, name }` in input order, omits unknown teams. Shared schema: `WorkflowsTeam { id, name }`, `WorkflowsReviewStep.candidateTeams` through a field resolver (`path: "WorkflowsReviewStep.candidateTeams"`, `parent`, as `SecurityTeam.roles` in `packages/api-core/src/graphql/security/addTeamSchema.ts`) that never fails the read. CMS and WB expose it through the shared type (no wrapper change).

- R211. **Gating and decorators** (Q10). Everything the app packages add lives under the three flag-gated roots (`CmsWorkflows` `packages/app-headless-cms-workflows/src/index.tsx`, `WebsiteBuilderWorkflows` `packages/app-website-builder-workflows/src/index.tsx`, `WorkflowsAdminApp` `packages/app-workflows/src/app.tsx`; each returns `null` unless `featureFlags.isEnabled("advancedPublishingWorkflow")`). The workflow list is loaded once and cached per namespace by the shared `ReviewUseCases` instance of each app (A74). No API change.
