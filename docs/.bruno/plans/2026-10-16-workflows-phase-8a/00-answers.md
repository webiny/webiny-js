- Q2 Scope: (a). 8a ships the Review details drawer (D88: timeline, owner, source, comments, skipped-by-assignment) and all six step states in tag, popover and details. 8b: Restart dialog, running and failed messages, runs, AI issues, Background task link, Failed steps tab.
- Q3 Trash and delete error: (a). The base CMS (`DeleteEntry`, `DeleteEntryRevision`, `PermanentlyDeleteEntry`, `BulkAction`) and WB (`DeletePage`, `DeletePageRevision`, trash-bin delete, bulk) gateways throw one typed error in `@webiny/app` carrying code and data; the workflows packages decorate the use cases and react to `ActiveReviewOnTrash`.
- Q4 Dialog order: (a). The normal trash or delete dialog comes first; the server refuses with `ActiveReviewOnTrash`; the warning lists the blocking reviews; Confirm calls the app cancel-for-delete wrapper and then repeats the action, with no second confirm. Covers trash, revision delete, permanent delete and bulk. This revises the D134 order (new D-entry, D157).
- Q5 Content Reviews: (a). One route and one menu item per app (CMS, WB) rendering the shared app-workflows view with the app's gateway. No global route in 8a.
- Q6 Toasts: (a). `INotificationInput` (app-admin) gains optional link, duration, position and an error variant; every workflows toast uses it (bottom right, 8 s, close button, link); other admin toasts stay unchanged. The plan verifies the 3-visible cap and the oldest-dropped default.
- Q7 Team names: teams must be visible through workflows (workflows cannot function without teams). (a): review responses carry per step `candidateTeams: [{ id, name }]`, resolved server-side in api-workflows; only the team lookup runs under `withoutAuthorization` (SEC-66 pattern), exposing id and name only. API change in 8a (shared review shape plus CMS and WB responses). Follow-up later, not 8a: phase 7 messages could use the team name (revisit A62).
- Q8 Reviewer picker: (a). A small `ReviewerPicker` in app-workflows over the admin-ui `AutoComplete` (disabled items "Unavailable" and "Current owner"), generalised in 9b.
- Q9 Live updates: (a). Refetch the visible list on own actions and on any incoming `workflows.notification` for the same namespace, with the "New reviews are available." notice; no polling. 8b extends it.
- Q10 Workflow presence: keep the existing decorator approach (field-selection and row-mapper decorators on lists, decorators on the CMS and WB editor components), registered only when the workflows feature is on; CMS and WB without workflows stay unchanged. Each app's workflows feature loads its workflow list once, cached per namespace; the editor decorator shows the bar only for a model with a workflow, then calls `getTargetReview`. No API change for this.

## Contract review decisions (2026-10-16)

- Q11 Layering and generalisation (decision A): keep layering. The gateway interface is shared (app-workflows) and each app implements it; the use cases are shared implementations parameterised by the app's gateway (no duplicated use-case code per app); each app token exposes use-case-style methods (getTargetReview, start, approve, ...) and shared presenters depend only on that use-case interface (code-style no-mixed-layers-in-dependencies). User instruction: "Keep stuff generalized as much as possible. Only real different stuff needs to be in the CMS / WB app." app-workflows holds everything app-neutral (domain, fragments/DTOs/mappers, use-case interfaces and implementations, presenters, views, dialogs, picker, toasts, activity and notification handling, list/widget/details logic, the trash/delete warning flow, generic decorator logic); the CMS and WB packages hold only the GraphQL operation documents and the gateway, the registration binding their gateway to the shared use cases (per-app token per Q1 (c)), and thin glue at app-specific extension points. Record in R202 and D159 and as a Global Constraint: no logic duplicated across the CMS and WB packages.
- Q12 WB revision delete hook (decision B): add a WB `BlockPageRevisionDeleteWhileInReview` server hook in 8a.1 (same `Workflows/Review/ActiveReviewOnTrash` error and data shape) so the admin WB revision decorator is live. Superseded by Q14: the planner found the API has no WB revision-delete operation (only `WbMutation.deletePage`), so Q14 builds it first (R235).
- Q13 Sharing boundary (decision C): app-workflows shares only field fragments, DTO types and mappers of the shared `Workflows*` types; operation documents and gateways are app-owned (R202, D159).
- Q14 WB revision delete (user, 2026-10-16, after the planner reported that the API has no WB revision-delete operation): "There must be a delete revision for page builder. If it does not exist, we will make it." The plan therefore adds the WB `deletePageRevision` mutation (use case, events, GraphQL, permissions) in 8a.1, with the workflows hooks for it (R235-R236).
- Q15 Published WB revision delete (decision D, 2026-10-16): keep today's behaviour: "if now a user can delete a published page, they can do that in the future as well; we won't change how that thing works". `TrashPageUseCase`/`DeletePageUseCase` have no publish check and no unpublish side effects, so `deletePageRevision` follows the CMS `DeleteEntryRevision` rules including deleting a published revision, with no extra unpublish handling (R236, A85).
