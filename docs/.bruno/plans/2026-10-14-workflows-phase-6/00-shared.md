# Workflows Phase 6: AI step

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workflow author can add an AI step. The author writes the instructions, picks the model (only models that have a configured connection are offered and saved, D101) and allowlists tools. The engine runs the step as the same private background task as an automation (`workflowsStepRun`, now step-type-neutral), attributed to the requester with authorization off (R161 of phase 5). The AI reads the target and, through the two built-in tools `readTarget` and `updateTargetFields`, may edit a bounded set of fields (CMS top-level and nested object fields by dotted path; Website Builder page title, properties and SEO only). It answers with a structured decision `{ approved, comment, issues[] }`, which the engine applies through the base approve/reject use cases with an `ai` actor. Every failure fails the step with a fixed reason; failed AI steps are restartable through the phase 5 restart path. The step type, capability and runner live in `packages/ai-powerups`; `packages/api-workflows` gains the tool registry, the target editor port and the neutral runner, and no AI dependency. Admin UI, notifications and human confirmation of AI decisions are out of scope.

**Architecture:** Eleven sub-phases, built bottom up. Each ships and tests alone; every one ends green on the phase 2-5 tests it touches.

1. **AI actor and shared reach** (`packages/api-workflows`, 6.1): `AI_STEP_TYPE`, `getAiActor`, and the step-type-neutral `StepRunReachService` (trigger, `reachRun`, abort, fail) that `AutomationStepType.reach` now calls. No behaviour change.
2. **Step runner dispatch** (`packages/api-workflows`, 6.2): the `StepRunner` abstraction and registry, `AutomationStepRunner` (the automation logic moved out of the handler), the handler dispatching by step type, neutral failure hooks and stuck detection, and the task's timeout signal (R168, user answer Q1). Phase 5 tests stay green unchanged.
3. **Review step issues** (`packages/api-workflows`, 6.3): `AiIssue`, `ReviewStep.issues`, the shared GraphQL type, approve and reject accepting `issues`.
4. **AI tool registry** (`packages/api-workflows`, 6.4): `WorkflowAiTool` abstraction and registry, the shared `listAiTools` operation.
5. **Target editor port and built-in tools** (`packages/api-workflows`, 6.5): the `ReviewTargetEditor` port, `readTarget` and `updateTargetFields` with the stale re-check and the bypass around the write only.
6. **CMS adapter** (`packages/api-headless-cms-workflows`, 6.6): the bounded `cms.*` editor, read then update (R172).
7. **Website Builder adapter** (`packages/api-website-builder-workflows`, 6.7): the `wb.page` editor, reads the whole page except the element tree (summary), write only `properties.title` and the `properties.seo` scalar keys (R172).
8. **Model selection** (`packages/api-workflows`, `packages/ai-powerups`, 6.8): the async save-time check hook on `StepType` (run only for new or changed steps, R165); the `ConfiguredAiModelsService` (the one source of "models with a configured connection", R169); `ResolveAiCapabilityUseCase.execute` gains the optional `model` (R169, user answer Q2).
9. **AI step type** (`packages/ai-powerups`, 6.9): the `@webiny/api-workflows` dependency, the "Workflow review" capability, the editor model list operation (registered only when `aiPowerups` and `advancedPublishingWorkflow` are both on, R177), `AiStepType` with save-time validation and reach.
10. **AI runner** (`packages/ai-powerups`, 6.10): the prompt builder and output schema, `AiStepRunner` (input cap, timeout, tool set, outcome mapping), the registration of the `ai` step type and runner, and the end-to-end test (user answers Q4, Q5).
11. **Docs** (6.11): the AI tools developer guide, spec, roadmap, decisions and stale "phase 6" comments.

**Tech Stack:** TypeScript, `@webiny/feature` DI, zod 4 (`z.toJSONSchema`), `@webiny/api-core` (`Ai`, `TaskService`, `TaskDefinition`, `IdentityContext`), `@webiny/background-tasks` (`TaskController`), the AI SDK `ai` package already used by `ai-powerups`, `@webiny/api-graphql`, vitest, `@webiny/api-headless-cms-testing`.

## Global Constraints

- **No helper functions or private methods that wrap a dependency call** (use case, service, reader, repository, logger). Call dependencies inline in the owning class with the Result pattern or an inline `try`/`catch`. Shared logic that needs dependencies becomes a DI service named `...Service`. Pure functions (no dependency, no I/O) are allowed. Inline duplication of dependency calls is intended.
- **R87:** app wrappers turn every dependency throw into a failed Result with the persistence error type, never `NotAuthorized`, never a rejected promise. The same holds for the target editor adapters and the AI tool handlers: a throw becomes a failed Result or a tool error text, never a rejected promise into the runner.
- **D132:** engine use cases take explicit inputs (actor, viewer ids) and check no permissions. Wrappers read identity and check permissions; GraphQL resolvers call only wrappers or shared configuration use cases.
- **SEC-66:** `canUserRead` / any candidate read check runs as the request identity, never inside `withoutAuthorization`. `ListUsersUseCase` / `GetUserUseCase` need `withoutAuthorization` (they require `adminUsers.user`): wrap only those calls, never a read check.
- DI conventions: one abstraction or implementation per file; implementation file named after its class; namespace types; no inline object types; minimal barrels.
- Before every commit: `git add .`, `yarn > /dev/null 2>&1`, `node scripts/generateTsConfigsInPackages.js`, `yarn adio`, `yarn check-ts-configs`, `yarn format:fix > /dev/null 2>&1`, `yarn lint:fix`, `yarn webiny sync-dependencies`, `yarn build -p <package> --no-cache 2>&1 | tail -30` for changed packages, `git add .`. Restore `.gitleaks.toml` (`git checkout -- .gitleaks.toml`); never commit it, `docs/.reports` or `.superpowers`.
- Commits: Conventional Commits, one `-m` for the subject and a separate `-m` for the trailer block, ending with exactly:
  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_01U31bVptN4E9cWVxet6Tjxn
  ```
  Never push, amend or revert.
- **Tests are targeted:** run the test files you add or change and the files covering the changed code, by path (`yarn test packages/<pkg>/__tests__/<file>.test.ts`, the same with `yarn test:os`). Never a whole package suite unless the dispatch asks. Run `test:os` runs one at a time (parallel runs clash on port 8001). `packages/background-tasks` tests use `yarn test` by path. `packages/ai-powerups` runs both `yarn test` and `yarn test:os` by path once its `ci.config.json` exists (Task 20 adds it; before that, `yarn test` only).
- Type-check tests, per package the task touched: `yarn check:test:types -p <folder> --report cli 2>&1 | tail -40` (folder name, e.g. `api-workflows`, `ai-powerups`; several as `-p a,b`) prints no errors.
- TDD: failing test first, record RED before source.
- `@webiny/api-aco` stays app-package only. `api-workflows`, `api-headless-cms-workflows` and `api-website-builder-workflows` gain no AI dependency and no dependency on `@webiny/ai-powerups` (R177). `@webiny/ai-powerups` gains `@webiny/api-workflows` (Task 16) and, for the end-to-end test only, `@webiny/api-headless-cms-workflows` and `@webiny/api-headless-cms-testing` as devDependencies (Task 20).
- **No model is called in a test.** Tests use a mock `Ai` (a fake `generateText` result and a fake `listModels`) plus fake settings (connection presets with and without `apiKeyEncrypted`, the source of R169) from `packages/ai-powerups/__tests__/__helpers/`; nothing fakes `listModelsByConnections` (it reads `AiConnectionFactory` registrations, which nothing registers); the end-to-end test drives the real handler with the real tool registry and a CMS target.
- **Raw errors never reach a step.** Provider messages, settings paths, API keys and thrown messages are logged with `Logger.error` and replaced by the fixed texts of R170 (a tool's own refusal text returned to the model is the only message that is not fixed, and it never contains a provider or storage error).

## Review Focus

1. **A stale AI result lands after cancel or restart** (D7, D27, SEC-68). The LLM call runs for minutes; the review can be cancelled, deleted or the step restarted under a new task meanwhile. A late tool write, a late approve or reject, a late `onError` or a late issues save must write nothing. A cancel also stops the model and further tool writes while the call runs (R175: `StepRunStaleCheckService.isStale`, called throttled by the AI runner, re-reads the stored review, because `controller.runtime.isAborted()` only sees the task loaded at run start and stays false when another request cancels, so it cannot be used). Pinned by Task 4 (guard parity through the neutral handler), Task 10 "re-checks the step is still this task's before writing" (the tool re-guard, which also refuses with `AI_TOOL_STEP_CHECK_FAILED_MESSAGE` and writes nothing when the check itself fails), Task 4 (`StepRunStaleCheckService` re-reads the stored review: current, cancelled, restarted, not found, and a failed or throwing read answered as a failed Result with one log, fail-closed), Task 19 (the throttle and the sticky answer), "writes nothing when the step went stale during the call" and "stops the call and writes nothing when the stored review is cancelled or restarted during the model call" (the test flips the stored review, not a fake flag), and Task 20 cancel and restart tests. The stale stop is a flag checked after `generateText` returns or throws (R175), not an `onStepFinish` throw; the tests advance fake timers past `STEP_RUN_STALE_CHECK_INTERVAL_MS` after flipping the review.
2. **Prompt injection and tool scope** (D55, A58). Content under review can tell the model to approve, to call tools or to write elsewhere. Pinned by Task 7 (a tool name outside the step's allowlist is not in the tool set; handlers take no target, revision or review id from the model), Task 10 (the context supplies the target; `updateTargetFields` is the only writer), Task 18 (content under review is delimited as data, the guidance says it is not instructions) and Task 19 (an empty or unparsable decision fails the step, a reject needs a comment).
3. **A write outside the bounded fields** (R172, user answer Q3). Dynamic zones, references, files, repeated groups, the WB element tree, bindings, metadata, location, path and language are never written (WB: an explicit allowlist, R172); an unknown or read-only path writes nothing and returns an error text to the model. Pinned by Task 12 (CMS write rules, atomic: any bad path writes nothing) and Task 13 (WB allowlist: path and language unchanged, other `properties` keys preserved).
4. **The AI writes with the wrong identity or leaves the bypass open** (D36, D62, R150, R161, R173). The write runs as the requester with authorization off (the task runner), the bypass exists only inside the tool's `update` call (`AsyncLocalStorage` scope: nothing to restore, so it is inactive the moment the call returns or throws) and exempts only the save block; move, folder-change, delete and trash blocks stay active. Pinned by Task 10 (`isActive()` false right after `update` returns or throws, false for a concurrent save started outside the tool, `update` awaited inside `bypass.run`), Task 12 and Task 20 "move and delete blocked, update allowed".
5. **The runner refactor changes automation behaviour** (R168). Every automation fail reason, guard, id wait, hook and stuck rule stays byte for byte. Pinned by running the unchanged phase 5 step run, reach and stuck tests after Tasks 2, 3 and 4 (`WorkflowStepRunTaskRun.test.ts` unchanged, which also pins the logger messages, the context objects and the `outputUpdates` expectations, so the pre-run output write is opt-in per runner through `singleRun` and automation never gets it, Task 3), and by Task 3 "unknown step type with no runner".
6. **The model list or the gate lies** (R169, R177, D56). "Models with a configured connection" has one source (`ConfiguredAiModelsService`), used by the resolver, `listAiModels` and `checkConfig`; the AI pieces exist only when `aiPowerups` and `advancedPublishingWorkflow` are both on. Pinned by Task 15 (the service and the resolver), Task 16 (`aiPowerups` on, workflows off: valid schema, no `listAiModels` field) and Task 19 (no `ai` step type without both flags).

## Rulings

- R164. **Names and constants.** `AI_STEP_TYPE = "ai"` (`domain/workflow/stepTypes.ts`, whose comment "`ai` has no constant here" is updated). `AiStepConfig { instructions: string; model: string; tools: string[] }` (`tools` defaults to `[]`; `model` is the full id `"<providerId>/<modelId>"`, as `Ai` expects). Capability id `workflows.review`, label `Workflow review`, default role `standard`. AI actor (spec 5.2, D58, D107): `{ type: "ai", id: <requester id>, displayName: <requester displayName> }`, `identityType` omitted (R141 mirror); `ActorType` already has `"ai"`.
- R165. **Save-time AI validation** (D101, D109). `AiStepType.validate` is pure (`WorkflowValidationError`): the malformed shell text `Step "<title>" needs AI instructions and a model.` is replaced by two exact texts, checked in this order: `Step "<title>" needs instructions.` (trimmed non-empty, no minimum length, no default prompt) and `Step "<title>" needs a model.` (trimmed non-empty); `Step "<title>" uses the AI tool "<name>", which is not defined.` for a `tools` entry the registry does not know; a duplicate `tools` entry is deduplicated, not an error. Config is stored as entered (instructions as typed, model trimmed, tools deduplicated in first-seen order). The I/O check is a second, async hook `StepType.checkConfig` (R169): `Step "<title>" uses the model "<model>", which is not available.` when the model is not in the `ConfiguredAiModelsService` list (R169). `StoreWorkflowUseCase` runs `validate` for every step first, then `checkConfig` for every step that defines it **and is new or whose config changed** versus the stored workflow (step matched by `id`, config compared deeply; on create every step counts as new), so a stored workflow whose model or connection was removed later can still be saved without touching that step (reach and run keep failing with the model-not-available reason, R169); a throw in `checkConfig` is a `WorkflowPersistenceError` (R87).
- R166. **`listStepTypes` ai row.** With the type registered the row comes from the registry like any other: `available: true`, `unavailableReason: null`, `configSchema = z.toJSONSchema(aiStepConfigSchema, { io: "input", unrepresentable: "any" })` with `.meta({ ui: "textarea" })` on `instructions` (R138). Without the type the R132 placeholder row stays unchanged (`aiPowerups` flag text). Save of an unregistered `ai` step keeps R132's message. `ListWorkflowStepTypesUseCase` needs no change; the placeholder test gets a registered-type case.
- R167. **Tool registry** (spec 9.3, D55). Never the global `AiSdkTools`. Multi-registered abstraction `WorkflowAiTool` (`features/aiTools/WorkflowAiTool/`): `name` (unique, `^[A-Za-z][A-Za-z0-9_]{0,63}$`, at most 64 characters), `title`, `description`, `inputSchema: zod.ZodType`, `execute(input, context): Promise<WorkflowAiToolResult>`; `WorkflowAiToolContext { review: ReviewData; step: ReviewStep; requester: Actor; task: StepRunTaskIdentity }` supplied by the runner, so a handler never takes a target, revision, review or step id from the model. `WorkflowAiToolRegistryService` (deps `[[WorkflowAiTool, { multiple: true }], Logger]`; `get(name)`, `list()`, last registration per `name`; a tool with an invalid name is dropped and logged once with `Logger.error`, never thrown, R87) returns the tools; turning them into an AI SDK tool set is the runner's job (api-workflows has no AI dependency). A tool the step does not allowlist is absent from the tool set. Shared `ListWorkflowAiToolsUseCase` (`editor` only, refusal action `"list AI tools"`, a throwing permission read or tool list is a `WorkflowPersistenceError`, R138 mirror) and `WorkflowsQuery.listAiTools`, rows `{ name, title, description }` (no schema), sorted by `title`. Built-ins `readTarget` and `updateTargetFields` are registered by `WorkflowsFeature` (R173).
- R168. **Runner reuse** (user answer Q1: reuse `workflowsStepRun` with a step-type-neutral step runner). One private task, id `workflowsStepRun`, input `{ reviewId, stepId }` (R142, R148), one stale guard, id wait, hook set, stuck detection, abort and restart for every step type. New multi-registered abstraction `StepRunner` (`features/stepRun/StepRunner/`): `type`, `singleRun: boolean` (true = the runner never returns `continue`; the handler persists the output before calling it, R170), `failureReasons: { error; aborted; stuck }` (fixed texts), `maxIterationsReason(step): string`, `getActor(requester: Actor): Actor`, `run(params): Promise<StepRunnerOutcome>` (outcome `approved | rejected | continue`, `approved` and `rejected` carry optional `issues`; a failure is a thrown `StepRunFailure`, R146). `StepRunnerRegistryService.get(type)`. The handler reads the step type from the review snapshot and dispatches; a type with no runner fails the step with the existing `The step type "<type>" is not available.` through the one failure path, and its `onError`, `onAbort` and `onMaxIterations` hooks use the neutral fixed texts `The step failed.` and `The step was aborted.` (`onMaxIterations`: `The step failed.`), so no hook throws; stuck detection also covers such a step and fails it with `The step failed.`; automation keeps its own texts because its runner exists, and phase 5 hook tests built with the automation runner registered stay green. `AutomationStepRunner` holds the moved automation logic (lookup, config and settings parsing, iteration cap, `bypass.run(definition.run)`, reasons `The automation ...` byte for byte, log messages and context objects identical: `taskId`, `reviewId` and `stepId` are rebuilt from the run params). The handler owns what is shared: read, guard, id wait, identity (R161), the post-run re-guard, applying approve/reject with `actor: runner.getActor(requester)`, `actorTeamIds: []`, the one failure path and the timeout signal (R175). `StepRunReachService` is the one reach path both step types use (trigger as the requester, `reachRun`, abort after a failed `reachRun`, fail with a given reason, R149, R143, R159). Phase 5 tests stay green unchanged; a test that must change is a regression to explain in the task.
- R169. **Model selection** (user answer Q2; D101). The workflow author chooses the model on the step. `ResolveAiCapabilityUseCase.execute(capabilityId, model?)` gains an optional second argument `model` (full id). Without it nothing changes. With it: the capability still has to exist and be enabled (`AiCapabilityDisabledError` as today, so the licence and enabled gate stay), the model is used as given (no role or override), and the connection is the first settings connection preset with a truthy `apiKeyEncrypted` whose `sdkName` equals `sdkNameFromModel(model)`, found through `ConfiguredAiModelsService.findConnection(model)`; no such connection, or an unparsable model, fails with the new `AiModelNotAvailableError` (`Capabilities/AiModelNotAvailableError.ts`, message `The model "<model>" is not available. Add a connection for its provider under Settings → AI Power-Ups.`); `roleId` is `null`, `fellBackToStandard` false, guidance and additional instructions are the capability's. **Source of "models with a configured connection"** (one DI service, `ConfiguredAiModelsService`, `features/ConfiguredAiModels/` in ai-powerups; `Ai.listModelsByConnections()` is NOT used, it reads `AiConnectionFactory` registrations that nothing registers): `list()` is `Ai.listModels()` filtered to the providers whose `providerId` equals the `sdkName` of a settings connection preset with a truthy `apiKeyEncrypted` (the resolver's own source), rows `{ id, name, providerId, providerName }` with `id = "<providerId>/<modelId>"` and `name = modelName`, deduplicated by `id`; `findConnection(model)` returns the preset the resolver uses. Both return a `Result`. `ResolveAiCapabilityUseCase` (model argument), `ListWorkflowAiModelsUseCase` and `AiStepType.checkConfig` all use it. The editor offers only these models: the ai-powerups extension adds `WorkflowsQuery.listAiModels` (R176), `editor` only, refusal action `"list AI models"`. Save refuses others (R165 `checkConfig`, the same service). A model or connection removed after save fails the step on reach or run with the R170 model reason; the step is restartable.
- R170. **AI fail reasons** (fixed texts, stored in `comment` and `runs[].reason`; raw errors only logged, R146 mirror). `The AI step configuration is not valid.` (config no longer parses); `The AI tool "<name>" is not available.` (an allowlisted tool is no longer registered, at reach and run); `The AI review capability is not available.` (capability disabled, licence lapsed or settings unresolved, D40); `The model "<model>" is not available.` (`AiModelNotAvailableError`); `The content is too large for the AI review.` (R175); `The AI review timed out.` (R175); `The AI review failed.` (provider error, thrown error, tool setup error); `The AI review returned no decision.` (no valid structured output); `The AI review rejected without a comment.` (D100, comment trimmed under `REJECT_COMMENT_MIN_LENGTH`); `The AI review did not finish in <n> steps.` (`<n>` = `AI_STEP_MAX_TOOL_STEPS`, the tool loop hit its cap without a decision); `The AI review was aborted.`; `The AI review task ended without a result.` (stuck); `The AI review could not be started.` (trigger failed). `StepRunner.failureReasons`: `error` = `The AI review failed.`, `aborted` = `The AI review was aborted.`, `stuck` = `The AI review task ended without a result.`; `maxIterationsReason` returns `The AI review failed.` (the AI task is one iteration, A56, so the ceiling is never reached); `AiStepRunner.run` fails with `failureReasons.error` when `iteration` is greater than 1, before any model call, so a re-invoked task never pays for a second call. `StepRunner.singleRun` is `true` for `AiStepRunner` and `false` for `AutomationStepRunner`. For a `singleRun` runner only, the handler persists `controller.state.updateOutput({ idWaits, state })` (the existing output shape, `state` kept as read, `null` when none) once the id wait is over and BEFORE it calls the runner (R175), and refuses a re-entered task whose `iteration` is greater than 1 through the one failure path with `failureReasons.error`, before the runner is called: a re-entered task then reads the fixed `idWaits` and gets a real `iteration` of 2. Without that write the output is only written on `continue`, `idWaits` falls back to `iterations - 1` and `iteration` is 1 again. The automation runner is not `singleRun`: the handler writes nothing before it, so the phase 5 output writes and every phase 5 test stay byte-identical. `AiStepRunner.run` keeps its own `iteration` > 1 check as defence in depth.
- R171. **Outcome mapping and issues** (D39, D100). The model answers `aiReviewOutputSchema` `{ approved: boolean, comment: string, issues: AiIssue[] }`. `approved: true` approves with `comment` (empty allowed) and the issues; `approved: false` rejects with `comment` (trimmed, at least `REJECT_COMMENT_MIN_LENGTH`) and the issues. Approve and reject go through the base use cases with the AI actor and `actorTeamIds: []`; the task is one iteration (never `continue`). `AiIssue { fieldPath: string | null; severity: "error" | "warning" | "info"; message: string; suggestion: string | null }`, at most `AI_STEP_MAX_ISSUES = 50` kept (extras dropped, logged), `fieldPath` clamped to 500 characters, `message` and `suggestion` to 2000. `ReviewStep.issues: AiIssue[]` defaults to `[]` for steps written earlier (mapper default, no migration, like R139); `Review.restart` resets it to `[]`; approve and reject store it on the step; facts and events are unchanged (they carry no issues). `AI_STEP_MAX_TOOL_STEPS = 20`. Issues display belongs to the admin phases.
- R172. **Bounded writes** (user answer Q3). The `ReviewTargetEditor` port (spec 9.3) reads in full and writes a bounded set. Every read field carries `writable`. CMS (`cms.<modelId>`): read all fields with `path`, `label`, `type`, `value`; nested `object` fields flatten to dotted paths (`address.street`); a field is writable only when it is a top-level or nested-object field of type `text`, `long-text`, `number`, `boolean` or `datetime`, not `multipleValues`, and not inside a `multipleValues` object; dynamic zones, references, files, rich text and every other type are read-only; a path the model does not define, or a read-only path, is rejected. Values are validated against the field type and the model's validators by the CMS update path; one bad path rejects the whole call and writes nothing (atomic). Website Builder (`wb.page`): read the page title, properties and SEO plus a read-only summary of the element tree; write only through an explicit allowlist: `properties.title` and the SEO scalar keys `properties.seo.title`, `properties.seo.description`, `properties.seo.canonicalUrl`, `properties.seo.noIndex`, `properties.seo.noFollow` (the SEO group of the page editor; `properties.seo.metaTags`, `properties.social`, `properties.image`, `properties.tags` read-only). `properties.path`, `properties.language` and everything else (`elements`, `bindings`, `metadata`, `location`, status, `extensions`) are read-only. The page editor port reads the page and writes the full merged `properties` object (a partial blob would wipe keys). `ReviewTargetEditor.update` returns the applied paths; failures are `ReviewTargetEditorError` with a text safe to show the model (adapters log the real error and return a generic text for non-validation failures).
- R173. **Writes only through tools, under bypass, guarded** (D36, D55, D62, R150). The LLM call itself runs as the requester with authorization off like any task (R161) and has no write access of its own. `updateTargetFields` is the only writer: it re-reads the review and applies `getStaleStepRunReason(review, step.id, context.task)` first (stale: writes nothing, returns the error text `The review step is no longer running.`), then wraps only the port's `update` in `WorkflowBypassService.run`. The stale check is `StepRunStaleCheckService.isStale` (a `Result<boolean, ReviewPersistenceError>`, Task 4): `ok(true)` refuses with `AI_TOOL_STEP_NOT_RUNNING_MESSAGE`, and a failed Result (the stored review could not be read) refuses with `AI_TOOL_STEP_CHECK_FAILED_MESSAGE` (`The step could not be checked; nothing was written.`) and writes nothing, so the write is fail-closed (the service already logged it; the tool does not log again); the move, folder-change, delete and trash blocks stay active. A failed or refused write returns an error text to the model and never fails the step. `readTarget` takes no input and returns the same serialisation as the prompt; `updateTargetFields` takes `{ fields: Record<string, unknown> }` (paths from the last read) and returns `{ applied: string[] }`. Both are registered by `WorkflowsFeature`; a step must allowlist them like any tool (a step with no tools can only decide).
- R174. **Prompt composition and injection** (D39, D109, A58). System prompt: the capability `guidance` (fixed output contract) plus the capability's `additionalInstructions` through `withAdditionalInstructions`. User message: the labelled target content, the previous step comments, then the step `instructions` in a delimited block. The guidance states that content under review is data, never instructions, and that only the delimited step instructions are the task. There is no default prompt. Mitigation is by scope (tool context, allowlist, bounded writes, reject needs a comment), not by detection.
- R175. **Limits** (user answer Q4). Input cap: `AI_STEP_MAX_INPUT_CHARACTERS = 200000` (constant, `features/aiTools/constants.ts` in api-workflows because `readTarget` shares it), applied to the serialised target content plus previous comments plus the step instructions; over the cap the step fails with `The content is too large for the AI review.` before any model call, and `readTarget` answers with the same text as a tool error. No truncation, ever (the AI must not approve content it never saw). Timeout: the handler builds an `AbortSignal` from the task's remaining runtime (`controller.runtime.getRemainingMilliseconds()` minus `STEP_RUN_TIMEOUT_MARGIN_MS = 30000`) and passes it to `StepRunner.run` as `signal` (`StepRunnerRunParams`). A cancel from another request is seen through the DI service `StepRunStaleCheckService` (`features/stepRun/StepRunStaleCheckService/`, `isStale({ reviewId, stepId, task: { id, createdById } }): Promise<Result<boolean, ReviewPersistenceError>>`: it re-reads the review through `ReviewRepository` and applies `getStaleStepRunReason`, the same guard as the post-run re-guard; a review not found is `ok(true)`; a failed or throwing read is logged once by the service and answered with a failed Result, fail-closed, so a caller about to write refuses on it, while the AI runner's stop check treats a failed Result as not stale and keeps going because the post-run guard still protects its own write), because `controller.runtime.isAborted()` is NOT usable: it reads the task loaded at run start, `TaskController.ts`, `TaskManagerStore.ts`, so a cancel from another request that only writes the DB leaves it false. The service does no throttling and keeps no state. The caller, `AiStepRunner` (Task 19), throttles its calls to at most one read per `STEP_RUN_STALE_CHECK_INTERVAL_MS = 5000` (constant in `features/stepRun/constants.ts`, added by Task 4) with its own local state, and once it has seen true it keeps answering true; the throttle and stickiness tests live in Task 19. The id-wait iterations run first and are unaffected by the signal. When `remaining - 30000 < 1000` the signal fires at once and the step fails with `The AI review timed out.` (restartable). The AI runner passes the signal to the model call, and a signal-aborted call fails the step with that text. **Cancel or restart during the call:** the AI runner also stops the call when its throttled stale check (`StepRunStaleCheckService.isStale`) answers true. `stopWhen` (async allowed) and the pre-tool check only set a local `stale` flag (`stopWhen` returns true once the flag is set; a tool that sees it returns an error text and writes nothing, in addition to the tool's own pre-write re-guard, R173). There is no `onStepFinish` check: the AI SDK swallows throws from it (its notify try/catch), and a stopped `generateText` has no output, so reading `result.output` throws `NoOutputGeneratedError`. `AiStepRunner.run` checks the `stale` flag right after `generateText` returns or throws, BEFORE reading any output, and throws `StepRunFailure` with `failureReasons.aborted`; the handler's post-run guard still writes nothing for a stale step. **Re-entry:** for a `singleRun` runner only (the AI runner), once the id wait is over and before the runner is called, the handler persists `controller.state.updateOutput({ idWaits, state })` and refuses a re-entered task with `iteration` > 1 through `failureReasons.error`, so a re-entered task sees a fixed `idWaits` and `iteration` 2 (R170); a runner with `singleRun` false (automation) gets no such write, so its behaviour is unchanged. The check and the tool set are built inline in `AiStepRunner.run`, with no private helper or wrapper method around `tool.execute`. The automation runner ignores the signal and never calls the stale check.

## Assumptions

- A56. The AI call is one `generateText` per task iteration; the task never returns `continue`. A call that outlives the task's remaining runtime fails the step with the timeout reason, restartable (each restart is a new run and a new model cost). A cancel or restart stops the call between tool steps (R175, through the AI runner's throttled `StepRunStaleCheckService.isStale` check, so up to 5 seconds later; a failed check read does not stop the call), not mid-token.
- A57. An AI edit leaves earlier approvals valid, as for automations (D36, D62); the entry revision the review points at is the one edited.
- A58. Prompt injection from content under review is mitigated by scope (tool context, allowlist, bounded writes, reject needs a comment), not by detection.
- A59. The tool re-guard (R173) narrows but does not close the race between its check and the write; a write that lands in that window, or a model call whose result is discarded as stale (a cancel stops the call only between tool steps and is seen at most 5 seconds late, R175, so the step in flight finishes), are accepted like the phase 5 races (A51).
- A60. `ConfiguredAiModelsService` (R169) lists models of providers that have a connection with a stored key without proving the key works; a bad key fails the run with `The AI review failed.`, restartable.
- A61. Tool names are unique across the registry; the last registration of a name wins (like every registry here). Developers register their own `WorkflowAiTool` through the same abstraction; a custom tool's write path is the developer's responsibility (the guide says so, Task 21).
