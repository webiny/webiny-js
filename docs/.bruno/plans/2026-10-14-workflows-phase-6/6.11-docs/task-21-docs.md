A tool is a function the model may call while it works. Webiny ships two (`readTarget`, `updateTargetFields`, section 4); developers register their own (section 3). The AI step type is added by `@webiny/ai-powerups` and exists only when both `aiPowerups` and `advancedPublishingWorkflow` are on (R177); the tool registry and the target editor port live in api-workflows. 4. **The built-in tools.** `readTarget` (no input) returns the content under review as `{ title, fields[] }`, each field `{ path, label, type, value, writable }`; `writable` tells the model what it may change. `updateTargetFields({ fields })` (an empty object answers `No fields were given.`) takes `{ "<path>": value }` using paths from the last `readTarget` and returns `{ applied: string[] }`; it is the ONLY way an AI step changes content. State the bounds (R172): CMS (`cms.*`) top-level and nested-object fields of type `text`, `long-text`, `number`, `boolean`, `datetime`, not `multipleValues` and not inside a `multipleValues` object; references, files, rich text, dynamic zones and every other type are read-only; Website Builder (`wb.page`) `properties.title` and the SEO scalars `properties.seo.title`, `.description`, `.canonicalUrl`, `.noIndex`, `.noFollow` only, everything else (path, language, elements, bindings, metadata) read-only. A bad path, a read-only path or a value the target rejects writes NOTHING (atomic) and the refusal text goes back to the model, which may try again; a refused or failed write never fails the step. Before every write the tool re-reads the stored review and refuses with `The review step is no longer running.` when the review was cancelled or the step restarted meanwhile, and with `The step could not be checked; nothing was written.` when that check itself failed (fail-closed). Only the write is wrapped in the workflow bypass (`WorkflowBypassService`), so the save block does not reject the AI's own edit; moving, deleting and trashing the content stay blocked (D36, D62, R150, R173). A step with no tools can only decide.
5. **Allowlisting and what a workflow author sees.** `listAiTools` (shared `workflows` root, `editor` only) returns `{ name, title, description }` per tool sorted by title; the editor shows them as the allowlist. Save refuses a `tools` entry the registry does not know (`Step "<title>" uses the AI tool "<name>", which is not defined.`). The save-time check also answers `Step "<title>" has an invalid AI configuration.` (the config no longer parses) and `Step "<title>" could not be checked: the configured AI models could not be loaded.` (the model list could not be read); these are save-time texts, distinct from the run-time reason `The AI step configuration is not valid.` (`AI_STEP_INVALID_CONFIGURATION_REASON`). Separately, a tool that was allowlisted and is later unregistered fails the step on reach and run with `The AI tool "<name>" is not available.` (restartable). Only allowlisted tools are given to the model for that step. The step's model must be among the models that have a configured connection (`listAiModels`, `ConfiguredAiModelsService`, R169); a model removed later fails the step with `The model "<model>" is not available.`.
6. **Who the tool runs as, and R161.** The AI run is attributed to the REQUESTER with authorization turned OFF for the whole run (R161 of phase 5, R173): `IdentityContext` holds the requester, and nothing the tool calls checks permissions. A tool is therefore NOT limited by the requester's permissions; the developer must scope their own code (touch only what the tool exists for, take no id from the model, read the target through the context). The decision itself is applied with an `ai` actor that names the requester (`{ type: "ai", id: <requester id>, displayName: <requester displayName> }`, R164).
